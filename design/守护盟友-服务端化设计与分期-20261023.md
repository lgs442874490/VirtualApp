## 0. 结论速览（TL;DR）

**Q1：服务器模式下，为什么"不改 App"也能自动驻防？**

因为自动驻防链路需要的三样东西全部已在服务端具备，App 只是配置端/展示端：

| 要素 | 服务器现状（证据） | 结论 |
|---|---|---|
| 游戏会话 + 推送入口 | `SessionKeeper.LiveSession` 持有常驻 `WjdrEngine`；`engine.addMessageHook` 已挂 WarNotify/ServerWarState/ServerShieldResponder（`SessionKeeper.java:471-482`、`:424-436`） | 服务端能收到与 App 本地完全相同的 `notify_world_alliance_situation_*` 等推送 |
| 协议执行能力 | `engine.request(...)` 已在服务端大量使用（`ServerTasks`/`ServerFieldTasks`/`ServerBearTasks`）；编队 `Exec.formation(engine,1)`（`Exec.java:275`）、坐标 `Exec.point`（`Exec.java:113`）现成可复用 | type=5 驻防、加速、撤防都是普通 c2s 请求，服务端可以直接发 |
| 配置下发 + 状态回显 | App `FnParams` → `/v1/vault/sync` `params` → `VaultStore.Account.roleParams`（`VaultHttpApi.java:166,225`、`VaultStore.java:109`），先例 `ServerWarState.configOf`（`ServerWarState.java:304`）；结果写 `mod:{fpid}:{sid}:guardian` 由 `/state` 回 App（先例 `ServerShieldResponder.saveState:161-178`） | 开关/阈值/编队/白名单**不改 App 也能下发**；日志/状态回显走既有通道 |

反过来说：App 本地 guardian 只挂在 **App 进程**的 `RoleSessionKeeper.LiveSession` 上（`RoleSessionKeeper.java:284-285,500-501`），服务器模式下 App 不持有游戏会话、`DailySchedulerService.onGameEvent` 已 no-op（`design/反应式开盾服务器化-P1-2-20261019.md:8-9`），所以 `GuardianEngine.attach` 永远不会被调用 → 必须由服务端实现。生产证据也印证：`st:2026-10-23:48460403:888:guardian = 4`，`log` 文案 `"待迁移到模块化目录"`（`ModularRoundRunner.java:103-109` 的未收录补记路径）。

> ⚠️ 边界说明：**执行链路**不需要改 App；但"T3 用户可见/可开关"仍需 App 小改（`FeatureGate.GUARDIAN` 当前 `implemented=false`，`FeatureGate.java:86,154`）——这是 P2 的产品化工作，与执行链路解耦。P0/P1 内测可直接用服务端 roleParams/策略 API 控制。

**Q2：最小闭环需要动哪些文件？**

| # | 文件 | 改动 | 量级 |
|---|---|---|---|
| 1 | **新建** `vault-server/src/main/java/com/carlos/vaultserver/ServerGuardianEngine.java` | 推送钩子解析（复用 `ServerShieldResponder.marchesOf/targetUidOf`）、威胁表、规则/门控、状态与 `mod:` 回显、生命周期 | ~500-700 行 |
| 2 | **新建** `vault-server/src/main/java/com/carlos/vaultserver/ServerGuardianLauncher.java` | 编队构造、`req_world_march type=5`（含 A-2 变体）、endtime 校验、撤防 `off_work`、幂等/并发闸 | P0 ~200 行 / P1 ~600 行 |
| 3 | **修改** `vault-server/.../SessionKeeper.java` | `LiveSession` 增 `guardian` 字段；online 分支挂载+唤醒；`shutdown` 清理 | ~20-30 行 |
| 4 | 可选（P1）`vault-server/.../ServerWarState.java` | 抽出"行军事件总线/压缩检测"供 Guardian 订阅，避免双解析；P0 可不改（独立解析） | ~50-100 行 |
| 5 | 可选（P0 手动触发）`vault-server/.../VaultHttpApi.java` | 新增 policy action `guardian` 手动触发/查询；或复用 roleParams 开关由真实威胁驱动 | ~30 行 |

**App 侧：P0/P1 零改动**（配置走 roleParams、状态走 state/mod 回显）；P2 需 `FeatureGate.java`（`implemented=true`）、`FnRegistry.java:96` 文案、`HomeActivity`/`FnDetail` 入口开关与状态行。

**Q3：是否必须改 SessionKeeper？**

**必须，但改动很小（~20-30 行，3 处）**。原因：服务器模式下 `LiveSession` 是唯一持有 engine/登录态/重连/让位的对象；推送钩子要在有 engine 时挂（参考 `help/shield` 惰性挂载 `SessionKeeper.java:424-431`）、动作要在 `online` 时才允许（`:445-446` 的 `s.tick(engine)` 模式）、shutdown 要停守护执行器。如果不改 SessionKeeper，只能从 `WarNotify` 分发（它只有 hook、拿不到会话对象/不能发请求）或在 `Main` 里遍历会话（无公开 API）——都不可行。

**基础设施复用度评估**：会话/推送/编队/时钟/协议封装/战争判定 ≈ 70% 已具备；缺的是"驻防发射执行器 + 卡秒调度 + 状态机产品化"。

**分期与 ETA**（人日，含单测；不含用户真机配合等待）：P0 前置探针 0.2 → **P0 最小闭环 2.0** → **P1 自动威胁驱动+卡秒+加速 3.0** → **P2 多盟友/动态/产品化 4.0-5.0**；真机对拍 1.0-1.5；**合计 9-12 人日**。

## 1. 背景与目标

### 1.1 需求定位

用户 T3 高级会员六项之一=「守护盟友」：盟友主城被敌方行军攻击时，自动向该盟友**卡秒驻防**（我方部队到达时刻早于敌方到达 0.5~5s），并支持战报判定/撤防/常驻戒备/预驻防。
功能分级现状：`design/全流程行为与分级门控-20261023.md:17,200` 标注 **🟡 部分实现**（威胁判定/闸门/探针完成，自动驻防未接产品流程），`FeatureGate.java:86` 当前隐藏。

### 1.2 在服务器模式下的行为目标

| # | 目标 | 验收口径（可观测） |
|---|---|---|
| G1 | 盟友主城被**进攻**行军攻击时，服务端自动发出 type=5 驻防且先于敌方到达 | 服务端日志 `fireAt/ourEnd/enemyEnd` 差值满足 0.5s≤Δ≤5s（服务器秒域）；游戏内战报出现"驻防参战/防守成功" |
| G2 | 敌方**加速**时，我方同步加速（道具），保持先至 | 从 situation_update 到 speedup 请求 p95 ≤800ms（服务器侧计时） |
| G3 | 威胁解除（敌召回）→ 撤防释放队列；敌落地 → 等战报后撤防 | `off_work` 发出且 code=0；队列恢复 |
| G4 | 默认关/可回滚；不花钻石；不占死日常队列 | 总开关关闭时零请求；P0/P1 无 `req_shop_quick_buy` 钻石路径；日常任务照常（战时由既有闸门统一让位） |
| G5 | 战报成败可回显 App | `mod:{fpid}:{sid}:guardian` 子项 + `log:`/`srv:guardian` 账本；App 不改也能在"今日页/日志"看到 |

### 1.3 非目标（本设计不做）

- 不做跨角色联合调度（每角色独立实例；多角色并行=多个实例）。
- 不做进攻性拦截/半路截击；只做使馆驻防（type=5）。
- 不做钻石加速/钻石释队（`guard.diamond_*` 一律保持关闭；P2 再评估）。
- 不做 App 本地模式回归（App 代码已具备，维持现状；本设计只补服务器模式）。
- 不做 UI 设计细节（P2 只列改动点）。

## 3. 服务端化方案

### 3.1 总体架构与执行位置

```
vault-server / SessionKeeper.LiveSession（每角色）
 ├─ WjdrEngine（推送线程） ── engine.addMessageHook ──┐
 │                                                     ▼
 │                                         ServerGuardianEngine（本次新增）
 │                                           ├─ onPush：解析 marchesOf/targetUidOf → ThreatTrack
 │                                           ├─ 盟友域判定：notify_world_alliance_situation_* 为盟友目标
 │                                           ├─ 规则：type∈{1,2} / 开关 watch|intercept / power_min / eta_max
 │                                           ├─ 威胁升级：endtime 前移≥N → EXTREME 锁存
 │                                           └─ 任务提交 guardExec（专用单线程）
 ├─ SessionKeeper.LiveSession（会话线程 1s）     │
 │    ├─ online 分支：guardian.attach(engine)    │  （只挂一次）
 │    ├─ online 分支：guardian.tick(engine)  ────┤  （门控+唤醒，不阻塞）
 │    └─ 让位/暂停/顶号/离线：guardian 一律不动作 │
 └─ guardExec（daemon，单线程）  ◀──────────────┘
      ├─ 卡秒等待：engine.serverClock().waitUntilSec(fireAt)（300ms 重估）
      ├─ 发射：req_world_march{type:5, endpoint, formation, extra} → 校验 endtime
      ├─ P1 加速链：req_world_march_speedup{id,itemid,owner(uid字符串)}
      ├─ 撤防：req_world_march_off_work{id}（在途召回 req_world_march_recall{id}）
      └─ 状态：mod:{fpid}:{sid}:guardian / srv:guardian:{fpid}:{sid}:* / FileLog
```

**执行位置选择（关键决策）**：

| 位置 | 候选 | 结论 |
|---|---|---|
| 推送钩子线程 | engine 推送线程 | **只做解析入账**（微秒级），绝不发请求（App 教训：R3 加速链有阻塞请求，`GuardianEngine.java:694-699` 明确用异步线程） |
| 会话线程 tick（1s） | `SessionKeeper.java:445-446` 同款 | 只做"online 校验 + 脏标记唤醒"；**不放卡秒等待**（1s 粒度不够，且阻塞心跳/采集） |

### 3.4 type=5 驻防协议参数（P0 必须精确）

来自 App 生产实证（`design/守护盟友-协议实证-20261015.md:65-74`、`GuardianLaunch.java:664-687`、`design/守护盟友-会话交接-20261017.md:29-40`）：

```text
# 发起驻防（c2s）
req_world_march {
  type:     5,                       // A-1 实证：type=5, target_type=1 = 驻防(增援)行军
  endpoint: {x, y},                  // 目标盟友主城坐标（int 格）
  formation: formationPayload,       // 编队（英雄+各兵种 count），服务器用 Exec.formation(engine,1) 构造
  extra:     {}                      // A-2 变体自发现：空 / {target_uid:uid} / {param1:uid} 三选一，code=0 即锁定
}
# 成功响应（实证形状）：{"code":0,"march_info":{"id":<marchId>,"endtime":<serverSec>,"state":2,"type":5,...}}
# 失败码：2814=同城已有我方援助(弱驻防可 replace)；2815/1510=目标不同盟；2878=队列满；301=英雄不在城；2806=行军不存在
```

**服务器侧实现要点**：

1. 变体：按空 → `target_uid` → `param1` 顺序尝试，code=0 后锁定变体（进程内静态字段，跨账号共享；与 App 相同）。**P0 前置验证项 V2**：服务器会话首单实测锁定变体（同引擎同账号，预计与 App 一致）。
2. 编队：`Exec.formation(engine, 1)`（客户端第 1 队布阵英雄；10 万库存上限内 40/30/30 兵种，`Exec.java:275-300`）。P0 固定第 1 队；P1 支持 roleParams `formation_squad` 与 301 英雄轮换（复用 App 变体轮试思路）。
3. 校验：响应 code=0 且 `endtime > 0` 才算成功；否则按错误码：2878 队列满 → P0 有限重试（≤3 次×2s，**不撤采集**，与 App 的强仲裁不同——服务器模式撤采集会影响日常，属 P2 决策）；301 英雄不在城 → 换下一队/标记；2815/1510 → 目标非盟友，拉黑目标 10 分钟；2814 → 已有驻防，跳过。
4. 幂等：`srv:guardian:{fpid}:{sid}:inflight` 记录 targetUid → {marchId, enemyMarchId, ourEndSec, state}；同 target 存在在途/驻扎任务时不再发（对齐 App `INFLIGHT`/`ACTIVE` 语义 `GuardianLaunch.java:48,135-150,179-188`）。
5. 撤防：在途=`req_world_march_recall{id}`；已驻扎=`req_world_march_off_work{id}`（4/4 实测 code=0，`design/守护盟友-会话交接-20261017.md:30`）。**不要用** `req_embassy_repatriation`（空操作/2894）。
6. 队列表：P0 只按"最近 1 次发射成功"记账；P1 用 `ServerFieldTasks.marchCapacity`（`ServerFieldTasks.java:551`）+ 行军态势查询（`:268-290`，`req_world_march_detail_4_player_situation`）计算可用队列。

### 3.6 配置暴露 API（不改 App 的下发/回显通道）

**范围**：服务端检测 → 规则 → **立即发射** type=5（无卡秒等待、无加速）→ 记录 → 威胁解除撤防。目标是"第一次由服务器发出并成功驻防"，验证协议/编队/队列/状态通道全链路。

| 交付物 | 验收口径 |
|---|---|
| `ServerGuardianEngine`（onPush/威胁表/规则/门控/状态/清理） | 单测 ≥12；开关关闭时零请求 |
| `ServerGuardianLauncher`（type=5 三变体/编队/endtime/off_work） | 单测 ≥8；变体锁定 + code 分类 |
| `SessionKeeper` 接线（字段/attach/tick/shutdown） | 服务器启动后日志"守护钩子已挂载 fpid:sid"；离线/暂停/让位不动作 |
| 状态回显 `mod:{fpid}:{sid}:guardian` + `srv:guardian:{fpid}:{sid}:last` | App 不改也能在日志/今日页看到文案 |
| （可选）`/v1/vault/policy` action=guardian test-fire | 无真实敌情时闭环验证 |

**真机验收（需用户/QA 小号配合 0.5 人日）**：小号攻击盟友城（无加速）→ 服务端日志 `检测→发射→ourEnd vs enemyEnd` → 游戏内出现"驻防参战"战报；撤防后己方队列恢复；全程零钻石消耗、未登录 App 自动化。

**风险**：R1 content 解析、R2 变体、R3 队列满（P0 有限重试）；误解为"已产品化"（明确仅内测开关）。

### 4.2 P1 — 自动威胁驱动 + 卡秒 + 加速（真正可用的守护）· 3.0 人日

**范围**：P0 + 精卡等待（300ms 重估）+ D 标定（近/中/远 EWMA）+ 压缩/EXTREME 检测 + 对等加速（301900/301901，预算上限）+ 战报成败（校准码表，未知不判不撤）+ 威胁结束双分支撤防 + 多威胁排队/并发≤2。

| 交付物 | 验收口径 |
|---|---|
| 卡秒调度（guardExec + `serverClock.waitUntilSec`） | 我方 endtime ≤ 敌 endtime−1s 且 ≥−5s（生产秒域）；日志可复算 Δ |
| 压缩检测 + EXTREME 锁存（≥3 次/24h） | 敌 3min→5s 压缩场景：检测到首次压缩 ≤600ms 内发射（P1 目标 95% 可拦，道具充足） |
| 对等加速链 | 敌加速后 800ms p95 内发出 speedup；耗尽/floor 时诚实止损（召回或落地） |
| 标定表（D） | 每次发射自动入样；近/中/远区分；样本缺失回退 38s |
| 战报判定 | `notify_new_mail_syn` first_type=30 → 胜/负/未知；未知不撤防 |
| 观测键型 | `srv:guardian:*` 账本 + `mod:` 文案 + FileLog；P2 可被日报消费 |
| 单测 | 新增 ≥25（压缩判定/卡秒公式/加速选档/预算/撤防分流/码表） |

**验收**：真机对拍 ≥3 场（敌不加速/加速/召回），指标见 §1.2 G1-G3；连续 7 天 dry_run（`watch=true, intercept=false`）误触发=0。

**风险**：R4 卡秒窗口依赖服务器秒域；R5 风控（300ms 重估只读推送不额外请求，压力可控；加速请求按预算限流）；R6 与日常任务队列竞争（P1 只在发射瞬间占 1 队；战时让位由 ServerWarState 现有闸处理）。

### 4.3 P2 — 多盟友/动态/产品化 · 4.0-5.0 人日

**范围**：

**验收**：T3 用户可见可关；多角色隔离（A:888 与 A:724 互不污染）；7 天 dry_run 报告；误触发=0；单日无钻石消耗。

## 6. 安全与失败模式

| 模式 | 规则 |
|---|---|
| **默认关** | roleParams `p:guardian.sub.intercept=false`（App FnDetail 默认 `false`，`FnDetail.java:184-186`）；服务端环境 `VAULT_GUARDIAN=off` 一级 kill switch（P2 实施；P0 用未配置即不跑）。`watch=true` 时只观测只写日志（dry_run），不发任何请求 |
| **只防盟友** | P0/P1 只消费"联盟域"推送（`notify_world_alliance_situation_*`，语义=指向本盟的行军）；世界域推送（`notify_world_situation_info_*`）在服务器无盟友坐标表时**不处理**（避免误判邻城） |
| **不花钻石** | P0/P1 禁止 `req_shop_quick_buy`/钻石加速/钻石释队；加速只用背包道具（301900/301901），预算 `p:guardian.strategy.speedup_budget`（默认 4×25%+2×50%/任务，耗尽→止损并告警） |
| **队列保护** | 发射前在途任务数 ≤2（每角色）；同 target 只 1 单；2878 队列满 → 有限重试（≤3×2s）；**P0/P1 不撤采集**（服务器日常任务与守护共享队列；"战时召回采集"属 P2，默认关） |
| **战报缺失/未知** | 未知 `second_type` 不判成败、不撤防（P4P7 先例 `design/守护盟友-P4P7完善-实施说明-20261022.md:12-15`）；战报超时（30s）→ 记 unknown，按威胁 del 分支撤防 |
| **顶号/让位/暂停** | 只在 `STATE_ONLINE` 动作（`engine.sessionState()` 门控，同 `ServerShieldResponder.java:114-128`）；`takeover/recovering/PAUSED` 期间事件只入威胁表不入执行；回连后按事件保鲜（≤10min，参考 `ServerShieldResponder.EVENT_TTL_MILLIS:63`）补处理，过期丢弃不在旧情上发兵；human_first 让位语义不抢登录 |
| **幂等** | marchId 去重；同 target 在途/驻扎不重复发（2814/已驻防先例）；同 (target, enemyMarch) 只处理一次；跨重启从 `srv:guardian:inflight` 恢复（P1） |
| **限流/风控** | 推送解析零额外请求（复用已到达数据）；发射/加速请求受预算 + 并发上限 + 随机抖动（±300ms，设计 §14 对策）；EXTREME 检测依赖已有 `situation_update` 推送，不新增 300ms 轮询（App 的轮询通道服务器不做，纯推送驱动，风控面更小） |
| **回滚** | 参数级：`p:guardian.sub.intercept=false`（roleParams 热载 60s，参照 `ServerWarState.configure:94` 周期热载 `SessionKeeper.java:438-442`）；进程级：env `VAULT_GUARDIAN=off`（P2）；代码回滚：guardian 是新增类 + SessionKeeper 3 处小改，回滚=去掉接线即可 |
| **多角色隔离** | 状态键/威胁表/执行器全部带 `fpid:sid`；同 fpid 多角色互不共享（Ally 教训 `AllyMap.java:6-11`）；主动执行只在该角色会话 online 时 |
| **观测** | FileLog 结构化行（检测/规则/发射/加速/撤防/战报，字段：fpid:sid/敌march/目标/endSec/D/Δ/ourEnd/code）；`mod:` 文案；`srv:guardian:*` 账本；P2 接 `HealthMonitor`（如"在线但 24h 无守护钩子"告警） |
| **失败模式清单** | ①推送内容解析失败→守卫降级只告警（V1 前置）；②发射持续 2878→放弃并告警（不撤日常队）；③时钟未校准→拒绝卡秒，退化为"立即发射"；④编队构建失败→SKIP 告警；⑤加速道具耗尽→保留先至或召回止损；⑥目标退盟(2815/1510)→拉黑 10min；⑦被顶号→停止执行并状态标注 |
