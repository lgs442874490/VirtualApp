## 4. P1-1 方案（评估后复用 6c51c45，必须加门禁）

### 4.1 可复用的部分
分支 `modify/native-login-auto-discover-20261105-1211`（提交 `6c51c45`）中：
- `VaultEngine.readLiveSessionXmlOnDisk()` / `readLiveSessionTokenOnDisk()`；
- `SessionProbe.parseSessionToken()`；
- `AccountStore.updateFpidAndToken()`（fpid+token 一起回填，服务器模式 pushToken）；
- `SessionProbeTest` 的 `parseSessionToken` 用例。

### 4.2 不可原样合并的原因（3 个门禁缺口）
1. `adoptLiveSessionIfPossible` 在入口 `fpid` 为空时接受 live 里的**任意号**（只校验 `liveOwner == entryId`）。`liveOwner` 只记录“哪个入口启动的”，不记录“live 里会话是哪个号”；同入口换号后会改掉入口身份（用户看到的“入口变成书记”）。
2. `syncSessionOwner` 在 `liveOwner` 为空时仍允许回填（旧数据/归属未知），存在串号面。
3. `updateFpidAndToken` 的 `pushToken` 是 fire-and-forget，换号回填会覆盖服务器 token 且失败静默。

### 4.3 推荐实现（按此落地）
1. **只按需触发**：删掉 `EntryDetailActivity.onResume` 里的 `adoptLiveSessionIfNeeded` 自动调用；改为在以下动作前显式回填：
   - 点「登录并运行自动化」；
   - 打开「角色管理」且角色为空时；
   - 点角色行「登录」。
2. **双门禁**：
   - `liveOwner == entryId`（必须）；
   - 入口 `fpid` 为空（原生型）→ 允许回填，但必须 toast 明确“已识别为本入口登录的号 X”；
   - 入口 `fpid` 非空且与 live 不一致 → **拒绝回填**，提示“请先从本入口启动并确认登录的是哪个号”。
3. **不改 onResume 的入口身份**；所有回填动作在主线程回调后重读 `acc`。
4. **服务器模式**：回填后 `pushToken` 保留，但加失败日志（只记 fpid，不记 token）。
5. **测试**：
   - `TokenOwnership`/新 `LiveSessionAdopt` 纯逻辑：owner 不匹配、fpid 不匹配、空会话、入口空允许、同号允许；
   - `SessionProbe.parseSessionToken` 正常/登出/缺失键；
   - 回归：原生入口 token 空 + live 有效 → 运行自动化放行。

### 4.4 涉及文件（预计）
`VaultEngine.java`、`EntryDetailActivity.java`、`HomeActivity.java`、`SessionProbe.java`、`AccountStore.java`、`SessionProbeTest.java` + 新增纯逻辑测试。

## 5. 复现与验证

### 5.1 复现（真机，v4.2.68）
1. 容器里有两个入口：A（原生登录，无 token）、B（已登录，如“书记”）。
2. 从 B 启动游戏并保持登录，回 A 详情页。
3. 点 A 的「导出 token（迁移/备份）」→ 旧代码会读到 B 的会话并（A.fpid 为空时）把 B 的号绑进 A；「设置 token」预填随之显示 B 的号。
4. 在 A 粘贴导出内容并启动 → live 被 wipe+注入，B 的登录现场被覆盖。
> 修复后：步骤 3 直接提示“当前游戏里的登录不属于本入口，无法导出”；设置 token 换号需二次确认。

## 6. 已污染入口的恢复（给用户）

修复只防止再发生，**不会自动回滚**已被改写的入口：
1. 确认目标号自己的 `fpid----token`（从原设备/上号器/服务器 `token/get` 获取，不要用当前 live 的 token）；
2. 在目标入口点「设置 token」粘贴，出现「确认换号」时确认；
3. 启动该入口，确认游戏内登录号正确后，可点「保存当前登录现场」固化快照；
4. 若入口备注/号已被改成别人，可在「修改备注名」修正；不建议直接删除入口（会丢快照）。
