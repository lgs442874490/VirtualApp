# 真机监控 · 服务端任务级协议监控 + App 监控页（2026-10-25）

> 分支：`add/dev-monitor-20261025-1622`（基于 master `bbecd10`；未提交，等用户审核）
> 用户要求：「你给真机调试加个监控，我从新跑一遍原生游戏的领取跟任务那些，有在跑的，都是功能缺失（做了但是没有效果）」
> 用户确认：① 监控加在**服务端任务级协议监控 + App 监控页**；② 用户会**手动打开原生游戏客户端领一遍/做任务**。

## 1. 要解决什么

任务实际由 `vault-server` 执行（App 启动即锁定服务器模式，本机不建会话）。真机上看到「有在跑」，
但游戏里没有效果。缺的是**可观测性**：不知道每个功能到底发了哪些协议、游戏回了什么码/什么数据、
任务凭什么判 CLAIMED、以及用户手动在原生游戏里操作后服务端看到的会话/快照变化。

本批只加监控，**不改任何任务判定/协议逻辑**。

## 2. 事件模型（唯一契约）

`MonitorStore` 内存环形缓冲（默认 5000 条）+ 落盘 `data/monitor/monitor-yyyyMMdd.jsonl`（JSONL，64MB 轮转 `.1`）。
每条事件公共字段：

| 字段 | 说明 |
|---|---|
| `seq` | 单调递增序号（记录时自动补），App 增量拉取游标 |
| `ts` | 毫秒时间戳（服务端） |
| `kind` | `task.start` / `task.end` / `io.req` / `io.rsp` / `session` / `notify` / `mark` / `error` |
| `fpid` / `sid` | 账号 / 区服（可空） |
| `fn` / `name` / `trigger` | 任务 id / 中文名 / 触发来源（节奏|手动|服务器|整轮） |
| `proto` | 协议名（io.* / notify） |
| `code` | 游戏返回码（io.rsp；空响应=-1，无 code 字段=0） |
| `durMs` | 请求耗时 / 任务耗时 |
| `msg` | 人读文案（task.end 为任务 message；session 为状态说明；mark 为用户打点） |
| `args` | 出站参数（截断） |
| `data` | 响应/推送内容（截断） |
| `trunc` | 内容被截断时 true |

示例：

```json
{"seq":101,"ts":1792916000000,"kind":"task.start","fpid":"48460403","sid":"888","fn":"login_rewards","name":"登录好礼","trigger":"节奏"}
{"seq":102,"ts":1792916000012,"kind":"io.req","fpid":"48460403","sid":"888","fn":"login_rewards","proto":"req_login_reward","args":{}}
{"seq":103,"ts":1792916000060,"kind":"io.rsp","fpid":"48460403","sid":"888","fn":"login_rewards","proto":"req_login_reward","code":0,"durMs":48,"data":{"rewards":[...]}}
{"seq":104,"ts":1792916000061,"kind":"task.end","fpid":"48460403","sid":"888","fn":"login_rewards","cat":"CLAIMED","msg":"已领取","rewards":"钻石×30","durMs":61}
{"seq":105,"ts":1792916010000,"kind":"session","fpid":"48460403","sid":"888","event":"takeover","msg":"检测到顶号/人工登录，按 human_first 让位"}
{"seq":106,"ts":1792916020000,"kind":"notify","fpid":"48460403","sid":"888","proto":"notify_daily_claim_info","data":{...}}
{"seq":107,"ts":1792916030000,"kind":"mark","msg":"用户打点：原生游戏领取前"}
```

### 3.2 TaskTrace 约定

```java
TaskTrace.Context c = TaskTrace.begin(fpid, sid, fn, name, trigger); // 幂等；未启用时零开销
TaskOutcome o;
try { o = def.executor.run(tc); } catch (Throwable t) { o = classify(t); } finally {}
o.durationMs = ...; c.end(o);   // 落 task.end（cat/message/rewards/durMs）
```

- ThreadLocal 上下文；`autoCloseable` 防泄漏；嵌套 begin 只认最内层（整轮→动作两层时以动作为准）。
- `TaskTrace.attachNotify(engine, fpid, sidSupplier)` 在 `LiveSession` 构造时挂一次：
  notify 白名单默认「领取/任务」域（`notify_daily_claim*`、`notify_dailyquests*`、`notify_mail*`、
  `notify_activity*`、`notify_*reward*`、`notify_quest*`、`notify_achievement*`、`notify_supply*`、
  `notify_value_exchange*`、`notify_vip*`、`notify_fourteen_sign*`、`notify_seven*`、`notify_login*`、
  `notify_stage*`、`notify_chapter*`、`notify_backpack*`）；可用 `VAULT_MONITOR_NOTIFY=all|off` 覆盖。
- io 录制：跳过 `req_heartbeat`；任务上下文为空时记 `fn=""`（会话通道，登录/补充请求也可见）。
- 内容截断：`MonitorStore.contentLimit()`；序列化异常不得影响任务执行（全部 try/catch）。

### 3.3 API 契约（App ↔ server）

`POST /v1/vault/monitor`，op=`vaultMonitor`（ApiSign 同现有 POST）。

请求字段（扁平）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `action` | `query` | `query` / `mark` / `status` |
| `since` | 0 | 只取 seq > since |
| `limit` | 200 | 1..1000 |
| `kinds` | "" | 逗号分隔 kind 白名单（空=全部） |
| `fpid` | "" | 只看某账号 |
| `includeData` | "1" | "0" 剥离 args/data 轻量列表 |
| `msg` | "" | `action=mark` 时写入的文案 |

响应 `data`：

```json
{"enabled":true,"events":[...],"count":12,"lastSeq":107,"minSeq":96,"mem":107,"dropped":0,"serverTime":1792916030000}
```

`action=mark` → `{"enabled":true,"seq":108,"serverTime":...}`；`action=status` → `MonitorStore.status()`。

### 3.4 环境变量（部署时启用/回滚）

| 变量 | 默认 | 说明 |
|---|---|---|
| `VAULT_MONITOR` | `off` | `on` 启用（生产部署时在 `/etc/vault-server.env` 加） |
| `VAULT_MONITOR_DIR` | `<dataDir>/monitor` | 落盘目录 |
| `VAULT_MONITOR_MEM` | `5000` | 内存事件数 |
| `VAULT_MONITOR_MAX_BYTES` | `67108864` | 单文件上限 |
| `VAULT_MONITOR_CONTENT` | `2000` | 单字段截断字符数 |
| `VAULT_MONITOR_NOTIFY` | （白名单） | `all` 全量 / `off` 不录推送 |

回滚：删 `VAULT_MONITOR` 后重启（或临时改 `off`）；监控只写文件、不改任务逻辑、不发游戏协议。

## 5. 真机操作步骤（交付后）

1. 服务端部署含监控的 jar，`/etc/vault-server.env` 加 `VAULT_MONITOR=on`，重启，`GET /healthz`。
2. App 装机（新构建，同版本号覆盖安装，数据保留）。
3. App → 工具箱 → 真机监控 → 自动刷新开。
4. 用户进原生游戏前点「打点」→ 手动领取/做任务 → 回 App 再点「打点」。
5. 观察：会话被顶（`session takeover`）→ App 让位 → 重新登录快照（`notify_*` 领取/任务域）
   → 再在 App 里跑自动化，看对应功能的 `io.req/io.rsp/task.end`。
6. 证据：App 导出 JSONL + 服务端 `data/monitor/*.jsonl`；归档 `qa/evidence-20261025-dev-monitor/`。

## 6. 验收标准

- 服务端单测：`MonitorStore`（record/query/环形裁剪/轮转/close/环境变量）与 `TaskTrace`
  （上下文归属/异常不外溢/心跳过滤）全绿；`MonitorApi` 路由测试（签名/query/mark/未启用）全绿。
- App 单测：`MonitorFormat` 渲染/过滤、`VaultSync` 请求字段构造全绿。
- 不改任务判定：`vault-server` 全量测试与 `app` 全量测试不回归。
- 真机：App 监控页能拉到服务端事件；用户手动登录原生游戏后能看到 `session` 事件与登录后
  `notify` 快照；自动化执行能看到 `task.start → io.req → io.rsp → task.end` 完整链路。

## 7. 明确不做

- 不改任何任务的协议参数/判定逻辑/领取口径；
- 不抓原生游戏客户端的加密流量（抓不到）；只观察服务端会话被顶/重连后的登录快照与协议行为；
- 不常开监控写盘（默认 off，调试期由 env 打开）。
