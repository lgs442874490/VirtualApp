## 1. 背景与目标

### 1.1 问题不是功能重复，是同一套告警逻辑被实现了两遍

同一件事（“敌人对我/盟友发起进攻，要告警”），在两个引擎里各有完整一套：名单、判定、文案、去重、出口。两份实现必然漂移，2026-11-09 的“巨兽集结误报”只是漂移第一次被用户当场抓住：

- 战争通知的 `classifyMarch` 早就有 PvE 判定（`WarNotify.java:337`），观察点 A2 分支没有（当日补上，`WatchPointEngine.java:1634-1641`）；
- 两份 A2 文案各拼一遍，兵力阈值一处可配（`WatchPointStore.feintTroopsBelow`）、一处硬编码 `1000L`（`WarNotify.java:998`）；
- 两条通道靠一行硬编码互斥来“不重复推”：`if (alert && isMonitoredUid(owner)) alert = false;`（`WatchPointEngine.java:1650-1651`），而两边的名单**没有任何同步代码**。

### 1.2 目标

1. **唯一口径**：PvE、自循环、同联盟、友军、目标城、威胁分级、侦查限流只在 `AlertRules` 实现一次，两个引擎都调用它。
2. **唯一文案**：A1 情报 / A2 敌袭 / A3 资源 / A4 运维四套模板只在 `AlertText` 实现一次。
3. **唯一名单**：用户只维护一份「关注玩家」，主键是**玩家肉眼可见的 fid**；观察点需要的城坐标由 fid 自动派生。
4. **唯一去重**：`owner+marchId` 全局唯一（跨账号），同目标 30s 聚合（仅迁城 + 集结）。
5. **唯一出口**：所有告警先写 `WatchEventStore`，再由出口分发；App 时间线与短信因此对观察点告警也可见。
6. **唯一配置**：出口、静默、冷却、名单生效角色合并为一份。

### 1.3 非目标（明确不做）

- 不合并扫描引擎与推送解析引擎。整图扫描、迁城跟踪、采集点、侦查配额、跨区探测（`WatchPointEngine`）与破城结算、昵称解析、战报邮件关联（`WarNotify`）职责不同，强行合并会变成大泥球。
- 不改游戏协议层与 `WjdrEngine` 消息钩子。
- 不改破城结算规则（`breachOf`，`WarNotify.java:718-723`）。
- 不改短信发送实现（App 侧 `SmsManager`），只保证事件先入库。
- P5（扫描与推送互为兜底）本期只预留字段，不实现。

```
               ▼
```

## 3. 术语与标识口径

| 标识 | 含义 | 谁可见 | 现状 |
|---|---|---|---|
| **fid** | 玩家角色档案里的“账号 ID”，纯数字 | **玩家肉眼可见**，用户输入/展示只用它 | `PlayerDirectory.Entry.fid`（`PlayerDirectory.java:37`），由协议 `info.fid` 解析（`:173-174`） |
| **uid** | 游戏内部玩家 ID | 仅代码/日志可见，**不让用户填** | 两套名单、城缓存、行军 owner 都用它 |
| **fpid** | 号库账号标识（一个号库账号可含多角色） | 运维/App 内部 | `VaultStore.Account.fpid` |
| **kid** | 区服 ID | 玩家可见 | 名单/城缓存附带 |
| **aid** | 联盟 ID | 仅代码可见 | 联盟简称由 `PlayerDirectory.abbrOfAid` 映射 |

**统一规则（用户已确认）**：

1. 名单主键、用户输入、导入导出、页面展示一律用 **fid**。
2. 内部存储 `fid → uid → 城坐标` 的解析缓存；匹配行军 owner 时用 **uid**。
3. fid→uid 的权威解析是 `PlayerDirectory.byFid`（`PlayerDirectory.java:73-77`）+ `SessionKeeper.resolveUidByFid`；现有战争通知 `add` 已经做过一次（`VaultHttpApi.java:1336-1347`），本次把它变成名单服务的统一入口。
4. 解析失败（目录未建、玩家不在目录、跨区）时条目状态为 `UNRESOLVED`，**不参与匹配、不静默丢弃**，后台在整图扫描完成/目录刷新后重试，并在 App 上显示“待解析”。

> 为什么不是让用户填 uid：用户已明确“uid 只有代码可见”。现有观察点页已经做到“填 fid → 查询 → 自动回填 uid/坐标”（`WatchpointActivity.java:374-410`），战争通知页是在服务端换算（`VaultHttpApi.java:1336-1347`），两边体验不一致，本次统一为“用户只填 fid”。

### 4.2 已经存在的共享（正面先例，沿着它继续）

- `WarNotify.isPveMarch` 直接调用 `WatchPointEngine.isPveMarchDeep`（`WarNotify.java:830-832`），这是全链路**唯一**一处口径共享；
- 守护盟友 `ServerGuardianEngine.ingestWarNotifyThreats` 也直接调 `WarNotify.classifyMarch`（`ServerGuardianEngine.java:1878-1910`），不复制过滤；
- 2026-11-04 起 `classifyMarch` 的注释就写着“战争通知 + 守护盟友共用；抽成纯函数，避免两套过滤漂移”（`WarNotify.java:309-323`）。

**这证明“抽纯函数 + 双方调用”在本项目是可行且已验证的路线**；告警中枢只是把这个模式从“PvE 一个函数”扩大到“规则 + 文案 + 名单 + 去重 + 出口”。

### 4.3 现状里的“死配置/死开关”（设计时必须处理，不能照搬）

| 配置 | 现状事实 | 处理 |
|---|---|---|
| `WatchPointStore.alertTypes` | 只在默认值/校验/快照/落盘出现，**引擎无消费点** | 统一为 `AlertConfig.routeEnabled`（A1-A4），并真正接入路由 |
| `WatchPointStore.cityTargetOnly` | **引擎无消费点**（实际一律按 `cityNear` 判定） | 删除或并入 `routeEnabled` |
| `incomingRallyFollowerAlerts` | `WE:1633` 已把 type 限为 2/102，而开关只过滤 99/100 → **不可达** | 统一后在类型归类阶段生效；若仍无意义则删除 |
| `WarNotify` 的侦查分支 | `type==1` 在 `classifyMarch` 已被 `scout` 拒绝（`:347`），`emitAction` 的 `ACT_RECON` 分支不可达 | 侦查由 A1 路由统一处理，删除死分支 |
| `troopsTag` / `shouldAlertMonitor` | 生产无调用，仅单测 | P1 清理，测试迁移到 `AlertText`/`AlertRules` |
| `statRallyFollowerIgnored` | 无自增点，恒 0 | 删除或接入 |

### 4.4 现状里的不一致（统一时要显式修掉）

1. 观察点 `alert()` **不校验** `vault.json watch.enabled` 总开关，只校验 `watchpoint.wecomEnabled + webhook + 静默`（`WatchPointEngine.java:2722-2725`）；WarNotify 校验 `cfg.enabled`（`WarNotify.java:232`）。
2. 观察点坐标上限 `1200`（`WatchPointStore.java:154`）与引擎 `MAP_MAX=1199`（`WatchPointEngine.java:54`）不一致。
3. 观察点 `alertExec` 单线程且 `waitWecomSlot` 保证 ≥3s 一条（`WatchPointEngine.java:2748-2753`）；WarNotify 是独立线程池，两边并发各自限速，企微侧没有全局 20 条/分钟的统一控制。
4. `ALERT_DEDUPE_MS=15min`（`WatchPointEngine.java:75`）与 `cooldownSeconds`（默认 300s）是两套时间语义，同一逻辑在不同链路表现不同。

## 5. 目标架构与模块职责

### 5.1 新增模块（`vault-server/src/main/java/com/carlos/vaultserver/alert/`）

| 类 | 职责 | 不做什么 |
|---|---|---|
| `MarchEvent` | 统一事件模型（§6） | 不含业务判定 |
| `AlertRules` | 唯一判定口径（§8），纯函数优先 | 不写 I/O、不拼文案 |
| `AlertText` | 四套文案模板（§11.5），纯函数 | 不查去重、不发网络 |
| `AlertHub` | 编排：归一化→判定→去重→聚合→发射 | 不解析协议、不扫描地图 |
| `WatchlistService` | fid 名单 CRUD + fid→uid→坐标派生（§9） | 不做判定 |
| `Deduper` / `Aggregator` | 去重键、聚合窗口（§10） | 不决定是否告警 |
| `AlertOutbox` | 事件库 + 企微 + 短信桥（§11） | 不改文案语义 |
| `AlertConfig` | 合并后的配置模型（§12） | 不兼容旧字段解析（由适配层做） |

### 5.2 两个引擎的改造点（最小侵入）

| 引擎 | 保留 | 改为调用中枢 |
|---|---|---|
| `WatchPointEngine` | 扫描、迁城跟踪、采集点、侦查配额、跨区探测、建筑增量、攻击者跟踪 | ① 判定：`onMarch` 的 A1/A2 分支 → `AlertRules`；② 文案：`incomingAlertText/outgoingAlertText/resourceAlertText/gatherAlertText/buildingAlertText` → `AlertText`；③ 名单：`isMonitoredUid` → `WatchlistService.uidOf(fid)` 派生集合；④ 出口：`alert(key,text)` → `AlertOutbox.emit()`；⑤ 删除 `isMonitoredUid` 硬互斥 |
| `WarNotify` | 推送解析、跟踪表、破城结算、昵称解析、战报邮件关联 | ① 判定：`classifyMarch` → `AlertRules`（保留 `MarchVerdict` 兼容壳，内部委托）；② 文案：`wecomText` → `AlertText`；③ 名单：`matchWatched*` → `WatchlistService`；④ 去重/冷却 → `Deduper`；⑤ 出口 → `AlertOutbox` |

> 关键：**不改两个引擎的“数据怎么来”**。`WarNotify` 仍然解析 `march/situation/mail`，`WatchPointEngine` 仍然扫描整图。中枢只接管“拿到一条行军之后怎么判、怎么写、怎么发”。

### 5.3 数据流（一条行军的完整生命周期）

```
PUSH: WarNotify.handleMarch(m)
  → MarchEvent.fromPush(m, proto, observerFpid, observerSid)
SCAN: WatchPointEngine.onMarch(m, ctx)
  → MarchEvent.fromScan(m, kind, rect, observerFpid)

  → AlertHub.submit(e)
      S0 归一化（补 fid/城坐标/联盟/目录）
      S1-S12 AlertRules.evaluate(e, cfg, ctx)  → Verdict{accepted, route, reject, threat}
      S13 Deduper.tryAcquire(alertKey)          → 跨账号全局唯一
      S14 Aggregator.feed(aggregateKey, e)      → 30s 同目标聚合（仅迁城 + 集结）
      S15 Quota.allow(route, ownerUid)          → 5min3条（A1/A3）
      S16 AlertOutbox.emit(record)
            → WatchEventStore.append（唯一事件源，幂等）
            → 企微（开关/静默/全局限速）
            → App 轮询 /v1/vault/events → 时间线 + 短信
```

## 6. 统一事件模型 `MarchEvent`

### 6.1 字段

| 字段 | 类型 | 来源 PUSH | 来源 SCAN | 说明 |
|---|---|---|---|---|
| `ownerUid` | long | `m.owner` | `m.owner` | 行军发起人（内部匹配键） |
| `ownerFid` | String | 目录反查 | 目录反查 | 展示/名单主键；解析失败为空 |
| `marchId` | long | `m.id` | `m.id` | 全局唯一键的一部分 |
| `marchType` | long | `m.type` | `m.type` | 1/2/4/5/6/8/100/102/… |
| `behavior` | String | `behaviorOf` | `a1/a2/resourceBehavior` | 侦查/进攻/集结出征/驻防增援/采集/建设/破坏/迁城 |
| `sx,sy` | int | `startpoint` | 同 | -1=未知 |
| `ex,ey` | int | `endpoint`/`target` | 同 | -1=未知 |
| `startSec,endSec` | long | `starttime/endtime` | 同 | 游戏服时钟 |
| `troops,troopsTotal` | long | `troopsOf/troopsTotalOf` | 同 | 0=未知 |
| `pveReason` | String | `pveMarchReason(m)` | 同 | 空=非 PvE；非空=命中特征 |
| `selfMarch` | boolean | `isSelfMarch` | 同 | 归一化时算一次 |
| `ownerAid` | long | 城缓存/目录 | 同 | 未知=0 |
| `targetUid` | long | `cityNear(ex,ey)` | 同 | 未知=0 |
| `targetAid` | long | 同上 | 同 | 未知=0 |
| `rawProto` | String | proto | null | 排查用 |
| `source` | enum | `PUSH` | `SCAN` | P5 兜底预留 |
| `observerFpid` | String | 会话账号 | 扫描账号 | 仅诊断，**不参与去重** |
| `observerSid` | long | 会话 sid | 扫描 sid | 同上 |
| `detectedAt` | long | now | now | 毫秒 |

### 6.2 构造约定

1. **只做归一化，不做判定**：`fromPush`/`fromScan` 可以填 `selfMarch/pveReason/ownerAid/targetAid`，但“是否该告警”全部交给 `AlertRules`。
2. **坐标未知用 -1**，不允许用 0 表示未知（0,0 是合法地图坐标）。
3. **PvE 判定只调用 `WatchPointEngine.pveMarchReason` 一处**；`WarNotify.isPveMarch` 保留为薄壳，内部委托同一函数（现状已是）。
4. **fid 反查失败不阻塞**：`ownerFid=""`，判定链路继续（匹配用 uid），展示用昵称/备注兜底。

## 7. 接口设计

### 7.1 判定结果

```java
package com.carlos.vaultserver.alert;

public enum Route { A1, A2, A3, A4 }

public enum Trigger { PLAYER, AREA, ALLY, OPS }   // T1/T2/T3/T4

public enum ThreatLevel { UNKNOWN, FEINT, THREAT } // 只影响文案，不影响拒绝

public final class AlertVerdict {
    public final boolean accepted;
    public final String reject;        // 拒绝码，见 §8.2；null=通过
    public final Route route;          // accepted 时非空
    public final Trigger trigger;
    public final ThreatLevel threat;
    public final String alertKey;      // 去重主键，见 §10
    public final String aggregateKey;  // 聚合键，见 §10
}
```

### 7.2 规则入口（唯一口径）

```java
public final class AlertRules {
    /**
     * 唯一判定入口。纯函数：不写 I/O、不读可变全局状态（cfg/ctx 都是显式入参）。
     * 顺序即拒绝优先级，见 §8.1。
     */
    public static AlertVerdict evaluate(MarchEvent e, AlertConfig cfg, AlertContext ctx);

    /** 兼容壳：WarNotify.classifyMarch 迁移期内部委托，保持 MarchVerdict 字段/拒绝码不变。 */
    public static WarNotify.MarchVerdict classifyForWarNotify(String proto, Map<String,Object> m,
                                                              AlertConfig cfg, AlertContext ctx);
}
```

`AlertContext` 只含判定需要的只读快照：

```java
public final class AlertContext {

```

### 7.3 中枢入口


### 7.4 名单服务

### 9.1 数据模型

```json
    "routeEnabled": {"A1":true,"A2":true,"A3":true,"A4":true}
```

### 9.2 fid → uid → 城坐标 派生链

```
用户输入 fid
  → PlayerDirectory.byFid(fid)                     （PlayerDirectory.java:73-77）
  → 命中：uid/nick/aid/kid 回填，health=OK
  → 未命中：health=UNRESOLVED，触发 refreshAsync（目录 6h TTL，整图扫描后重建）
  → uid → 城坐标：cityByUid / cityNear（整图扫描缓存）
  → 派生 monitorTargets（只读视图，不再单独存储）
```

**规则**：
1. `monitorTargets` 从“用户维护”改为“名单派生”。引擎里 `isMonitoredUid` 读派生集合，不再读 `WatchPointStore.monitorTargets`。
2. 关注区域（`protectRects`）保持不变，仍由用户维护，属于 T2 通道。
3. 派生失败（目录未建/目标不在图内）时，观察点无法定位该玩家，但推送侧（T1）仍能凭 uid 命中并告警——这正是“两条来源、一份名单”的价值。
4. 解析重试：整图扫描完成（`finishScan`）后、目录刷新完成后各重试一次；`resolvePending` 幂等。

### 9.3 三套旧名单的迁移映射

| 旧数据 | 位置 | 迁移规则 | 目标状态 |
|---|---|---|---|
| `VaultStore.Account.watchTargets[].uid` | `vault.json` 各账号下 | 按 uid 反查 `PlayerDirectory.byUid(uid).fid`；命中→`source=MIGRATED_WATCH`；未命中→`health=UNRESOLVED, legacyRaw=uid` | 并入全局名单 |
| `WatchPointStore.monitorTargets[]`（uid,nick,x,y） | `watchpoint.json` | `uid>0`：反查 fid 后并入（已存在则合并备注/坐标）；`uid<=0` 的纯坐标条目→丢弃并写入迁移报告 | 并入全局名单；坐标转派生缓存 |
| App `EnemyWatchStore` seed（888 服 4 个 uid） | App prefs `enemy_watch` | 全仓无 UI 调用 `save()`（死代码）；迁移时以 `source=MIGRATED_LOCAL`、**`enabled=true`** 写入（平稳过渡，避免迁移瞬间漏监控），解析失败的标 `UNRESOLVED` 并在页面提示 | 本地副本清空，服务端保留条目 |
| `VaultStore.WatchTarget.enabled=false` | 同上 | 迁移后保持 `enabled=false` | 保留暂停语义 |

**迁移原则（用户已确认“自动并入 + 废弃本地”）**：
- 迁移**幂等**：以 `fid` 为键 upsert；重复执行不产生重复条目。
- 迁移**不丢用户意图**：`enabled=false` 保留；`note` 保留；`legacyRaw` 保留原值便于排查。
- 迁移**产出报告**：`POST /v1/vault/alert/migrate {dryRun:true}` 返回 `{merged,skipped,unresolved,conflicts}`，先 dryRun 再执行。

## 10. 去重、聚合、限流

### 10.1 键与 TTL 总表

| 用途 | 键 | TTL | 作用域 | 说明 |
|---|---|---|---|---|
| 主去重 | `alert:{route}:{ownerUid}:{marchId}` | 15 分钟 | **全局跨账号** | 同一行军只产生一条事件；替代 `alerted` 的 `m:owner:id` 与 `cooldown` 的 `fpid / uid / action` |
| 聚合 | `agg:{route}:{ex}:{ey}:{behavior}` | 30 秒窗口 | 全局 | 仅集结类 + 迁城；普通进攻不聚合一；聚合记录带 `count/attackers[]` |
| 冷却 | `cool:{route}:{targetUid}:{behavior}` | `cooldownSeconds`（60..3600，默认 300） | 全局 | 防止同目标同行为连续刷；跨账号 |
| 结算冷却 | `cool:{route}:{targetUid}:{action}:done` | `cooldownSeconds` | 全局 | 保留现有 `done` 后缀语义 |
| 配额 | `quota:{route}:{ownerUid}` | 5 分钟窗口，3 条 | 全局 | A1 情报 / A3 资源；沿用 `SCOUT_WINDOW_MS/SCOUT_MAX_PER_WINDOW` |
| 侦查重放 | `once:{ownerUid}:{marchId}` | 5 分钟 | 全局 | 轮询重放不重复扣配额（沿用 `scoutCountOnce`） |
| 事件幂等 | `event:{alertKey}` | 事件库生命周期 | 全局 | `WatchEventStore.append` 前查重，防双写 |

### 10.2 跨账号全局去重（用户已确认）

- 键**不含** `fpid/sid`：同一行军被多个账号会话看到（`matchWatchedAnyAccount`、联盟态势推送到达多个角色）只产出一次。
- `observerFpid/sid` 只写入事件字段，用于“谁先看到”的诊断，不参与键。
- 并发安全：`Deduper` 用 `ConcurrentHashMap.compute` 原子占位（沿用 `WarNotify.throttled` 的写法，`WarNotify.java:1088-1098`）。
- 清理：懒清理（`removeIf`）+ 每 60s 一次 `sweep`（沿用观察点 `alerted` 的清理策略，`WatchPointEngine.java:1002,1529-1532`）。

### 10.3 同目标聚合（用户已确认 30s，仅迁城 + 集结）

- 触发：A2/A4 类，`aggregateKey` 相同。
- 窗口内：不立即发射，累计 `count`、`attackers[]`（最多 8 个）、`troopsMax`、`firstDetectedAt/latestDetectedAt`。
- 窗口到期（30s）或首条时发射一条聚合记录，`aggregated=true`。
- 单条记录正文仍用 `AlertText`，但标题加 `（共 N 条）`，正文列前 8 个攻击者。
- 迁城：观察点现有 `moveAlertWindowMs=60_000`（`WatchPointEngine.java:394`）改为 `aggregateWindowMs=30_000`，与集结共用同一 `Aggregator`。
- 普通进攻（A2 type=2 非集结）**不聚合**，即时发射；仅集结类（99/100/102/10/12）与 A4 迁城聚合。

### 10.4 冷却与配额

- `cooldownSeconds` 沿用 `VaultStore.validateWatchConfig` 的 60..3600 clamp（`VaultStore.java:298-311`）。
- A1/A3 配额沿用“5 分钟 3 条/人”，但计数维度从“每账号”改为“全局 ownerUid”（现有 `ScoutPushQuota` 已是按敌人 uid，`ScoutPushQuota.java:31-43`）。
- 配额不占冷却：命中配额直接静默，不写 `cool` 键（沿用观察点行为，`WatchPointEngine.java:1616`）。
- 全局企微限速：从观察点的“单线程 ≥3s”提升为 `AlertOutbox` 内的统一令牌桶（20 条/分钟），两个来源共享同一额度。这是修复 §4.4 第 3 条不一致的必要条件。

### 10.5 状态存储

- 内存 `ConcurrentHashMap`（与现状一致，重启即清空）。
- 不落盘：行军生命周期短（`TRACK_TTL_MS=30min`），落盘收益低。
- 清理：每 60s `sweep`；`Deduper` 超过 4096 条时淘汰过期项（沿用观察点 4096 上限的做法，`WatchPointEngine.java:494-496`）。

## 11. 出口统一

### 11.1 事件库是唯一源

所有通过 S16 的告警**先**写 `WatchEventStore`，**再**决定企微：

```
AlertOutbox.emit(record)
  → events.append(record)         // 幂等：alertKey 已存在则跳过
  → 企微 if (enabled && webhook && !quiet && 令牌桶有额度)
  → 短信由 App 轮询 /v1/vault/events 消费（服务端不直发）
```

这直接解决“观察点告警在 App 里看不到”：观察点告警入库后，`NotifySettingsActivity` 的“最近事件”和 App 短信轮询自动可见（`WarNotifyPoller.java:68-118`）。

### 11.2 事件 schema

沿用 §7.8 的扩展字段；`phase=action` 为发起事件，`phase=settle` 为结算事件（仅 A2，保留现有 `outcome/breach/battleCodes`）。

### 11.3 企微

- 开关：`alert.wecomEnabled` + `alert.webhookUrl`；静默：`alert.quietStart/End`（沿用 `inQuietHours` 的跨夜语义）。
- 发送：`WeComNotifier`（重试 2 次、errcode 校验，`WeComNotifier.java:22-75`）。
- 限速：统一令牌桶（20 条/分钟，≥3s 间隔），两个来源共享。
- 失败：只记日志，不回滚事件（事件已入库，App 时间线仍可见）。

### 11.4 短信

- 保持 App 侧实现（`WarNotifyPoller.sendSms`、`WarNotifyGate.gate`）；服务端不新增短信出口。
- 统一后短信自然覆盖观察点事件，因为事件已入库。
- 短信文案由 App 用事件字段拼（`WarNotifyGate.formatSms`），与企微文案不同源是现状，本次不改（避免扩大范围）。

### 11.5 文案模板（`AlertText` 唯一实现）

| 路由 | 标题 | 字段 | 现状来源 |
|---|---|---|---|

## 16. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 全局去重导致“某个账号看不到” | 用户以为漏推 | 事件带 `observerFpid`，时间线可查；文档明确“全局唯一”口径（用户已确认） |
| fid→uid 解析依赖整图扫描/目录 | 冷启动期名单 UNRESOLVED | 解析失败不阻塞 T1（推送侧可用 uid 命中）；页面显示“待解析”；`resolvePending` 重试 |
| 旧接口双写不一致 | 旧 App 看到过期数据 | 单写 `alert.*` + 读时合成；迁移期只跑一次迁移 |
| 观察点事件入库增加 seq 压力 | 事件库 200 条环形被观察点占满，战争通知事件被挤掉 | 事件库容量从 200 提升到 500；或按 `route` 分桶；P3 前压测确认 |
| 聚合改变用户感知（延迟 30s） | 用户觉得“变慢” | 只对集结类 + 迁城生效，普通进攻即时发；首发仍即时发射 |
| 文案统一改变习惯 | 用户以为坏了 | 文案字段结构不变，只统一阈值来源；发布说明列出差异 |
| `roleUidScope` 语义误用 | 名单生效角色配置导致漏推 | 保留现有豁免（名单命中即处理），并在页面提示 |

**回滚总策略**：每个 P 阶段一个独立 feature flag（`alert.rules.v2` / `alert.watchlist.v2` / `alert.outbox.v2` / `alert.page.v2`），默认开、出问题单开关回退；数据迁移只做加法（upsert + legacyRaw），不做破坏性删除。

## 17. 已确认口径（2026-11-09 用户拍板）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 总开关冲突取 OR 还是 AND | **OR**：`alert.enabled = watch.enabled OR watchpoint.enabled`；迁移后页面只保留一个开关 |
| Q2 | 旧 uid 反查不到 fid 时 | **保留 `UNRESOLVED` + `legacyRaw`**，页面提示重填 fid |
| Q3 | `monitorTargets` 纯坐标条目（无 uid） | **丢弃 + 写迁移报告**（坐标由扫描自动得到） |
| Q4 | App 本地 seed 迁移后状态 | **默认启用（`enabled=true`）平稳过渡**，避免迁移瞬间漏监控；解析失败标 `UNRESOLVED` 并提示。详见 §9.3 末段 |
| Q5 | A2 是否用 T1∪T2∪T3 并集 | **按建议：并集**（解释见下） |
| Q6 | 事件库容量 | **200 → 500**，`FETCH_LIMIT=100` 不变 |
| Q7 | 聚合窗口与范围 | **30s，仅迁城 + 集结类（99/100/102/10/12）**；普通进攻即时发 |
| Q8 | P5 互兜底 | **本期只预留 `MarchEvent.source` 字段**，不实现 |
| Q9 | 旧 App 兼容期 | **下一个强制升级版本发布后 30 天**，之后删除 `watch.*` 镜像 |
| Q10 | 文档目录 | 本次按你指定放 `docs/design/`；后续可整体迁移到根 `design/` |

**Q5 一句话解释**：A2「敌袭」现在有两种触发方式——战争通知是“我关注的人出手”（T1），观察点是“我的关注区域/友盟城被打”（T2/T3）。过去两者各管一段、靠一行硬编码避免重复；并集就是“任一条件满足就告警”，重复由全局 `alert:{route}:{ownerUid}:{marchId}` 消掉。按建议取并集。

**Q4 平稳过渡说明（为什么启用不会“大规模人员被打”）**：
1. 本地 `EnemyWatchStore` 实际是死代码：全仓无 UI 调用 `save()`，`enabled` 默认 false，仅 `EnemyWatch` 本地模式挂载；迁移只带入 seed 的 4 个 uid + 现有服务端名单并集，条目数有限。
2. 迁移只做一次 fid upsert，不会新增“全网玩家”；是否推送仍由 S1-S15 判定（PvE/同联盟/友军/目标城/去重/聚合/配额）压住。
3. 若出现误报，页面可单条 `enabled=false` 或关闭 `routeEnabled.A2`，不必回滚迁移。
4. 建议上线后 24h 对比“迁移前/后事件条数 + 企微条数”，异常再收紧。
