## 4. 关键设计说明（实现取舍，均不改变行为）

1. **LOCK 时刻推导**：`engine.lastRequestLockWaitMs()` 只在请求结束后可读，故 `lock = 请求发起时刻 + 锁等待`；未发请求记 `-1`。字段名与需求 R0-1 一致。
2. **outcome 判定**：`opened`=开盾成功；`failed`=发过请求但未成功；`skip`=门控/冷却/未发请求；`dropped`=陈旧/到达超保鲜期被丢弃；`timeout` 预留（R2 优先通道才产生，本期不实现）。
3. **trace 消费**：1Hz tick 与紧急唤醒拍共用同一 responder 实例，输出后立即清空 trace 字段，保证单次紧急路径**至多 1 条** trace。
4. **聚合输出格式**：需求 R0-2 给定单条格式串，按 `pushWake={}/{}/{}ms`（P50/P95/P99）单行输出，保留 `n={}`。
5. **到达观测 unmapped**：保留 `source=SITUATION_DEL`，追加 `unmapped=true` 与 `marchId=0`，便于分支 2 脚本按 `source` + `marchId>0` 过滤；已映射槽位重复 del 不会误标 unmapped。
6. **健康日志**：仅在 `calibrateRaw` 成功入样后判定；首次校准把 24h 计时起点设为当时单调钟，避免启动即刷健康日志。
7. **决策侧紧急兜底 trace**：紧急阈值可能由时间推进跨过（推送时 remain>20s、tick 时 ≤20s），此时没有新的紧急推送触发 WAKE；在 `decideInner` 发现 `urgent` 且无 pending trace 时补开一条（`wake=-1`），保证每次紧急开盾都能回溯。`decide` 的 `try/finally` 对无 trace 决策只是常量级空转。

## 6. 遗留项与风险

1. **未部署验证**：AC-1/AC-3/AC-5/AC-10 需部署后 24h（上限 72h）日志验证，属 M2/M3 里程碑，非本阶段。
2. **trace 并发边界**：极端情况下（紧急 push 与 1Hz tick 同拍，且 tick 先持 `ticking` 单飞）trace 会在下一拍输出，`push→resp` 会包含该等待；这是真实时延，不是埋点误差。
3. **`lastRequestLockWaitMs` 竞态**：同引擎并发请求极短时间内可能覆盖，仅影响观测精度（毫秒级），不影响开盾逻辑。
