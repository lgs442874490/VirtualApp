## 2. 协议依据（来自 `app/src/main/assets/wjdr/*.spb`）

### 2.1 专家额外情报

```text
notify_expert_quests.request:
  quests  : array<quest{id,progress}>
  finishs : array<finishs{id,isgetaward}>

req_get_expert_quest_award.request:
  quest_id : int          # tag=0
```

### 2.2 曙光市集（协议名 duck_market）

```text
notify_duck_market_act_info.request:
  act_info : duck_market_act_info{ id, ..., rewarded_idx_lst[] }
  task_info: duck_market_task_info{ quests[], finishs[{id,isgetaward}] }   # 与 act_info 同级

req_duck_market_get_quest_award.request: { act_id, quest_id }
req_duck_market_get_cost_award.request : { act_id }
```

> 关键修正：旧代码写成 `act_info.task_info`，而协议里 `task_info` 是通知根字段。
> 这正是“执行了但状态一直不更新/永远领不到”的直接原因之一。

### 2.3 领取状态判定

- `isgetaward` 兼容 `Boolean` 与字符串 `"true"`；
- 响应成功（`code=0`）或已领/未开放类错误码（4302/4303/7500/7501 等）都会写台账；
- 台账按天失效，避免“游戏通知仍保留可领项”导致第二天误跳过。

## 3. 去重实现：`ClaimLedger`

文件：`vault-server/src/main/java/com/carlos/vaultserver/task/ClaimLedger.java`

```text
键：ledger:<fpid>:<sid>:<scope> → { itemKey: "yyyy-MM-dd" }
scope：
  expert_extra  itemKey = questId
  dawn_market   itemKey = "quest:<questId>" / "cost"
```

行为：

1. 同一子项**当天只请求一次**；成功或“已领”类错误码即落账；
2. 第二次及以后轮次直接跳过，不再发协议、不再产生奖励弹窗；
3. `mark()` 时清理非当天旧键，避免状态文件无限增长；
4. 台账随 `StateStore` 持久化，重启服务器不丢；
5. 模块文案每轮都会写入 `mod:`，包括“未开启/无可领/失败”，避免 App 一直显示上一轮旧状态。

配套修正：

- `ServerTasks.unclaimedFinishIds(Object)` 统一解析 `finishs` 的**数组**与 `"id.0"→item` 的 **map** 两种形状；
- `RoundRunner` 的子项状态改为：`ok→2`、`skip→4`、`fail→3`（旧代码把 `skip` 记成“已领取”，是“界面显示完成但游戏内没奖励”的来源）；
- `LogStore.applySubResults` 客户端同样改为 `skip→ST_SKIPPED`、`fail→ST_FAILED`。

## 4. 采集编队弹窗

文件：`app/src/main/java/com/carlos/vault/daily/FunctionActivity.java`

入口：日常 → 野外采集 → **采集编队**（替代原“高级参数 JSON”）

| 控件 | 配置键 | 说明 |
|---|---|---|
| 编队 | `squad_index` | 0=自动（沿用游戏当前编队）；1~5=游戏内第 N 队 |
| 矿种 | `resources_named` | `MEAT/WOOD/COAL/IRON`（肉/木/煤/铁，可多选） |
| 矿点等级 | `min_level` | 1~6，实际从该等级向下搜索到 1 级 |
| 队列数 | `max_queues` | 1~5，与当前在途队列取空位 |
| 只采满矿 | `strategy.send` | `full` / `any` |

保存时：

```json
{"squad_index":1,"resources_named":["MEAT","WOOD","COAL","IRON"],
 "min_level":5,"max_queues":4,"strategy":{"send":"any"}}
```

服务器 `ServerFieldTasks.formationFor()` 优先读取 `squad_index`：

```java
int squad = p.optInt("squad_index", 0);
if (squad > 0) return Exec.formation(tc.engine, squad);
```

真机验证：选择“第1队”→保存后 5 秒内服务器 `roleParams.gather` 已变为上述 JSON，
且旧的 `hero_ids/troop_count/target_amount/carry_per_troop` 全部消失。

证据：

| 编队 `code=2` | 全库存/比例超出兵种存量、单队无上限 | 按各兵种存量夹取，单队上限 50,000 |
| 英雄列表为空 | `notify_hero_init` 真机是 `{"50042.0":{hero}}` | 兼容 map 键与 `data[]` 两种形状 |
| 探险速刷 `Struct field expects Map` | `fight_heros_data` 直接传了数组 | 传 `{source:1, fight_heros:[…]}` |
| 总动员 `req_mobilization_open_info` 异常 | 无请求字段却传 `null` | 改传空对象 |
| 战斗护盾协议异常 | `free_id` 写死 1 | 从 `notify_city_item_init[].free_id` 读取 |
| 联盟排名/红包等误报异常 | 无数据/未开放时抛协议异常 | 已归 SKIPPED 或返回明确状态 |
