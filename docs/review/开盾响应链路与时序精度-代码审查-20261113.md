### 2.2 P1

#### P1-1 trace 上下文由 6 个独立 volatile 字段组成，begin（推送线程）与 emit（会话线程）无互斥 → 丢 trace / 半条 trace / 无聚合样本

- **位置**：`vault-server/src/main/java/com/carlos/vaultserver/ServerShieldResponder.java:361-369`（字段）、`:495-498`（推送线程 begin）、`:508-510`（推送线程写 wake）、`:2036-2045`（begin 重置全部字段）、`:2048-2055`（`recordTraceResp` 只写 resp/lockWait，**不写 reqStart**）、`:2063-2106`（emit 分段读 + 无条件清空）、`:1065-1067`（决策后写 `traceOutcome`）。
- **问题**：一条 trace 的原子单元是「traceId+push+wake+reqStart+resp+lockWait+outcome」七个字段，但它们不是原子的；`onPush`（引擎 hook 线程）与 `tick`（`shieldExec`/会话线程）之间没有任何互斥。`tick()` 的单飞（`:890-897`）只约束"同一时刻只有一拍在跑"，**不约束 onPush 与该拍并发**（`attach` 注释明确"推送线程调用"，`:446-450`）。
- **影响（可复现思路）**：以 07:00 同型场景为例，加速推送每 0.3–1s 一次、一次紧急决策（含 8s 超时的 `req_use_item`）可能持续数百毫秒到数秒：
  1. 推送 A 紧急 → `beginUrgentTrace()`（push=A）→ 提交 tick；
  2. tick 进入 `openShield`，`reqStart` 已置（`:1192`），正在等响应；
  3. 推送 B 紧急 → `beginUrgentTrace()` 把 `reqStart` 重置为 `-1`、push 改为 B；
  4. 响应返回，`recordTraceResp` 只写 resp/lockWait（reqStart 仍为 -1）；
  5. `decide` 的 finally `emit` 读到 push=B、wake=B、reqStart=-1、resp=A → 输出 **lock=-1 且 outcome=opened** 的自相矛盾 trace；随后清空字段，**B 的 trace 被静默吞掉**（B 自己的决策拍 `tracePushMs<=0`，不再输出）。
  6. 另有一条路径：emit 读字段读到一半时 B 调用 begin，则日志里的 `id`（`:2090` 读的是字段而非局部快照）属于 B，其余字段属于 A（串号）。
- **后果**：AC-1「任意一次紧急开盾四段可还原」在最需要它的高频加速场景下不成立；`lock=-1` 使该样本不满足聚合条件（`:2095`），AC-5 的 push→resp 分布在这些事件上直接缺样本。
- **依据**：字段声明 `:363-369` 全为 volatile 但无组合原子性；begin/emit 分别在推送线程与决策线程；单飞范围仅 `tick`。
- **优先级**：**P1**（观测数据错误/缺失，且命中目标场景；不影响开盾本身，故非 P0）。

#### P1-2 紧急开盾走免费盾时 trace 缺 LOCK/RESP（R0-1 阶段④未覆盖该路径）

- **位置**：`ServerShieldResponder.java:1104-1120`（`openShield` 免费盾分支，`:1107` 调 `ServerTasks.freeShield`）；请求实际发在 `vault-server/src/main/java/com/carlos/vaultserver/task/ServerTasks.java:4120`（`req_city_item_free_use`）；emit 的聚合条件 `ServerShieldResponder.java:2095`。
- **问题**：紧急路径经免费盾开盾时，请求由 `ServerTasks.freeShield` 内部发出，`ServerShieldResponder` 未打 `traceReqStartMs`、也未调用 `recordTraceResp`，于是 trace 输出 `lock=-1 resp=-1` 而 `outcome=opened`，且不进聚合。
- **影响**：需求 R0-1 的触发条件明确包含「或紧急任务实际发出开盾请求」，阶段④ 要求 RESP = 收到响应或超时时刻；该路径四段不可还原、AC-5 无样本。频率：`battle_shield.free` 默认关闭（2026-11-13 决策），开启账号每日首次紧急开盾命中（≤1 次/日/角色）。
- **依据**：`freeShield` 内确有 `tc.engine.request(...)`（`ServerTasks.java:4120`）；`ServerShieldResponder` 的 `useItem`/`buyAndUseShield` 是仅有的打点处（`:1192/1194`、`:1219/1221`）。
- **优先级**：**P1**（需求条目缺口，修复成本约 2 行；若用户接受可降级为已知缺口并延期）。

### 2.3 P2（逻辑 / 边界 / 文档）

> 每条给出：问题、影响、依据、优先级（均为 P2）。

#### 运行错误 / 竞态

**P2-1 LOCK 读取的是引擎级共享值，可被其他请求覆盖（疑点 2 成立，概率低但非零）**
- 位置：`app/src/main/java/com/carlos/vault/wjdr/WjdrEngine.java:218`（字段）、`:996` / `:1030`（持锁后写入）、`:1133-1135`（getter）；读取点 `ServerShieldResponder.java:2051`。
- 问题：`request()` 在 `unlock()` 之后才返回，`recordTraceResp` 的读取发生在 `unlock` 之后；若此时锁队列中的下一个请求（心跳/任务/采集）已 `lock()` 成功并写入 `lastRequestLockWaitMs`，本次 trace 会读到**别人的**等待时长。
- 影响：`lock = reqStart + 其他请求的 wait`，会污染 `wake→lock`（R3-1 判据阈值仅 50ms）与 `lock→resp`，可能把 C1 达标误判为不达标；不会影响开盾行为。
- 依据：`requestLock` 为公平锁，unlock 即 unpark 下一个等待者；写入点在 `lock()` 返回处，读取点在其后。
- 不确定性：窗口仅微秒级（我们的返回路径 vs 对方的唤醒路径），实测概率应很低；但在"请求串行是主因"的既有高竞争环境下不排除。

**P2-2 埋点调用插在业务关键调用之前（onPush 的唤醒路径）**
- 位置：`ServerShieldResponder.java:495-498`（`beginUrgentTrace()` 在 `wakeUrgent()` 之前）。
- 问题：`beginUrgentTrace` 内会调用注入的 `nowMs` supplier（`:2039`）。生产为 `System.currentTimeMillis()` 不会抛；但一旦该调用抛异常，`wakeUrgent()` 被跳过，紧急唤醒丢失 —— 这是本 diff 唯一"埋点失败可改变行为"的位置。
- 影响：理论行为变更（R0-6）；实测生产风险≈0。
- 依据：`urgent` 分支原为单行 `wakeUrgent()`，现被两条语句串联。

**P2-3 `decide` 的 finally emit 未整体兜底**
- 位置：`ServerShieldResponder.java:937-944`。
- 问题：`emitUrgentTrace` 若抛异常，会取代替换 `decideInner` 的原异常（Java finally 语义）。
- 影响：实际不成立 —— `clockOf`（`:2109`）与 `serverNowSec`（`:1713`）均吞 `Throwable`，`FileLog` 不抛（`:95-107`、`:117-125`），`latency.add` 只做数组/排序；仅测试注入的 supplier 可能抛。结论：生产不构成缺陷，建议防御性 `try/catch`。
- 依据：逐条核对 emit 内所有可能抛出点。

**P2-4 到达观测在推送（hook）线程同步落盘**
- 位置：`ServerShieldResponder.java:652-671`（`logArrival` 内 `FileLog.info`）经 `:623/627/636/639` 由 `attach` 的 hook 回调（`:444-452`，推送线程）触发；`FileLog.java:95-107` 内 `w.println + w.flush()`（synchronized）。
- 问题：R0-5 规定输出 `FileLog.info`，但落地线程是 hook 线程；`id_arr` 一次可含多个槽位，逐条同步 flush。
- 影响：到达风暴时 hook 线程被磁盘 IO 拖慢，属 R0-6「不改变响应时序」的轻微时间性影响（不改变逻辑）；既有推送路径本就有 `FileLog.warn` 先例，可接受。
- 依据：调用链 attach → onSituationDel → logArrival → FileLog.log。

#### 逻辑 / 口径

**P2-5 决策侧兜底 trace 把 PUSH 记成"决策时刻"（疑点 6 成立）**
- 位置：`ServerShieldResponder.java:984-986`、`:2036-2045`。
- 问题：`beginUrgentTrace()` 在 `decideInner` 内调用时把 `push` 记为当前 tick 时刻，而 R0-1 阶段① 定义 PUSH = onPush 算出 urgent 的时刻。R0-1 的触发条件本身允许"紧急任务实际发出请求"这一路，因此不算越界，但语义与字段名不一致。
- 影响：单条 trace 的 `push→resp` 实为"决策→resp"，且 `wake=-1`；消费脚本若不处理会把它当日志异常样本。目前 `wake=-1` 可辨识（测试 `urgentDiscoveredInDecision_stillEmitsTraceWithWakeMinusOne` 已固化）。
- 依据：`:986` 守卫 `urgent && tracePushMs <= 0L`；`beginUrgentTrace` 无"来源"入参。

**P2-6 钻石购盾双请求：LOCK/RESP 只保留最后一个请求，total 含两段，且无请求数标注（疑点 7 成立）**
- 位置：`ServerShieldResponder.java:1205-1240`（buy `:1219/1221`，use `:1231` → `:1192/1194`）。
- 问题：`traceReqStartMs` 被第二次请求覆盖，第一段请求（购盾）只体现在 `resp - push` 总量中，没有分段归因；同一 trace 内 `lock`（= 第二次请求起点+等待）与 `resp` 自洽，但 `total` 与 `lockResp` 不同源。
- 影响：钻石路径（默认关闭）的 `push→resp` 无法拆成"购盾/使用"两段；AC-5 对该路径只能看总量。日志无请求数，消费侧无法识别。
- 依据：`buyAndUseShield` 两次调用 `request` 且各调一次 `recordTraceResp`。

**P2-7 聚合窗口只有"输出后重置"，无最长跨度（疑点 8 成立）**
- 位置：`vault-server/src/main/java/com/carlos/vaultserver/ShieldLatencyAggregator.java:31`（windowStart）、`:38-46`（add）、`:49-56`（maybeFlush）。
- 问题：窗口仅在输出后重置；当样本稀疏（例如 1 条/小时）时，需累计到 10 条才输出，窗口可跨数小时/数天，P50/P95/P99 混入不同分布。
- 影响：与需求「每 200 条或每 60 秒（先到先输出）」相比，"n<10 只累计不输出"的可解释读法是"跨窗累计"，因此**字面合规**；但 AC-5 的分布判读会被跨时段混合污染，尤其昼夜负载差异大时。
- 依据：`:50-51` 同时要求 `count>=10` 与 `now-windowStart>=60s`，二者都不满足时窗口起点不变。

**P2-8 健康日志的 `sinceCalib` 恒为 0（字段无信息量）**
- 位置：`app/src/main/java/com/carlos/vault/wjdr/GameServerClock.java:130`（`lastCalibMonoMs = nowMono`）与 `:152`（`nowMono - lastCalibMonoMs`）。
- 问题：健康日志在校准流程内输出，`lastCalibMonoMs` 刚被更新为本次样本时刻，因此 `sinceCalib` 恒为 0（或个位数毫秒）。
- 影响：R0-3 要求的字段存在但无诊断价值；AC-10 想看的"距上次校准多久"实际不可得。
- 依据：同一 `synchronized` 块内先更新后读取。

**P2-9 健康日志只在有新样本时判定，24h 无样本则不输出（疑点 9 成立）**
- 位置：`GameServerClock.java:146-153`。
- 问题：24h 周期判断嵌在 `calibrateRaw` 内；某 `WjdrEngine` 若 24h 内无任何校准样本（无推送、无请求），不会输出「时钟健康」。
- 影响：AC-10 的 `delta` 序列会断档；"无样本"本身是重要诊断信号（时钟可能未校准），当前无观测。
- 依据：`:146` 是 `else if`，只在样本入窗后求值。

**P2-10 去重集合的上界清空语义（边界）**
- 位置：`ServerShieldResponder.java:652-662`（`:658`、`:661`）。
- 问题：`arrivalLogged` 超过 256 时整体 `clear()`，会连同刚加入的 marchId 一起清掉，之后同一 march 的 del 可再记一次；`arrivalSlotSeen` 只增不删，槽位被新行军复用后其 unmapped 样本会被永久抑制。
- 影响：极端量级（>256 次到达/进程生命周期，或槽位复用）下"同一 marchId 只记首次"与 unmapped 采样不严格；正常量级无影响。
- 依据：清空位置在 `add` 之后、无豁免当前键。

**P2-11 到达观测的 mapped-but-untracked 缺口（疑点 11 成立，但不是 R0-5 缺陷）**
- 位置：`ServerShieldResponder.java:331`（`enemyMarches` 为 `ConcurrentHashMap`）、`:634-640`（映射存在但 `remove` 返回 null 则不记）。
- 问题：槽位能映射到 marchId，但该行军未被 `trackEnemyMarches` 收录（缺 owner/类型、PvE 过滤，或已过 10min TTL 被剪枝）时，`situationSlotMarch` 被消费而**无到达观测**。
- 影响：R1-1 样本可能偏少；需求 R0-5 的触发条件字面是"成功从 `enemyMarches` 移除行军时"，因此**不算违反需求**，属可观测性缺口，建议在 R1 阶段补「mapped-but-untracked」分流。
- 依据：`:636` 只在 `remove != null` 时记录；`:684-688` 的过滤条件。

**P2-12 陈旧 pending trace 可跨拍/跨离线输出**
- 位置：`ServerShieldResponder.java:909`（非在线直接 return，不 emit）、`:926-931`（`etaCheckAtMs` 未到不 decide）、`:2099-2106`（只在 emit 时清空）。
