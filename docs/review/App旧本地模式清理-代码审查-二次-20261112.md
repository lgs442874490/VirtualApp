## 3. P3 观察（不阻断，可选处理）

1. **`DailySchedulerService.APP` 缺 `volatile`** —— [DailySchedulerService.java:31](../../app/src/main/java/com/carlos/vault/daily/DailySchedulerService.java#L31)：主线程 `onCreate` 写、`NotificationListenerService` binder 线程读，无 happens-before 保证。实践风险极低（服务启动先于通知回调），但按内存模型应加 `volatile`；非 final 静态字段用大写命名亦不合 Java 惯例，可改 `private static volatile Context appCtx;`。
2. **短信通道恢复后的「补发」效应（行为变化）** —— [WarNotifyPoller.java:68-92](../../app/src/main/java/com/carlos/vault/daily/WarNotifyPoller.java#L68-L92)：修复前该通道从未真正工作（游标不推进）；修复后若用户 `sms_on=true` 且手机号有效，下一轮会从**旧游标**拉取积压事件并逐条发送。`WarNotifyGate` 有冷却与 `sentIds` 去重，但若服务端 `/events` 返回量大，可能短时间集中发送。建议发布说明提示「短信告警恢复」；服务端返回量上限/`minSeq` 截断未核实（服务端不在本次范围）。
3. **`code==0 && data==null` 仍会写时间戳** —— [HomeActivity.java:373-381](../../app/src/main/java/com/carlos/vault/HomeActivity.java#L373-L381) 与 [VaultSync.java:350-365](../../app/src/main/java/com/carlos/vault/VaultSync.java#L350-L365)：服务端返回成功信封但无 `data` 时，状态缓存不更新却写 `last_fullsync`，10 分钟内不再拉状态。边界极窄（正常 `/state` 必带 `accounts/states`），可选加 `data != null` 条件。
4. **token 纯空白未拦截** —— [RoleManagerSheet.java:192](../../app/src/main/java/com/carlos/vault/RoleManagerSheet.java#L192) 用 `isEmpty()`，纯空白 token 仍会走登录；可改 `trim().isEmpty()`。
5. **类注释与实际不符** —— [EnemyWatchStore.java:15-18](../../app/src/main/java/com/carlos/vault/daily/EnemyWatchStore.java#L15-L18) 标题仍为「本地敌情 seed 数据存储」，正文已说明不再 seed，建议标题同步为「本地敌情名单（迁移读取）」。
6. **旧设备残余迁移（口径确认项）** —— 旧版本 `seedIfNeeded` 只要用户打开过通知设置/迁移就会写入 4 个 uid；这些设备升级后 `entries()` 仍能读到并迁移。与「旧设备已有名单仍可迁移」口径一致；旧 prefs 中 `seeded=true` 残留仍可用于识别 seed 来源（「seeded=true 且 entries 恰为那 4 个 uid → 视为 seed 不迁移」），若需更彻底可后续处理，当前不构成缺陷。
