> 所属需求：`design/网页版账号页复刻-需求分析与复刻方案-20261021.md`（§4.3 S-01~S-07）
> 分支建议：`add/account-pool-server-20261021-0100`（从 master `c8f2e3f` / 含 v4.1.4 发版提交的 master 拉出）
> 目标：先做服务端控制面与状态模型（App 端 M2 依赖本契约），保持现有 `/v1/vault/sync|token|status|state|policy|automation` 兼容，不破坏线上 App v4.1.4。

## 1. 鉴权与请求约定
- 沿用现有签名：`buildSignedBody(op, fields)`（`ts/nonce/sign`），服务端 `ApiSign` 校验；新增 OP 名需同步加入白名单/映射。
- 请求：POST JSON（扁平字段 + 复杂数据用字符串字段）；响应信封 `{"code":0,"message":"ok","data":{...}}`；业务失败用非 0 code + message。
- 所有接口幂等：重复动作安全；对不可执行状态返回 `code!=0` 且 `message` 说明（如 `ALREADY_ONLINE`/`ROLE_NOT_FOUND`/`FIPD_BUSY`）。

## 2. 数据模型
### 2.1 账号池视图（VaultStore.Account 扩展）
```json
{
  "fpid": "48460403",
  "accountName": "48460403",          // 备注名（可空）
  "activeSid": "888", "activeUid": "35371154",
  "workspaceCount": 2,
  "onlineCount": 1,
  "keep": true,                        // 账号级统一自动化（现有语义）
  "roles": [
    {"sid":"888","uid":"35371154","name":"隆科多","level":70,"power":208350000,
     "enabled":true,
     "state": {
       "online": true,
       "runState": "RUNNING",          // RUNNING|PAUSED|STOPPED
       "recoveryState": "AVAILABLE",   // AVAILABLE|DISABLED|ACTION_REQUIRED|WAITING_RETRY
       "statusMessage": "",
       "takeoverRecoveryActive": false,
       "nextRecoveryAt": 0,            // epoch ms，WAITING_RETRY 时倒计时用
       "startupInProgress": false,
       "loginInProgress": false,
       "runScheduleState": "ACTIVE"    // ACTIVE|PAUSED
     }}
  ]
}
```
- `state` 由 SessionKeeper 运行态推导；无会话 = 离线（online=false, runState=STOPPED）。
- 同 fpid 同一时刻至多 1 个角色 `online=true`（游戏服单会话约束，强制）；跨 fpid 可并行。
- `onlineCount` = 该账号 online 角色数；全局 `onlineCount` = 所有账号 online 角色数。

## 3. 新增接口
### 3.1 `POST /v1/vault/accounts`（op=`vaultAccounts`）
入参：`commonFields`（pkg/appVersion）。
出参 data：
```json
{"serverTime": 1792..., "onlineCount": 2,
 "accounts": [ /* §2.1 数组 */ ]}
```
用途：App 账号页列表 + 状态轮询（5s）。要求轻量（不返回配置/params/state 大字段），单次响应 ≤ 50KB（2~10 账号规模）。

### 3.2 `POST /v1/vault/role-action`（op=`vaultRoleAction`）
入参：`fpid`, `sid`(数字字符串), `uid`(数字字符串), `action` = `login|logout|pause|resume|stop`。
语义：
- `login`：启动/恢复该角色会话（登录中→在线）；若同 fpid 有其它在线角色，先停止它们并返回 `stoppedRoles:[{sid,uid}]`（响应提供以便 App 提示互斥）；成功后该角色 `runState=RUNNING`，账号 `keep=true`。
- `pause`：会话保留、暂停任务执行；`runState=PAUSED`；默认策略为「顶号/恢复策略自动恢复」占位（P0 简化：暂停后由 resume 或 login 恢复）。
- `resume`：`PAUSED→RUNNING`（无会话则等价 login）。
- `logout`：主动下线（等价 stop 但保留 keep/自动化配置，供 App 需要时再登录）。
- `stop`：销毁会话，`runState=STOPPED`，不自动恢复；账号 keep=false 仅当该账号无其它在线角色（避免误关自动化）。
出参：`{"accepted":true,"state":"RUNNING","message":"","stoppedRoles":[...]}`；失败 code 见 §1。
约束：动作串行化（单角色/单账号锁），并发安全；同一请求重复执行幂等。

### 3.3 `POST /v1/vault/account-action`（op=`vaultAccountAction`）
入参：`fpid`, `action`=`login-all|stop-all`。
语义：账号下所有工作区角色批量；受同 fpid 单会话约束（login-all 依次尝试，最终仅 1 个在线；返回实际在线角色与每角色结果）。
出参：`{"accepted":true,"results":[{"sid","uid","ok","message"}],"onlineCount":1}`。

### 3.4 `POST /v1/vault/global-action`（op=`vaultGlobalAction`）
入参：`action`=`login-all|stop-all`。
语义：所有账号批量；`login-all` 每账号最多 1 角色在线（默认取该账号 activeUid，否则工作区第一角色）；返回每账号结果与全局 `onlineCount`；执行中 App 轮询 `/accounts` 显示进度（P0 不做服务端进度推送）。
出参：`{"accepted":true,"accounts":[{"fpid","ok","onlineUid","message"}],"onlineCount":2}`。

### 3.5 现有 `/status` 扩展（兼容）
在 `accounts[]`（或 status 现有结构）增加 §2.1 的 `state` 对象；旧字段保留（App v4.1.4 不受影响）。`/state` 状态键不变。

## 4. 运行时与持久化
- `SessionKeeper` 增加按 `(fpid, sid, uid)` 的显式控制方法：`startRole/loginRole/pauseRole/resumeRole/stopRole`，供新接口调用；现有 `reconcile()` 仍以账号 `keep` 为自动恢复依据，但**显式动作优先**（并持久化期望状态，重启后恢复：在线集合 = 最后一次成功 login 且未 stop 的角色集合）。
- 新增持久化（VaultStore/vault.json）：每角色 `desiredOnline`(bool)、`runState`、`enabled`；重启加载后 reconcile 恢复 desiredOnline 角色（同 fpid 只取最近一次）。
- 并发上限：全局 `maxConcurrentSessions`（配置项，默认 8），超限返回 `code=429` 语义（现有信封 code 用非 0 自定义，如 1001）。
- 资源：每会话按现有 SessionKeeper 模式（协议连接+定时任务）；暂停时停止任务调度但保持连接/心跳（P0 简化，可后续优化）。

## 5. 测试要求（M1 完成门禁）
- 单测（JUnit，沿用现有 `VaultHttpApiTest/VaultStoreTest/SessionKeeper*Test` 风格）：
  1. role-action login/stop/pause/resume 状态转换正确、幂等、错误 code；
  2. 同 fpid 互斥：login 另一角色会 stop 前一个并返回 stoppedRoles；
  3. 跨 fpid 并行：两账号 login 后 onlineCount=2、各自 RUNNING；
  4. account-action/global-action 汇总与部分失败；
  5. `/accounts` 视图/计数/state 字段完整；
  6. 持久化：重启 store 后 desiredOnline 恢复（可用文件级测试）。
- 基线：server 测试 ≥120 全绿 + 新增测试；不得削弱现有测试。
- 真机/联调由 M4（test CLI glm-5.3）验证，不在 M1 内做。

## 6. M1 实现备注（dev 2026-10-21，分支 add/account-pool-server-20261021-0100）

> 以下为按契约实现时定稿的细节/偏差，均向后兼容；M2 App 端按此对接。

- **错误码表**（信封 code，HTTP 恒 200）：1004 账号不存在；1401 角色不存在/会话角色不匹配；1402 角色未在线（pause）；1403 角色已停用（enabled=false，已收纳）；1404 账号缺少 token；1429 并发会话达上限（契约 §4 的 429 语义）；3002 参数/未知 action。重复 login 已在线同角色按**幂等成功**（accepted=true, state=RUNNING，不返回 ALREADY_ONLINE 错误）；暂停中 login 等价 resume。`FIPD_BUSY` 未使用（P0 互斥为同步停旧会话，无异步忙态）。
- **/status 扩展键名**：旧 `state` 是字符串引擎态（online/logging/…），为不破坏 v4.1.4，新运行态对象放 **`roleState`** 键（字段同 §2.1 state），角色池数组放 `roles[]`（每项含 state 对象）。`/v1/vault/accounts` 内仍用 §2.1 原名 `state`。
- **sync 角色种子**：`accountsJson` 的 `roles[]` 每项现支持可选 `uid/name/level/power/enabled`（旧客户端不带 = 缺省，行为不变）。带 uid 的角色进账号池；sync 为 App 全量意图 —— 每次同步按「keep && 该角色==active」重算全账号 desiredOnline（两次 sync 之间显式 role-action 优先）。
- **keep/desiredOnline 关系**：login → 目标角色 desiredOnline=true、active 指向它、keep/auto=true；stop → desiredOnline=false，且该账号无 desired 角色时 keep/auto=false（不自动恢复）；logout → 同 stop 但**保留 keep**。有角色条目的账号 reconcile 一律以 desiredOnline 为准（显式动作优先于 keep）；仅 v4.1.4 旧数据（keep=true 且 activeUid 缺省、无条目）回落旧行为。
- **重启恢复**：RoleEntry（desiredOnline/desiredAt/runState/enabled）持久化于 vault.json；重启 reconcile 恢复 desiredOnline 角色，同 fpid 取 desiredAt 最近一次；暂停态（runState=PAUSED）一并恢复（连接重连、任务仍暂停）。
- **暂停语义（P0）**：会话保留，心跳/断线重连继续；采集/互助/反应式开盾/整轮与单任务调度全部停止（submitRound 拒绝）；手动「登录并运行自动化」（ensureSession）会解除暂停。
- **并发上限**：`VAULT_MAX_SESSIONS` 环境变量，默认 8；login 超限返回 1429；reconcile 恢复时超限则延后（记日志）。
- **OP 白名单**：服务端 op 与端点一一绑定（无独立列表），已注册 vaultAccounts/vaultRoleAction/vaultAccountAction/vaultGlobalAction；**App 端 VaultSync 的 op 集合需在 M2 同步加这 4 个**。
- ** takeover 倒计时**：主动让位（policy yield）的 nextRecoveryAt 精确；引擎自发顶号按 30 分钟默认探测间隔估算；断线退避（WAITING_RETRY）暂无精确时刻，nextRecoveryAt=0（App 显示「即将恢复」）。
- **测试**：156 全绿 = 基线 120 + 新增 36（VaultStoreRoleStateTest 10、SessionKeeperRoleControlTest 12、AccountPoolApiTest 14），覆盖契约 §5 全部 6 类场景。
