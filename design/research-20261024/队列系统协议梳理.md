## 0. 结论摘要（15 行）

1. **普通队列容量是客户端派生值，不是服务端下发字段**。网页版权威公式在 `MarchCapacityState.java:174-180`（`worldMarchCapacity`）：`capacity = 1 + Σ科技{1007,1020,1027}(有等级各+1) + (VIP≥6 且 vip_active_endtime>now ? 1 : 0) + Σ临时buff(buff_map[10505], expire_ts>now) + max(0, extra_march.value)`。**A/B**
2. `notify_world_player_init` **没有 `world` 也没有 `capacity` 字段**：19 份真实登录快照均无；两份日志全文 `capacity` 出现 **0 次**（`"capacity"` / `world.capacity` 均为 0）。网页 `worldInit`（`BehemothAccountState.java:2319-2344`）只读 `march_info[] / mass_master_marchs[] / world_extra_march / city_point / jump_kid`。**A/B**
3. 本仓库 App 与 Server 都读 `notify_world_player_init.world.capacity`（`FieldTasks.java:208-214`、`ServerFieldTasks.java:600-608`、`ServerTasks.java:4145-4156`）→ 永远取不到 → **恒回退 3**（Server 巨兽侧回退 0 直接永不自发）。这是当前最大缺口。**A+B**
4. 占用口径（`BehemothAccountState.java:3052-3058`）：push 维护的 `marches` 中 **排除** `NON_NORMAL_QUEUE_MARCH_TYPES` 后的去重 march id ∪ `massMasterMarches` 中 `type==99` 的 id。**B**
5. 空闲（`:3067-3073`）：`marchLimitReached ? 0 : max(0, capacity - occupied - max(0,pending))`；`pending` = 本地已发未确认派兵数（网页日常服务传 0，巨兽任务传 `task.pending`）；收到错误码 2878 时置 `marchLimitReached`（`:915-924`）。**B**
6. **"上限 6" 不是公式钳制**：`worldMarchCapacity` 无任何 clamp；6 出现在配置校验与业务层（§1.3）。公式自然上限 5（1+3 科技+1 VIP），+1 临时队列刚好 6；extra_march 理论上可破 6。**B**
7. 特殊队列 9 类（`BehemothAccountState.java:83`）：301 营救任务／411 巨熊集结／801 燃霜取件／804 燃霜冶炼／**901 未确认**／**1001 未确认**／1002 至尊盛宴／1201 雪原商路护送／1405 乱斗空投。**A/B/C**（901、1001 仅 C）
8. **特殊队列不进普通占用计数，但仍在推送/召回/诊断列表里**；`req_world_march type=4/5/99/100/102/501...` 等普通类型都占普通队列——尤其 **type=99 加入集结占普通队列**，而 **411 发起巨熊集结不占**。**A/B**
9. 真实样本推算（A）：80971192 K888 VIP2+科技(1020)→ capacity≈2 且正好 2 队 type=4 在外；94450730 K916 VIP4+科技2→ capacity≈3、0 队在外；94450730 K913 VIP11→4；80971192 K913 VIP9→4。`world_extra_march` 可见样本全为 `{}`，buff 样本无 10505。**A**
10. 本仓库占用口径三套且都不对：App 只数 `type=4`（低估）；Server 巨兽数全部类型（高估）；Server 采集按类型计数但只取 4/110。**B（本仓库源码）**
11. 队列只能在 App 侧配 1–5（`FieldTasks.java:53`、`FunctionActivity.java:1368`、`ServerFieldTasks.java:36`），无法配 6；网页版配置是 1–6。**B**
12. `req_world_march_detail_4_player_situation` 在日志中 **10 次全部 `{"code":2}`**（参数被拒），无任何成功响应样本 → 该查询作为占用主源未验证；`notify_world_player_init.march_info` 是已验证可靠源（GuardProbe 实时撤防就在用它）。**A**
13. `notify_player_march_*` 实时推送确有样本（type=99 + `mass_slave.master_type=501/102`），但 `notify_mass_march_*`、`notify_world_add_extra_march`、`notify_vip_update`、`notify_research_complete` 在日志中 **0 条**。**A**
14. 建议统一 `QueueInfo{capacity, occupied, idle, specialOccupied, byType, pending, lastUpdatedMillis, source}`；实现放 `com/carlos/vault/wjdr/protocol/`（两侧构建都已 include 该包，见 `vault-server/build.gradle:37-42`），根治 App/Server 漂移。**建议**
15. 决策推荐：复刻网页公式（否决读 world.capacity）＋只读层硬钳 1..6＋pending 计入但限时（30s）＋特殊队列仅排除计数仍暴露查询＋守护预留由调用方扣减＋App/Server 共用同一 QueueInfo。**建议**

## 1. 容量公式与数据源

### 1.1 权威公式（B，逐行）

`modules/behemoth/service/MarchCapacityState.java:174-180`：

```java
int worldMarchCapacity(int extraMarches, long serverTimeSeconds) {
    long technologyQueues = MARCH_QUEUE_TECHNOLOGIES.stream()
        .filter(tid -> normalResearch.getOrDefault(tid, 0L) > 0L).count();          // 1007/1020/1027
    long vipQueues = vipInitialized && vipLevel >= 6 && vipActiveEndTime > serverTimeSeconds ? 1 : 0;
    long temporaryQueues = temporaryBuffs.values().stream()
        .filter(b -> b.active(serverTimeSeconds)).mapToLong(CapacityBuff::marchQueues).sum(); // buff_map[10505]
    long total = 1 + technologyQueues + vipQueues + temporaryQueues;
    return toIntExact(total + max(0, extraMarches));
}
```

常量：`MARCH_QUEUE_TECHNOLOGIES = {1007, 1020, 1027}`（`:31`）；`MARCH_QUEUE_TECHNOLOGY_LEVELS = {10071→1007, 10201→1020, 10271→1027}`（`:32`，即 `tid_lev = tid*10+lev`）；`MARCH_QUEUE_VIP_LEVEL = 6`（`:33`）；`DEFAULT_MARCH_QUEUE_COUNT = 1`（`:34`）。
上层包装：`BehemothAccountState.normalQueueCapacity()`＝`marchCapacityState.worldMarchCapacity(extraMarches, currentServerTimestamp())`（`BehemothAccountState.java:3063-3065`）。

> 注意：**公式里没有英雄/指挥中心/科技容量/装备/官职**——那些只参与"每队兵量容量" `normalMarchCapacity`（`capacityFor`/`totals`，`MarchCapacityState.java:159-200,373-398`），与"队列条数"是两套东西，勿混。

### 1.3 "上限 6" 在哪校验/钳制（B）

`worldMarchCapacity` **没有 clamp**。6 分布在三层：

| 层 | 位置 | 内容 |
|---|---|---|
| 任务配置校验 | `modules/behemoth/config/BehemothTaskConfig.java:53,71` | `queueCount<0||>6` 非法；`queueCount+joinQueueLimit>6` 非法 |
| 任务配置校验 | `modules/attack/config/AttackTaskConfig.java:14,122-126` | `MAX_QUEUE_COUNT = 6`；`normalizeQueues` 只保留 1..6 |
| 任务配置校验 | `DailyHuntConfig.java:26,60`；`DailyIntelligenceConfig.java:23`；`DailyBehemothConfig.java:19`；`DailyRoleScopedConfigResolver.java:123-124` | 各自 `queueCount` clamp 1..6 |
| 业务运行时 | `modules/daily/service/DailyFrostfireService.java:1843-1847` | `effectiveQueueCapacity = clamp(state.normalQueueCapacity(), 1, 6)` ← **唯一对容量值本身硬钳 6 的地方** |
| 业务运行时 | `modules/daily/service/DailyBrawlWarService.java:510` | 普通行军 ≥6 时停止派兵（且 1405 不计入普通） |

结论：**6 是配置/业务上限，公式本身自然上限 5+1**；若照抄公式，建议只读层 `clamp(1..6)`（保留 raw 值做诊断），既对齐 Frostfire 也不掩盖异常。

### 1.4 占用/空闲口径（B）

```
occupied = |{ m.id : m ∈ marches, m.type ∉ NON_NORMAL } ∪ { m.id : m ∈ massMasterMarches, m.type == 99 }|   // :3052-3058
idle     = marchLimitReached ? 0 : max(0, capacity - occupied - max(0, pending))                            // :3067-3073
```
- `marches` 维护：`addMarch` 只 `putIfAbsent`（`:2658`）；`updateMarch` 合并 `change/del`（`:2666-2674`）；`removeMarch` 移除并 `clearMarchLimitReached()`（`:2692-2699`）。
- 陈旧清理 `purgeCompletedMarches()`（`:3557-3577`）：`state==0` 直接删；`endtime+grace <= now` 删，grace=411→30s、state4→120s、其它→600s（`isProjectionStale`，`:3578-3595`）。**读取占用前必须调用**（`snapshot`/`queueDiagnostics`/`marchQueues` 都先 purge）。
- `pending` 语义：网页日常服务全部 `snapshot(0)`（如 `DailyGatherService.java:387,567`），只有巨兽自动化传 `task.pending`（`BehemothAutomationService.java:279,398,463,541`）。
- 暴露给 UI/任务的快照：`BehemothAccountStateSnapshot{capacity, occupied, idle, activeBoss, activeJoined, ...}`（`modules/behemoth/model/BehemothAccountStateSnapshot.java:12`）。

## 5. QueueInfo API 建议（共享实现）

**落点**：新建 `app/src/main/java/com/carlos/vault/wjdr/protocol/QueueInfo.java`（**纯 java.util/纯函数**）。两侧构建均已 include `com/carlos/vault/wjdr/**`（`vault-server/build.gradle:37-42`），**无需改构建**；避免再出现 App/Server 两份实现漂移。

```java
public record QueueInfo(
    int capacity,                 // 普通队列容量（公式派生，已 clamp 1..6）
    int rawCapacity,              // 未 clamp 原值（诊断：>6 报警）
    int occupied,                 // 普通占用（NON_NORMAL 已排除）
    int idle,                     // marchLimitReached ? 0 : max(0, capacity-occupied-pending)
    int pending,                  // 本地已发未确认（调用方注入）
    int specialOccupied,          // 特殊队列占用（NON_NORMAL 命中）
    boolean marchLimitReached,    // 2878 置位，march_del 清零
    Map<Long,Integer> byType,     // type -> count（含特殊，供盛宴/护送/乱斗使用）
    long lastUpdatedMillis,       // 本地状态更新时间（毫秒）
    String source                 // "push" | "player_init" | "detail_query" | "fallback" | "empty"
) {
    public static final Set<Long> NON_NORMAL = Set.of(301L,411L,801L,804L,901L,1001L,1002L,1201L,1405L);
    public static final Set<Long> QUEUE_TECHS = Set.of(1007L,1020L,1027L);

    /** 纯公式：1 + 科技 + VIP + 临时buff + extra；serverNow=秒。 */
    public static int capacityOf(Map<Long,Long> research, int vipLv, long vipEndSec,
                                 Collection<int[]> activeQueueBuffs, int extraMarch, long serverNow);
    /** 从 notify 表构建（登录/重连）：world_player_init + all_research + vip + buff_show + extra。 */
    public static QueueInfo fromNotifies(Map<String, Map<String,Object>> notifies,
                                         long serverNowSec, int pending, long nowMillis);
    /** 增量应用一条 notify；返回新实例（不可变，便于两侧复用与单测）。 */
    public QueueInfo apply(String proto, Map<String,Object> data, long serverNowSec, long nowMillis);
    /** 统一下限/钳制（只读层）。 */
    public static int clampQueueCount(int capacity);          // clamp(1..6)
    public static int normalOccupiedOf(Collection<Map<String,Object>> marches,
                                       Collection<Map<String,Object>> massMasters);
    public static int specialOccupiedOf(Collection<Map<String,Object>> marches);
    public static Map<Long,Integer> countsByType(Collection<Map<String,Object>> marches);
}
```

**赋值规则（与网页 1:1）**
1. `capacity`：科技（`researched[tid].lev>0`，tid∈{1007,1020,1027}）+ VIP(`vip_lv≥6 && vip_active_endtime>now`) + 临时 buff（`buff_map[10505]` 且 `expire_ts<=0||>now`）+ `max(0,extra_march.value)` + 1；只读层 `clamp(1,6)`，原值存 `rawCapacity`。
2. `occupied`：`marches` 中 `type∉NON_NORMAL` 的去重 id 数 + `massMasterMarches` 中 `type==99` 的去重 id 数（两集合按 id 去重）。
3. `specialOccupied` / `byType`：含特殊类型的全量计数（只读展示，不参与 idle）。
4. 陈旧清理：`state==0` 立即剔除；`endtime+grace<=now` 剔除（grace=411→30s、state4→120s、其它→600s）。
5. `pending`：由派队调用方注入（成功 `+1`，收到对应 add/2878/超时30s `-1/清零`），`snapshot` 时传入。
6. `source`：`push`（有 add/update/del）、`player_init`（仅登录快照）、`detail_query`（自查成功）、`fallback`（全缺→按 1 或 3 保守）、`empty`。

**接入点（建议顺序）**
1. `ServerFieldTasks.gather/intel/hunt` 与 `FieldTasks.gather`：容量/占用改读 `QueueInfo`，删除各自 `marchCapacity`。
2. `ServerTasks.behemothLaunch/behemothJoin`、`ServerGuardianEngine.freeMarchSlots`：换用同一 `QueueInfo`（顺带修 P0-2）。
3. `TaskWakeRouter`：容量类 notify（`notify_all_research`/`notify_research_complete`/`notify_vip_info`/`notify_buff_show*`/`notify_world_add_extra_march`）→ gather/intel/hunt/behemoth 失效重算；`notify_player_march_*` 已有。
4. `ServerGuardianEngine`/`ServerBearTasks`：预留数从 `capacity` 扣（`idle - reserved`），不写进公式。

## 6. 决策点与推荐

| # | 决策点 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| D1 | 容量来源 | ①复刻网页公式 ②读 `world.capacity` ③手动配置 | **①为主 + ③作 override（默认关）** | ②字段不存在（A 证据）；①有 4 角色真实样本可对账；③留给公式未覆盖的运营补偿 |
| D2 | 普通队列上限 | ①硬钳 6 ②不钳 ③钳 5 | **① `clamp(1..6)`（只读层），保留 rawCapacity** | 与 Frostfire `:1845`、BehemothTaskConfig `:53,71` 一致；不掩盖 >6 异常（raw 上报） |
| D3 | pending 是否计入占用 | ①计入 ②不计 | **①计入，且 30s 超时自清** | 网页语义如此（`normalQueueIdle`），可消除"连点两轮派超"；30s 防悬挂 |
| D4 | 特殊队列暴露 | ①仅排除计数 ②排除且暴露查询 ③一并计入 | **②**：`specialOccupied`+`byType` 暴露，`idle` 不算 | 盛宴(1002)/护送(1201)/乱斗(1405)/巨熊(411) 需要"是否已有该特殊队在途"，但不能占普通槽 |
| D5 | 守护/驻防预留 | ①写进公式 ②调用方从 capacity 扣 ③不预留 | **②**：`QueueInfo.reserved` 或调用方 `capacity-reserved`（App `GuardianEngine.reserveQueues` 语义保留：常驻 2、战时 6） | 网页也是业务侧扣（allianceMine/heavyLifting），公式保持纯粹 |
| D6 | VIP frozen 是否算数 | ①照网页忽略 frozen ②frozen 则不计 | **①先照网页**，日志标注 frozen 差异，真机对账后决定 | 网页是唯一权威；样本中 vip11+frozen=1 恰好可用于验证（容量 4 vs 5 的差别） |
