## 2. 协议盘点结论（决定实现口径）

### 2.1 资源矿采集（R1）

1. **等级无法从响应字段读取**：`req_world_map_search` 响应只有 `code/point{x,y}/is_create`；`req_world_mapobj` 的 `map_resource` 只有 `{id,uid,aid,march_id,kid,bomb_time,create_time}`。等级 = 搜索请求 `level_min=level_max=L` 过滤构造而来（网页版同款；`WorldMapSearchSchemaTest` 亦断言 point 仅 x/y）。
2. **搜索 payload**：`{mapobj_type:2, level_min:L, level_max:L, res_id:102-105(直传,不再减101), is_full:fullResourceOnly}`。
3. **逐级降级**：每队列从 `queue.level` 递减到 1；该级返回 2872（无矿）→ 继续降级；命中 `content.point` 即目标。
4. **等级上限**：`notify_game_init{project_start_ts, open_time, servertime}` → 对齐开服时间算 `battlefieldDay`；`day>=701 ? 9 : 8`。真实日志样本 battlefieldDay=785/786（9 级已解锁）。
5. **出征 payload**：`req_world_march{type:4, endpoint:point, formation:{hero_id[]:{k,v}, soldier[]:{k,v}}, extra:{}}`；联盟矿 `type=110`；响应 `content.march_info.id` 回填队列↔行军映射。
6. **错误码**：2872 搜索空（降级）/ 2878 队列满（停止本轮+置 limitReached）/ 401 兵不足 / 403 英雄被占 / 2816+2822 矿点变化（下轮重搜）/ 8619 兵工厂战锁(300s) / 8637 燃霜战锁(60s)。
7. **网页版配置模型**：`DailyGatherConfig{QUEUE_COUNT=6, MAX_RESOURCE_LEVEL=9}`；每队列 `{id,enabled,resourceType,resourceLevel,formationMode,formationId,infantry,lancer,marksman}`；ROLE 编队不得跨队列重复（`validated()`）。
8. **本仓库缺口**：等级封顶 6、队列封顶 5、无每队列配置、编队固定 `1+(sent%3)`、容量读不存在的 `world.capacity`、march 计数用恒 `code=2` 的查询（`ServerFieldTasks:35-36,103,107,600-608`、`FieldTasks:52-53,208-214`、`FunctionActivity:1349,1368`）。

### 2.2 队列系统（R2）

1. **容量是客户端派生值**（服务端不下发）：
   `capacity = 1 + Σ科技{1007,1020,1027}(有等级各+1) + (VIP≥6 且 vip_active_endtime>now ? 1:0) + Σ临时buff(buff_map[10505], expire_ts>now) + max(0, world_extra_march.value)`。
2. **数据源**：`notify_all_research.researched`、`notify_research_complete.tid_lev`、`notify_vip_info{vip_lv,vip_active_endtime}`、`notify_buff_show{map,buff_map,expire_ts}`、`notify_world_player_init.world_extra_march.value`、`notify_world_add_extra_march`。
3. **占用**：`marches` 中 `type ∉ NON_NORMAL={301,411,801,804,901,1001,1002,1201,1405}` 去重 id ∪ `mass_master_marchs` 中 `type==99`；`idle = limitReached ? 0 : max(0, capacity-occupied-pending)`；2878 置 `limitReached`，march_del 清零。
4. **特殊队列映射**：301 营救/情报、411 巨熊集结、801+804 燃霜矿区、901/1001 未确认（低置信）、1002 至尊盛宴、1201 雪原商路护送、1405 乱斗空投。**411 不占普通队列，type=99 上车占普通队列**。
5. **上限 6**：公式自然上限 5（1+3 科技+1 VIP），+1 临时队列=6；网页只在配置校验与 `DailyFrostfireService clamp(1..6)` 硬钳。本实现只读层 `clamp(1..6)` 并保留 raw。
6. **真实样本**：VIP2+科技1020 → capacity≈2 且 2 队 type=4 在外；VIP11 → 4~5；80971192:913 有 2 队 type=1201（特殊，不占）。
7. **不可用查询**：`req_world_march_detail_4_player_situation{owner,kid}` 生产日志 10/10 `{"code":2}`，不可作为占用主源 → 占用以 `notify_world_player_init.march_info` + `notify_player_march_*` 推送维护。
8. **本仓库缺口**：4 处读 `world.capacity`（`FieldTasks:208-214`、`ServerFieldTasks:600-608`、`ServerTasks:4145-4156`、`ServerGuardianEngine:960-975`）恒回退 3/0；占用三套口径全错；无 pending/limitReached；队列上限夹 1..5。

## 3. 架构设计

### 3.1 核心资产库（共享纯 Java，App/Server 同源编译）

包：`app/src/main/java/com/carlos/vault/wjdr/asset/`（`vault-server/build.gradle` 的 `include 'com/carlos/vault/wjdr/**'` 已覆盖，**零构建改动**）。

```text
CoreAssetRegistry (进程级，按 AssetKey 管理)
   └── CoreAssetLibrary（每角色 1 实例）
         ├── 单写者 accept(proto, content)   ← engine inbound hook
         ├── AssetParsers（10 个域解析器，FULL_REPLACE/PATCH/APPEND_OR_REPLACE）
         ├── AssetState（可变内部态）→ AssetSnapshot（不可变，volatile 读）
         ├── READY：必需协议集齐（BASE_RESOURCE_NOTIFICATIONS 11 + recover + intelligence）
         ├── listeners（version + dirtyDomains 变更通知）
         └── refresh 标记（平台层任务线程执行 req 后回灌 applyResponse）
```

**域与快照**（`AssetSnapshot` 不可变）：

```java
MetaAssets meta;            // nickName/level/power/uid/kid/fid/alliance
ClockAssets clock;          // serverTimeSec/projectStart/openTime/kingdomDay/maxResourceLevel
CalendarAssets calendar;    // activities id→{begin,end,group}
ResourceAssets resources;   // Map<Long,Long> + diamond()/meat()/wood()/coal()/iron()/steel()
RecoverAssets recover;      // Map<Long,RecoverItem{count,max,recover,nextCalcTs,interval}>
StaminaAssets stamina;      // 由 recover[201] 派生：currentAt(nowSec)/max/recoverAt
BackpackAssets backpack;    // Map<Long,Long>
QueueAssets queue;          // §3.2
IntelAssets intel;          // radarLevel/radarExp/powerLevel/nextEventTime/events/dispatchable()
BehemothAssets behemoth;    // monsterMaxLv/lastDailyTime/dailyCounts/autoJoin
BearAssets bear;            // reserveTime/massStart/massEnd/coolEnd/autoReserve/participation
WarAssets war;              // 敌方行军事实 Map<Long,ThreatFact>（判定仍属 WarState）
GuardianAssets guardian;    // 盟友坐标/使馆驻防/自己驻防行军
```

**更新管线**：interest filter → parse → merge（init 替换/update 增量）→ 逐域 equals 变更检测 → `version++` → 锁外通知 → （可选）节流投影落盘。解析异常不抛，记 `parseErrors`/`staleDomains`。

**就绪与读取**：`awaitReady(15s)` 替代固定 sleep；`snapshot()` O(1)；`awaitChange(sinceVersion, timeout)`；`missingProtocols()` 可诊断。READY 前任务保守 SKIP，不猜数据。

**平台接线**：
- Server：`SessionKeeper.LiveSession` 引擎创建后 `CoreAssetRegistry.global().attach(engine, fpid, sid, uid, epoch)`；inbound 钩子第一顺位 `lib.accept(proto, content)`；`req_*` 响应由任务线程 `lib.applyResponse(proto, content)` 回灌（巨熊 trap/巨兽 auto_join 等）。
- App：`RoleSessionKeeper` 同一 attach（原生模式）；服务器模式下 App 读服务端投影。
- **state 投影**：服务端资产库在 version 变化后节流（≤1 次/秒）写 `srv:asset:{fpid}:{sid}`（JSON：version/ready/maxResourceLevel/kingdomDay/queue{capacity,occupied,idle}/resources{diamond,meat,wood,coal,iron}/stamina{current,max,nextRecoverAt}/updatedAt），经既有 `/v1/vault/state` 通道回 App，采集设置页用于展示等级上限与队列占用。

**服务端执行**（`ServerFieldTasks.gather` 重写）：

4. 按 `nextQueueId` 环状取未绑定启用队列 → 搜索（level 递减到 1，`req_world_map_search`，2872 降级）→ 编队（ROLE：FormationResolver + 每队列兵量；AUTOMATIC：自动最强/权重）→ `req_world_march type=4` → 成功记 `marchId`、`lib.applyResponse` 更新占用；错误码按 §2.1-6 处理。

## 4. 最终实现效果（验收口径）

## 7. 风险与边界

| 风险 | 缓解 |
|---|---|
| 资产库解析字段与实际帧不一致（sproto 类型口径 1=bool/2=string 反直觉；日志截断 1201 字符） | 解析器以 `.spb` schema 为准；真实帧 fixture；类型断言单测；异常不抛只记 stale |
| READY 协议缺失导致任务 SKIP | `missingProtocols` 可诊断；15s 超时；仅对必需域硬门控，可选域缺失降级 |
| 队列占用 pending 不精确 | 以 push+login 快照为主；2878 兜底；映射对账；宁可被服务端拒也不超发 |
| 每队列编队重复导致英雄占用 403 | App 保存拦截（同 ROLE 编队仅一个队列）+ 服务端防御性 SKIP |
| 配置双端/旧服务器兼容 | v2 内嵌 + 旧键双写投影 + 版本号；v2 缺失走旧分支 |
| 9 级门槛数据缺失 | 资产库 `clock.maxResourceLevel` 派生；缺失默认 8；逐级下搜天然兜底 |
| 大改采集执行导致回归 | 旧分支保留（无 v2 时逐字节旧行为）；按队列逐步替换；灰度单账号 |
