## 0. 结论速览（TL;DR）

1. **App↔服务端 JSON 契约基本对得上（`formations/hero_ids/soldiers/ratio/total` 逐字段一致，含 shield/spear/bow 别名）**，但**服务端对编队的“合法性校验”几乎为零**：英雄数不封顶、不查重复、不查职业唯一、不查编队可用性——这是生产 415 的直接通道（生产 415 样例就是 **5 个 hero_id** 下发的请求）。
2. **301/403 处置在 AUTO 路径是完整的（黑名单+换候选），在 ROLE 路径是空转的**：`resolveRole()` 完全不读 `HeroAvailability`，被 301 拉黑的编队英雄会在 TTL 10 分钟内被同一编队反复重发（生产 301 拉黑 49 次，均发生在 AUTO 采集，但 ROLE 模式一旦上线即会踩这个洞）。
3. **406 的根因已定位到可修点**：旧构建未做“按英雄容量夹取”，生产 406 样例是 2 名 1 级英雄带 3046 兵（估算容量仅 ~600-1000）。当前代码 `FormationResolver.autoOutcome():157-158` 已加 `MarchCapacityCalculator.capacityFor` 夹取，**但夹取只在 `capacity>0` 时生效**；一旦英雄等级/容量组件缺失返回 0，回退到 `min(stock,50000)` 就复发。且 ROLE 显式兵量超容量是 **SKIP 不发**，不是夹取（旧版是缩放重分配）。
4. **415 的“自适应”是死代码**：`HeroAvailability.autoHeroLimit()` 无任何调用者，`clearHeroLimitHint()` 也无调用者；`autoProfessionHeroes()` 恒定按职业各选 1（≤3），从不消费 415 下调。当前构建不会再发 5 英雄（415 首因已消除），但若账号上阵位 <3 则 415 会永久循环（每个队列每轮失败，无收敛）。
5. **406 缩放只降不升**：`soldierScalePercent` 一旦 25% 永不清零（无成功回调清位），同一进程内后续编队永久缩水。生产当前构建未见 406/415 新样例（10-25 日志 0 条），但机制不完整。
6. **编队目录（App 消费的唯一来源）有三个硬伤**：①`capacity` 恒 0（读错源：`notify_world_player_init.world.capacity`，生产不存在该键；正确源是 `QueueCapacity.rawCapacity()` 公式，同进程 asset 队列日志显示 capacity=3）；②state 键 `srv:formation:catalog:{fpid}:{sid}` **没有 uid 维度**，而生产同一 fpid+sid 真有两个角色（`48460403|888|35371154` 大号 + `48460403|888|88280792` 小号）互相覆盖；③空快照会被缓存，导致 **218 次“英雄目录未同步” SKIP**（生产实证，10-24 215 条 + 10-25 3 条）。
7. **hero name 引号根因不在 notify 解析**：`notify_hero_init` 里根本没有 name 字段（原始帧实证 `{id=50028.0, lev=1.0, star=0.0, ...}`），服务端按设计回落 `HeroCatalog.name(id)`，而 `HeroCatalog` 的 NAMES 表字面量本身带转义引号（`"\"巴希提\""`）。star=0 是真实数据（原始帧 star=0.0），power=0 是该帧无 power/fight_num 字段（不是解析 bug）。
8. **旧版网页后端（release 288）能力远超当前服务端**：保存期强校验（≤3 英雄、职业唯一、队长必须在队、MANUAL 总量≤英雄容量、PERCENTAGE 比例和 1..100）、运行时容量扩张重分配、多编队候选回退、同功能 protectedHeroes 防抢、巨熊模板（g01-g14，发车+6 上车队，5:5:90）、编队记忆快照（游戏 prefab 保存/恢复，`req_soldier_set_prefab`）、一键编队（quick-formation）、游戏编队同步（GAME 来源引用 `-id`）、按英雄数分档的出征上限（3/2/1/0 英雄 limit）。**当前服务端只落地了其中“单编队 + 比例自动分配”这一小块**。
9. **两个可以直接复用的现成资产**：①旧版把游戏内 6 个编队槽的 prefab 从 `notify_soldier_init.prefab` 读出来（服务端当前只读 `soldier`，直接丢弃 `prefab`）；②spb schema 里 `req_soldier_set_prefab`（c2s）、`formation_rate`、`notify_battle_hero_arrange_data`（s2c）都在，引擎 `engine.request(proto,args)` 对 schema 内任意协议通用——**编队记忆/游戏编队同步不需要新 schema，只需要解析+落 state+发请求**。
10. **最小改造集合**：目录 v2（uid 键 + capacity/limits/gameFormations/prefab/captain/available）、ROLE 校验三件套（英雄数/重复/职业+黑名单+容量夹取）、formation_ids 候选列表 + 旧版 fallback、415/406 自适应接线、编队记忆 state + `formation.*` role-action、巨熊模板目录。分 P0/P1/P2 见 D/E。

## B. 载荷与错误码分析（301/403/406/415，含生产样例）

### B.1 `req_world_march.formation` wire 语义（已被生产实证）

```
formation = {
  "hero_id": [{"k":1,"v":50038},{"k":2,"v":50042},{"k":3,"v":50006}],   // k=上阵位次1..n, v=英雄id
  "soldier": [{"k":10300,"v":279},{"k":20100,"v":426},{"k":30300,"v":425}] // k=士兵id, v=数量
}
```
- 生产实证（`vault-20261025.log:10757`，01:48:02 +08）：`hero_id=[{k=1,v=50038},{k=2,v=50042},{k=3,v=50006}]`，`soldier=[{k=10300,v=279},{k=20100,v=426},{k=30300,v=425}]`，该请求随后 **301**；换候选后 `hero_id=[{k=1,50019},{k=2,50012},{k=3,50028}]` 成功（march#46）。
- 与旧版一致：`DailyMarchFormationResolver.heroPairs` = `pair(index+1, heroId)`（`DailyMarchFormationResolver.java:393-395`）；服务器把队长/顺序按 `captainFirst` 重排（`DailyRoleFormationService.captainFirst`），当前服务端**没有 captain 概念**，顺序=App hero_ids 顺序。
- 士兵 pair：c2s schema 元素是 `pair_int_int`（k=兵种 id、v=数量），不是 `{id,count}`（`Exec.java:135-142`）。s2c 推送才是 `formation_soldier{id,count}`——两套 schema 命名，写错会编码成空结构（注释已记录历史坑）。
- **typed soldier 数量口径**：一个兵种只发**当前最高档 id 一个 pair**，数量=该档可用量；服务端 `FormationCatalog.baseStock` 只统计最高档（`FormationCatalog.java:300-325`），低档不计入 → 不会超发，但会**低估**可用兵力（低档兵永远用不上）。旧版 `state.availableSoldiers` 同样是“最高档”口径（`BehemothAccountState.availableSoldierCounts`）。
- 50000 上限来源：老 `Exec.formationWithHeroes` 注释“全库存会被服务端以参数错误拒绝（code=2）”，现全链路统一 `MAX_SOLDIERS_PER_MARCH=50000`。生产小号库存 2416，不会触发；大号库存 30 万+ 会被夹。
- hero 数量：`hero_id` k 从 1 连续编号（`Exec.heroPairs:123-133` 跳过非正 id 后重排）。

### B.2 capacity 夹取公式与实际生效点

- 公式（共享 `MarchCapacityCalculator`，App/Server 同源，`MarchCapacityCalculator.java:10-20,113-117`）：
  `capacity = floor((Σ英雄容量 + 固定容量) × (10000 + 万分比加成) / 10000)`
  - 英雄容量按 `lev`（与 `training_lev` 取大）查 1..75 级表（`:34-40,179-200`）；
  - 固定容量 = 500 基础 + 指挥中心(331) + 科技 + 专家(7004) + 家园(生命树 7000/容量建筑 7036) + buff 10506/10507；万分比=Σ10508；
  - 缺数据 → `Estimate.ready=false`，`capacityFor` 返回 **0**（`:291-294`，“调用方视为未知、不做夹取”）。
- 生效点（**只有两处**）：
  1. AUTO：`autoOutcome` → `capacity=capacityFor(engine,heroIds)`；`if(capacity>0) target=min(target,capacity)`；再乘 `soldierScalePercent`（`FormationResolver.java:155-160`）。
  2. ROLE 且“库无兵量、走 total/ratio 分配”：`if(capacity>0) total=min(total,capacity)`（`:265-268`）。
- **不生效的路径**：ROLE 且库有显式兵量 → 超容量直接 **SKIP**（`:248-254`），不夹取；capacity=0 → 全部路径不夹取。
- 旧版对照：容量是“运行时上限”，还会叠加 avalanche（雪崩技能加成）与 cyril（巨熊技能加成），并把配置兵量按加成**放大后重分配**（`DailyRoleFormationService.effectiveLimit/expandedFixedTarget`，见 C.3）。当前服务端没有 avalanche/cyril 加成项 → 容量天然偏小（宁低勿高，安全但不 1:1）。

### B.4 仍会导致失败/空转的分支（修 301/403/406/415 的必读）

1. **ROLE 不复查 301/403 黑名单**：`resolveRole`（`FormationResolver.java:183-279`）从不调用 `HeroAvailability.isBlocked`，也没有按 hero 排除候选（ROLE 是固定编队，无法换人）。后果：编队英雄外出期间，该队列每轮重复 301/403，直到英雄回城（TTL 对 ROLE 无意义）。旧版做法：`roleFormation` 发现 away → `fallback()` 用空闲英雄 + 排除其他编队 protectedHeroes（`DailyMarchFormationResolver.java:205-233,350-363`）。**建议**：ROLE 命中黑名单→本队 SKIP 并把原因写清楚；或新增“编队不可用回退 AUTO”参数（旧版即如此）。
2. **ROLE 英雄数/重复/职业校验缺失**（A.2）：库被写坏 → 415/301。
3. **ROLE 显式兵量超容量/库存 = SKIP**（不发）：连续 CPU/请求无收益；App 不知道容量（目录 capacity=0/无 limits）→ 用户配的兵量大概率超限。
4. **capacity=0 时无夹取**：`capacityFor` ready=false（英雄等级未同步/固定容量组件缺失）→ AUTO 直接 `min(库存,50000)`，这正是旧构建 406 的复现条件。生产当前 `hero catalog` 已能解析 `lev`，风险中等，但**部署新号/推送变更时会复发**。
5. **415 自适应死代码**：`autoHeroLimit` 无调用者（`HeroAvailability.java:99-105`，仅单测 `HeroAvailabilityTest:67` 覆盖）；`clearHeroLimitHint` 无调用者（`:117-119`）；`noteHeroCountRejected` 写入的 hint 永远不被 `autoProfessionHeroes` 消费。且 `autoProfessionHeroes` 本就最多 3 人，无法再“降到 2 人以下”以外的调整 → 415 自愈逻辑对当前算法无意义。
6. **406 缩放不恢复**：`soldierScalePercent` 只在 406 时降，成功分支不清零；`HeroAvailability.clear()` 只在会话清理/测试调用。→ 同一进程内一次 406 后永久缩水（除非重启）。
7. **AUTO 英雄候选受职业目录限制**：`autoProfessionHeroes` 要求 `HeroCatalog.profession(id)` 在 1..3（内置 62 英雄表，`HeroCatalog.java:17-146`）。新英雄不在表 → 永远不进 AUTO 编队（更好英雄反而选不到）；同时 AUTO 选不满 3 职业时静默用 2 人（`FormationResolver.java:349-367`），容量骤降 → 兵量被夹小。
8. **`strongestHeroes(≤5)` 是 legacy 死代码**（`:329-342`，仅单测 `FormationResolverTest:392`）：线上 415 的 5 英雄来源是旧构建；新构建别再把 `MAX_AUTO_HEROES=5` 当契约。
9. **采集 v2 多队列无“轮内英雄预留”**：除巨熊（`planJoinAttempts` 有 `usedHeroes`，`ServerBearTasks.java:1633-1665`）外，采集 4 队列逐队解析时只依赖资产库 `busyHeroIds`（异步 push，可能滞后）→ 同轮 2 个队列可能选中同一英雄 → 403。旧版用 `reservedHeroes` + `protectedHeroes` 解决（C.3）。

### B.6 hero name 引号 / star=0 / power=0 根因（定案）

- 生产 `hero catalog` 原始帧（`vault-20261025.log:8429`，17:25:31 UTC = 01:25:31 +08）：
  `raw={id=50028.0, lev=1.0, star=0.0, skills={...}, recruit_ts=..., hint=true}{id=50002.0, lev=1.0, star=0.0, ...}`
  —— **没有 name 字段，也没有 power/fight_num 字段**。
- `FormationCatalog.heroOf` 先取 `name/nickName/nick_name`，空则回落 `HeroCatalog.name(id)`（`FormationCatalog.java:364-376`）；`HeroCatalog.NAMES` 的字面量就是 **`"\"巴希提\""`**（`HeroCatalog.java:84-146`）→ 所以 state 里是 `"\"巴希提\""`。**结论：根因是内置英雄名表自带转义引号（数据缺陷），不是 notify 报文解析，也不是 JSON 二次转义。**
- `star=0`：原始帧 `star=0.0`，`firstLong` 对 0 继续尝试下一个键、最终返回 0，**是真实值**（该账号英雄未升星）。
- `power=0`：该推送形状无战力字段（旧网页用 `power/fight_num/powerFight`，`BehemothAccountState.explicitHeroPower`），当前 `firstLong("power","fight_num","fight_capacity")` 全 miss → 0。**后果**：`HERO_STRENGTH` 排序退化为 level→star→id（`FormationCatalog.java:253-262`），AUTO 选“最强”实际按 id 降序，低战力英雄可能先上。
- 小 P1：`HeroCatalog` 的 62 英雄固定表既当名字表又当职业表，新英雄缺职业 → AUTO 选不到（B.4-7）。

### C.2 保存期校验（`DailyRoleFormationService.validated/normalizeHeroIds/validateOwnedHeroes/validateManualSoldiers/validateRatios`）

1. 名称非空、≤30 字符（服务端不校验；App ≤20）。
2. 英雄必须属于当前角色已同步英雄（`formationHeroOptions`）；**同一编队不能选两个相同职业**；**≤3 个**；英雄编号无效/重复 → 抛错。
3. **队长**（captainHeroId）必须属于本编队英雄；运行时 `captainFirst()` 把队长排到 `hero_pairs` 第 1 位。
4. `allocationMode` 必填（MANUAL/PERCENTAGE）。
5. MANUAL：三兵量 ≥0、总和 ≤ `normalMarchCapacity(heroIds)`（按英雄数容量）→ 否则“不能超过当前英雄数量对应的最大出征数量”。
6. PERCENTAGE：三比例 ≥0、**合计 1..100**（不是必须 100），保存时按 `allocatePercentages(limit, ratios)` 预计算兵量落库。
7. 内置模板编队可编辑不可删（`delete` 拒绝 `builtIn()`）；`DailyFormationReference.repeatable` 的内置编队不可编辑。
8. 编辑/新增时 `version` 自增（并发保护）；当前服务端无版本概念。

### C.3 运行时解析（`DailyMarchFormationResolver` + `DailyRoleFormationService.runtimePlan/automatic/fallback`）

1. **先看行军占用同步**：`WorldMarchHeroOccupation.readyForPlanning()` 不 ready → WAITING（`SYNC_PENDING`/`SYNC_ERROR`），不用“猜”的占用状态派队。当前服务端用资产库 `busyHeroIds`（`FormationCatalog.java:192-207`），无 ready 门。
2. **自动编队（AUTOMATIC）**：`idleHeroFormation(excluded)`（排除 reservedHeroes + busyHeroIds）→ `automaticRuntimePlan` 用**持久化的 50:20:30** 权重 + `effectiveLimit` 分配。
3. **ROLE 编队**：取候选 `formationIds[]` 列表，**逐个尝试**；每个编队：
   - 英雄与 `reservedHeroes` 冲突 → `HERO_RESERVED`，继续看下一个编队；
   - 英雄不在城/被占用（`snapshot.idleHeroes` 不含 或 busyHeroIds 含）→ 若 `allowFallback`：`fallback()` 用**空闲英雄**（排除 reserved + busy + `protectedHeroes`）按该编队兵量重算；否则 WAITING `HERO_AWAY`；
   - 否则按编队兵量/比例 + `effectiveLimit` 计算（见 4）。
4. **容量与兵量计算**：
   - `effectiveLimit = floor((capacityBeforePercentage + avalancheBonus + cyrilBonus) × (10000+bp)/10000)`（`effectiveLimit/fixedRuntimeBonus`）；
   - MANUAL：`expandedFixedTarget = min(floor((configuredTotal+fixedBonus)×(10000+bp)/10000), effectiveLimit)`，再按三兵量当权重 `allocate()` 重分配（即**容量涨了会按原比例放大兵量**）；
   - PERCENTAGE：`allocatePercentages(newLimit, ratios)`：targetTotal=round(limit×ratioSum/100)，再按比例最大余数分配；
   - **巨熊内置模板**：`min(oldTotal, newLimit)`（固定 1 兵，不放大）。
   - `DailyRoleFormationCalculator`：`allocate` 用**最大余数法**（`IntegerAllocationSupport.allocateLargestRemainders`），不是简单 floor；比例和 >100 在保存期已拒。
5. **下发前兵量夹取**：`state.availableSoldiers(plan.infantry,...,reservedSoldiers)` 夹到实际可用库存；若 `plan.totalSoldiers()>=50000` 且家里可用总兵力 `<50000` → WAITING `SOLDIERS_SHORT`（**下限门槛**），不派。
6. **预留与保护**：同一次运行内 `reservedHeroes/reservedSoldiers` 跨队列累积；`protectedHeroes` = 同一模块其它已选编队的英雄集合，**fallback 不许抢**（`protectedHeroIds`）。当前服务端采集 v2 无这两样。
7. 失败语义：不可用返回 WAITING（下轮重试），**不静默换编队**；服务端同原则（SKIP），但 ROLE 换编队的回退能力没有。

### C.4 编队记忆快照（`RoleFormationMemoryService` / `DailyRoleFormationMemoryEntity`）

- 表 `daily_role_formation_memory`：ownerUserId, accountKey, roleUid, **memoryKind(DAILY/BATTLE)**, **snapshotJson**, slotCount, version, savedAt。
- **保存（记忆）**：从 `notify_soldier_init.prefab` 解析游戏内编队槽（旧版 `BehemothAccountState.soldierInit`：`prefab=[{id,prefab:{hero_id[],soldier[] | formation_rate[],formation_name}}]`），跳过空槽；同槽同时有 soldier 数量和比例 → 报错；`formation_rate` 缺失的 k=1/2/3 自动补 0；落 DB。
- **恢复**：对每个槽发 **`req_soldier_set_prefab`**，payload `{prefab:{id, prefab:{hero_id, soldier|formation_rate, formation_name}}}`，槽间隔 500ms（可配 `wjdr.daily.formation-restore-interval-millis`），逐槽收集失败码；恢复要求账号在线 + `marchCapacity().initialized()`。
- 覆盖保护：已有记忆时 `POST /memory` 需 `overwrite=true`，否则报“重新记忆会覆盖旧记忆”。
- **当前服务端状态**：①`Exec.soldiersFrom` 只读 `soldier`，**直接忽略 `prefab`**（`Exec.java:234-270`）；②没有记忆 state/接口；③spb schema 已有 `req_soldier_set_prefab`(c2s)、`formation_rate`、`prefab`、`formation_name`，`engine.request(proto,args)` 通用可用 → **无需新协议**。

### C.5 巨熊模板（`DailyBearFormationTemplateService/Catalog` + `DailyBearFormationConfig`）

- 模板目录：`g01..g14` × {spender(大氪)/mid(微氪)/free(零氪)/preview}，每条=**1 支发车队（≤3 英雄）+ 6 支上车队（每队≤3 英雄）**；`JOIN_QUEUE_COUNT=6`、`TEAM_HERO_LIMIT=3`、**比例固定 5:5:90**（`DailyBearFormationTemplateCatalog.java:14-16`）。
- 应用模板（`apply`）：校验当前角色是否拥有模板全部英雄（缺失→`MISSING_HEROES` + 返回可用模板列表）；把发车队+6 上车队**写入编队库**（PERCENTAGE 5/5/90，命名“巨熊·发车队(x)/上车队N(x)”），并把 `{templateId, appliedAt, launchFormationId, joinFormationIds[6]}` 存到配置 section `bearFormation`；`GET /binding` 读回绑定。
- 巨熊配置 `DailyBearFormationConfig`：id **0..6（0=发起集结，1-6=上车槽）**，`enabled`、`formationMode`、`formationId`、三兵量（0..1e9）；`ROLE 且 enabled` 必须有 formationId；只有含 `formationMode/formationId` 键的旧配置才视为统一编队（否则 disabled）。
- 当前服务端：`join_formations` 支持 **1-6 上车槽**（无 0=发车），`SERVER bear` 发车用 `cfg.paramsMap` 走 `FormationResolver`（`ServerBearTasks.java:1333-1342`）；**没有模板库/绑定/5:5:90/发车+6队成套写入**。

### C.6 一键编队（`DailyQuickFormationController/Service`）

- `POST /api/daily/roles/{accountRoleId}/quick-formation`：按内置模板把**采集前 min(4,队列上限) 队设 ROLE+GATHER_MEAT/WOOD/COAL/IRON**；巨兽（queueCount=1 才设）、情报（WILD）、狩猎（queueCount=1 才设）、英雄使命（BEHEMOTH）逐模块设置；每模块返回 `{module,status:applied/skipped/failed,message}`，失败不中断其它模块。
- 内置编队（`ensureBuiltInFormations`）：GATHER_WOOD/IRON/COAL/MEAT（单英雄 50000/50001/50002/50003，**90000 兵 1:1:1**）、BEHEMOTH（吉娜 50008+卢姆 50029+最强盾，**1 兵**）、WILD（同 3 英雄，**120000 兵 10:10:80**）；`oneInfantry`（9000000001，1 盾兵 0 英雄）、`randomHeroOneSoldier`（9000000002）。
- 当前服务端：无 quick-formation，无内置模板，无“发车队/一兵队/无英雄队”概念（`ResolvedFormation.usable()` 要求 soldierPairs 非空且 heroPairs 非空，`ResolvedFormation.java:87-91,97-104` → **无英雄一兵队无法构造**，旧版 `heroesOnly`/`mercenaryAllianceBossFormation` 支持 `heroPairs=[]`）。

### C.7 每功能绑定 / 默认（`DailyBuiltInFormationDefaults` + 各 Config）

- 旧版每功能配置保存 **`formationMode` + `formationIds[]`（列表，去重；`DailyFormationConfigSupport.explicitFormationIds`）**，默认值为内置模板 id（采集 4 队各绑 GATHER_*；情报/狩猎绑 WILD；巨兽/英雄使命绑 BEHEMOTH）。
- `formationMode` 缺省推导：`formationIds 非空 → ROLE，否则 AUTOMATIC`；NORMAL/CUSTOM→ROLE。
- 出征士兵默认：采集队列 40000/30000/30000（`DailyGatherFormationFields`）；巨熊 5:5:90（模板）。

### E.5 resolver 改造（分层，保持 FALLBACK 零变化）

1. `resolveOutcome`：无参数 → FALLBACK（不变）。
2. ROLE：
   - a. `formation_ids[]` 逐个尝试（新）；单 id 兼容；
   - b. 校验：≤3、无重复、职业唯一（缺 profession→只校验已知项）、在目录；
   - c. 过滤 `HeroAvailability.isBlocked` → 有则记录 `HERO_AWAY` 并尝试下一候选/回退 AUTO（参数 `formation_fallback=AUTO`，缺省关）；
   - d. 兵量：显式兵量超容量 → **按容量同比缩放**（`scaleTotal(oldTotal, oldLimit, newLimit)` 旧版公式）而非 SKIP；超库存才 SKIP（或按库存缩放，参数化）；
   - e. capacity 未知（=0）→ 保持“不夹取但记录 WARN”（不阻塞旧行为）。
3. AUTO：
   - a. 英雄候选 = `autoProfessionHeroes` 上限 `min(3, autoHeroLimit)`（接线 415 hint）；`HeroCatalog.profession=0` 的英雄不参与 AUTO；
   - b. capacity>0 才夹取；成功后 `clearHeroLimitHint` + `SOLDIER_SCALE_PCT=100`（成功回调）；
   - c. 同轮 `usedHeroes` 由调用方传入（采集 v2 多队列预留）。
4. `FormationCatalog`：capacity 改 `QueueCapacity.rawCapacity(...)`/`AssetState` 同源；空快照不缓存；实现 `onNotify(notify_hero_init/notify_soldier_init/notify_soldier_update)` 增量刷新；日志带 fpid/sid/heroes 数。
