## 0. 结论摘要（先看这里）

1. **`WVRX-UVXL-NH79-2J5N` 不是设备号，而是永久兑换码**。授权服务端记录显示它已于 **2026-10-18 01:30:18** 绑定到 **Xiaomi 2602BRT18C**；最后一次成功校验是 **01:39:46**，`verify_count=2`。按客户端 10 分钟校验节流，若进程存活，01:49 左右应有下一次校验；服务端没有。**这支持“激活后约 9 分钟内进程终止/被系统杀掉”的判断，但不能替代设备端日志。**
2. **当前环境读不到该小米设备的崩溃日志、ANR trace、tombstone**：ADB 只连接了 vivo V2141A（Android 14）和一台模拟器；`/data/tombstones` 权限拒绝，`/data/anr` 下文件为 `system:system 600` 读不到；`logcat -b crash` 为空；本仓库和本机没有 WVRX 或小米设备的历史日志。**报告不会编造该设备的日志内容。**
3. **同代码路径上已确认两类崩溃/无响应证据**：
   - 2026-09-11 的 **前台服务超时崩溃**：`ForegroundServiceDidNotStartInTimeException`，进程 `com.gof.china`，服务 `com.carlos.multiapp/GameKeepAliveService`。根因是服务当时声明在 `:p0`（与游戏同进程），Unity 首启占满主线程，5 秒内未 `startForeground`。**当前 4.1.1/4.1.2 清单已把服务移回宿主主进程，该崩溃在 4.1.0+ 已修复。**
   - 2026-10-11～10-13 的 **8 条 `data_app_anr`**：其中 **7 条**是 `com.gof.china/com.unity3d.player.DDUnityLaunchActivity` 的 `Input dispatching timed out ... FocusEvent(hasFocus=false)`，进程均为 `com.carlos.multiapp:p0`，版本 4.1.0（23500）。ANR 时 Java 主线程停在 `MessageQueue.nativePollOnce`（空闲），Unity 线程 CPU 约 124%、RSS 约 1.18GB。**这不像 Java 主线程死循环，更像容器窗口焦点事件在 Unity 冷启动期间未被确认，5 秒超时后系统杀进程。**
4. **发现一个高置信度代码缺陷**：`VaultEngine.isContainerGameAlive()` 用 `ActivityManager` 的 `processName.startsWith("com.gof.china")` 判断游戏是否存活；但系统里该进程的真实名称是 `com.carlos.multiapp:p0`（ANR 原文 `Process: com.carlos.multiapp:p0`，`Cmd line: com.gof.china`）。同一文件里另一个方法 `isContainerGameRunning()` 用 `/proc/<pid>/cmdline` 匹配 `com.gof.china`，口径才是对的。**`killGameAndWait()`、`SessionSaver`、快照/提取 token 路径都依赖前者，可能误判“游戏已退出”**，进而在旧游戏仍存活时执行 wipe/注入/存档/新启动。多开/快速切号会放大这个竞态，是本次闪退/无响应最值得优先验证的代码根因。
5. **发布包存在确定性缺陷**：根目录 `无尽号库-v4.1.1` 与 `v4.1.2` APK 内 `lib/arm64-v8a/libvbox.so` 的 sha256 前缀均为 **`a0f06e48`（原版未打补丁）**，而长期记忆中的修复版应为 **`0dd16cb7`**。`tools/release.sh` 直接 `assembleRelease`，既不换入 `.workbuddy/artifacts/fix-apk/lib-release.aar.patched`，也不校验 so 哈希。**Android 14+ 上 `renameat2` hook 丢 `flags` → `EINVAL` → 容器内游戏资源更新/改名失败的根因修复没有进入发布包。** 这会造成游戏下载/更新失败，严重时表现为启动卡死或闪退。
6. **当前 master 自带回归测试不是全绿**：`./gradlew :app:testDebugUnitTest` 共 **118 例，4 例失败**，全部在 `RegistryAndDefaultsTest`。原因是新增 `guardian`、`achievement_claim`、`act_snowtrade` 后，测试仍按 53 项/18 项默认关/旧分类计数断言；实际是 56 项、21 项默认关、分类 10/11/15/7/7/2/4。UI 是动态取 56，文档仍写 50。**这是发布门禁问题，不是线上崩溃的直接原因。**
7. **其它已确认的功能异常**：`DailySchedulerService.onStartCommand()` 每次启动都 `tick()`，而 `ensureStarted()` 会被每条游戏通知反复调用（真机 `lastStartId=5`）→ 多条 10 分钟巡检链并存；`DailyRunner.runSingle()` 没有按 fpid 串行化，通知触发的多条线程可能关闭彼此常驻会话再 fresh 登录；真机 `notify_events.txt` 已出现 `target gather ... IllegalStateException: 协议调用失败: req_players_base_info`。
8. **后台保活结论**：当前端侧保活是“宿主前台服务 + VA `:va_core` 前台服务 + 电池白名单 + 1 秒会话扫描 + 3 秒/60 秒心跳 + 8s→300s 重连”。真机上宿主 `oom_score_adj=0`、`:va_core=200`，App 已在电池白名单；但游戏进程 `:p0` 并不直接被宿主前台服务覆盖。原生无尽冬日后台运行会显著延长分身游戏存活，最可能来自三类机制叠加：**Doze/唤醒锁（原生游戏让设备保持活跃，心跳不被冻结）**、**OEM 游戏模式/进程冻结策略**、**LMK 回收顺序（原生游戏作为缓存进程先被回收，替容器游戏吸收内存压力）**。长期方案应优先把自动化搬到 `vault-server`（项目已有服务器模式），手机端只保留“玩游戏”场景；不建议用静音音频等激进手段作为默认方案。

## 3. 崩溃定位与根因分析（对应问题 1）

### 3.1 已证实的崩溃 #1：前台服务 5 秒超时（历史，已修复）

证据文件：`.workbuddy/artifacts/r2_crash.log`（2026-09-11）。

```
FATAL EXCEPTION: main
Process: com.gof.china, PID: 4346
android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground():
ServiceRecord{... com.carlos.multiapp/com.carlos.vault.GameKeepAliveService}
```

同日 02:18、02:22、02:28 连续 3 次，进程分别为 `com.gof.china` 的 4346/7224/9757。

**根因（已证实 + 代码注释互证）**：当时 `GameKeepAliveService` 声明在 VA 的游戏 stub 进程 `:p0`，与 Unity 游戏同进程；829MB 资源首启把该进程主线程打满，`startForegroundService()` 后 `onStartCommand` 排不上队，5 秒死限被击穿，系统抛异常并杀掉调用方（游戏进程）。

**修复状态（已证实）**：
- `app/src/main/java/com/carlos/vault/GameKeepAliveService.java:61` 在 `onStartCommand()` 第一行同步调用 `startForeground()`；
- `app/src/main/AndroidManifest.xml:132` 的 `GameKeepAliveService` **没有** `android:process=":p0"`；
- 代码注释明确记录“必须留在宿主主进程”；
- 修复提交 `bbeed85`（2026-09-24），4.1.0（23500）起包含。
- 对 4.1.1/4.1.2 APK 用 `aapt2 dump xmltree` 复核，service 节点也没有 `process` 属性。

**结论**：如果小米设备运行的是 **4.1.0 之前**的包，这个崩溃仍然成立；如果运行 4.1.0+，该特定崩溃应已消失。需要设备 `versionCode` 才能排除。

**定位结论（证据等级：已证实现象 + 代码/系统行为推断）**：
- 这不是“Java 主线程死循环/锁死”导致的 ANR，因为 Java 主线程在 `nativePollOnce` 空闲。
- 超时事件是 **窗口焦点丢失事件（FocusEvent hasFocus=false）**，窗口属于 `DDUnityLaunchActivity`；容器用 `ShadowActivity$P0` 托管游戏 Activity。焦点事件由应用主线程处理，但 Unity 冷启动期间窗口/输入通道可能尚未就绪，或焦点在宿主/旧游戏实例/新游戏实例之间切换，导致 5 秒内没有 ack。
- 多开/分身会显著放大：两套 Unity 实例、两套窗口、两套资源加载、CPU/IO 竞争，焦点切换更多，5 秒窗口更容易被击穿。这解释了“多开/分身场景更容易闪退/无响应”的现象方向。
- 该 ANR 会以“应用无响应”形式出现；用户点关闭或系统杀进程后，主观上就是“闪退”。

### 3.3 高置信度代码缺陷：游戏存活判断口径错误（多开/切号的关键）

代码位置：

- `app/src/main/java/com/carlos/vault/VaultEngine.java:204` `isContainerGameAlive()`
- `app/src/main/java/com/carlos/vault/VaultEngine.java:219` `killGameAndWait()`
- `app/src/main/java/com/carlos/vault/VaultEngine.java:865` `isContainerGameRunning()`
- `app/src/main/java/com/carlos/vault/SessionSaver.java:167`

`isContainerGameAlive()`：

```java
ActivityManager am = ...;
List<RunningAppProcessInfo> ps = am.getRunningAppProcesses();
for (RunningAppProcessInfo pi : ps) {
    if (pi.processName != null && pi.processName.startsWith(GAME_PKG)) return true;
}
```

`isContainerGameRunning()`：

```java
File[] dirs = new File("/proc").listFiles();
for (File d : dirs) {
    String cmd = readCmdline(pid);
    if (GAME_PKG.equals(cmd)) { running = true; break; }
}
```

**矛盾点（已证实）**：系统 ANR 原文是 `Process: com.carlos.multiapp:p0`、`Cmd line: com.gof.china`。`RunningAppProcessInfo.processName` 来自 `ProcessRecord.processName`，即 `com.carlos.multiapp:p0`；它**不会**以 `com.gof.china` 开头。`/proc/<pid>/cmdline` 才是 `com.gof.china`，所以 `isContainerGameRunning()` 的口径正确。

**影响链（代码审查，需目标设备一次实验确认）**：
1. `launchEntry()` 开头 `killGameAndWait(10000)` → `killGame()` 后循环检查 `isContainerGameAlive()`；若它始终为 false，会**立即返回 true**，即使旧游戏进程还活着。
2. 紧接着 `wipeGameInternal()`、`restoreBaseline()`/`unzip(snapshot)`、`injectSession()`、`setLiveEntryId()` 全部在旧游戏仍可能写文件时执行。
3. `SessionSaver` 的“游戏已死才允许写快照”保护同样失效，可能在游戏写 prefs/资源时 zip live 目录，产生**不自洽快照**。
4. `captureEntrySnapshot()`/`extractCurrentSession()` 也走 `killGameAndWait()`，同样可能读到半写状态。
5. 多开/快速切号时，旧游戏没死、新游戏又启动 → 两套 Unity/窗口/焦点 → 正是第 3.2 节 ANR 的触发条件；同时可能把 A 账号的 live 数据注入/覆盖到 B 账号。

**确认实验（不改代码即可做）**：
- 启动容器游戏，执行 `adb shell ps -A -o PID,NAME,ARGS | grep -E 'gof|carlos'`，确认 `NAME=com.carlos.multiapp:p0`、`ARGS=com.gof.china`。
- 在 `isContainerGameAlive()`/`isContainerGameRunning()` 各加一行日志（或用一个调试入口分别调用），比较两者返回值；若前者 false、后者 true，即证实。
- 观察 `killGameAndWait` 的耗时：若几乎是 0ms 返回，而 `ps` 仍能看到 `:p0`，即证实误判。

**修复建议**：`isContainerGameAlive()` 改为调用 `isContainerGameRunning()`（`/proc` 口径），或在 `ActivityManager` 结果里同时匹配 `processName` 和 `cmdline`；`killGame()` 后清空 `procScanAt` 缓存；`killGameAndWait()` 用 `/proc` 轮询直到进程消失；`launchEntry()` 加 per-account/全局锁，确保旧实例真正死亡后再 wipe/注入/启动。

### 3.4 发布包确定性缺陷：引擎 `renameat2` 修复未进入 APK

**证据（已证实）**：

| 产物 | `lib/arm64-v8a/libvbox.so` sha256 前缀 |
|---|---|
| `无尽号库-v4.1.1-HTTPS加密版.apk` | `a0f06e4838404790`（原版） |
| `无尽号库-v4.1.2-HTTPS加密版.apk` | `a0f06e4838404790`（原版） |
| `app/sdk/lib-release.aar`（仓库） | `a0f06e4838404790` |
| `.workbuddy/artifacts/fix-apk/lib-release.aar.patched` | `0dd16cb7f9dc5a2e`（修复版） |

长期记忆记录的机理：`libvbox.so` 的 `new_renameat2` 由 `new_renameat` 复制时漏写第 5 参 `flags`；内核 `do_renameat2()` 校验 `flags & ~(NOREPLACE|EXCHANGE|WHITEOUT)`，`flags≠0` 时返回 `EINVAL`。这会导致容器内游戏 `.temp` 文件无法改名为 `.bytes`，表现为“下载更新文件失败”，严重时游戏初始化失败/卡死/闪退。该 bug 仅在 **Android 14+（SDK≥34）** 可达；小米 2602BRT18C 很可能满足。

`tools/release.sh:72` 直接 `./gradlew :app:assembleRelease --offline`，没有：
- 换入 `.workbuddy/artifacts/fix-apk/lib-release.aar.patched`；
- 清理 Gradle `transforms-3` 缓存；
- 校验 APK 内 `libvbox.so` 哈希；
- 运行 `testDebugUnitTest`。

**结论**：4.1.1/4.1.2 发布包**确定没有带上引擎修复**。如果小米设备上的游戏在启动时需要下载/更新资源，这就是一条能直接导致“启动卡死/闪退”的确定性缺陷；如果资源已是最新，则不一定触发。需要在小米设备 logcat 中查 `renameat2`、`EINVAL`、`Couldn't rename file`、游戏更新日志来确认本次是否命中。

- **会导致“行为不一致”**：`behemoth`/`bear`、`gather` 一次性、`shield` 裁剪、`arena` 无过滤、`act_joy` 仅监测、`act_brawl` 仅成就、`fishing` 仅领奖等，属于有意裁剪/待补齐；用户按原版预期使用会认为“功能失效”。
- **可借鉴原版的点**：
  - 原版 `GameAccountSessionService` 的登录预算/租约/全局并发控制，比号库 `RoleSessionKeeper` 的“竞速登录 + 8 次失败降级”更稳；
  - 原版 `core/notification` 可作为号库通知体系的参考；
  - 原版 release 378 的 `supply` 本地等待、`endless` 状态指纹等修复，可作为号库细节优化参考。
- **建议**：功能开发以京东云 release 378 为基线；但**不要把原版代码当作本次 Android 闪退的修复依据**，崩溃修复必须在 VA/端侧代码里做。

## 6. 后台保活分析（对应问题 4）

### 6.1 当前端侧保活机制（代码事实）

真机现状（vivo V2141A，2026-10-18 02:0x）：
- `dumpsys activity services`：`DailySchedulerService` `isForeground=true`，`foregroundId=4210`；VA `KeepAliveService` `isForeground=true`，`foregroundId=2781`。
- `dumpsys deviceidle whitelist`：`com.carlos.multiapp` 已在白名单。
- `dumpsys power`：`mWakefulness=Awake`、`mIsPowered=true`、`mDeviceIdleMode=false`、`Wake Locks: size=0`（当前没有跑任务）。

- 游戏进程 `:p0` 当前未运行，无法直接测其 oom_adj。

### 6.2 为什么“后台跑原生无尽冬日”会延长分身游戏存活

这是多机制叠加，需用实验区分；按可能性排序：

1. **Doze/唤醒锁效应（最可能）**  
   原生游戏在后台仍可能持有 `PARTIAL_WAKE_LOCK`、音频焦点、网络/反作弊线程，或至少让设备保持较高活跃度，使系统不进入深度 Doze。容器侧的心跳（TCP）和 `:p0` 游戏进程因此不被冻结，服务器会话不容易超时；一旦设备进入 Doze，网络被推迟、心跳停发，服务端会判定离线，游戏也可能被冻结/回收。
2. **OEM 游戏模式/进程冻结策略**  
   vivo/Xiaomi 的“游戏加速/游戏空间”可能按包名或进程 cmdline 识别游戏。原生游戏在跑时，系统处于游戏场景，可能放宽对同场景进程的冻结；容器游戏的 cmdline 也是 `com.gof.china`，可能被一并照顾。不同 OEM/版本策略不同，需要目标机验证。
3. **LMK 回收顺序**  
   原生游戏是独立 UID 的缓存进程；当内存压力上来时，LMK 按 oom_adj/最近使用顺序回收。若容器游戏处于可见/前台服务状态（oom_adj 较低），原生游戏会先被杀，替容器游戏吸收内存压力；原生游戏不在时，容器游戏可能成为下一个被回收的缓存进程。**这能解释“原生游戏在后台反而让分身活得更久”**。
4. **CPU/GPU 频率与热/功耗状态**  
   原生游戏让 CPU/GPU 保持较高频率，减少容器侧 Unity/网络线程被调度延迟的概率；但这也会增加发热和耗电，不是稳定的保活机制。
5. **同 UID 前台服务覆盖范围**  
   宿主 `GameKeepAliveService`/`DailySchedulerService` 是前台服务，但 Android 的 importance 是**按进程**的；宿主 FGS 不必然提升 `:p0` 的 oom_adj。部分 OEM 按 UID 分组保活，部分不按。原生游戏的存在可能间接改变系统对“游戏场景”的判定。

### 6.3 不依赖原生无尽冬日的可行方案

| 方案 | 效果 | 风险/成本 | 适用 |
|---|---|---|---|
| **A. 服务器模式（首选）** | 自动化跑在 `vault-server`，手机端不需要 24h 常驻；手机关机不影响挂机 | 需要服务器/网络；账号数据上传；已有实现 | 日常自动化、互助、推送唤醒 |
| B. 保持游戏 Activity 可见（分屏/悬浮窗/PiP） | 可见进程 oom_adj 低，最接近“真前台” | 用户必须让游戏可见；分屏/PiP 兼容性；耗电 | 用户想边玩边挂 |
| C. 游戏进程内增加前台服务（延迟启动） | 直接提升 `:p0` importance | 5 秒超时风险回归；需游戏主线程空闲后启动；VA 进程模型复杂 | 技术验证项，不建议直接上线 |
| D. `mediaPlayback` 前台服务 + 静音音频 | 防 Doze、保持 CPU/网络；常见但激进 | 耗电、OEM 反感、Android 14+ FGS 类型/政策、用户通知打扰 | 仅作为最后手段，需用户明确同意 |
| E. 电池白名单 + OEM 自启动/后台锁定 + 精确闹钟 | 降低被冻结/被杀概率 | 需要用户手动设置；不同 ROM 路径不同 | 所有方案的基础配置 |
| F. `AlarmManager`/`JobScheduler` 周期唤醒 + 重连 | 维持协议会话；不能保游戏进程 | Doze 限制；频繁唤醒耗电 | 自动化会话兜底 |
| G. 无障碍/通知监听检测死亡并重启 | 死后恢复，不是“保活” | 后台启动 Activity 限制；政策风险 | 兜底 |
| H. DeviceOwner/锁屏 kiosk | 最强，但不适合消费级分发 | 设备管理权限、合规 | 不推荐 |

**推荐组合**：
1. **日常自动化走服务器模式**（A）——这是唯一能在手机关屏/关机时长期稳定的方案；
2. 手机端保留 B/E：需要玩游戏时用分屏/悬浮窗保持可见；同时完成电池白名单 + OEM 自启动/后台锁定；
3. 不为“游戏进程 24h 后台”默认启用 D；如果必须，先做 24h 耗电/发热/封号风险评估，并提供开关与明确提示；
4. C 作为引擎侧研究项，先在测试机验证 `:p0` 内延迟 `startForegroundService` 是否可行，避免重演 5 秒超时崩溃。

### 6.4 保活验证方法（可执行）

A/B 对照，至少 4 组：
