## 2. 发现（按优先级）

### P1-1（已修）加速把 ETA 压到「tick 周期 + 请求往返」以内时，盾必开在到达之后

- **位置**：`ServerShieldResponder.java:834-846`（`gateSec` 与挂起/触发判定）。
- **问题（修复前）**：`before_arrival` 只在 `remain <= etaSec(默认2)` 时开盾；加速推送虽会置脏，但决策仍在 1Hz 会话 tick 内串行执行，实战中调度延迟约 4.7 秒，盾完成比到达晚约 4 秒。
- **影响**：敌方使用加速道具时保护失效；已由 03:35 事故证实（到达 03:35:47、开盾 03:35:50.956）。
- **处置**：① 紧急加速（剩余 ≤20s，或连续加速 ≥3 次且累计提前 ≥ 初始剩余一半）**跳过卡秒当拍开盾**；② `onPush` 命中紧急时通过 `setUrgentWakeup` 回调宿主，`SessionKeeper` 用独立单线程 `shieldExec` 立即执行 `tick`（请求仍走 `engine.requestLock` 串行）；③ 非紧急加速仍保留 `max(etaSec, 8s)` 余量；未加速场景保持原语义。
- **依据**：`acceleratedEta_opensImmediately_notWaitForEta`、`threeAccels_wakesUrgentAndOpens`（唤醒回调计数）、`threeSmallAccels_notUrgent`。

### P1-2（已修）挂起写 `etaCheckAtMs` 未校验风险快照，可能吞掉并发加速更新

- **位置**：`ServerShieldResponder.java:840`（`synchronized (riskLock) { if (risk != r) return false; ... }`）。
- **问题（修复前）**：tick 读到旧 `Risk` 后，推送线程可能已写入更早 ETA 的新 `Risk` 并清零 `etaCheckAtMs`；旧 tick 随后无条件写回「旧到达时刻 - 2 秒」，把新风险的判定点推迟。
- **影响**：连续加速/多波并发时，开盾可能退化到旧 ETA 时刻（晚于实际到达）。
- **处置**：写前做引用快照校验；不一致则本拍让位，由下一拍处理新风险（推送线程已置 dirty）。
- **说明**：单线程单测无法构造精确交错，本项以代码路径审查为准，属确定性竞态窗口。

### P2-1（已处置）会话线程长任务阻塞导致开盾延迟 —— 事件驱动 + 独立执行器

- **位置**：`ServerShieldResponder.java` 的 `setUrgentWakeup` / `wakeUrgent`；`SessionKeeper.java` 的 `shieldExec()` / `ensureShieldTick`。
- **问题（修复前）**：开盾决策只在 1Hz 会话 tick 内执行，同线程的守护盟友召回/整轮任务会把它推迟数秒（本次 03:35:46.3 推送 → 03:35:50.956 开盾，延迟约 4.7 秒）。
- **处置**：紧急加速时推送线程只回调唤醒（不持锁、不发请求），`shieldExec` 单线程执行 `tick`，与 1Hz 会话拍并行；请求由 `engine.requestLock` 串行化，不与任务/心跳交叉发送。`tick` 增加 `ticking` 单飞，避免两拍并发推进采集 watch 状态机。
- **残留**：`shieldExec` 与会话拍的并发属新增路径，尚无 SessionKeeper 层集成测试（见 §4）；线程在会话关闭时 `shutdownNow` 回收。
- **依据**：`threeAccels_wakesUrgentAndOpens`（第 3 次加速触发唤醒且当拍开盾）。

### P2-2（未修，后续）服务器时钟偏差约 3 秒，由安全余量吸收

- **位置**：`ServerShieldResponder.java:1502-1517`（`serverNowSec`）。
- **问题**：`GameServerClock.locked()==true` 时仍存在约 3 秒偏差（03:35:44 `remain=167` vs 守护盟友同刻推算 ≈164），会让卡秒整体晚 3 秒；未触发「未校准」告警。
- **影响**：加速场景已被 8 秒余量覆盖；未加速场景仍按 2 秒卡秒，3 秒偏差可能让「抵达前 2 秒」变成「抵达后 1 秒」。
- **处置**：**后续项**。`GameServerClock` 为 App/Server 共用全局时钟，改动面大，本次不改；建议单独任务：locked 后校验 offset 偏差 >2 秒告警，并在卡秒中扣除。

### P2-3（已修）到达后补盾与正常开盾在状态上不可区分

- **位置**：`ServerShieldResponder.java:896-900`、`:924-930`、成功文案 `:954/:973/:991` 附近。
- **问题（修复前）**：`remain<0` 仍写「已使用背包 2小时护盾（code=0）」，用户无法判断本次是否已接战。
- **处置**：`lateArrival` 时状态/日志追加「（敌方已到达，可能已接战）」。

## 3. 行为变化与回归风险评估

1. **未加速场景不变**：`r.accelerated=false` 时仍按 `etaSec` 触发，AC-06 语义未变（`multiWave_keepsEarliestEta` 通过）。
2. **加速场景分两档**：紧急（剩余 ≤20s 或 ≥3 次且提前过半）当拍开盾；非紧急保留 `max(etaSec, 8s)` 余量。最坏情况提前约 18 秒（剩余 20s 即开），2 小时盾时长损失可忽略。
3. **`lateArrival` 只影响文案**，不影响开盾顺序（免费→背包→钻石）与幂等。
4. **挂起让位**：`risk != r` 时返回 false（本拍无动作），依赖推送线程已置 dirty；已确认 `onPush` 在 `riskLock` 内先写 `risk` 再 `dirty.set(true)`，下一拍会处理。
5. **新增并发路径**：`shieldExec` 与 1Hz 会话拍并行；`tick` 单飞保证同一实例不并发；请求串行由 `engine.requestLock` 保证；`shieldExec` 在会话关闭时回收。
6. **唤醒回调只在紧急时触发**：非加速/非紧急推送不会产生额外线程任务，避免线程池被高频推送打满。

## 4. 测试缺口（单列）

1. **竞态无法单线程复现**：`risk != r` 的交错时序没有集成/并发用例；建议后续加「推送线程与 tick 并发」的并发测试（可用 CountDownLatch 注入）。
2. **SessionKeeper 并发路径未覆盖**：`shieldExec` 与 1Hz 会话拍并行、`tick` 单飞的组合没有集成测试；单测只覆盖「唤醒回调被调用 + 当拍开盾」，线程模型需真机/集成回归。
3. **时钟偏差未覆盖**：`serverNowSec` 慢 3 秒的回归用例未加（可在 `responder(nowMs, serverSec)` 注入不同步时间源验证「未加速时仍晚到」的旧行为，作为 P2-2 后续任务的先红用例）。
4. **真机回归未做**：需按 TDD 报告 §6 在服务器上复现「挂起→加速→提前开盾」与「到达后补盾文案」两条。
