# 活动功能热更启用 · 可行性评估（2026-11-06，含 GitHub 方案调研）

> 评估对象：用户提出的"新增活动功能/活动页面时，App 端点击更新即可启用、无需重新下载安装 App"。
> 评估依据：`app/src/main/java/com/carlos/vault/daily/HotConfig.java`、`vault-server/.../HotConfigRoutes.java`、`design/热更新自托管与参数选项化-20261025.md`、`design/全流程行为与分级门控-20261023.md`，以及 GitHub 主流热更/插件化方案的公开文档与仓库状态（2026-11-06 查询）。
> 追加背景（2026-11-06）：用户明确希望"最起码小规模改动新增一些活动页面不需要重新安装更新包，点击下载更新就可以了"，因此本版在原评估基础上补充"页面级热更"的方案调研与推荐路线。

---

## 1. 结论（先给答案）

| 问题 | 结论 |
|---|---|
| 现有 `hotconfig` 能否做到"点检查更新即启用、不重装"？ | **能，但仅限配置/声明式能力**（数值/目录/单步领取/开关） |
| "新增活动**页面**"能否不重装？ | **能，但不是靠 Tinker 类补丁**：需要先发一次版做"页面容器"（H5 或声明式 DSL），之后新增活动页面 = 服务端发布页面 + 配置下发，点击更新即生效 |
| Tinker / Bugly 类热更能否新增页面？ | **不能**。Tinker README 明确限制：`Can't update AndroidManifest.xml, such as add Android Component`（[Tencent/tinker](https://github.com/Tencent/tinker)） |
| 插件化（Shadow/RePlugin）能否新增原生页面？ | **能**（Shadow 支持四大组件），但接入成本高，且与本项目 VirtualApp 容器存在 hook 冲突风险，需 PoC；RePlugin/Atlas/VirtualAPK 维护风险高或已归档 |
| 推荐路径 | **方案 A：H5 活动页容器（主）**；方案 B：声明式 JSON 活动页（增强）；方案 C：Shadow 插件化（仅当必须原生且 PoC 通过）；方案 D：Tinker 类（明确排除） |
| 本期边界 | **只更新评估与开发计划，不实现代码**（2026-11-06 用户确认：本期只更新文档与计划） |

一句话：**"新增活动页面、不重装"可行，但它的本质是"页面容器化 + 配置下发"，不是传统 dex 热补丁。** 需要一次发版把"容器"装进 App；之后页面内容与活动配置可热更。

## 2. 现有热更机制事实（已核实）

### 2.1 链路

```
hotconfig.json（vault-server dataDir）
   │  GET /v1/vault/hotconfig（{base} 占位替换为请求 Host）
   ▼
App HotConfig：启动 init / 每 6h 到点刷新 / 手动「检查更新」checkServer
   │  version > 本地 version 才落盘并 apply（立即生效）
   ▼
消费方：nums（数值）/ catalogs（目录）/ claims（声明式领取）/ disabled（禁用功能）
```

- 服务端：`HotConfigRoutes.serveHotConfig` 读取 `dataDir/hotconfig.json`，把 `{base}` 替换为请求方 scheme+host 后原样返回；文件缺失 404。
- App：`HotConfig.init()` 先读 `filesDir/hotconfig/config.json`（adb 放置可离线），再按 6h 限频拉远端；`checkServer()` 是手动检查（绕过限频），命中新版本即写本地并 `apply`。
- 广播：`adb broadcast com.carlos.multiapp.HOT_REFRESH [--es url ...]` 可在锁定屏/后台强制刷新。
- 安全边界：内容 ≤ 2MB；**当前不做任何代码/Dex 加载**（`HotConfig` 类注释明确）。

### 2.2 已支持的热更字段（`HotConfig.java`）

| 字段 | 语义 | 消费方 |
|---|---|---|
| `version` | 热更包版本（整数）；**只有大于本地才应用** | `checkServer`/`fetchAndApply` |
| `apk` | 整包更新信息（versionCode/versionName/url/notes/sha256/sizeBytes） | 「检查更新」弹窗 → 浏览器下载 → **系统安装器（仍需安装）** |
| `nums` | 数值参数覆盖 | 各功能读 `HotConfig.num(key, def)` |
| `catalogs` | 目录覆盖 | 读 `HotConfig.catalog(s)`，缺失回落 assets |
| `claims` | 声明式领取：`{id,name,proto,args,notify}` | 每日轮收尾执行；`proto` 必须是 App 已实现协议 |
| `disabled` | 禁用功能 id 列表（远端止血） | `runTasks` 强制跳过 |

### 2.3 现有机制的关键限制

1. **`version` 必须递增**：只改内容不加 `version`，App 不会应用。
2. **`claims` 只能表达"单步、固定参数"的领取**：无分支/循环/条件/战斗/多协议编排。
3. **`claims` 的 `proto` 必须是 App 端已实现的协议**。
4. **现有 hotconfig 无 UI 能力**：不能新增页面/入口/弹窗；只能改已有功能的行为/参数/可见性。
5. **整包更新不是"无需重装"**：`apk` 块只是引导下载，仍需系统安装。
6. **6h 缓存 + 手动检查**：不点检查更新时最迟 6 小时生效；旧设备 `prefs hot_url` 残留会优先于默认源。
7. **权限矩阵下发不依赖热更**：由 license-server 的 activate/verify 下发，与 hotconfig 独立。

## 3. GitHub 主流热更/插件化方案调研（2026-11-06）

> 维护状态取自 GitHub API（`pushed_at`/`archived`，查询于 2026-11-06）；能力边界取自各仓库 README。

| 方案 | 仓库/来源 | 最近推送 | 归档 | 能力边界（对"新增活动页面"） |
|---|---|---|---|---|
| Tinker | [Tencent/tinker](https://github.com/Tencent/tinker) | 2026-10 | 否 | dex/so/资源补丁；**不能改 Manifest、不能新增四大组件** → 不能新增 Activity 页面；适合 bug 修复 |
| Bugly 热更新 | 腾讯 Bugly（Tinker 封装，平台服务） | — | — | 同上；强依赖平台/基线版本，新增页面不适用 |
| Robust | [Meituan-Dianping/Robust](https://github.com/Meituan-Dianping/Robust) | 2022-04 | 否 | 方法体替换；不新增类/资源/组件 → 不能新增页面 |
| Shadow | [Tencent/Shadow](https://github.com/Tencent/Shadow) | 2026-10 | 否 | 插件化：支持四大组件、Fragment、so、自定义 Theme → **可新增原生页面**；需宿主改造，官方说明接入需二次开发 |
| RePlugin | [Qihoo360/RePlugin](https://github.com/Qihoo360/RePlugin) | 2025-09 | 否 | 插件化：支持新增插件/组件；框架较老（Android P 后适配少），维护低活跃 |
| VirtualAPK | [didi/VirtualAPK](https://github.com/didi/VirtualAPK) | 2023-07 | **是** | 插件化；**已归档**，不再维护 |
| Atlas | [alibaba/atlas](https://github.com/alibaba/atlas) | 2022-01 | 否 | 动态组件；停更，排除 |
| Play Feature Delivery | [Android 官方](https://developer.android.com/guide/playcore/feature-delivery) | — | — | 原生动态功能模块，但**仅限 Google Play 分发**；本项目侧载 APK，不适用 |
| H5 + JSBridge | WebView（系统能力） | — | — | 活动页面用 H5；一次发版容器后，页面内容由服务端下发 → **新增页面无需发版** |
| 声明式 JSON UI | 自研（参考服务端驱动 UI） | — | — | 一次发版渲染器；活动页面用 JSON 描述 → 无需发版；能力受渲染器限制 |

### 3.1 与本项目架构的冲突点（关键）

本项目 App 是 **VirtualApp 容器宿主**（`com.carlos.multiapp`，引擎已 hook AMS/ClassLoader/资源等）。若再叠加：

- **Tinker**：同样依赖 ClassLoader/资源替换 → 双重 hook，冲突与崩溃风险高；且不支持新增 Activity。
- **Shadow/RePlugin**：插件化框架本身要 hook Instrumentation/ClassLoader/AMS 代理 → 与 VA 的 hook 叠加，稳定性未知；Shadow 官方也说明接入需一定二次开发。
- **H5/DSL**：不触碰系统 hook，与 VA 零冲突 → **风险最低**。

> 结论：从"与现有容器共存"的角度，H5/DSL 容器明显优于任何 dex/插件化方案。

## 5. 推荐路线与交付边界

### 方案 A（推荐，低风险）：H5 活动页容器（**用户已确认方向；本期不实现**）

> 2026-11-06 用户确认：路线选方案 A；本期只更新文档与计划，容器与活动配置链路待后续立项实现。
> 已确认能力边界见 §5.1；托管方式：**vault-server 静态目录 + hotconfig.activities 下发**。


**一次性发版**（后续活动页面全部热更）：

1. 新增活动中心入口（或复用现有"活动"入口），打开一个专用 `WebView` Activity（与主界面隔离）。
2. 预埋 JSBridge（白名单、参数校验）：`openGame()`、`claim(proto, args)`（仅允许白名单协议）、`close()`、`getLicenseInfo()`、`toast()`、`track()`。
3. `hotconfig.json` 新增 `activities` 列表：

```json
{
  "version": 2026110701,
  "activities": [
    {
      "id": "act_spring_2026",
      "name": "春日活动",
      "url": "{base}/v1/vault/activity/act_spring_2026/index.html",
      "start": 1767225600000,
      "end": 1769904000000,
      "roles": [2, 3, 4],
      "enabled": true
    }
  ]
}
```

4. App 启动/检查更新拉取 `activities` 并落盘；活动中心按配置展示入口；打开 H5 页面。

**之后新增活动**：服务端发布 H5 页面 + 在 hotconfig 增加一条配置（递增 version）→ 用户点「检查更新」或启动后自动拉取 → 活动入口出现，无需重装。

**适用**：活动说明/规则/排行榜展示/领取按钮（Bridge 调已有协议）/跳转游戏。
**边界**：Web 观感；复杂原生交互/离线/性能敏感场景需 DSL 或发版；Bridge 能力必须白名单。

#### 5.1 已确认的能力边界（2026-11-06）

| 能力 | 结论 | 实现方式 |
|---|---|---|
| 基础展示（规则/说明/奖励列表） | ✅ 必须包含 | H5 页面静态内容 |
| **领取奖励** | ✅ **已确认核心能力** | JSBridge `claim(proto, args)`，仅允许白名单协议；参数与结果回传 H5 |
| **倒计时 / 排行榜 / 进度** | ✅ **已确认核心能力** | 倒计时用服务端时间（Bridge `getServerTime` / 接口）；排行榜/进度由服务端提供活动数据接口，H5 请求或经 Bridge 转发 |
| 跳转/拉起游戏 | ⏸ 未选，列为后续可选 | Bridge `openGame()`（预埋后启用） |
| 离线可用 | ❌ 本期非目标 | 弱网提示 + 重试；关键活动如需离线改用方案 B（DSL） |

> 说明（2026-11-06 已拍板）：排行榜/进度数据源 = **游戏协议抓包之后在服务端统计**，H5 不自行计算；Bridge/接口只读取服务端统计结果。

#### 5.2 立项决策（2026-11-06 用户确认）

| 决策项 | 结论 |
|---|---|
| 活动数据源 | 游戏协议抓包 → **服务端统计**；H5 通过 Bridge/接口读取统计结果（不在前端算） |
| 是否纳入权限矩阵 | **纳入**：新增功能 key `activity_center`（随容器一次发版）；服务端 `featureSeed` 39 → 40 项 |
| 默认可见角色 | 建议默认 T2（普通会员）可见，管理员可在矩阵中勾选；GM 恒开（最终默认等级在实现时按运营口径定） |
| H5 归属与发布 | 建议在仓库新增 `activity-web/<activity-id>/`（纯静态）；构建产物上传 vault-server `data/activity/<id>/`；hotconfig url 指向 `/v1/vault/activity/<id>/index.html`；vault-server 增加静态路由（或 nginx 映射）；回滚=保留上一版目录 + 配置指回；灰度=`enabled`/`roles` |

### 方案 B（增强）：声明式 JSON 活动页

一次性发版做渲染器（组件：文本/图片/按钮/列表/倒计时/进度条；动作：打开 URL/调协议/关闭），之后活动页面用 JSON 描述并由 hotconfig 下发。原生观感、可离线；但渲染器能力决定上限，复杂布局/动画仍需扩展（发版）。

### 方案 C（不推荐，除非必须原生）：Shadow 插件化

可新增原生 Activity，但需宿主接入 Shadow、插件独立编译/签名/下载/校验；与 VA 的 hook 冲突需 PoC（建议先做 1–2 天最小 demo：VA 宿主中加载一个 Shadow 插件 Activity，验证启动/返回/资源/so/稳定性）。成本高，不建议作为首期方案。

### 方案 D（明确排除）：Tinker/Bugly/Robust

Tinker README 明确不能新增 Android 组件；Robust 只做方法替换。二者都不满足"新增活动页面"。

## 6. 落地前置（若选 A/B）

1. **发一次版**：容器（WebView 活动中心 + JSBridge + `activities` 解析）。
2. **服务端**：hotconfig 增加 `activities`；活动 H5 托管在 **vault-server 静态目录**（已确认）；配置递增 `version`。
3. **安全**：H5 域名白名单；JSBridge 方法白名单 + 参数校验；仅 HTTPS；活动页在独立 Activity/WebView 中运行；不把任意 H5 加载进主界面。
4. **灰度/回滚**：`activities.enabled`/`disabled` 下架；H5 内容版本回滚；App 侧 `version` 回退需重新下发旧版配置。
5. **验收**：后台/配置新增活动 → App 点检查更新 → 入口出现 → 打开 H5 → 领取走 Bridge → 关闭返回；停用后入口消失。
6. **权限**：`activity_center` 纳入功能矩阵；未勾选的角色看不到活动中心入口（与现有 `FeatureGate` 矩阵一致）。

## 7. 风险与边界

| 风险 | 说明 | 应对 |
|---|---|---|
| VA + 插件化冲突 | 双 hook（VA + Shadow/Tinker）稳定性未知 | 优先 H5/DSL；如必须原生，先 PoC |
| targetSdk 26 / Android 14 | H5/DSL 无动态代码加载，风险低；Tinker/插件化需真机验证 | 真机矩阵测试 |
| 商店政策 | Play 禁止动态代码；本项目侧载分发不适用，但需自担风险 | 仅侧载；签名校验 |
| H5 安全 | Bridge 暴露任意协议 = 高危 | 白名单 + 参数校验 + 独立 WebView |
| 弱网/离线 | H5 依赖网络 | 本地缓存 + 重试；关键活动用 DSL |
| 版控 | hotconfig.version 必须递增；旧 `hot_url` 残留 | 运营流程 + 广播覆盖 |
| 维护风险 | Tinker/RePlugin/Atlas/VirtualAPK 维护低/停更 | 不选；选活跃的 Shadow 也需自维护 |

---

## 8. 最终判定（更新版）

1. **"新增活动页面、点击更新即可、不重装"可行**，但实现方式是"页面容器化 + 配置下发"，不是 Tinker 类 dex 补丁。
2. **推荐方案 A（H5 活动页容器）**：一次发版做容器，后续活动页面全部热更；风险最低、与 VA 零冲突。
3. 若要求原生观感/离线，追加方案 B（声明式 JSON 渲染器）。
4. Shadow 插件化可新增原生页面，但成本与 VA 冲突风险高，仅在"必须原生"且 PoC 通过时考虑。
5. Tinker/Bugly/Robust 明确不满足"新增页面"；AAB Dynamic Feature 不适用侧载。
6. **本期交付边界（2026-11-06 确认）**：只更新本评估与开发计划，**不实现容器/配置链路**；实现需另立开发计划，并包含"一次发版"（容器）与 vault-server 活动托管。
