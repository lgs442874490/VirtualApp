## 一、背景与目标

`13b24f0` 把起号流程对齐网页版 0→9（钻石兜底、动作顺序、收尾、里程碑、商店补资源），实跑打通但代码审查发现 3 项 P1 与 10 项 P2。本需求的目标是：**在不改变已实跑通过的 0→9 主链路行为前提下，修复 3 项 P1 并一次性收敛 10 项 P2**，使批处理路径与单号挂点路径语义一致、资源表正确、钻石消耗可控、状态机终态完整。

## 二、范围与非目标

### 范围内

- 13 项缺陷修复：P1-1、P1-2、P1-3、P2-1 ~ P2-10。
- 涉及模块：`vault-server` 的 bootstrap 包；`app` 模块的 `WjdrEngine`（推送通道）与 `BootstrapForms`（状态文案）。
- 新增/补齐单测，覆盖审查报告第三节列出的 7 类缺口。

### 非目标

- 不做 0→9 真机/真号实跑验证（归运营部署阶段）。
- 不改起号规划器（`BootstrapPlanner`）的动作选择策略与动作序列。
- 不改建筑/家具等级表、商店商品目录、协议字段名。
- 不做单号挂点的 UI 改版；`BootstrapForms` 仅新增 `ENDED` 映射。
- 不处理审查报告未列出的新问题；发现新问题记录到后续项，不扩范围。

## 四、功能需求（参数级）

编号与审查报告对应：R-01~R-03 = P1-1~P1-3；R-04~R-13 = P2-1~P2-10。

### R-01 资源表合并顺序（P1-1）

- **触发**：任意一次 `BootstrapService.syncLoadData(loadContent)`。
- **输入**：`loadContent`（可能不含 `res`/`bag`/`items` 快照）；增量来源见 R-05。
- **行为**：
  1. 先以本轮快照构建 `BootstrapState`（**不应用增量**）；
  2. `mergeLegacyFrom(previous)` 用 `putIfAbsent` 补齐本轮缺失键；
  3. 最后应用本轮增量，按 `id` 累加。
- **参数**：
  - 资源 id `< 100000` → `resources` 表；`>= 100000` → `backpackItems` 表（沿用现状）。
  - 增量符号保留：正数加、负数减；同一 id 多条增量求和。
  - `res_update` 为 `null`/空数组时：**不清空**资源表，也不改变任何计数。
- **输出**：`resources[id] = old[id] + Σdelta`；无旧值时 `old = 0`。
- **边界**：首次同步（`previous == null`）时等价于「0 + 增量」；本轮有 `res` 快照时以快照为准再加增量。
- **验收**：给定 `old[103] = 1000`，调用 `syncLoadData({res_update:[{id:103,count:-900}]})` → `resourceCount(103) == 100`（而非 `-900`）。

### R-02 会话状态按 fpid 持久化（P1-2，方案 A）

- **触发**：单号挂点每次 `single-*` 请求新建 `BootstrapService`。
- **行为**：新建 `BootstrapSessionState`（进程级 `SHARED`，`ConcurrentHashMap<scope, Holder>`），按 `holdScope`（= fpid；单测可为空串）保存以下 8 项：

  | 字段 | 类型 | 默认 | 用途 |
  |---|---|---|---|
  | `worldKingdomInfoSent` | boolean | false | world kingdom info 是否已发 |
  | `worldFogSent` | boolean | false | fog 是否已发 |
  | `worldKingdomId` | long | 0 | fog 的 kid |
  | `worldAttempts` | int | 0 | world 连续失败次数（R-08） |
  | `finishPassDay` | String(`yyyy-MM-dd`) | "" | 收尾当日标记 |
  | `lastResUpdateSeq` | long | 0 | 增量消费序号（R-05） |
  | `failedDiamondItems` | Set\<Long\> | 空 | 永久失败的钻石道具 |
  | `resourceEnded` | boolean | false | 是否已 ENDED |
  | `resourceExhaustedAttempts` | int | 0 | 耗尽计数（R-07） |

- **参数**：
  - `scope` 为空串时（单测默认构造）→ 使用独立 store 实例，不跨测试共享。
  - 每次读取一个 scope 的 holder 时创建一次，之后复用；holder 内字段读写需线程安全（`synchronized` 或原子类型）。
  - 新增 `clearScope(scope)`：起号重跑、账号删除、批次取消时清理。
- **输出**：跨请求可见同一状态；`BootstrapService` 的 8 项实例字段替换为 store 读写。
- **边界**：同一 fpid 两个 HTTP 请求并发时，不得出现丢失更新（读-改-写需在同一临界区）。
- **验收**：
  1. 熔炉 7 + 情报推送存在时，连续两次 `single-run-next`，第二次不再发送 `req_world_kingdom_info`；
  2. 连续两次 `single-run-next`，`finishPass` 的邮箱/里程碑只执行一轮；
  3. 同一增量推送不因重建 service 被重复应用。

### R-03 建筑 51 退避与购买冷却（P1-3）

- **触发**：升级建筑返回 `51`，且熔炉等级 `>= 5`，且钻石直升（`upgradeWithDiamond`）失败。
- **行为**：
  1. `markRetry(holdKey(action), 30_000L)`（沿用 `ACTION_RETRY_MILLIS`）；
  2. 写购买冷却键 `"buy:" + holdKey(action)`，30_000L；冷却内同动作不再执行 `buyMissingResources(costs, true)`；
  3. 返回 `WAITING` + 现文案 + `preparation`。
- **参数**：退避 30s、购买冷却 30s；熔炉 `< 5` 的建筑 51 继续走既有通用 30s 退避分支。
- **输出**：`WAITING`，`errorCode=51`，`step`。
- **边界**：同一轮内多次 51 只触发一次购买；冷却到期后允许重试。
- **验收**：连续两轮 `runNext`（间隔 < 30s）对同一 51 建筑，第二轮不出现 `req_shop_buy`，也不扣钻石。

### R-04 world 推进不再每轮阻塞（P2-1）

- **触发**：每轮 `runNext`。
- **行为**：`worldAdvance()` 仅在「world 未完成」时才探测情报（`intelEvents()`）；world 两件套已完成后不再调用 `intelEvents()`/`collectNotifies`。
- **参数**：`intelEvents()` 内部 `collectNotifies(2500)` 保留，但调用次数降为「world 未完成期间每轮至多一次」。
- **输出**：world 完成后单轮 `runNext` 的额外阻塞 ≤ 1s（不含真实动作与 step 间等待）。
- **验收**：构造 world 已完成的 service，连续调用 `runNext`，断言未调用 `collectNotifies`（用假端口计数）。

### R-05 资源增量累积缓冲（P2-2，方案 A）

- **触发**：服务端推送 `notify_resource_update`。
- **行为**：
  1. `WjdrEngine` 新增 `pendingResUpdate`（`ConcurrentHashMap<Long, Long>`，id→累计 delta）；
  2. 入站监听收到 `notify_resource_update` 时，从 `{data:[{id,count}]}` 逐条累加（**不再覆盖**）；
  3. 新增 `public Map<String,Object> consumeResourceUpdate()`：原子取走当前累积并清空（返回 `{data:[{id,count}]}` 形状，保持与旧路径一致）；
  4. `BootstrapService.ProtocolPort` 新增 `default Map<String,Object> consumeResourceUpdate() { return null; }`，`EnginePort` 直通；
  5. `syncLoadData` 优先消费该通道；缺失（单测回放/旧路径）时回退 `loadContent.get("res_update")`。
- **参数**：同一 id 多条推送累加；消费即清空；`seq` 字段不再需要（由累积表语义替代）。
- **输出**：两轮之间发生的多次相同内容增量不再丢失。
- **边界**：无推送时 `consumeResourceUpdate()` 返回 `null` 或空数组，`syncLoadData` 不改变资源表；进程内未消费数据在起号重跑时清理。
- **验收**：连续推送两次 `{id:103,count:-900}`，一次 `syncLoadData` 后资源减少 `1800`（而非 `900`）。

### R-06 ENDED 终态接线（P2-3）

- **触发**：`runNext` 返回 `ENDED`（资源耗尽）。
- **行为**：
  1. `BootstrapBatchRunner.AccountState` 新增 `ENDED`；`isTerminal` 增加 `"ENDED"`；
  2. `runLeveling` 检测 `stateView.status == "ENDED"` → `entry.state = ENDED`，`entry.error = blockedReason/message`，不再等待 10 分钟；
  3. `BootstrapService.status()`/`runState()` 在 `resourceEnded == true` 时返回 `ENDED` 与对应文案；
  4. API `batchStatus` 自然透传；App `BootstrapForms` 的 `stateText`/`badgeType`/`accountStateText`/`batchStateText` 增加 `ENDED → "已结束（资源不足）"`、badge `warn`。
- **参数**：`ENDED` 为终态（不可再推进，不可自动重试）；`ENDED` 不计入 `FAILED` 统计。
- **输出**：批次入口结束，`entry.state == ENDED`；App 显示「已结束（资源不足）」。
- **验收**：3 次耗尽 → `ENDED`；`runLeveling` 遇到 ENDED 立即结束该号；`runUntil` 遇 ENDED 停止。

### R-07 资源耗尽语义对齐网页版（P2-4）

- **触发**：升级返回 `51`。
- **行为与参数**（严格对齐网页版 `BootstrapService.java:1438-1500`）：
  1. 先 `claimBackpackDiamonds()` + `topUpResources()`（含购买）；
  2. `purchase.coverable` 口径：`unsupplied.isEmpty()`；`unsupplied` = 生肉(102)/木材(103) 购买后剩余缺口 + 煤炭(104)/铁矿(105) 全部缺口（统帅商店不卖煤/铁，故有煤/铁缺口即 `coverable=false`）；
  3. 熔炉 `>= 9`：`coverable=true` → 计数清零；`false` → `resourceExhaustedAttempts++`；`attempts >= 3` 或已 `resourceEnded` → `ENDED`；否则 `WAITING`；
  4. 熔炉 `< 9`：先 `upgradeWithDiamond` 一次（**不再要求 `>= 5`**）；若熔炉 `>= 5` 再试一次；失败后：`!coverable && 熔炉 >= 7 && stall >= 10` → `ENDED`，否则 `WAITING`；
  5. `resourceExhaustedAttempts` **只在钻石直升成功时清零**（普通动作成功不再清零）。
- **输出**：`ENDED` 时带 `resourceEnded=true` 与 `unsupplied` 摘要。
- **验收**：
  1. `coverable=false` 连续 3 次（熔炉 9）→ `ENDED`；
  2. `coverable=true` 时计数不增；
  3. 熔炉 4 也尝试一次钻石升级；
  4. `buyMissingResources` 返回 `coverable`/`unsupplied`，煤/铁缺口使 `coverable=false`。

### R-08 world 推进失败重试（P2-5）

- **触发**：`req_world_kingdom_info` 或 `req_world_map_fog` 请求异常；或 kid 三种字段都取不到。
- **行为**：
  1. 失败**不置**「已发送」；`worldAttempts++`；`worldAttempts >= 3` → 告警 `FileLog.warn` 并放弃 world（置已发送，避免每轮刷）；
  2. kid 取不到 → 不发送 fog，计一次失败，文案与日志带「未取到 kingdom id」。
- **参数**：上限 3 次（与 R-08 的 `worldAttempts` 同一计数，成功即清零）。
- **验收**：连续 3 次失败后不再发请求并有告警；第 1 次失败后下一轮仍会重试。

### R-09 finishPass 当日语义（P2-6）

- **触发**：熔炉 `>= 7` 的每日收尾。
- **行为**：
  1. `finishPassDay` **仅在** `mailCount > 0 || achievements > 0 || diamonds > 0` 时置为当天；
  2. 当天日期取 `ProtocolPort.serverNowMs()`（新增 `default long serverNowMs() { return System.currentTimeMillis(); }`，`EnginePort` 转发 `engine.serverClock()` 服务器毫秒，未校准回退本机）；
  3. 时区固定 `Asia/Shanghai` 计算日期。
- **验收**：首次三项全空 → 不置位，当日后续新增邮件仍会收尾；`claimAchievements` 处于 5 分钟退避（返回 0）时不置位。

### R-10 里程碑形状回退（P2-7）

- **触发**：`req_achievement_info` 响应。
- **行为**：仅当 `infos` 为**非空数组**时按里程碑形状解析；`infos` 缺失或为空数组时回退 `list`/`achievements`/`data` 的 `state/can_get/status` 形状。
- **验收**：`{infos:[]}` + `{list:[{id,state:2}]}` → 能领 list 项；`{infos:[{id,complete:true,received:false}]}` → 只领 infos 项。

### R-11 失败钻石道具区分错误类型（P2-8）

- **触发**：`req_use_item` 打开背包钻石道具失败。
- **行为**：仅 `ProtocolException.code == 51`（道具不存在/不可用）时加入 `failedDiamondItems` 永久跳过；网络异常、限流、其它码 → 不加入，下一轮可重试。
- **验收**：抛 51 后第二次不再请求；抛 `RuntimeException`（非 51）后第二次仍请求。

### R-12 默认值统一（P2-9）

- **触发**：未显式传 `buyShopResources` 的调用方。
- **行为**：`BootstrapApi` 默认值与 `BootstrapConfig.fromMap` 默认值统一为 **`true`**；`BootstrapConfig.defaults()` 同步为 `true`。
- **验收**：`fromMap(Map.of())` 与 `batchStart` 缺参时，`buyShopResources == true`。

### R-13 代码格式（P2-10）

- **触发**：`BootstrapService.java:836` 行内两条语句合并。
- **行为**：拆成两行，缩进与文件其余方法一致。
- **验收**：该行代码风格检查通过，语义不变。

## 五、非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | R-04 落地后，world 已完成时单轮 `runNext` 不再固定阻塞约 5s；批次总时长目标由 358s 向 178s 靠拢（以实跑阶段复核） |
| 并发 | 同一 fpid 的并发单号请求不丢状态更新；不同 fpid 互不污染 |
| 兼容 | `ProtocolPort` 全部新增方法带 `default` 实现，既有单测回放端口无需改动即可编译 |
| 可维护 | 新增会话状态集中在一个类内，字段注释与审查报告编号对应；状态有 `clearScope` 清理入口 |
| 可观测 | world 放弃、购买冷却、ENDED、耗尽计数变化均有 `FileLog` 记录，含 fpid |
| 内存 | `pendingResUpdate` 与 `BootstrapSessionState` 在起号重跑/取消/账号删除时清理，不无限增长 |

## 六、异常与边界

| 场景 | 期望行为 |
|---|---|
| 推送通道不可用（default 实现） | `consumeResourceUpdate()` 返回 null → 回退 `loadContent.res_update`，行为与现状一致 |
| 服务端时钟未校准 | `serverNowMs()` 回退本机毫秒，不抛异常 |
| 同一 fpid 并发 `single-run-next` | 状态一致，不丢更新；允许重复动作但不重复消费增量 |
| 钻石余额为 0 | `coverable=false`，不发起购买，不抛异常 |
| 熔炉已达 10+ | R-07 的 `>= 9` 分支覆盖，返回 ENDED 语义 |
| `res_update` 中 id=0 | 忽略该条（沿用现状） |
| 批次被取消 | `clearScope` 清理该 fpid 状态 |
