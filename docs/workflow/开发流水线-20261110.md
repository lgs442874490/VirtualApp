# 开发流水线：需求计划 → TDD → 代码审查 → 运营部署

- 生效日期：2026-11-10
- 适用范围：本仓库所有功能开发与发布（例外见文末）
- 与 `AGENTS.md` 的关系：`AGENTS.md` 是强制规则，本文是操作细节与交接话术

## 为什么一阶段一个会话

DSH 的 Agent 预设（模式）在会话开始时绑定，**不能在会话中途切换**；换阶段必须新建会话并选择对应预设。阶段之间不共享对话历史，所以统一靠 `docs/` 下的文件交接。

## 总览

| 阶段 | 会话预设 | 技能 | 产出 | 放行条件 |
|---|---|---|---|---|
| 一、需求计划 | 需求计划 | 预设自带 | `docs/requirements/<主题>-需求文档-<yyyyMMdd>.md`、`docs/plans/<主题>-开发计划-<yyyyMMdd>.md` | 需求全部【已确认】+ 用户确认两份文档 |
| 二、TDD 实现 | 标准模式 | `tdd-loop` | `docs/qa/<主题>-TDD报告-<yyyyMMdd>.md` + 代码改动 | 测试先红后绿；验收项逐条通过；构建/静态检查通过 |
| 三、代码审查 | 代码审查 | `code-review-handoff` | `docs/review/<主题>-代码审查-<yyyyMMdd>.md` | 无 P0；P1 有明确处置；测试缺口有结论 |
| 四、运营部署 | 运营部署 | 预设自带 | `docs/deploy/<主题>-部署记录-<yyyyMMdd>.md` | 用户确认部署清单；回滚可执行并验证过 |

同一个主题的四份文件使用**同一个主题名**，方便跨会话串联。

## 一、需求计划

- 新建会话，选择「需求计划」预设。
- 工作规则：需求拆到参数级（输入/输出/行为/边界/权限/非功能/验收）；不清楚、不确定的绝不猜测，直接反问；需求全部【已确认】后才产出文档，确认前禁止写任何代码。
- 产出：需求文档 + 开发计划，**必须同时落盘**，只停留在对话里视为未完成。
- 放行：需求无【不清楚】项 + 用户确认两份文档。
- 交接：会话结尾会给出一段可直接复制的交接提示词（新建会话 → 选择「标准模式」→ 引用两份文件路径）。

## 二、TDD 实现

- 新建会话，选择「标准模式」，加载 `tdd-loop` 技能（输入 `/tdd-loop`，或直接说"加载 tdd-loop"）。
- 输入：需求文档、开发计划、`AGENTS.md`（分支命名、commit/merge 人工确认、语言约定）。
- 流程：对计划中每个可验证条目按 **红 → 绿 → 重构** 推进；先写会失败的测试，再写最小实现，测试全绿才进入下一条；不删除、不跳过、不弱化既有测试。
- 产出：代码改动 + `docs/qa/<主题>-TDD报告-<yyyyMMdd>.md`（用例、对应验收项、红→绿证据、全绿输出、遗留项）。
- 放行：验收项逐条可判定通过；相关测试与构建全绿。
- 按 `AGENTS.md`：先建分支（`{add|modify|delete}/{功能简述}-{yyyyMMdd-HHmm}`），commit 前等用户确认。

## 三、代码审查

- 新建会话，选择「代码审查」预设，加载 `code-review-handoff` 技能（输入 `/code-review-handoff`）。
- 输入：变更范围（优先直接读 `git diff`，不依赖转述）、需求文档、开发计划、TDD 报告、审查边界。
- 审查顺序：潜在运行错误 → 逻辑错误 → 边界条件风险 → 测试覆盖缺口；可读性等一律后置。
- 输出：按 P0/P1/P2 排序，每项带 `文件路径:行号`、问题、影响、依据；只报有证据的问题。
- 产出：`docs/review/<主题>-代码审查-<yyyyMMdd>.md`。
- 放行：无 P0；P1 有明确处置；测试缺口有结论。审查默认只读，确需改代码先列计划等确认。

## 四、运营部署

- 新建会话，选择「运营部署」预设；**先把权限预设切成 `read-only` 或 `workspace-write`**，不得沿用全权限默认值。
- 输入：代码审查结论、部署目标与环境、待发布版本/提交。
- 流程：只读盘点 → 部署清单（目标与环境 / 前置检查 / 执行步骤 / 回滚方案 / 监控与验收 / 风险与沟通）→ 用户确认清单 → 逐步执行并逐步报告。
- 产出：`docs/deploy/<主题>-部署记录-<yyyyMMdd>.md`（清单、执行记录、回滚验证结果、遗留项）。
- 放行：用户确认部署清单；破坏性操作前已给出回滚命令并获确认；回滚已验证可执行。

## 交接话术模板

**需求计划 → TDD**

```text
加载 tdd-loop，按 @docs/plans/<主题>-开发计划-<日期>.md 实现，需求见 @docs/requirements/<主题>-需求文档-<日期>.md。
遵守 AGENTS.md：先建分支，commit/merge 前找我确认。
```

**TDD → 代码审查**

```text
加载 code-review-handoff，审查 <分支> 相对 master 的 diff。
需求见 @docs/requirements/...，计划见 @docs/plans/...，测试报告见 @docs/qa/...。
```

**代码审查 → 运营部署**

```text
发布 <版本/提交> 到 <环境>。审查报告见 @docs/review/...，按运营部署模式先给部署清单，我确认后再执行。
```

## 目录约定

- `docs/requirements/` 需求文档
- `docs/plans/` 开发计划
- `docs/qa/` 测试 / TDD 报告
- `docs/review/` 代码审查报告
- `docs/deploy/` 部署清单与执行记录
- 目录不存在时创建；文件名带主题与 `yyyyMMdd`。

## 例外与豁免

- 纯文档、纯文案、单文件小修：可跳过 TDD 与部署阶段，但需求确认与自审仍要留痕。
- 线上事故修复：允许先修复再补记录，但必须在同一主题下补齐需求/计划/审查文档，并在提交说明中注明原因。
- 任何阶段发现需求未确认或与现状冲突：退回需求计划阶段，不得跳过确认直接实现。
