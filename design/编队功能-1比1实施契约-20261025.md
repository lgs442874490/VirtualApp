## 0. 架构决策（重要，所有包按此写）

| 数据 | 事实源 | 说明 |
|---|---|---|
| 编队库（我的编队 8 内置 + 自定义） | **App** `SharedPreferences("formation_library")`，随 params `formation_library` 字符串上传服务端 | 保持现有单向契约，不新增 App→服务端写接口；服务端只读解析 |
| 自动编队全局比例 | App 库内 `automatic_settings`（同时接受服务端目录下发兜底） | 保存即上传 |
| 英雄目录 / 出征容量 / 游戏编队 / 编队记忆状态 / 雪猿容量 | **服务端目录 v2**（state 键）→ App 读 | 服务端从游戏推送采集 |
| 游戏内编队 | 服务端解析 `notify_soldier_init.prefab` → 目录 `gameFormations[]`（只读镜像） | App 展示只读；编辑 = 副本（本地 CUSTOM） |
| 编队记忆 保存/恢复 | **服务端动作**（游戏协议 `req_soldier_set_prefab`，500ms 间隔） | App 通过 `/v1/vault/role-action` 调 `formation.memory-save` / `formation.memory-restore` |
| 巨熊模板（30 套）与一键编队 | **App 本地**（模板数据内置 asset；缺失英雄用目录校验），结果写回 App 编队库/功能参数 | 与网页版 user-visible 行为一致 |

**不做**（网页版也没有）：编队数量上限、编队默认标记、记忆自定义槽、模板编辑、编队级兵种等级控件、HTTP 403 表占用。

App 编队库仍按 `fpid:sid` 隔离；**uid** 仅用于服务端 state 键（同 fpid:sid 多角色）。

### 2.1 `FormationModel`（编队实体 v2）

```java
public final class FormationModel {
    public long id;                 // >0 自定义/内置；<0 游戏编队(=-slotId)；0=新建未保存
    public String name = "";        // 显示名（≤30 字符）
    public String source = "CUSTOM";        // CUSTOM | GAME
    public String templateKey;              // ONE_INFANTRY|RANDOM_HERO_ONE_SOLDIER|GATHER_WOOD|GATHER_IRON|GATHER_COAL|GATHER_MEAT|BEHEMOTH|WILD|null
    public boolean builtIn;
    public final List<Long> heroIds = new ArrayList<>();   // 顺序=上阵顺序，≤3
    public Long captainHeroId;              // 必须 ∈ heroIds；null=用 heroIds[0]
    public String allocationMode = "MANUAL";// MANUAL | PERCENTAGE
    public long infantry, lancer, marksman; // 兵力数
    public int infantryRatio, lancerRatio, marksmanRatio;  // 0..100
    public long totalSoldiers;              // 三兵种合计（派生）
    public boolean allHeroesAvailable;
    public final List<Long> unavailableHeroIds = new ArrayList<>();
    public long version = 1;
    public long updatedAt;

    public FormationModel copy(); public long soldiersTotal();
    public boolean isGame(); public boolean isBear();  // isBear = name.startsWith("巨熊·")
    public String effectiveCaptain();      // captain 合法返回之，否则 heroIds[0] 或 null
    public JSONObject toJson(boolean compact);  // compact=false 写全量 v2 字段；compact=true 仅旧字段（服务端兼容）
    public static FormationModel fromJson(JSONObject o); // 容忍旧字段/别名
}
```

### 3.3 `FormationLibrary`/`FormationSpec` 新字段（T3，向后兼容）

`FormationSpec` 新增：`captainHeroId`(Long)、`allocationMode`(String, MANUAL/PERCENTAGE)、`source`(CUSTOM/GAME)、`templateKey`(String)、`builtIn`(boolean)、`version`(long)、`updatedAt`(long)、`teamSize`(int=上限3)。
`FormationLibrary` 新增：`automaticSettings` int[3]；`formations` 解析允许 `id<0`（GAME 源，只读；ROLE 绑定不允许选 GAME → 用副本）；`parseSpec` 缺省：captain=heroIds[0]，allocationMode= hasExplicitSoldiers()?MANUAL:PERCENTAGE。
**兼容**：旧 App 只写 `hero_ids/soldiers/ratio/total` → 全部缺省推导，现有行为不变。

### 3.4 `FormationResolver`（T3）改造要点

- ROLE：校验（英雄 ≤3、无重复、职业唯一、`available`/黑名单）；失败 → 尝试 `formation_ids[]` 下一候选；仍失败 → SKIP 并写清原因（不再下发非法 payload）。
- 兵量：显式兵量 > 容量 → **按容量同比缩放**（`scale = capacity/total`，各兵种 floor，余数补盾），不再 SKIP；库存不足 → 按库存缩放；`capacity<=0` → 不夹取+WARN（保持旧行为）。
- AUTO：候选人 `profession != 0`，上限 `min(3, autoHeroLimit)`；415 → 递减 1（下一轮生效）；406 → `SOLDIER_SCALE_PCT` 75→50→25；成功后复位（成功回调由 T3 在 `resolveOutcome` 出口统一处理）。
- 黑名单：ROLE 也读 `HeroAvailability.isBlocked`，命中 → 记 `HERO_AWAY`，按 `formation_fallback`（params，默认 `SKIP`）决定回退 AUTO 或 SKIP。
- 多队列同轮英雄预留：`usedHeroes` 入参（ServerFieldTasks.gatherV2 传入）。
