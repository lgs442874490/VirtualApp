### 3. 建筑/家具数据形状

```
loaddata.building_info = {
  "302": { bid:302, base:{ lv:1, status:0,
             furniture:{ "302000401": { fid:302000401,
                                        base:{conf_fid:401, type:24, lv:1},
                                        sid_list:[3,4] } } } }
}
```
- **家具（=生产工位）在 `base.furniture` 里**（不在顶层）
- `sid_list` 是**真实上岗状态**（`survivor.fid_work` 恒为 0，不可信）
- 家具 `base.type`：24=伐木/采矿类工位，9/30/42 其它生产工位
- 委任协议：`req_survivor_send_or_fired{sid, fid_work, type:1}`，`fid_work` 用家具的 `fid`

## 四、⚠️ 两个待处理卡点（新会话重点）

### 卡点 A：51 动作会让主线 WAITING 不前进（优先级最高）

**现象**：
```
51 缺口明细 升级 大熔炉 到 8 级：资源103[需120000/普通1600/安全3860000]
→ status=WAITING「资源或道具不足，等待补充后重试」
→ 之后每轮重复同一动作，主线不再推进
```

**已查明**：
- 资源**够**（安全木材 386 万 > 需求 12 万）
- 直接调 `req_upgrade_furniture{bid:302,conf_fid:401,add_lv:1}` → `{code:0, lv:2}` **成功**
- 所以 51 是**特定动作自身的前置限制**（实测是铁矿厂家具 601），不是通用资源问题

**已做**：`BootstrapService.upgradeRejected` 里加了 30 分钟长退避（`holdKey`）

**未做（新会话要补）**：**planner 没有联动 hold 集合**
- 现在：`markRetry(holdKey)` 只是不再重试，但 planner 下一轮**仍然选同一个动作** → 还是 WAITING
- 需要：`BootstrapPlanner` 或 `runNext` 的建筑分支里，**过滤掉被 hold 的动作**，让 planner 选下一个可行动作
- 建议改法：在 `runNext` 拿到 `plan` 后遍历 `plan.actions()`，跳过被 hold 的；全部被 hold 才 WAITING
- 相关位置：`BootstrapService.runNext` 末尾的建筑分支 + `BootstrapPlanner.plan`

### 卡点 B：煤/铁获取慢（次要）

- 商店**不卖**煤(100133)/铁(100143)：实测 `code=801`（新版注释也写「统帅商店不售卖」）
- 只能靠：煤矿厂/铁矿厂产出 + 任务奖励 + 兑换码奖励箱
- 熔炉 8 级需要 煤 25000 + 铁 6300，产出需要时间
- **可选优化**：优先升级煤矿厂/铁矿厂 + 把更多幸存者委任到煤铁工位
