## 二、发现（按优先级）

### P1-1 res_update 与旧资源合并顺序错误：无 `res` 快照的轮次会把增量从 0 起算

- **位置**：`vault-server/src/main/java/com/carlos/vaultserver/bootstrap/BootstrapState.java:127-132`（先 `applyResources(res)` 再 `applyResourceUpdate`）、`BootstrapService.java:398-401`（`fromLoadData` 之后才 `mergeLegacyFrom(previous)`）、`BootstrapState.java:250-257`（`putIfAbsent` 只补“缺的键”）。
- **问题**：`fromLoadData` 先建新表并应用增量，增量写在 **0** 的基线上；随后 `mergeLegacyFrom` 用 `putIfAbsent` 合并旧值，而该键已存在（值=增量），旧库存永远不会被并入。即“旧值 + 增量”被算成“0 + 增量”。
- **影响**：只要某轮 `req_loaddata` 合成结果里没有 `res`/`bag`（`notify_resource_init` 未到或重连后丢失，runner 用 `putIfPresent` 合成，缺失即不 put），资源表就会被写成纯增量值，常见为**负数或严重偏小**。后续 `missingOf`/`costAmount`/钻石预算全部基于错误资源，导致：商店买错量、误判 51、51 缺口明细失真。触发概率中等（依赖推送时序），后果是钻石与批次时间损失。**P1（高）**
- **依据**：`applyResourceUpdate` 对 `resources.merge(id, delta, sum)`（`BootstrapState.java:218-230`），`mergeLegacyFrom` 对 resources `putIfAbsent`（`BootstrapState.java:252-254`）；`syncLoadData` 顺序（`BootstrapService.java:398-401`）。复现思路：`syncLoadData({res_update:[{id:103,count:-900}]})` 后 `resourceCount(103) == -900`，而非“old − 900”。交接中 601 卡点根因（“资源表只增不减”）说明该链路本就敏感，本次接入后正确性依赖 `res` 每轮必在。

### P1-2 单号挂点每请求重建 service，本提交新增的会话级状态全部失效

- **位置**：状态字段 `BootstrapService.java:328-341`；使用点 `577-614`（world）、`620-646`（finishPass）、`387-397`（res_update 去重）；重建点 `BootstrapApi.java:489-497`。
- **问题**：`serviceOf` 每次 `single-*` 请求都 `new BootstrapService(...)`，只有 hold 表（`BootstrapHoldStore.shared()`）按 fpid 共享。本次新增的 `worldKingdomInfoSent`/`worldFogSent`/`worldKingdomId`/`finishPassDay`/`lastResUpdateSignature`/`failedDiamondItems`/`resourceEnded`/`resourceExhaustedAttempts` 都是实例字段，跨请求即丢。这与 `BootstrapApiTest.java:316-321` 已确立的“单号每次重建 + hold 跨请求共享”设计相冲突。
- **影响**：熔炉 ≥7 且情报推送已到达（`port.notify` 非 null，单号 `EnginePort.notify` 直通引擎最近一次推送）时：
  1. `single-run-next` 每次调用都走 `worldAdvance` 的 `!worldKingdomInfoSent` 分支，**只发 `req_world_kingdom_info` 并返回 STARTED**；`worldKingdomId` 随实例丢失，`worldFogSent` 永不置位，`req_world_map_fog` 永不发送，后续情报/收尾/主线全部不放行——单步模式对该段等级**功能卡死**。`single-run-until` 每次请求固定重发 kingdom info + fog 两步。
  2. `finishPassDay` 丢失 → 每次请求都重新执行 4 轮邮箱 + 里程碑 + 背包钻石（重复网络请求）。
  3. `lastResUpdateSignature` 丢失 → 每次请求把“最近一次”增量重新应用一遍；叠加 P1-1，单号路径资源表几乎不可用。
  4. `failedDiamondItems`/`resourceEnded` 丢失 → 失败钻石道具每请求重试、ENDED 状态不持续。
  批处理路径（每号一个实例，`BootstrapBatchRunner.java:410-413`）不受影响，所以本次 0→9 实跑暴露不出来。**P1（高）**
- **不确定项**：若单号会话始终未收到 `notify_intelligence_info/events`，则 `worldAdvance` 首行即返回 empty，第 1 条“卡死”不出现；其余三条仍是确定的重复请求/重复应用问题。

### P1-3 51 建筑钻石兜底失败后无退避，每轮强制按动作全量成本买资源

- **位置**：`BootstrapService.java:875-907`（建筑 51 分支所有出口都 `return`，**没有任何 `markRetry`**）；`1018-1025`（`topUpResources` 内 `buyMissingResources(costs, true)`）。
- **问题**：家具 51 分支会 `markRetry(holdKey, 30s)`（`908-923`），但建筑 51 分支直接返回 `WAITING`，不写 hold；planner 侧不会过滤该动作，下一轮（runner 间隔 5s）再次执行同一动作 → 再次 `topUpResources` → 再按**动作成本全量**（`costAmount` 忽略库存，`1053-1056`）购买资源包。
- **影响**：熔炉 5–8 且建筑 51 持续（服务端 51 未必是资源原因，也可能是前置/道具）时，每 5s 消耗一次钻石购买（受“钻石余额/200 包”上限约束，`1164-1194`，即最多把钻石花光）；批次靠 `MAX_IDLE_ROUNDS`（10 分钟）兜底判 FAILED。实跑证据“商店买木材 3 次”证明该路径生效，资源长期不足时会被放大成**钻石浪费 + 10 分钟空转**。**P1（中高）**
- **补充**：本提交把“家具 51 短退避 30s”实现成了**所有非建筑分支**的 51 都 30s（熔炉 <5 的建筑 51 也落到 `915` 行），与交接文档“仅家具改为 30 秒”的表述不一致。

### P2-1 熔炉 ≥7 后每轮 runNext 固定多阻塞 5 秒（耗时回归主因）

- **位置**：`BootstrapService.java:578`（`worldAdvance` 首行就调 `intelEvents()`）、`2161`（`claimIntelligenceRewards` 再调一次）、`2253`（`collectNotifies(2500)`）；`collectNotifies` 实为 `Thread.sleep`（`app/src/main/java/com/carlos/vault/wjdr/WjdrEngine.java:666-672`）。
- **影响**：即使 world 动作早已完成，每轮 runNext 仍先睡 2.5s（world）+ 2.5s（情报）≈ 5s，叠加 runner 的 5s 轮间隔 → 每轮约 10s。这是交接中“358s vs 178s”的可解释部分，也放大了批次总时长。**P2（性能，可量化）**

### P2-2 res_update 去重按字符串签名，内容相同的两次真实增量会被吞掉

- **位置**：`BootstrapService.java:387-397`。
- **问题**：`String.valueOf(resUpdate)` 作为唯一签名且只保留“上一次”。若服务端先后两次推送**内容完全相同**的增量（如两次同价消耗/同额奖励），第二次会被判定为重复而丢弃。
- **影响**：资源表偏高（少扣/少加），51 时缺口算小、买资源不足。不确定项：取决于服务端是否会重复相同增量；若 push 带 seq/时间戳，应改用它做键。**P2（中）**

### P2-3 ENDED 是新增状态但未接线：批次按“起号停滞 FAILED”处理，status 仍显示 READY

- **位置**：`BootstrapService.java:453-455`、`887-899`；判定侧 `BootstrapBatchRunner.java:698-752`；状态侧 `BootstrapService.java:2833-2844`。
- **问题**：`runLeveling` 只认 `furnace >= target`（SUCCESS）与 `started == 0` 后的 `blockedReason/message` 关键字；没有 `ENDED` 分支。`status()`/`runState()` 也没有 ENDED。
- **影响**：① `target<=9` 且熔炉≥9 时批次先判 SUCCESS，所以批处理中 ENDED **实际不可达**（死路径，与交接“补 P1 目标 10/ENDED”相符）；② 若单号/未来 target>9 触发 ENDED，批次会用 `stateView.blockedReason`（可能含“资源或道具不足”）走等待分支空转 10 分钟，或按“起号停滞”FAILED，语义与文案都不对；③ UI 仍显示“可以执行下一步”。**P2（中）**

### P2-4 资源耗尽计数与网页版语义不一致

- **位置**：`BootstrapService.java:798`（任何成功动作都 `resourceExhaustedAttempts = 0`）、`878-907`（无条件 ++、仅 ≥9 判 3 次）。
- **问题**：对照网页版（`design/research-20261111/wjdr-tool-new/modules/bootstrap/service/BootstrapService.java:1438-1500`）：(a) 首次 51 即无条件 `upgradeWithDiamond`（本地要求熔炉≥5 才尝试）；(b) 仅在 `purchase.coverable == false` 时累加 attempts（本地不区分是否可覆盖）；(c) 熔炉 ≥7 且 stall≥10 即 ENDED（本地只有 ≥9 且 3 次）；(d) 只有钻石成功才清零（本地任何成功动作都清零）。
- **影响**：① 熔炉 <5 的建筑 51 本地不尝试钻石、改 30s 退避，可能比网页版慢或卡；② 穿插辅助动作时 3 次计数被清零，ENDED 永不触发，退化成 10 分钟空转；③ 不可覆盖与可覆盖混为一谈，可能过早 ENDED（熔炉 9）。**P2（中）**

### P2-5 worldAdvance 失败也置“已发送”，且 kid 解析失败后 fog 永不重试

- **位置**：`BootstrapService.java:594-599`、`600-612`。
- **影响**：一次网络抖动/协议失败即整会话放弃 world 推进；`kid/kingdom_id/kingdom.id` 都取不到时 `worldKingdomId=0`，fog 永不发送也不告警。**P2（低中）**

### P2-6 finishPass 的“当日一次”语义过粗

- **位置**：`BootstrapService.java:620-646`。
- **问题**：`finishPassDay = today` 在判断前无条件赋值：① 首次三项全空也记为“今天已收尾”，当天后续新增邮件/里程碑不再走收尾（常规轮 `489/496/505` 有兜底，故实际影响有限）；② `claimAchievements()` 若正处 5 分钟退避（返回 0），也被记为完成；③ 用 JVM 默认时区 `LocalDate.now()`，与游戏日重置/服务端时钟不一致时会提前或延后一天。**P2（低中）**

### P2-7 claimAchievements 的 infos 形状判定排他，7902 依赖退避兜底

- **位置**：`BootstrapService.java:1586-1601`、`1608-1618`。

### P2-8 failedDiamondItems 对临时失败也永久跳过

- **影响**：`catch (Exception)` 不区分 51（道具不存在）与网络/限流异常，一次抖动即本会话不再开钻石道具，可能直接削弱 8→9 钻石兜底的资金。**P2（中低）**

## 三、测试覆盖缺口

现有新增测试（`BootstrapServiceTest.java:321-370、767-782、904-933`、`BootstrapStateTest.java:261-273`）覆盖了：钻石兜底成功/失败、finishPass 只做一次、res_update 单次去重、增量正负应用、world 首次消费。**未覆盖**：

1. **无 `res` 快照 + `res_update`** 的合并顺序（P1-1 的直接复现用例；现有用例第二次喂入的相同增量被去重分支提前移除，掩盖了顺序缺陷）。
2. **单号挂点跨请求**：熔炉 ≥7 + 情报推送存在时 `single-run-next` 的 world/finishPass/去重/失败钻石行为（P1-2）。现有 `BootstrapApiTest` 只覆盖熔炉 2 级与 hold 跨请求。
3. **51 建筑钻石兜底失败后的退避与购买次数**（P1-3）：如断言第二次 runNext 不应再次 `req_shop_buy`/不重复扣钻。
4. **ENDED 全链路**：3 次耗尽 → ENDED；`runUntil` 遇到 ENDED 停止；批次 `runLeveling` 对 ENDED 的判定（P2-3）。
5. **`buyMissingResources(costs, true)`**（force 模式）无任何测试，现有两个用例只测 `force=false` 包装方法（`BootstrapServiceTest.java:1199-1233`）。
6. **worldAdvance 的失败路径/kid 缺失/fog 发送**（P2-5）无测试。
7. **finishPass 跨日与退避交互**（P2-6）、**claimAchievements 7902 与 infos 空数组回退**（P2-7）、**resourceExhaustedAttempts 被成功动作清零**（P2-4）均无测试。

风险结论：本次改动的 P0 行为（0→9 主链路）有实跑 + 单测双证；但**边界与单号路径几乎无测试**，P1-1/P1-2 属于“当前实跑掩盖、条件变化即复发”的类型。

## 四、修复建议（单独标注，不改变上述问题描述）

1. **P1-1**：在 `fromLoadData` 内先按“快照 + 旧值合并”构建资源基表，再统一应用 `res_update`；或把 `mergeLegacyFrom` 移到 `applyResourceUpdate` 之前（最小改法）。补一条“无 res 快照 + 增量”单测。
2. **P1-2**：把 world/finishPass/res_update 去重/失败钻石/ENDED 状态放进按 fpid 共享的存储（可扩展现有 `BootstrapHoldStore`，与 hold 同寿命）；若暂不做，至少在交接/文档中显式声明“单号挂点不支持这些对齐语义”，并给 `single-run-next` 降级文案。
3. **P1-3**：建筑 51 钻石失败分支写 30s hold（复用 `holdKey`），并对 `force=true` 购买加冷却/单轮预算；参考网页版 `coverable` 语义，只在“买完可覆盖仍失败”时计数。
4. **P2-2**：去重键改用推送自带的 seq/时间戳；若无，改为“每次 `syncLoadData` 消费后从推送通道清除 `res_update`”，避免同内容误判。
5. **P2-3/P2-4**：`ENDED` 在 `BootstrapBatchRunner` 与 `status()/runState()` 里作为终态处理；耗尽计数只在钻石成功/可覆盖时清零，补齐 ≥7 的 10 次阈值与 `<5` 也尝试一次钻石（对齐网页版）。
6. **P2-6**：`finishPassDay` 只在至少一项实际完成时置位；日期取服务端时钟（`GameServerClock`）。
7. **P2-1**：`worldAdvance` 不再每轮调 `intelEvents()`（用缓存快照或只在 world 未完成时探测）；这是压低 358s→接近 178s 最直接的改动。
8. **P2-10**：修复 `BootstrapService.java:836` 的格式。

## 五、放行结论

**不通过（阻断）**。无 P0，但存在 3 项 P1：

- 阻断项 1：P1-1 资源表合并顺序（数据正确性）。
