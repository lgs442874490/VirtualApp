## 三、P0（已修复）

### P0-1 导出 token 在入口无号 ID 时，把全局 live 的任意账号绑定到本入口
- **原位置**：`app/src/main/java/com/carlos/vault/EntryDetailActivity.java` 原 1685-1697（`doExportToken`）；`VaultEngine.extractCurrentSession` 1169-1179；`AccountStore.setToken` 684-697。
- **问题**：只比较 `st.fpid` 与 `acc.fpid`；`acc.fpid` 为空时直接 `setToken(acc.id, st.fpid, st.token)`，且全程无 `store.getLiveEntryId() == acc.id` 校验。`setToken` 还会 `pushToken` 到服务器。
- **影响**：在原生登录入口导出时，若 live 里是别人的号，会把别人的 `fpid+token` 写进本入口并上传服务器；后续启动注入该 token，覆盖 live 中原账号的登录。
- **修复**（`EntryDetailActivity.java:1677-1740`）：
  - 导出前硬校验 live 归属必须是本入口，否则拒绝导出、不杀游戏；
  - 读会话后按最新归属二次判定；
  - live 登录号与入口记录不一致 → 拒绝导出（不复制到剪贴板）；
  - 原生入口（`fpid` 空）只复制、不自动写入本入口。

### P0-2 「设置 token」静默换号，注入覆盖原账号
- **原位置**：`EntryDetailActivity.java` 原 1570-1594；`AccountStore.setToken` 684-697；`VaultEngine.invalidateEntrySession` 1821-1832。
- **问题**：粘贴任意 `号ID----token` 即改写入口 `fpid+token` 并摘掉 live 归属，无任何“换号”确认；下次启动必然重新注入，原账号登录现场被替换。
- **修复**（`EntryDetailActivity.java:1570-1616`）：
  - 入口已有号且粘贴的是另一个号 → 弹「确认换号」，明确提示会替换游戏内登录现场；
  - 原生入口首次绑定不拦截（正常操作）；
  - 落库逻辑抽为 `applyToken`，保留原有 `invalidateEntrySession` 与重读 `acc` 的修复。

### 本次新增的防回归资产
- `app/src/main/java/com/carlos/vault/TokenOwnership.java`：导出决策与换号判定纯逻辑。

## 四、P1（未修复，按优先级）

### P1-1 原生登录入口运行自动化被“没有 token”硬挡
- **位置**：`EntryDetailActivity.java:1500-1505`、`469-474`；`HomeActivity.java:2919-2931`、`2941-2948`。
- **问题**：这些入口只查 `acc.token`，不尝试从 live 的 `session_key` 回填；当前 HEAD 不存在 `adoptLiveSessionIfPossible`。
- **影响**：原生登录型入口永远无法运行自动化，即使游戏已登录、live 有可用会话。
- **依据**：相关修复 `6c51c45` 只存在于未合并分支 `modify/native-login-auto-discover-20261105-1211`。
- **修复建议**：见交接文档 §4（按需回填 + 双门禁 + 确认提示，不可 onResume 静默回填）。

### P1-2 `syncSessionOwner` 用带进程门的读取，游戏退出后恒为空
- **位置**：`VaultEngine.java:1582-1597`（1584 行 `readLiveSessionFpid`）；对比 `captureGuardReason` 使用的 `readLiveSessionFpidOnDisk`（1412-1437、1883）。
- **问题**：`launchEntry` 的 keepLive 分支（1732-1734）与 `autoSaveEntrySnapshotLocked`（1346）都在 `killGameAndWait` 之后调用 → 恒空 → 归属同步实际不生效。
- **影响**：入口 fpid 与 live 会话不一致时无法自动校准，是“同一时刻不同页面显示不同号”的土壤。
- **修复建议**：改用读盘版本并校验 `liveOwner`，与 `captureGuardReason` 统一口径；补 JVM 用例。

### P1-3 导出源是“全局 live 当前登录账号”，不是“本入口账号”
- **位置**：`EntryDetailActivity.java:1665-1740`；`VaultEngine.extractCurrentSession` 1169-1179。
- **现状**：P0-1 已加归属硬门，实际导出源已被限制为“本入口的 live”；但 `extractCurrentSession` 本身仍无 owner 参数，未来若新增调用方仍可能误用。
- **修复建议**：给 `extractCurrentSession` 增加 entryId/owner 入参或返回值携带 owner，从 API 层消除误用面。

### P1-4 `readCurrentSession` 只认 `account_session_cn` 单键、只取第一个匹配
- **位置**：`VaultEngine.java:1124-1161`（1140-1145）。
- **风险**：会话若写其它键或多账号并存，会读不到/读到旧值；需真机 prefs 样本确认，标注不确定性。

## 五、P2（后置）

1. `doExportToken` 的 `onPostExecute` 在主线程执行 `store.setToken`（写盘 + 网络），有卡顿风险。
2. 导出/设置 token 无日志（fpid 可记、token 严禁），串号现场难排障。
3. UI 门禁只查本地 `acc.token`，与服务器模式“服务器已有 token”不一致，可能误拦。
4. 文案不统一（“该账号没有可用 token”/“当前账号没有 token”），且未给出下一步动作。
