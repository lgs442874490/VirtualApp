## 五、与审查报告 §8 建议的偏差（供二次审查重点复核）

1. **154 不复位家具 51 计数**（审查 §8 建议「153/154/UPGRADE 成功三处均复位」）。
   - 理由：601 死循环的实测形态是 `UPGRADE 51 → 本地重置 0 → CREATE 154 → 再 UPGRADE 51`；
     若 154 复位，计数每轮被清零，永远到不了上限，P1-1 的终态检测在生产**永不触发**，与本次修复目标冲突。
   - 现状：153（阶段切换）与 UPGRADE 成功复位；154 只标记等级 1、不复位，已由用例
     `upgradeFurniture_51_154DoesNotResetCounter` 固化（二次审查 §8-1 缺口已补）。
2. **「服务端观测等级持续低于本地等级才计数」未做成计数门控**（审查 §8 建议）。
   - 理由：真实 601 样本中服务端观测等级与本地一致（均为 1），若以此为门控会**漏掉唯一已证实的死循环样本**。
   - 现状：计数仍覆盖所有 `UPGRADE_FURNITURE` 51；原因区分通过「文案不再臆测原因 + `[诊断51]` 打印 stall/limit 与家具表」实现。
   - 若二次审查认为必须门控，可在拿到更多真机样本（观测等级 < 本地等级 / 相等 / 缺失）后再定。
3. **单号挂点（`single-*`）路径的 601 检测不生效**（二次审查 P2-2 补充）。
   - 单号挂点每请求 `new BootstrapService`，不仅 `terminalFailure` 不跨请求，`furnitureStall` 计数也不跨请求，
     且单次请求内同一动作受 30 秒 hold 限制，**单号路径永远累计不到 10 次**。
     本修复只对批次路径生效；部署验证/运行必须走批次模式，已在 `BootstrapApi.serviceOf` 注释登记。
4. **P1-3 最终处置：回退固定 salt（方案 b）**（二轮审查 P1-2 要求书面裁决，改为回退闭环）。
   - 恢复 `BootstrapService.createRole` 时间戳盐与 `DeviceFingerprint`「一角色一设备」契约；
     不再需要用户对「同账号同区多角色同设备」作书面接受。
   - 补 `DeviceFingerprintTest` 固化「同盐可复现 / 不同盐不同设备 / 同角色稳定」。
   - 若后续仍要「建号重试不漂移设备」，作为独立需求评审并登记已知限制后再改。
