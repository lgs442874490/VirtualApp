## 0. 结论摘要（TL;DR）

1. **"通用信息"在协议层分布很散，但权威源高度集中**：8 类数据中 6 类的权威源是"登录一帧 `notify_*_init` + 后续 `notify_*` 增量"，只有 2 类（巨熊预约、巨兽 auto_join 状态）需要低频 `req_*` 兜底。**没有轮询的必要**。
2. **队列**：容量是客户端派生值（`MarchCapacityState.worldMarchCapacity`，科技 1007/1020/1027 + VIP≥6 + buff 10505 + extra_march + 1），**不是** `notify_world_player_init.world.capacity`；占用 = `notify_world_player_init.march_info[]` + `notify_player_march_*` + `notify_mass_march_*`（type=99 计数）。本仓库三处实现（`FieldTasks.java:208-214`、`ServerFieldTasks.java:600-608`、`ServerTasks.java:4146-4156`）全部读错 → 恒回退 3/0。**引用 queue-researcher 同源结论**（`/tmp/vault-research/queue.md` §1/§3/§5）。
3. **钻石/资源**：`notify_resource_init`（id 101 钻石、102 肉、103 木、104 煤、105 铁、106 钢、110 联盟币…）+ `notify_resource_update{type:"add"|"del",data[]}` 是权威；`notify_recover_resource_init/update`（map 形，含 **201 体力**、203 免费盾、205 联盟捐献）；`notify_produced_resource_update`（全日志 19h 内 74 次，是心跳之外最高频 notify；突发时同一秒多条，含工位 `workstations[]`）是"当前产出量"；`notify_backpack_init/update` 是道具（资源包 100011-10014x、随机箱 100091/100094、自选箱 100101/100104、体力罐 610002、加速 200xxx、护盾 3023xx）。
4. **体力**：权威源 = `notify_recover_resource_init/update` 的 **id=201** 项 `{count,max_count,recover,next_calc_ts,interval}`；`notify_resource_init` id=201 与 `notify_resource_update` id=201 增量也维护它（网页 `resourceInit`/`resourceUpdate`）。**不在** `notify_world_player_init` / `notify_world_npc_init` / `req_players_base_info`（已按 schema 逐字段核实）。**meat(102)/wood(103) 是资源，不是体力**。当前体力 = count + 已过 interval 恢复量（`BehemothAccountState.currentStaminaLocked:2245-2262`），`count` 可超过 `max_count`（真实样本 1035/200）。
5. **情报**：`notify_intelligence_info` 是权威全量（`radar_level/radar_exp/power_level/project_start_time/events{}/next_event_time`）；`notify_intelligence_events` 增量 upsert、`events_del{ids[]}` 删除、`battle_result{id,success}` 改战斗结果、`power_info` 改雷达。事件类型由 `event_id` 经 `DailyIntelligenceEventCatalog` 映射（1 怪物/2 营救/3 英雄之旅/11 活动巨兽/100 冒险巨兽），派遣消耗 10 点（营救/英雄之旅 12 点）。**每日保留体力 50** 的依据是 `DailyIntelligenceService.staminaReserve():256-263`（开启情报即保留 50；狩猎暂停时 0），由巨兽消费（`DailyBehemothService:152,609`，`required = reserve + 25`）；本仓库对应 `ServerTasks.staminaReserve=50`（`:4529,4559`）。
6. **巨兽**：`notify_world_npc_init/update`（`monster_max_lv/last_daily_time/join_daily_count{}/master_daily_count{}/expert_reward_daily_count`）是每日次数与怪物等级权威；`req_alliance_activity_auto_join_info/open`（`auto_mass_id_list[]/just_soldier/limit/offline`）是原生自动上车状态；发车链路 `req_world_map_search{mapobj_type,level_min,level_max,res_id,is_full}` → `req_world_mapobj` → `req_world_march{type:102, extra{monsterid,prepare_time_index}}`，上车 `type=99 + extra{master_marchid}`。本仓库 `FieldTasks.behemoth` 只发 auto_join（固定类目 **1/4/3**、march_limit=3），`ServerTasks.behemoth` 已做发起/上车/体力门，但因容量/体力源读错而常跳过。
7. **巨熊**：`notify_alliance_trap_update`（tag 10430：`mass_start_time/mass_end_time/cool_end_time/donate/total_score/reserve_time/auto_reserve`）+ `req_alliance_trap_info`（tag 10401，**权威 `reserve_time`**，无 request 体）；`notify_alliance_trap_score_update{score,rewarded_lst}`。发车 `req_world_march{type:411}`、上车 `type=99`、对账 `req_world_mass_master_detail`。活动窗口 30 分钟、开赛前 10 分钟准备窗（`DailyBearSchedule`）；参与冷却 2 天（`DailyBearActionState.PARTICIPATION_COOLDOWN_SECONDS=172800`，用 `notify_alliance_init.player.trap_time` + `trap_extra.aid`）。
8. **战争状态**：App `WarState`（H0-H4 触发/ALERT/WARTIME/退出判定/任务闸）+ `ThreatBoard`（多敌情源）+ `ServerWarState`（服务端对等，`SessionKeeper` 挂钩子）。事实源：`notify_world_alliance_situation_{init,add,update,del,activity*,point_update}`、`notify_world_situation_info{,_add,_up,_del}`、`notify_player_march_{add,update,del}`、`notify_mass_march_{add,update,del}`、`notify_new_mail_syn`（`mail_cover_info.first_type/second_type`）、`notify_alliance_member_pos_{info,add,update,del}`、`notify_alliance_init`。字段：`march{id,owner,type(1 侦查/2 进攻/3 狩猎/4 采集/5 驻防),state(2 在途/3 到达/4 回程),starttime,endtime,target_type,aid,startpoint,endpoint,squad_list.soldier{},atk_city{target,target_aid,target_side},mass_master/mass_slave}`、world 系列外层 `power`。
9. **驻防队友（guardian）**：复用战争事实源（联盟域 situation 天然盟友域）+ `AllyMap`（`notify_alliance_member_pos_info/update` 的 `uid/x/y/kid`）+ 自己行军（`notify_player_march_*`）+ 使馆登记（`notify_embassy_world_march_add` 带 `march_detail.troop_limit`，`_del{id,num}`）+ `req_world_march{type:5}` 发驻防 / `req_world_march_off_work` 撤防 / `req_world_march_speedup{id,itemid,owner(字符串)}` 加速 / `req_world_mapobj` 查城（含 `map_city.shield_endtime/burn_endtime/nickName/aid`）。**"盟友在线"没有直接协议**（schema 全库无 online 字段；`req_alliance_members` 响应只有 `uid/rank`）；唯一近似是 `req_players_base_info.response.result[].offline_time`（需请求、可按 uid 批量）。
10. **现缓存盘点**：`WjdrEngine.notifies`（proto→最后一帧，无版本、无就绪、无增量语义）、`ServerNotifyHistory`（环形 allowlist，8 条/协议、2000 条、4MB、16 账号）、`SessionKeeper` 3 个钩子（wake/history/war）+ 惰性挂载 help/shield/guardian/ServerWarState（+ bear 惰性钩子），App 每会话 **6 个**入站监听（引擎自身 + HelpResponder + PushWakeDriver + ProtoLogger + EnemyWatch + GuardianEngine）、`CaptureTasks.captureAll`（每 10 分钟把 notify 解析成 `res:/questprog:/rallies:/mod:` 写 StateStore）。**直接读点：App 117 处（`notifyData` 43 + `notifyContent` 74），Server 107 处（56 + 51），合计 224 处**（其中 189 处为字面协议名，可直接统计 top）；top：`notify_world_player_init` 16 次、`notify_dailyquests` 10、`notify_soldier_init`/`notify_recover_resource_init`/`notify_hero_init`/`notify_backpack_init` 各 7、`notify_shelter_info` 6……
11. **为什么必须统一**：①同一帧被 6+ 钩子重复解析（每钩子各写一套 JSON 形状兼容）；②同一语义多套实现且已漂移（capacity 3 套全错、体力 2 套读法不同、情报权威源读错）；③固定睡眠等通知 **88 处**（`collectNotifies(1200/1500/2000/2500)`），登录/任务启动白等 1.2–2.5s/次；④`notifyData` 只解一层 `data/info/content`，对 `map` 形（`"201.0"`）与 `list` 形混用，各读点自行兜底 → 字段名一改就静默降级；⑤读不到就多发 `req`（巨兽"状态未知"跳过、专家情报"未同步"），req 数有明确下降空间（Server 166 处 `engine.request`、App 162 处）。
12. **设计建议一句话**：每角色一个 `CoreAssetLibrary`（纯 `java.util`，App/Server **同一份源码**编译，沿用 `WarState/ThreatBoard` 的 `srcDir '../app/src/main/java' include` 机制），单写者（inbound 钩子）→ 解析器 → 变更检测 → `version++` → 锁外通知 + 节流落盘；读者拿 `volatile` 不可变快照；就绪 = 登录必备协议集齐（网页 `BASE_RESOURCE_NOTIFICATIONS` 11 项 + READY 动作），通知到达后 **≤1s（p95）** 可见；兜底只做低频按需（produced/bear/allies 三类），不做全局轮询。
13. **推荐分期**：P0 四类（资源/体力+队列+情报+元数据/时钟）→ P1 巨兽/巨熊 → P2 战争/驻防（后两者已有独立判定机，资产库只提供事实表，**不复制判定**）。
14. **三个必须先修的既有 bug**（否则资产库"源"本身是错的）：`world.capacity` 读法（恒 3/0）、情报只读 `notify_intelligence_events`、巨兽/采集体力源读法不一致（update 与 init 优先级）。
15. **验收**：登录后 READY p50 ≤8s / p95 ≤15s；通知→快照可见 p95 ≤1s；单角色每日非心跳 req 下降 ≥30%；3 角色资产库常驻 ≤6MB（`-Xmx256m` 红线）；字段与 proto_log 证据抽样对拍 100% 一致。

### 2.4 为什么必须统一（结论）

- **正确性**：同一语义 3 套实现已漂移出 4 个 bug（上表）；资产库是"单一解析器 + 单一形状"。
- **时效**：固定睡眠 88 处，每次 0.4–2.5s；资产库用 `awaitChange(version)` 替代，登录/任务启动零白等。
- **成本**：224 处读点各自兜底、App 162/Server 166 处 req 站点重复请求；统一后"读不到"变成"READY 前不工作 + TTL 兜底"，req 数可量化下降。
- **可维护**：入站解析从 6 个钩子收敛到 1 钩子 + 1 分发器；App/Server 共用同一份源码（沿用 `WarState/ThreatBoard` 的 `srcDir include` 机制，`vault-server/build.gradle:37-42`）。
- **可观测**：`version/readyAt/staleness/parse-error` 一处打点，替代现在"每个任务各自写 mod 文案"。

`AssetSnapshot`（不可变，读者无锁）：
```java
public record AssetSnapshot(
    long version, long readyAtMs, long updatedAtMs, AssetKey key,
    MetaAssets meta, ClockAssets clock, CalendarAssets calendar,
    ResourceAssets resources, ProducedAssets produced, RecoverAssets recover,
    BackpackAssets backpack, QueueAssets queue, IntelAssets intel,
    BehemothAssets behemoth, AutoJoinAssets autoJoin, BearAssets bear,
    WarAssets war, GuardianAssets guardian,

    Set<String> staleDomains,            // TTL 过期域
    List<String> parseErrors)            // 解析失败留痕（不抛）
```

### 3.2 公共 API（读者视角，替代 `notifyData`）

```java
// 初始化/装配（RoleSessionKeeper / SessionKeeper 一处调用）
CoreAssetRegistry registry = CoreAssetRegistry.global();
CoreAssetLibrary lib = registry.attach(engine, fpid, sid, uid);   // 幂等；engine 重连复用同一 lib

// 读
AssetSnapshot snap = lib.snapshot();       // O(1)
ResourceAssets res = snap.resources();
StaminaAssets st   = snap.stamina();       // 或 lib.stamina()
QueueAssets q      = snap.queue();
IntelAssets intel  = snap.intel();

// 就绪（登录）
if (!lib.awaitReady(15_000L)) return skip("资产库未就绪: " + lib.missingProtocols());

// 变更等待（替代 collectNotifies/sleep）
long changed = lib.awaitChange(sinceVersion, 5_000L);   // 返回新版本；超时返回 sinceVersion

// 订阅（任务/UI/回显）
AutoCloseable sub = lib.addListener((version, domains, snap) -> scheduler.wake(domains));

// 兜底刷新（只允许任务线程调用；内部限频 + 在线校验 + 与 requestLock 串行）
RefreshResult r = lib.refresh(RefreshKind.PRODUCED_RESOURCES);   // → req_produced_resource_need_update + 等 notify ≤2s
RefreshResult b = lib.refresh(RefreshKind.BEAR_TRAP);            // → req_alliance_trap_info
RefreshResult a = lib.refresh(RefreshKind.ALLY_PROFILES, Set.of(uid...)); // → req_players_base_info（offline_time）

// 生命周期
lib.invalidate(InvalidateReason.TAKEOVER);   // 顶号/断线/换角色 → ready=false、version++、清敏感态
lib.close();
```

### 3.3 更新管线

```
inbound 帧 (proto, content)
   │ ① 兴趣过滤：proto 不在 ~45 个资产协议集合 → 直接返回（O(1) HashSet）
   ▼
writeLock {
  ② 解析：AssetParserRegistry.parse(proto, content) → DomainPatch（每域小 record，字段可空=不变）
  ③ 合并：仅把 patch 中非空字段写入对应域（init 类协议先替换域、update/add 类做增量/upsert；
          map 形（"201.0"）与 list 形统一在解析器内归一）
  ④ 变更检测：域 record 逐字段 equals；有变化 → dirtyDomains；无变化 → 直接返回（不 version++）
  ⑤ version++；按需重建变化域的不可变 snapshot（未变域引用旧对象）
  ⑥ 记录 protocolSeenAtMs / readyFlags（首个到达即置位）
  ⑦ 判定 READY：requiredProtocols ⊆ seen && engine.state==ONLINE && 无 parseErrors 致命项
}
   ▼
⑧ 锁外分发：listeners.onChanged(version, dirtyDomains, snapshot)   （异常逐个隔离）
⑨ 节流落盘（可选）：version 变化后 ≤1 次/秒，写 StateStore `asset:{fpid}:{sid}`（仅展示字段，
   带 version/updatedAt/restored=true）；崩溃重启先 `restored=true`，READY 前不信任
⑩ 观测：`asset_ready fpid=… sid=… ms=… protos=…`、`asset_update proto=… domain=… v=… dur=…`
```

要点：
- **单写者**：inbound 线程回调；解析器内部禁止 `engine.request`（WarNotify 教训：推送线程里发请求会自等死锁，见 `WarNotify` 类注释"严禁在推送线程调用"）。
- **高频协议**：`notify_produced_resource_update`（19h/74 次量级，突发秒级连发）解析成本 O(工位数)；快照只重建 `produced` 域（record 拷贝 ~百字节）。
- **init vs update 语义**：每个解析器显式声明 `snapshotMode`（`FULL_REPLACE` / `PATCH` / `APPEND_OR_REPLACE`），从根上消除 E4（`notifyData` 形状猜测）。
- **失败不抛**：解析异常记 `parseErrors`（≤16 条环形）+ 域标 stale，绝不影响其它帧（对齐 `AbstractBehemothStateRegistry` 的"监听器失败跳过"）。

**READY 动作**（网页 `afterInitialDataSync`）：
1. 唤醒所有 `awaitReady` 的任务（替代 `collectNotifies(1500)` 开头）；
2. 触发一次 `refresh(PRODUCED_RESOURCES)`（网页 `DailyInitialDataSyncService.warmupSnapshots:79-91` 同口径）；
3. 打点 `asset_ready`。

**超时策略**：`awaitReady(15s)` 超时 → 任务 SKIP（带 `missingProtocols`），**不发额外 req**（避免登录风暴）；断线重连 → `invalidate` + 重新等 READY（重连后 init 帧会重放，实证 `GuardianEngine` 注释"init=登录/回连快照"）。

### 3.5 主动刷新兜底（只在"必需且无推送"时）

| 数据 | 兜底协议 | 频率/触发 | 说明 |
|---|---|---|---|
| 产出资源/工位 | `req_produced_resource_need_update` | 登录 READY 后 1 次；TTL 15s（网页 `DailyAccountOverviewService:38` 15s 重试） | 响应仅 code，随后等 `notify_produced_resource_init/update`（≤2s）；失败不重试风暴 |
| 巨熊预约 | `req_alliance_trap_info` | 登录 1 次；距窗口 ≤2h 时 5min；平时 6h | 权威 `reserve_time`；本仓库 `ServerBearTasks` 已有同口径节流 |
| 巨熊目标 | `req_world_mapobj` / `req_alliance_building_list(_exist)` | 窗口前 10min 预热 60s | 只缓存 `map_alliance_trap` |
| 盟友在线/资料 | `req_players_base_info{uids[]}` | TTL 60s；仅"需要在线判定"的 guardian 流程 | 批量 uid；`offline_time` 近似在线 |
| 敌城盾/燃烧 | `req_world_mapobj` | 威胁入账时 1 次 + 60s TTL | `map_city.shield_endtime` |
| 巨兽次数 | **无**（不刷新） | — | `notify_world_npc_*` 缺失则标 stale，任务降级（不猜测次数） |
| 体力 | **无**（不刷新） | — | 缺失则 stale；体力门控退化为"只做队列门"（网页 `intelStaminaAllows` 同口径） |
| 情报/战争 | **无**（不刷新） | — | 纯推送；缺失 = 失明，按保守策略（NORMAL/不派）降级 |

**铁律**：兜底刷新必须在任务线程（非 inbound 线程）、必须复用会话 `requestLock`、必须有全局预算（例如每角色 ≤6 次/分钟、全部失败指数退避），且刷新结果只写资产库、不直接返回给调用方（保持"快照是唯一读口"）。

### 3.6 线程安全与内存预算（生产 `-Xmx256m`）

- **写**：`ReentrantLock`（公平可选，低频）；临界区内只做解析/合并/引用替换，**不做 IO、不回调外部**。
- **读**：`volatile AssetSnapshot` 引用读，无锁；域 record 不可变（`Map` 用 `Map.copyOf` / 不可变包装）。
- **等待**：`Condition.awaitNanos` + `version` 比较；唤醒丢失用循环判版本兜底。
- **失效**：`invalidate` 与 `accept` 同锁；`sessionEpoch` 进 `AssetKey`（防止旧会话帧写新库）。
- **内存预算**（3 角色、资产库常驻目标 **≤6MB**，单角色 ≤2MB）：
  - `backpack` 最多 ~1000 id → `HashMap<Long,Long>` ≈ 40KB；
  - `intel.events` ≤ ~50；`war.threats` ≤ ~50；`allies` ≤ ~100；`queue.marches` ≤ ~20；
  - 不保存原始 `Map` 帧、不保存 history（历史仍归 `ServerNotifyHistory`，两者职责分离）；
  - `parseErrors` 环形 16 条；`protocolSeenAtMs` 仅存协议名（≤200 项）；
  - 与 `ServerNotifyHistory`（4MB 上限）共存时，整机预算 ≈ 4MB + 6MB + 既有任务缓存，安全。
- **快照重建成本**：只重建 dirty 域；单域 record 构造 < 100µs；p99 目标 <5ms。

### 3.7 App 与 Server 是否共用

**推荐共用同一份源码**（唯一事实源），机制已在仓库中成熟：
- `vault-server/build.gradle:37-42`：`sourceSets.main.java { srcDir '../app/src/main/java'; include '.../wjdr/**', '.../guardian/WarState.java', '.../guardian/ThreatBoard.java' }`（注释明确"单一事实源，不做复制"）。
- 新包建议 `app/src/main/java/com/carlos/vault/wjdr/asset/`（与协议包同前装，天然无 Android 依赖），在 `vault-server/build.gradle` 的 include 里**已覆盖**（`com/carlos/vault/wjdr/**`），零构建改动。
- 平台适配层：
  - Server：`CoreAssetRegistry.attach(engine, fpid, sid, uid)` 由 `SessionKeeper.LiveSession` 调用；落盘用 `StateStore`。
  - App：`RoleSessionKeeper` 调用同一 attach；落盘用 `FnParams.modState`/SharedPreferences；UI 读 `snapshot()`。
- 唯一注意：App 侧 `RoleSessionKeeper` 现在挂 6 个钩子，**资产库接入时应把 ProtoLogger/EnemyWatch/GuardianEngine 的"原始帧解析"改为订阅资产库**（ProtoLogger 可保留原样 dump 原始帧用于逆向，不参与资产库）。

## 5. 决策点与推荐

| # | 决策点 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| D1 | 持久化 | ①仅内存 ②内存 + 落盘快照 | **②，但落盘只做"展示/重启提示"，权威永远是内存+推送** | `-Xmx256m` 下 JSON ≤数十 KB/角色可承受；重启后 `restored=true`、READY 前不信任，避免"用旧数据做决策"（账号池/P2 防回滚教训） |
| D2 | 更新驱动 | ①纯 push ②定时轮询 ③push + 低频按需兜底 | **③** | 6/8 类有推送；巨熊预约/盟友在线/敌城盾/产出需要按需 req；全局轮询会放大请求（现网 166 req 站点已过多），且与心跳/风控冲突 |
| D3 | 覆盖范围 | ①8 类全做 ②先 4 类 | **②但模型一次设计到位**：P0=资源/体力+队列+情报+元数据/时钟；P1=巨兽/巨熊；P2=战争/驻防 | P0 复用面最大、推送完备、风险最低；战争/驻防已有 `WarState/GuardianEngine` 判定机，迁移是"换输入源"而非新建，放最后 |
| D4 | 兼容策略 | ①一次性替换 ②渐进迁移 | **②渐进**（写侧先统一 → P0 → P1 → P2，逐域开关回滚） | 224 读点 / 7-8 个入站钩子 / 无回归基线；一次性替换回归面不可控 |
| D5 | 变更事件粒度 | ①全量 snapshot ②字段级 diff | **③version + dirtyDomains + 域 record 逐字段 equals** | 全量 snapshot 适合读者；字段级 diff 用于唤醒粒度（避免 `produced` 突发连发唤醒所有任务）；深 diff（JSON 树）不值得 |
| D6 | 对外暴露 | ①仅内部 API ②REST/UI 只读展示 ③REST 可写 | **②（P1 先 `/status` 摘要，P2 加 `/v1/vault/assets` 与 App 资产页）**；**不做 ③写接口** | 展示价值高（排障/用户可见 READY 与更新时间）；写接口会破坏"推送是唯一事实源" |
| D7 | 就绪判定 | ①engine ONLINE 即算 ②固定 sleep ③协议集齐 | **③**（网页 `BASE_RESOURCE_NOTIFICATIONS` + 域必需集） | sleep 是当前 88 处的病根；协议集齐可解释、可诊断（`missingProtocols`） |
| D8 | 与 `ServerNotifyHistory` 关系 | ①合并 ②保留 | **②保留**：历史负责"多实例原样帧"，资产库负责"最新状态域模型"；资产库的解析器可复用历史的深拷贝工具 | 两者职责不同；合并会让资产库承担活动多档的语义（那是任务层的事） |
| D9 | 是否替换 `engine.addMessageHook` | ①保留多钩子 ②资产库统一 1 钩子 | **②统一，但保留 ProtoLogger 原始帧 dump** | 6-7 次重复解析是主要浪费；ProtoLogger 是逆向工具，独立于资产库 |

## 6. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| K1 | **sproto 类型口径反直觉**：本仓库 codec 按 1=bool/2=string 解码（与常见 sproto 约定 1=string/2=bool 相反）；`proto_log` 又把 bool 转字符串且截断 1201 字符 | 高 | 解析器以 `.spb` schema 为准；日志 fixture 只用于字段名/结构；对每个域写"类型断言单测"（string 字段给非 true/false 值） |
| K2 | 字段/协议随游戏版本漂移（app 1.16.11 vs schema 10-09；`notify_world_npc_update` 已是 base=-1 部分帧） | 高 | `PATCH` 语义 + 缺省保留 + `parseErrors` 留痕；版本探测（`notify_game_init`/`req_loaddata`）+ 灰度期双写对比 |

| K5 | `req_world_march_detail_4_player_situation` 不可用（10/10 code=2） | 中 | 队列占用以 push 维护为主；该请求仅诊断用；`req_world_march` 响应可即时修正单条 march |
| K6 | 登录 replay 窗口：hook 晚挂会漏 init 突发 | 中 | `attach` 时用 `engine.notifyProtos()` 全量回填一次；README 写明"必须在 engine 创建后、login 前 attach" |

| K8 | 推送线程里发请求（死锁） | 中 | 解析器纯函数；`refresh` 仅任务线程；Code review 检查点 + 单测断言（inbound 线程调用 refresh 抛异常） |
| K9 | 双判定漂移（资产库 vs WarState/GuardianEngine） | 中 | 分层铁律：资产库=事实，判定机=策略；P2 迁移只换输入源，不改判定代码；24h 对比 |
| K10 | 内存（-Xmx256m） | 中 | 不存原始帧/历史；单角色 ≤2MB 目标；`/status` 暴露 `assets.bytes`（估算）+ 生产 heap dump 验证 |
| K11 | 快照重建抖动（produced 突发连发） | 低 | 域级重建 + 引用替换；若实测抖动，`produced` 改为"域内可变 + volatile 子引用" |
| K12 | App 侧钩子合并影响现有功能（互助秒回/唤醒/战争短信） | 中 | 合并只在 M6；先让资产库与旧钩子并存（同一 engine），用开关切换读侧；互助/短信保持独立钩子 |
