## 5. 专项：批次判定顺序「ENDED → 熔炉达标 → 终态 → started」的边界复核

**结论：顺序正确，未引入新的失败吞噬路径；有 2 处无害的瞬时不一致，建议登记（见 P2-2）。**

逐条推演：

1. **51 终态 + started>0**：终态在 started 判定前消费（`BootstrapBatchRunner.java:789-799`）→ FAILED，不再被「有进展」吞掉。✅ 主目标保持。
2. **51 终态 + 同轮熔炉已达目标**：`furnace >= target` 先判（`:780-785`）→ SUCCESS。目标已达成，判成功符合业务语义；P2-1 修复意图正确。
3. **51 终态 + 资源耗尽（ENDED）**：`stateView.runState` 由 `BootstrapService.runState()` 生成，其**先判 terminalFailure 再判 resourceEnded**（`BootstrapService.java:3282-3288`），因此终态存在时 `runState=FAILED`，批次 ENDED 分支不会触发，最终走终态 FAILED。两条路径不会互相覆盖；此场景极少，FAILED 更具可操作性。✅（需知晓）
4. **51 终态 + started==0**：终态先于 started 分支 → FAILED 且 error 为原始文案（无「起号停滞：」前缀）。✅
5. **未知码 FAILED（非 51）**：`runUntil` 不再设终态（`:823-824`），批次按既有逻辑处理（started>0 继续下一轮；started==0 且非等待原因 → 「起号停滞」。）。✅ 旧重试语义恢复。
6. **可达标成功与终态并存时的状态口径**：批次 entry 为 SUCCESS，但同实例 `service.status().runState` 为 FAILED（瞬时）。批次视图权威、且服务实例随后丢弃，不影响归档/回流；仅调试日志查询时可能困惑。低风险，见 P2-2。

未发现「该失败却继续跑满 120 分钟」的新路径，也未发现「该成功却被终态误杀」的常规路径（仅第 3 点的 ENDED/FAILED 归类差异）。

- **建议**：改为 `DeviceFingerprint.parse(DeviceFingerprint.forRole(...)).get("device_id")` 再比较；顺带补一条 `forNewRole` 与 `forRole` 同 uid 不同盐的差异断言。
- **优先级**：P2（测试有效性；不影响生产行为）。

### P2-2【低，可接受】终态与「同轮熔炉达标」并存时，批次 SUCCESS 与服务实例 `status().runState=FAILED` 瞬时不一致

- **问题**：同一轮先升到目标熔炉、随后家具 51 达上限时，批次条目为 SUCCESS，但该 service 实例的 `status()` 仍报 FAILED/终态文案；实例随后废弃，不持久化。
