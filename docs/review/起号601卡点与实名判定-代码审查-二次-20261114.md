## 4. P2 明细（不阻断，但应登记/择机修）

### P2-1【中低】终态范围比必要更宽，且批次层把「终态」排在「已达标成功」之前 → 两类边界误判

- **位置**：`BootstrapService.java:827-830`（`runUntil` 对**任何** `FAILED` 都写 `terminalFailure`）；`BootstrapService.java:1162-1167`（`upgradeRejected` 兜底分支：**未知错误码**也返回 `FAILED`）；`BootstrapBatchRunner.java:761-774`（终态判定）vs `:789-792`（`furnace >= target` 成功判定）。
- **问题**
  1. 旧实现里「未知码 FAILED」在 `started>0` 时会下一轮重试；现在变成**永久终态**（`runNext` 的早退守卫 `BootstrapService.java:541-546` 会一直返回 FAILED）。若未知码属于瞬时拒绝，账号被永久判失败。
  2. 终态判定排在 `furnace >= target` 之前：同一轮先执行到目标熔炉等级、随后某个家具动作 51 达上限时，账号会被判 `FAILED` 而不是 `SUCCESS`。
- **影响**：边界账号从「可重试/已达标」变为「失败」，需人工重跑；概率低，但方向与 P1-1 的「如实失败」初衷不完全一致。
- **建议**：只对**明确不可恢复**的码（51 达上限）设置终态，或把 `furnace >= target` 检查前置到终态判定之前（「已达标优先」）；未知码保留重试并单独计数。
- **优先级**：P2。

### P2-2【中】单号挂点（`single-*`）的 601 检测实际不生效：不仅终态不跨请求，51 计数也不跨请求

- **位置**：`BootstrapApi.java:552-561`（每个请求 `new BootstrapService`）；`BootstrapService.java:380`（`terminalFailure` 实例字段）、`:355-365`（`furnitureStall` 实例字段）；整改报告 §5-3 只声明了「终态不跨请求」。
- **问题**：单号路径每次请求都是新实例，`furnitureStall` 计数随实例丢失；且每个请求内同一动作受 30 秒 hold 限制，**单次请求不可能累计到 10**。因此单号路径的 601 客户端检测（10 次→FAILED）**永远不会触发**，`runState()` 也永远看不到 FAILED。
- **影响**：若运营用单号挂点驱动 601 账号，本次修复不生效，仍会无限重试（与修复前同）；只有批次路径生效。
- **建议**：部署记录明确「601 必须以批次模式验证/运行」；中期可把 `furnitureStall` 与 `terminalFailure` 上移到 `BootstrapSessionState`（按 fpid 共享），并定义「重新发起起号」的清除语义。
- **优先级**：P2（已知限制，需登记；不影响批次主路径）。

### P2-3【中】P2-6 降级对「显式指定 uid（`#uid`）」同样生效 → 可能登到默认角色并在错误角色上继续起号

- **位置**：`BootstrapBatchRunner.java:214-227`（`fpid|token#uid` 语义：**人工精确指定角色**）；`BootstrapBatchRunner.java:446-467`（`knownUid = entry.targetUid > 0 ? entry.targetUid : archivedRoleUid(...)`，两者失配都降级）。
- **问题**：显式 `#uid` 是操作者明确意图。钉扎失败时当前实现静默降级为「服务端默认角色」继续，违背操作者选择；同账号同区有两角色时默认角色可能是老号，后续起号动作会消耗**老号资源/钻石**，或在老号上做升级。
- **影响**：登错角色 → 资源被误耗、结果与预期角色不符；频率低（需 `#uid` 失效/多角色），但后果不可逆。
- **建议**：区分来源——`entry.targetUid > 0`（显式）失败时保持 fail-fast（保留现有异常语义）；只有 `archivedRoleUid`（启发式存档）失败时才降级，并在 `steps` 记录。当前用例 `BootstrapBatchRunnerTest.java:513-514` 恰好是显式 uid 降级，无法覆盖「存档 uid 降级」分支（见 §8 缺口 4）。
- **优先级**：P2。

### 8.2 「测试通过但生产无效」盲区判定

1. **已证实存在（P1-1）**：`limitFromConfig` 直接构造配置，绕过 `BootstrapApi.batchConfigOf/serviceOf`，导致「配置化」在测试中绿、在生产中恒为 10。

3. **P2-6 的真实性**：用例用 `FakeEngine`，不模拟真实引擎在钉扎失败后的断连/退避；本审查通过静态核对 `GameProtocolClient.request()` 的 `connect()` 确认生产可重连，但**这不是测试证明的**。建议在部署首批观察回退登录日志。
