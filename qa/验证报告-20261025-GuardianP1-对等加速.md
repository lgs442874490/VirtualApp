# 验证报告：守护盟友 P1「驻防对等加速」（2026-10-25）

> 分支：`add/guardian-speedup-20261025-1420`（基于 master `07b7e14`）
> 需求（用户口径）：SLG 侦查后约 2 秒即可进攻；威胁兵力超出配置档位时同步出征驻防；**敌方一开始加速，我方同步对等加速，始终保持比敌先到**；加速道具可无限消耗（只要保证驻防先到）；道具优先 25%，25% 能达到同等"保持先到"效果就只用 25%；道具不足是否使用钻石由**用户配置开关**决定（默认关）。

### 选档算法（用户口径）
1. 25% 优先：25% 能达成（可**多次叠加**）就只用 25%，不升 50%；
2. 25% 在库存/次数上限内不可达 → 才升 50%；
3. 不设道具预算 cap（受库存 + `max_speedups_per_march` + 单轮 6 发安全上限约束）；
4. 每次真实响应 endtime 回填后重算，不囤积领先（敌再压缩 → 新一轮最小响应）。

### 钻石路径（第二迭代）
- `diamond_speedup_enabled=false`（默认）：**零 quick_buy**，道具耗尽即诚实止损；
- 开关打开后，道具耗尽时走 App 同口径购买：`req_shop_quick_buy{use:false,id:301901,count:1}` → `code==0` 视为入包 → **同一轮立即用 301901 加速**；
- 三道安全闸：①开关双保险（防配置热载竞态）②**库存未知（背包快照未同步）绝不花钻石** ③`diamond_max_per_march`（默认 **3**，0=不限）单行军购买上限；
- 失败（非 0 码）只记 `speedup_diamond_buy_failed` 并终止，不重试、不冷却；购买+使用算 1 次链动作（不放宽单轮 6 发）。

### 配置（roleParams `guardian`；默认全部不改变旧行为）
| 键 | 默认 | 说明 |
|---|---|---|
| `speedup_enabled` | false | P1 对等加速总开关（开=敌加速时同步加速） |
| `speedup_margin_s` | 2 | 先至余量（秒）：我方 endtime 至少领先该值；0~60 之外回落 2 |
| `max_speedups_per_march` | 0 | 本行军加速发数上限（0=不限） |
| `diamond_speedup_enabled` | false | 道具不足时是否允许**真实购买**钻石道具（真花钻石） |
| `diamond_max_per_march` | 3 | 单行军钻石道具购买上限（0=不限；负数回落 3） |

**灰度环境变量覆盖**（App 暂无这些新键的参数入口时用；env 未设置 → 完全以 roleParams 为准）：
- `VAULT_GUARDIAN_SPEEDUP=1|0`：强制对等加速开关
- `VAULT_GUARDIAN_DIAMOND=1|0`：强制钻石开关（真实花钱，慎用）

## 四、风险与边界

- **未接真机**：协议形状来自 App 实证（`GuardianLaunch.java:913-1062`），购买链路仅 `code==0` 判定，需真机小号验证一次完整链路与钻石扣减；
- **执行器占用**：加速链在 guardian 单线程串行，单发 4s/购买 8s 超时 × 最多 6 轮，极端场景会占用同角色发射/撤防排队；灰度观察 latency，必要时拆第二执行器；
- **秒域取整**：我方 endtime 为秒级，领先刚好 margin 时可能 ±1s 抖动；按"先到"验收（≥1s）仍满足；
- **次数上限语义**：若 `max_speedups_per_march` 导致无法保证先到，planner 选择**不发**（不浪费道具）；
- 本分支**未部署**；部署后默认全关，需按上表配置（或 env 灰度）才生效。
