## 3. P1（需明确处置：修复 或 用户书面接受延期）

### P1-1【高】51 达上限返回的 `FAILED` 不是终态，批次层大概率吞掉失败 → 601 仍会跑到超时

- **位置**
  - `vault-server/src/main/java/com/carlos/vaultserver/bootstrap/BootstrapService.java:1039-1051`（达上限返回 `FAILED`，但未设置任何终态标记）
  - `vault-server/src/main/java/com/carlos/vaultserver/bootstrap/BootstrapService.java:790-816`（`runUntil` 在非 `STARTED` 时 break，失败只进 `summary.message`）
  - `vault-server/src/main/java/com/carlos/vaultserver/bootstrap/BootstrapBatchRunner.java:766-801`（只有 `started == 0` 才消费 `summary.message`；`started > 0` 一律按「有进展」继续）
- **问题**：`FAILED` 只是 `runNext()` 的一次返回值。`runUntil` 把它转成 `summary.message` 后，`runLeveling` 仅在 `started == 0` 时读取该消息并判失败；`started > 0` 时该轮按「有进展」处理，`FAILED` 结果只留在 `summary.results` 里（日志最多打印前 3 条）。`BootstrapService.runState()`（`:3235-3250`）也不会因该结果变为 `ENDED/FAILED`，服务侧没有任何终态标记。
- **影响（触发条件与后果）**：真实批次的一轮通常先执行领奖/委任/产出领取等动作（返回 `STARTED`），第 10 次家具 51 发生时 `started > 0` → 失败被忽略；下一轮 `furnitureStall` 已在 `:1043` 被 `remove`，计数从 1 重新累计 → 601 的「重置→CREATE(154)→UPGRADE(51)」循环继续，直到单号 **120 分钟**超时（`BootstrapBatchRunner.java:38/87/270`）。批次串行执行（`:312-316`），后续账号被一并阻塞；操作者看到的失败原因是「起号超时上限 120 分钟」，而不是「请重新发起起号」。**本次部署的核心目的（终止 601 死循环、如实失败并提示重跑）大概率无法达成。**
- **依据**：调用链 `runAccount → runLeveling → runUntil → runNext`；`started` 只统计 `STARTED`（`:804`）；失败结果未进入任何状态机。新增两个单测只断言 `svc.runNext()` 的返回值（`BootstrapServiceTest.java:2355-2377`），**没有任何 `BootstrapBatchRunner` 层用例**验证失败传导。
- **不确定性**：若第 10 次 51 恰好是该轮第一个动作（`started == 0`），批次会以「起号停滞：<message>」失败；因此是「大概率吞掉」而非「必然吞掉」。这也意味着同一账号在不同资源领取节奏下行为不一致，本身就不可接受。
- **优先级**：P1（高）。

## 5. 三个重点专项结论

### 5.1 51 上限阈值 10 是否误杀慢账号？

**结论：会，但主因不是「资源不足」，而是「计数不区分原因 + 153/154 不复位 + 纯次数阈值无统计支撑」。**

- 纯「本地资源不够」的慢账号**不会**被这个计数误杀：planner 在资源不足时直接阻断，不会发起 51（`BootstrapPlanner.java:300-304`）。
- 真正会被误杀的是「本地快照认为够、服务端说不够」的账号：资源快照滞后、前置条件未满足、家具实例未同步（正常同步滞后即可随时间自愈）——这些在 5–6 分钟内累计 10 次就会被判 `FAILED`。
- 更确定的一条误杀路径：9 次 51 → 154/153（计数不复位）→ 建筑升级后家具恢复可升级 → 第 1 次 51 即达上限判失败（`BootstrapService.java:992-1021`、`:938-942`）。
- 阈值 10 是经验值（TDD 报告自认），不能证明「5–6 分钟」足以覆盖所有同步滞后；且不可配置，后续调整需改代码发版。

**建议修复方向**（详见 §8）：153/154/服务端等级上升时复位计数；仅在「服务端观测等级持续低于本地等级」时计数（可区分「实例缺失」与「同步滞后」）；阈值移入 `BootstrapConfig`；文案不要断言未验证的原因。

### 5.2 msg 关键词是否过度放宽？

**结论：相对网页版只多 2 条，且两条都有实跑依据，不算「放宽到任意文案」；真正的风险是①关键词判定不受 status 门控（继承网页版口径）②新增关键词是子串匹配，可能命中失败文案（未取证）。**

| 关键词 | 网页版 | 本分支 | 备注 |
|---|---|---|---|
| 无需实名 | ✅ | ✅ | 一致 |
| 已实名 | ✅ | ✅ | 一致 |
| 已经实名 | ✅ | ✅ | 一致 |
| 已认证 | ✅ | ✅ | 一致 |
| already verified | ✅ | ✅ | 一致 |
| 已通过实名 | ❌ | ✅ | 新增，实跑文案「已通过实名认证，不能重复认证」 |
| 不能重复认证 | ❌ | ✅ | 新增，同上 |

- 与 `PhoneRegistrationPassportGateway.java:102-105` 对比，本分支只增加 2 条，与排查文档「实跑上游确有此文案」一致，**不属于无依据的过度放宽**。
- 但 `RegistrationService.java:145` 把关键词判定与 status/code 解耦：`status=0`、`code=3` 等明确失败码下，只要 msg 命中关键词仍会判通过。网页版同样如此，属同口径继承；若产品要求更严格，建议加 `status == 1` 门控并补负向用例（会偏离网页版口径，需产品确认）。
- 缺少「失败文案含已实名关键词」的负向用例（见 §7）。

### 5.3 指纹策略副作用

**建号固定指纹（`BootstrapService.java:2964`）**

- 副作用 1：同账号同区多角色共用同一设备身份，与 `DeviceFingerprint` 契约（`:41-48`）相反，多角色场景可能触发设备风控（见 P1-3）。
- 副作用 2：建号设备（`forNewRole(...,"create")`）与后续登录设备（`forRole(...,uid)`）**恒不相同**。改动前（时间戳 salt）也如此，不是回归；但固定 salt 后「建号→后续登录」的设备切换变成确定行为。若游戏侧对「设备变更」计分，需要评估（建议另立项：建号成功后用 `forRole(uid)` 重登一次，或在账号存档里固化创建设备）。
- 副作用 3：`createRole` 中 `applyIdentity` 的 `catch (RuntimeException ignored)` 注释写「退回引擎默认随机指纹」，但 `WjdrEngine.applyIdentity` 内部已吞掉异常、失败时保留的是**上一次的 pinned 身份**，不一定是随机值。该 catch 实际近乎死代码，注释与实现不符（低优先级，未单列 P2）。

**回退登录稳定指纹（`BootstrapBatchRunner.java:440-458` + `BootstrapService.java:3025-3048`）**

- 方向正确：先切 `forRole` 指纹再登录，不再用建号的一次性指纹探测老角色；少一次 loginauth。
- 新增的回退副作用（见 P2-6）：按存档 uid 钉扎后，若存档 uid 失效（角色被删/记录错误）或同账号同区有 2 个角色（`loginExisting` Javadoc 明确存在该场景），`loginExisting` 会直接抛「未能登录指定角色 uid=…」（`:3046-3047`），而旧路径 `targetUid=0` 会由服务端选默认角色继续。触发概率低，但后果是该号直接 `FAILED`。建议：钉扎失败时降级为默认登录并记录日志，而不是直接抛。
