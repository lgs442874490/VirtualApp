# 角色管理/工作区 — 同服多角色修复（2026-10-20）

- 分支：`fix/role-management-20261020-0105`（基于 master `f4b8de4`）
- 范围：App（RoleStore/RoleLogin/HomeActivity/EntryDetailActivity/VaultSync）+ vault-server（VaultStore/VaultHttpApi/SessionKeeper/SessionControl）
- 真机案例：账号 **48460403**，888 服同时存在「隆科多」uid=**35371154** 与「小鹿矿工5号」uid=**88280792**

## 1. 根因

| # | 现象 | 根因 |
|---|---|---|
| 1 | 角色管理列表里同服两个角色只显示一个 | `RoleStore.registerRole` 按 **serverid 单键**去重：同服第二个角色命中第一个的行，uid/name 被覆盖登记到同一行，列表只剩一条 |
| 2 | 工作区不显示该账号有两个角色 | 同上——roles 表被截断；账号卡「已启用角色 N」/「已加入 N」均读自被截断的表 |
| 3 | 开关/选择串到另一个角色 | `setEnabled`/`roleOf`/`updateUid` 全部按 serverid 定位，同服两行（修复前只有一行）时命中错误对象 |
| 4 | 服务器登录落错角色 | 当前角色身份只存 sid（`active:<fpid>` 为 long sid，`VaultSync` 只发 `activeSid`，server `VaultStore.Account` 只有 activeSid）；`SessionKeeper.loginBoundRole` 用 `srv:roleuid:<fpid>:<sid>` 缓存**单 uid**，同服第二角色无法表达，只能发现/缓存其中一个 |

本质：**角色身份被建模成了 serverid 单键，而游戏里角色身份是 (serverid, uid)**。

## 2. 方案

### 2.1 身份统一为 (serverid, uid)

新增纯 Java 工具类 `daily/RoleIdentity.java`（无 Android 依赖，JVM 单测直跑；vault-server 亦可复用）：

- `key/parseKey`：复合键 `"sid:uid"` 格式化/解析
- `sameIdentity`（严格）/ `matches`（宽松：一侧 uid 未知即候选）两档匹配语义
- `indexOf`（严格定位；uid≤0 退化 sid 第一行=旧口径）/ `indexOfLoose`（登记去重/升级）
- `countOfServer` / `ordinalOf`：同服第 N 角色
- `resolveUidForSid`：旧 active 键（只有 sid）迁移时按角色表补 uid（优先工作区内角色）
- `serverLabel`：行内可区分文案（`888服 · 同服第2角色`）

`RoleStore` 全部改走复合身份：

- `registerRole`：宽松匹配——旧 `uid=0` 记录在 uid 已知时**原地升级**（不产生重复行）；同 sid 两个已知 uid **新建角色行**（不再互相覆盖）
- `setEnabled`/`roleOf`/`updateUid`：新增 (sid,uid) 版；旧 3 参签名保留（退化该 sid 第一行），内部同源
- `updateUid(sid, fromUid, toUid)`：钉扎自愈**定点**纠正；改成 toUid 后若已存在同 (sid,toUid) 行 → 合并（enabled 取或，保留工作区成员）不留重复行
- 当前角色：新键 `active2:<fpid>` = `"sid:uid"`；`activeRoleEx()` 读新键，缺省回退旧键 `active:<fpid>`（long sid）并按角色表补 uid 后**惰性迁移写回**；`removeAccount` 同步清理新键
- `pickMainRole` 命中标签时连同 uid 一起设激活

### 2.2 登录钉扎（RoleLogin）

- `loginPinned(..., sid, uid)`：调用方给 uid（同服多角色必须）直接按 uid 钉扎；未给则查角色表已登记 uid；都未知走原「按 sid 登录 + 落地校验 + 回填」发现路径
- `wrongRole` 自愈按 (sid, knownUid) 定点，不再按 sid 第一行误改同服另一个角色
- `DailyRunner.run(...)` 新增带 uid 重载：本地（非服务器模式）跑日常时把激活角色 uid 一路透传到 `loginPinned`，同服多角色不会落到第一个角色；`HomeActivity.runList` 调用处已改传 `RoleStore.activeRoleUid`

### 2.3 UI（App）

- `home:current_role` 键升级为 `fpid:sid:uid`（uid>0 时；旧 `fpid:sid` 格式读取兼容，uid 段按 0 处理）
- 角色管理每行显示**可区分信息**：名称 + `K888服 · 同服第N角色`（同服多角色）或 `· uid 88280792`；头像种子带 uid
- 开关（`sheetRoleRow`/`roleMenu`）、点击、跑日常（`runRole`）、预登录启动（`launchRole` → `RoleLogin.loginPinned` 带 uid）、账号卡角色表（`roleEntryCard` 昵称带「同服第N角色」）全部按 (sid,uid)
- 工作区账号卡「已启用角色 N」/角色管理弹层「已加入 N」读全量 roles 表，计数正确
- `showRolePicker`/`EntryDetailActivity` 角色列表与切换按 (sid,uid)；「✓当前」按复合身份判定
- 角色级在线判定（`roleOnline`）在激活 uid 已知时按 uid 精确命中，同服两个角色不再被同一 actSid 同时判「在线」

### 2.4 上行/服务器链路

- `VaultSync.syncFields`：accounts 增加 `activeUid`（字符串，可空）；roles[] 每项增加 `uid`
- `VaultSync.learnServerRole`：服务器回传的 `activeUid` 用于登记角色 uid、写复合 `current_role`
- server `VaultStore.Account` 增加 `activeUid`（**解析/序列化/replaceAll 合并/snapshot 深拷贝全链路**，缺省 null=旧行为）
- `SessionKeeper.loginBoundRole` 两条路径：
  - **activeUid>0**：直绑该 uid。首次默认角色上线拉 `req_role_list` 校验 (kid,uid) 属于本账号 → 写缓存 `srv:roleuid:<fpid>:<kid>:<uid>`（键含 uid）→ 全新连接 `loginByRole`；之后缓存命中免校验直绑。绑定失败（落地 uid≠期望）清缓存按实际角色上线；**校验不过回退旧发现路径**，不硬绑
  - **activeUid 缺省（0/空/非法）**：`loginBoundRoleLegacy` 原逻辑逐字保留（sid 缓存单 uid + discoverRoleUid）
- `reconcile` 重启条件增加 `wantUid != parseUid(activeUid)`：同服切角色（sid 相同 uid 不同）也能重启会话
- `SessionStatus` 增加 `activeUid`：有会话取实际落地 uid，无会话取账号库下发值；`VaultHttpApi` 的 status/automation 快照回传（App 据此把服务器角色学回本地表）

## 3. 兼容

| 场景 | 行为 |
|---|---|
| 单角色账号（sid 唯一） | 全链路与原版一致：宽松匹配退化为按 sid；activeUid 空=旧发现路径 |
| 旧 roles 数据（uid=0） | 首次登录/采集学到 uid 后**原地升级**同一行，不重复 |
| 旧 `active:<fpid>`（long sid） | 首次读取时按角色表补 uid，写回 `active2:`，之后走复合键 |
| 旧 `current_role`（fpid:sid） | 新格式读取兼容；uid 段缺失按 0（sid 口径） |
| 旧客户端 sync（无 activeUid/roles.uid） | server 缺省 null/0 = 旧行为；status 回传空串，App 按 0 处理 |
| 旧 server（无 activeUid 字段） | App 多发字段被忽略；learnServerRole 对缺省按 0 处理 |

## 4. 已知限制（设计取舍，均已注明）

1. **roleConfig/roleParams/roleIdentity/采集状态仍按 sid 键**（App `DailyConfigStore`/`FnParams`/`AccountStore.getRoleSettings`、server `roleConfig`/`roleParams`/`roleIdentity`、`LogStore.dayStats`/`QuestStore`/`mod:`/`todo:` 等均为 sid 口径）。同服两个角色**共享**任务开关/参数/设备指纹/今日统计。原因：配置体系全链路按 sid 建模，改造面覆盖 App+server+存量数据迁移，风险远大于收益；同服多角色的核心述求（列表不丢、开关不串、登录落对角色）已由复合身份满足。后续如需角色级配置，再以 `sid:uid` 键迁移（RoleIdentity.key 已备好格式）。
2. **本地常驻会话按 fpid:sid 键**（`RoleSessionKeeper`）：同服两个角色不能同时起两条本地 keep-online 会话（会互踢），工作区同时开两个同服角色时本地只保一条；服务器模式无此限（server 侧已按 activeUid 精确绑定）。
3. **旧发现路径 `discoverRoleUid(kid)` 只能返回同服第一个角色**——正是 activeUid>0 直绑路径存在的原因；activeUid 缺省时行为不变。
4. 同服双角色的「今日完成/上次登录」统计按 sid 共享（见限制 1）。
5. `discoverRoles()` 的角色清单来自 req_role_list；个别区服响应不带 kid 时按 lastServerId 归属，uid 校验失败会安全回退旧路径。

## 9. UI 第二轮：「登录」语义统一 + 状态口径统一 + 展示标准化（2026-10-20）

用户提四点需求，全部落地。核心变化：**「登录」= 脚本模拟登录该角色在线**（切角色 → 上行 activeUid → 服务器建会话并触发整轮），**不是启动游戏客户端**；启动客户端仍走「启动分身」/角色菜单「🖥 启动游戏」。

### 9.1 账号页角色列表（需求 1）

- 列表视图（accView==0）由「简单卡片（只有账号级登录）」改回**账号分组框**：账号头（勾选/头像/备注+UID/⚙角色管理）+ 工作区角色表格（状态/昵称/区号/今日完成/上次登录/登录）。
- **移除「最多 4 行 + 还有 N 个」折叠**：全部工作区角色平铺可见（同服多角色账号不再有点不进的角色）；未加入工作区的账号显示提示 + 可点「⚙ 角色管理」。
- 每行「登录」按 **(sid,uid) 钉扎**（`HomeActivity.loginRole` → `VaultSync.loginRoleOnline`），与账号级登录同一后半程；整轮触发行为保持不变（fn=null 排队整轮）——若用户只想要「在线不要跑整轮」，以后可在弹层加开关，当前以「模拟登录在线」语义为准。
- 长按账号框 = 账号菜单（批量/登录并运行/启动游戏/角色管理/排序），与简单卡片时代的入口一致。简单卡片（accountSimpleCard）随之删除（其登录可达性由分组框角色行覆盖）。

### 9.2 账号详情页角色盒（需求 2）

- `rebuildRoles` **只渲染已加入工作区（enabled）的角色**；标题「工作区角色（N）」；空态提示「还没有角色加入工作区 —— 点右上『管理』添加」（可点直达弹层）。
- 「管理」按钮复用 `RoleManagerSheet`（与账号页同一个弹层，未加入工作区的角色在弹层里开开关）；原 `showRoleActions` 列表弹层删除。
- 每行新增「登录」按钮（`setCurrentRole` + `VaultSync.loginRoleOnline`），详情页不再只有账号级「登录并运行自动化」一个入口。

### 9.3 状态口径统一（需求 3）

| 位置 | 服务器模式 | 本地模式（legacy 兜底） |
|---|---|---|
| 账号页角色行 `roleOnlineLabel` | `VaultSync.cachedStatusOf` 按 sid+activeUid 匹配（`RoleDisplay.roleMatchesServerStatus`），无缓存显示「同步中」 | RoleSessionKeeper 会话快照（日常在线）+ live uid 反查（游戏在线）+ 快照激活角色推断（在线） |
| 今日页 `keepStatusText` | 同左，文案 `RoleDisplay.serverStateLabel` + 「· 服务器」后缀 | 同左（去掉后缀） |
| 角色管理行（`RoleManagerSheet`/详情页角色盒） | 同左 | 同左 |

- 文案映射收敛到纯函数 `RoleDisplay.serverStateLabel`：online→在线 / recovering→重连中 / takeover→被顶号暂停 / need_token→需重导token / 其余（含 null）→离线。
- 匹配规则（纯函数 `roleMatchesServerStatus`，可测）：新服务器（activeUid>0）必须 uid 均已知且相等（行 uid 未知保守判否）；旧服务器（无 activeUid）退到激活角色口径（已知限制：同服第二角色本地无法细分，同 §4.2）。
- App 启动即 `ensureServerMode`（自动化只允许服务器执行），**服务器模式是实际主口径**；本地分支保留为 legacy 兜底。

### 9.4 角色管理行展示标准化（需求 4）

- 三处（角色管理弹层行/账号页角色行/详情页角色盒）统一：**昵称**（`RoleDisplay.roleName`，空→「未同步」）+ **`K888 · UID 88280792 · 城堡 70 级 · 战力 20784万`**（`RoleDisplay.roleMetaLine`）。
- **移除「同服第N角色」文案**（序号随行序漂移、与 (sid,uid) 无稳定对应；同服多角色靠 UID 段区分）。
- 缺失段显示对应「未同步」：uid<=0→`UID 未同步`；level<=0→`城堡未同步`；power<=0→`战力未同步`；名称空→`未同步`。不编造数值。
- 开关保留按 (sid,uid) 独立（`RoleStore.setEnabled(fpid,sid,uid,…)`），同服两个角色互不影响。
- 战力格式 `RoleDisplay.wan`：≥1万且整数万去小数点（20784万），非整数保留一位（1234.6万），<1万原值。
- `K<sid>` 前缀保留区号信息（账号页表格另有独立「区号」列；弹层/详情页的元数据行是区号唯一展示位）。

## 7. P2 收尾：切角色上行延迟窗口的回滚竞态（2026-10-20 补修）

QA 验证报告 §3.1 记录：`setCurrentRole` 只写本地（active2/current_role），不触发上行；上传依赖 kickFullSync（10 分钟防抖）或其它状态变更。窗口内任何 `fetchState` → `learnServerRole` 会以服务端旧 `activeUid` 无条件 `setActiveRole`，可能把刚切的同服角色回滚（UI 表现为切完又跳回）。**已修复**，方案如下。

### 7.1 两层防护（缺一不可）

| 层 | 机制 | 挡住什么 |
|---|---|---|
| ① 待上传标记 | UI 切换入口统一调 `VaultSync.notifyRoleSwitched(fpid)`：`RoleStore.markRoleDirty` + `onAccountsChanged`（3 秒去抖全量 sync，上行窗口从 10 分钟压到约 3 秒）；一次 sync 成功（`code==0`）即 `RoleStore.clearAllRoleDirty`（payload 带全部账号，一次性清所有） | 「切换后才发起、同步前到达」的请求——`RoleSessionKeeper` 巡检（onAccountsChanged 后立刻 fetchState）、`autoSyncAccount`（打开页面即拉状态）等路径，回传必为旧角色，**时间戳条件判不出**（localTs < requestTs 会放行），必须靠标记拦 |
| ② 时间戳门控 | `RoleIdentity.shouldLearnActiveRole(localSid,localUid,localTs,serverSid,serverUid,requestTs)` 纯函数；`requestTs` 在 `fetchState`/`refreshStatus` 发起时捕获，透传 `cacheAccounts` → `learnServerRole`；`localTs` = `active2_at:<fpid>`（`setActiveRole` 每次写入刷新） | 「请求发起后、响应到达前」用户切角色——回传是切换前旧快照（localTs ≥ requestTs 跳过）；另挡本地已知 uid 时旧服务器 uid 缺失的降级回写 |

`learnServerRole` 只对**当前角色身份回写**（`setActiveRole` + `current_role`）上门控；`migrateRole`（sid=0 配置迁移）是无害增量学习，保持无条件。sync 持续失败时标记不清=继续拦截（本地优先，恢复后自愈）；`removeAccount` 同步清理两个新键。

> ⚠️ 末轮修正（见 §8）：P2 收尾时曾判断「registerRole 保持无条件」，真机验证（QA §3.4）证明该无条件正是 P1-2 元数据串行的根因——`registerRole` 的元数据学习现已加 `shouldLearnServerMeta` 门控。

### 7.2 兼容与边界

- 本地模式（无服务器）：`onAccountsChanged` 自动 no-op，待上传标记不会被读取（`learnServerRole` 只在服务端回传路径出现）。
- 旧数据 `localTs=0`：按「早于任何请求」放行学习；`localUid=0` 不拦服务端 uid 升级。
- 同时刻边界（localTs == requestTs）按跳过处理——误跳下次同步自愈，误采纳则用户可见回滚，风险不对称取保守侧。
- 已知残留：设备时钟被改回过去时时间戳层失效（待上传标记层不依赖时钟，仍有效）；sync 长时间失败期间不采纳任何服务端角色（保守，符合「本地选择优先」）。
- 单角色账号：回传身份与本地相同即 no-op，两层防护均不改变原行为。

### 7.3 接线点（全部切换入口）

- `HomeActivity.setCurrentRole(fpid,sid,uid)`（角色选择器/账号切换/loginAndRun 的公共漏斗）
- `HomeActivity.runRole`（跑日常前对齐激活角色）
- `HomeActivity.launchRole`（预登录启动）
- `EntryDetailActivity.setCurrentRole(sid,uid)`（角色操作弹层/角色行点击/登录并运行的漏斗）

## 8. 末轮修复：P1-2 服务器元数据串行 + P3 发现角色清洗（2026-10-20 补修）

ZCode 真机验证（QA 报告 v2）发现：P2 防回滚两件套实战通过，但暴露出 P1-2 与新的 P3 项。均已修复。

### 8.1 P1-2：learnServerRole 元数据污染同服第一行（QA §3.4）

**链路**：旧服务器 status 无 `activeUid` → 解析 `uid=0` → `learnServerRole` 在防回滚门控**之前**无条件 `registerRole(sid, uid=0, name/lv/power/alliance)` → `indexOfLoose` 宽松匹配（一侧 uid 未知即命中）→ 同服**第一行**的 name/level/power/alliance 被服务器会话角色的值覆盖。真机两版 APK 均复现：小鹿行被反复覆盖成隆科多的 lv70/战力 20784.1万/KFC；灰度窗口（App 新版 + 旧 server）内每次 fetchState 必现。仅显示层受损（uid=0 不写，身份/开关/登录目标不受影响）。

**修复**：`RoleIdentity.shouldLearnServerMeta(sid, uid, rows)` 纯函数门控——
- `uid>0`（新服务器下发 activeUid）：放行，`registerRole` 按 (sid,uid) 精确命中或新建，**正常路径不回归**；
- `uid<=0` 且该 sid 已有 uid 已知行：**跳过**本次元数据学习（宽松命中必落别人行上）；
- `uid<=0` 且该 sid 尚无已知行（单角色账号首次引导）：放行，uid=0 登记后由登录/发现升级；
- `sid<=0`：false（防御，不产生 sid=0 行）。

`learnServerRole` 的 `migrateRole`（配置迁移）与当前角色身份回写门控均不受影响。**这同时修正了 §7.1 曾作出的「registerRole 保持无条件」判断**——真机证明该无条件即本问题根因。

### 8.2 P3：发现角色修正名字时清洗残留元数据（QA §3.5）

**链路**：`discoverRoles` 的 RoleInfo 只带 name——修正行内名字时，旧的错误 level/power/alliance 残留（真机：小鹿行名字修正后仍显示隆科多的 lv70/KFC），与 P1-2 叠加时两行更难分辨。

**修复**：`RoleStore.registerDiscoveredRole`（发现路径专用）——复用 `registerRole` 去重/升级语义；按 `RoleIdentity.shouldClearStaleMeta(oldName,newName)` 判定：旧名字非空且与新名字不同（=旧名字是错的）→ 一并清零 level/power/alliance；名字未变（或旧名字为空=补全而非修正、新名字为空=不会覆盖）→ 不动，保住登录/采集学到的可信元数据。玩家正常改名会丢失旧元数据，下次登录/状态回传即重新学得，可接受。

### 8.3 P3：存量脏数据自愈引导（QA §3.6，流程项）

`removeAccount`/新装引导不改动。原缺陷已损坏的数据（隆科多行被小鹿 uid 覆盖）升级后不会自动拆两行，需用户点一次「+ 添加角色」（req_role_list 全量发现）自愈——真机已验证有效。

> **发布说明提示**：升级后如发现角色管理里有「名字和 uid 对不上」的行，打开该账号的角色管理，点一次「+ 添加角色」即可自动修正（会按服务器全量清单拆行/改名/清残留元数据）；此后每次服务器状态回传都会按身份学习，不再串行。
