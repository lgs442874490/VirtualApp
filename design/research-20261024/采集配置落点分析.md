## 0. 结论摘要

1. **参数链路已经是“App 本地写入 → 全量 sync → 服务端 roleParams → 任务执行时读取”的成熟通道**，采集配置新增字段**不需要新接口、不需要 App 协议改动**：只要写进 `FnParams` 的 `gather` 参数对象，`VaultSync.syncFields` 会随角色 params 自动上传，服务端 `TaskContext.params("gather")` 直接可见。
2. 采集配置现状是“**全局一套**”：`min_level`(1-6 全局) / `max_queues`(1-5) / `resources_named`(多选 4 种) / `strategy.send`(any|full) / `squad_index`(旧游戏内存编队) / `alliance_mine`(bool) + 批次10/11 的功能级统一编队（`formation_mode/formation_id/soldiers/ratio/total`），与网页版 **6 队列 × 每队列资源/等级/编队/兵量** 的 v2 模型差距明确。
3. 网页版 `DailyGatherConfig` 已是完整可抄的 v2 母本：**固定 6 队列、等级 1-9、每队列 ONE 资源 + AUTOMATIC/ROLE 编队 + 兵量(默认 40k/30k/30k)、全局 fullResourceOnly/采集加速 8h·24h/联盟矿/重物搬运/50:20:30 满编**，且 `validated()` 内含“**同一 ROLE 编队只能分配给一个采集队列**”的重复校验（`DailyGatherConfig.java:70-113`）。
4. 编队体系批次10/11 已闭环“功能级统一编队 + 编队库 + 巨熊 1-6 上车槽”；采集当前是 `formationFor(tc,"gather",1+(sent%3))`（`ServerFieldTasks.java:107`）——**同一功能级编队轮流派所有 slot，没有队列级绑定**；无编队参数时回退旧 `Exec.formation`（`ServerFieldTasks.java:190-241`），零行为变化。
5. 推荐方案：**roleParams["gather"] 内嵌 `v2` 对象**（web 字段命名对齐）+ 旧键**双写投影**（新 App↔旧服务端、旧 App↔新服务端双向兼容）+ **纯 JVM 共享解析器**（放 App 源树、vault-server `sourceSets` include，沿用 wjdr 引擎同源编译先例）；UI 用**独立 `GatherConfigActivity`**（6 队列卡片 + 全局项），入口挂在功能详情页「采集参数」卡片。
6. 迁移策略：**按“旧配置的生效行为”迁移**（resources_named、max_queues、min_level、strategy.send、formation_*、alliance_mine、squad_index），而不是按网页版默认值迁移——保证未配置的老账号升级后派队行为不变；“恢复默认”= 迁移推导出的行为等价默认。
7. 风险集中在四处：配置双向兼容、队列↔行军映射（决定“每队列独立”语义）、编队重复校验、UI 复杂度；其中队列↔行军 id 映射需要 R2（队列协议）结论支撑，是本方案唯一的外部依赖。
8. 工作量估算：P0 约 **40-45 人时**（共享模型+服务端队列化执行+独立设置页+测试），含联盟矿/加速/重物搬运的完整网页版 1:1 约 **55-60 人时**（≈7 人日）；分两批交付。

### 2.2 服务端 formation 包（批次10 冻结契约）

- `FormationLibrary.parse`：`{"formations":[…]}`，按 id 去重，宽容解析（`FormationLibrary.java:41-…`）。

- `FormationResolver`（核心，`:16-45` 注释含冻结契约）：

  - AUTOMATIC：最强英雄 ≤5 + 按比例在库存内分配（单队上限 50000）（`:138-162,317-375`）。
  - 库读取优先级：任务自身 params → `tc.params("formation")` → `tc.params("daily")`（`:483-493`）。
  - 旧行为回退：`Exec.formation(engine, squad_index)`（`:168-171,474-477`）。
  - 解析后 payload：`{hero_id:[{k,v}],soldier:[{k,v}]}`（`ResolvedFormation.toFormationPayload`）。
- `FormationCatalog`：从 `notify_hero_init/notify_soldier_init/notify_world_player_init` 采集快照，`SessionKeeper.java:467-474` 写 state 键 `srv:formation:catalog:{fpid}:{sid}`（英雄名/等级/星级/战力、兵种库存、容量），供 App 编队页读（`FormationStore.catalog:519-534`）。

## 3. 采集配置 v2 设计

### 3.1 是否与网页版字段命名对齐：**对齐**（camelCase + 枚举名 + 每队列扁平兵量）

理由：网页版已有 `toMap()/from()` 成熟 schema 与默认值、且我们的共享解析器/单测可以直接拿网页版 JSON 做黄金样本；网页版字段：`queues[].{id,enabled,resourceType,resourceLevel,formationMode,formationId,infantry,lancer,marksman}`、全局 `fullResourceOnly / gatherSpeedupEnabled / gatherSpeedupLevel(HOURS_8|HOURS_24) / gatherSpeedupDiamondPurchaseEnabled / gatherSpeedupDiamondDailyLimit / allianceMine{enabled,formationMode,formationId,infantry,lancer,marksman} / heavyLiftingEnabled / heavyLiftingQueue{…} / fullCapacity523Enabled`（`DailyGatherConfig.java:21,159-200`；`model/DailyGatherConfigQueueConfig.java:35-56`）。

### 3.2 建议 JSON schema（写入 `roleParams.<sid>.gather.v2`）

```json
{
  "v2": {
    "version": 2,
    "queues": [
      { "id": 1, "enabled": true,  "resourceType": "MEAT", "resourceLevel": 8,
        "formationMode": "AUTOMATIC", "formationId": null,
        "infantry": 40000, "lancer": 30000, "marksman": 30000 },
      { "id": 2, "enabled": true,  "resourceType": "WOOD", "resourceLevel": 8,
        "formationMode": "AUTOMATIC", "formationId": null, "infantry": 40000, "lancer": 30000, "marksman": 30000 },
      { "id": 3, "enabled": false, "resourceType": "COAL", "resourceLevel": 8, "…": "…" },
      { "id": 4, "enabled": false, "resourceType": "IRON", "resourceLevel": 8, "…": "…" },
      { "id": 5, "enabled": false, "resourceType": "MEAT", "resourceLevel": 8, "…": "…" },
      { "id": 6, "enabled": false, "resourceType": "MEAT", "resourceLevel": 8, "…": "…" }
    ],
    "fullResourceOnly": true,
    "maxQueues": 0,
    "allianceMine": { "enabled": false, "formationMode": "AUTOMATIC", "formationId": null,
                      "infantry": 40000, "lancer": 30000, "marksman": 30000 },
    "gatherSpeedupEnabled": false,
    "gatherSpeedupLevel": "HOURS_8",
    "gatherSpeedupDiamondPurchaseEnabled": true,
    "gatherSpeedupDiamondDailyLimit": 2000,
    "heavyLiftingEnabled": false,
    "heavyLiftingQueue": { "resourceType": "MEAT", "formationMode": "AUTOMATIC", "formationId": null,
                           "infantry": 40000, "lancer": 30000, "marksman": 30000 },
    "fullCapacity523Enabled": false
  }
}
```

字段约定：
- `resourceType`: `MEAT/WOOD/COAL/IRON` → 服务端 res_id **102/103/104/105**（不要沿用旧的“再减 101”，见 `ServerFieldTasks.java:38-70` 的 P0 修复）。
- `resourceLevel`: 1-9；服务端语义 **从该等级逐级向下搜索到 1 级**（网页版 `searchLevels`，`DailyGatherService.java:1376-1381,1413-1418`；我方现状同样 `min_level→1`，`ServerFieldTasks.java:103`）。
- `formationMode/formationId`: 引用 `roleParams.formation_library.formations[].id`；`AUTOMATIC` 时 `formationId` 必须缺省/null。
- `infantry/lancer/marksman`: 每队列兵量。ROLE 队列作为显式兵量直接用；AUTOMATIC 队列若 >0 则作为“按权重自动分配”的比例权重（网页版默认 40000/30000/30000；`DailyGatherFormationFields.java:12-17`）。
- `maxQueues`: 兼容字段，0/缺省 = 只按 `enabled` 数派出；>0 = 额外硬上限（多个旧配置迁移时保留旧 `max_queues` 语义），最终 `有效队列数 = min(启用队列数, maxQueues>0?maxQueues:6, 世界出征容量)`。
- 全局 `fullResourceOnly` 映射 `req_world_map_search.is_full`。
- 加速/重物搬运/523：**schema 先占位**，服务端 P2 实现；UI v1 可隐藏或显示“未开放”。
- **不加 `total`/`ratio` 到 v2**：AUTO 队列沿用功能级 `ratio/total`（批次10 页顶统一编队卡的“自动比例”），ROLE 队列用每队列兵量——避免与网页版字段漂移；若将来要支持每队列 total 再加可选字段。

### 3.3 存哪儿：**roleParams["gather"] 内嵌 `v2` 对象**（不用服务端新表/不新建伪功能）

- 为什么不是服务端新表：`vault.json` 的 account schema 变更+加载/序列化/接口改造（`VaultStore.java:79-132,302-330,425-447`）成本高，且服务端**不写回 roleParams**，新表也拿不到 App 的 UI 配置；另外账号池接口契约明确 `/accounts` 要轻量（`design/账号池M1-服务端接口契约-20261021.md:51`）。
- 为什么不新建 pseudo-fn（像 `formation` 那样）：`syncFields` 只遍历 `FnRegistry.all()`，新 fn 键需要特殊 case（`VaultSync.java:911-931` 已有 formation 先例但属补丁）；采集配置天然属于 `gather` 功能参数，放同对象最省事、语义最清晰。
- 兼容性：旧 App 的采集弹窗只 put 已知键（不清 v2），新服务端缺 v2 时走旧键；旧服务端忽略未知 `v2` 键 → **新旧交叉组合全部可用**；`v2` 内部带 `version` 便于将来 v3。
- 双写投影（同一对象顶层，兼容旧服务端/回滚）：写入 v2 后同步刷新旧键（见 §3.4 投影规则），这样“新 App + 旧 server jar”也能继续派队。

### 3.4 旧配置迁移（按“旧配置的生效行为”迁移，不丢语义）

迁移纯函数 `GatherConfigV2.migrate(JSONObject gatherParams)`，输入=现 `roleParams.gather` 顶层旧键，规则：

| 旧键 | 旧语义 | v2 落点 / 默认 |
|---|---|---|
| `resources_named: ["MEAT"…]` | 多选矿种池（空=肉+木） | 按 `i % n` 轮到启用队列 1..N；空 → `[MEAT,WOOD]`（与旧 server 默认一致，`ServerFieldTasks.java:56-70`） |
| `resources: [1-4]` 或 `[102-105]` | 历史数字资源（1-4 需 +101） | 同 `resources_named`（优先级低于 named） |
| `min_level: int(1-6)` | 全局最低/最高搜索等级 | 所有启用队列 `resourceLevel`（缺省 5，clamp 1-9） |
| `max_queues: int(1-5)` | 全局队列数 | 启用前 N 个队列、其余 disabled；`maxQueues=N` 保留 |
| `strategy.send: "full"/"any"` | 只采满矿 | `fullResourceOnly = ("full")`；缺省 false（**保旧行为**；网页版默认 true 属 G4 P2，不在迁移里改行为） |
| `squad_index: 0-5` | 旧游戏内存编队 | **不迁入 v2**；顶层键保留（服务端 legacy 分支仍用）；v2 队列默认 AUTOMATIC，UI 提示“旧内存编队已停用” |
| `formation_mode/formation_id`（功能级，批次10） | 统一编队 | 仅**队列 1** 继承 ROLE+id（网页版禁止同编队多队列，`DailyGatherConfig.java:85-101`）；队列 2-6 → AUTOMATIC，UI 提示可逐队列指定 |
| `soldiers`（功能级覆盖，批次11） | 功能级兵量 | 每队列兵量 = 覆盖值（>0 项逐兵种覆盖），其余取 40000/30000/30000 |
| `ratio/total`（功能级 AUTO） | 自动比例/总量 | 保留在顶层供 AUTO 队列使用；不落每队列 |
| `alliance_mine: bool` | 联盟矿开 | `allianceMine.enabled`（编队 AUTOMATIC，兵量默认 40k/30k/30k） |

**投影规则**（v2 → 旧键，供旧服务端/回滚）：
`min_level = max(启用队列 resourceLevel)`（旧 server 逐级向下搜可覆盖）；`resources_named = 启用队列资源去重`；`max_queues = clamp(启用队列数,1,5)`；`strategy.send = fullResourceOnly?"full":"any"`；`alliance_mine = allianceMine.enabled`；`formation_mode/formation_id/soldiers` 仅当所有启用队列一致时才写（否则写 AUTOMATIC 并移除 id）。**写 v2 时同时写投影；读时 v2 优先，v2 缺失才用旧键。**

默认值策略：
- 全新空配置：迁移函数对空对象也产出“旧行为等价默认”（肉+木、队列 1-3、等级 5、AUTO、any、full=false），保证用户只点“保存”不会把派队关掉。
- 网页版严格默认（6 队列全 disabled、fullOnly=true、等级 8、肉/木/煤/铁/肉/肉）作为 `defaultsForWeb()` 备选，可在页面“恢复默认”二级菜单提供；**P0 不做**，避免改变存量行为。

### 3.5 共享解析器（App 本地模式 + 服务端同一份）

- 现状机制：`vault-server/build.gradle:33-41` **直接把 App 源树编进服务端**（`srcDir '../app/src/main/java'` + include `com/carlos/vault/wjdr/**`、`RewardText.java`、`WarState/ThreatBoard`），注释明确“单一事实源、不做复制”。所以“server 有 `com.carlos.vault.wjdr` 引擎可共用”——**可共用的不是 wjdr 包本身，而是这套 sourceSets 同源编译机制**。
- 方案：新增纯 JVM 类 `app/src/main/java/com/carlos/vault/daily/gather/GatherConfigV2.java`（**零 Android import，只用 org.json**：模型/默认值/parse/toJson/migrate/projection/validate/effectiveQueues），在 `vault-server/build.gradle` 的 include 追加 `'com/carlos/vault/daily/gather/**'`。
- 不能共用的部分：`FormationResolver` 在 `com.carlos.vaultserver.formation`（App 不编译该包），`FormationStore`/`FnParams` 有 Android import（同 `design/守护盟友-服务端化设计与分期-20261023.md:122` 记录的 GuardianEngine 约束）。因此**编队解析仍双端各自实现**：服务端用 `FormationResolver`；App 本地模式（已强制服务器模式，属兜底）P2 再迁；P0 只共享“配置解析/迁移/校验”。
- 建议包名 `com.carlos.vault.daily.gather`（不进 `wjdr` 协议包，语义清晰），并在 include 加目录整体（未来 gather 相关纯函数都可放这里）。

## 7. 验收标准

### A1 保存后重启仍生效（App + 服务端）
- App：设置页保存 → `adb shell am force-stop <pkg>` → 重开 → 设置页/`daily_params` prefs 值不变；`server_mode` 下 3s 内 sync。
- 服务端：`vault.json` 的 `roleParams.<sid>.gather.v2` 与 UI 一致（字段逐项比对）；**服务端重启**后 `VaultStore.load` 恢复（`VaultStore.java:302-330`），无需重新 sync；执行日志仍用该配置。
- 反向：在服务器进程内改配置后（模拟 App 再保存）无需重启即下次执行生效（`SessionKeeper.submitRound:1497-1511` 每次整轮重建 params）。

### A2 服务端执行日志显示每队列 资源/等级/编队 与配置一致
- 在 `ServerFieldTasks.gather` 每次派队/跳过加结构化日志：`采集队列#{id} res={type}({resId}) lv={level} 编队={formation_mode}#{formation_id}/{实际英雄+兵量} 结果={ok|code}`（沿用 `FileLog.info`，参考 `formationFor` 的日志风格 `ServerFieldTasks.java:161-167`）。
- 验收：配置 3 条启用队列（肉8-自动 / 木7-指定编队#1 / 煤9-指定编队#2）→ 触发 1 个 cadence 周期 → 日志 3 行与配置逐字段一致；同时 `mod:{fpid}:{sid}:gather` 状态行含每队列摘要（可选 `mod:gather.queue{n}`）。
- 容量/上限：启用 5 队列但世界容量 3 → 只派 3 队；已有 type4 行军时 slots 正确扣减。

### A3 旧配置迁移不丢
- 单测：5 组旧 JSON（仅 `min_level`；`resources_named+max_queues`；`resources[1-4]`；`strategy=full`；`formation_mode=ROLE+id` / `alliance_mine=true`）→ v2 字段符合 §3.4 表；投影回旧键再 parse 幂等。
- 端到端：生产账号旧配置（`min_level=5,max_queues=4,resources_named=[MEAT,WOOD,COAL,IRON],strategy=any,alliance_mine=false`）升级后在**不改任何设置**的情况下派队行为不变（资源池、队列数、等级、fullOnly 与旧版一致）；日志对比升级前后各 1 轮。
- 回滚：新 App(v2) + 旧 server jar → 旧键投影存在（`min_level/max_queues/resources_named/strategy.send/alliance_mine` 均在顶层），旧 server 正常派队。
- 旧 App + 新 server：服务端 v2 缺失 → 走旧分支，输出与改动前逐字段一致（最好加一条回归对比）。

### A4 单测覆盖
- `GatherConfigV2Test`：parse/round-trip/宽容（坏 JSON、缺字段、未知枚举回默认）/defaults/migrate(≥5 组合)/projection 幂等/validate（重复 ROLE 编队、等级 0/10、enabled 无资源、ROLE 缺 formationId、兵量负数、6 队列缺失自动补齐）。
- `GatherQueuePlanTest`（server）：每队列 formation params 构造（ROLE 覆盖/AUTO 权重）、重复编队防御 SKIP、`maxQueues` 与容量夹取、v2 缺失走 legacy。
- 存量门禁不回归：App 现有 541 用例、server 796 用例全绿（数字见 `design/七模块-1比1复刻-任务清单-20261023.md:299-309`），新增用例纳入同套件。

### A5 零配置/无 v2 时行为零变化
- 不存在的 `v2` → `ServerFieldTasks` 输出（`log:/st:/mod:` 键型与文案）与改造前逐字节一致；`FormationResolver` 的 FALLBACK 契约不被改动（`FormationResolver.java:115-119`）。

### A6 UI 验收
- 6 队列逐个开关/改资源/改等级/选编队/改兵量；非法输入被拦并有中文提示；“应用队列1到全部”可用；“重置”二次确认；保存后返回功能页可见摘要（建议功能页采集卡片副标题显示 v2 摘要，如“3 队启用 · 肉8/木7/煤9 · 只采满矿”）。
- 证据留存：`qa/evidence-20261024-*` 新目录：设置页截图（全页/单队列/编队选择/校验错误/保存成功 toast）+ uiautomator dump（`*.xml`）。

## 8. 最不确定 / 需其他研究员输入的点

1. **每队列兵量在 AUTOMATIC 模式下的网页版真实语义**：反编译可见 `DailyGatherConfigQueueConfig` 带 infantry/lancer/marksman，但 `DailyMarchFormationResolver`/`DailyRoleFormation*` 的 AUTOMATIC 分支实现细节未展开（`model/DailyFormationResolveResult` 等），无法 100% 确认是“权重”还是“精确数量”。本方案按权重近似（`FormationResolver.auto(weights,total)`），P0 可接受；如需 1:1 需 R1/真机对照。
2. **队列↔行军映射的协议字段**：`req_world_march_detail_4_player_situation` 的 `detail.marchs[]` 是否稳定带 `id`/队列号（决定 A5 映射严格度）——依赖 R2（队列系统协议盘点）结论；若无 id 则退化为轮转指针（功能可用，极端下可能重复派同一队列配置 → 编队英雄被占用，服务端 SKIP 不崩）。
3. **9 级矿开服门槛数据源**：网页版用 kingdomProgress 第 701 天门（`DailyGatherService.java:304-337`），vault-server 目前无对等数据结构；本方案不硬拦（逐级下搜兜底），若要 1:1 需补数据源。
4. **产品取舍**：设置页是否也接管“联盟矿/加速”（P1）以及是否保留旧版游戏内存编队 `squad_index` 入口（本方案：v2 不接管 `squad_index`，旧键保留兼容）。
