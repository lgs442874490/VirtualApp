无尽号库 · 界面设计方案

面向「一人管 45 个号、每天早晚各跑一遍」的重度工具场景，把原来平铺 50 项功能的界面， 重构为「一眼知状态 → 一步跑全部 → 有事才进去看」的三段式操作界面。

v2 变更摘要 Changelog

按你的反馈调整了首页形态、补上账号页的角色管理能力，并把「列表 / 卡片」做成两页一致、彼此同步的视图切换。

项v1v2为什么
首页完成度环形 + 号库矩阵 + 限时窗口 保留原卡片设计：3 列游戏图标卡墙（图标 / 账号名 / 登录方式 · 时间）。只补两处——卡片右上角状态点、顶栏「跑全部」 原设计的识别度与手感是资产。它唯一答不上来的是"今天谁没跑"，所以只补状态点，不重做
账号页单行账号卡（头像 / UID / 活跃度条） 上半区只放"这是谁"：无尽冬日头像 + 名字（取自备注）+ 登录方式标识（原生 / token）+ UID，右侧一枚带齿轮的「角色管理」；下半区是已启用角色区（最多 4 个），每行 = 状态（在线 / 离线） / 昵称 / 区号 / 今日完成 / 上次登录 / 登录按钮 账号的价值在角色上，管理动作要能在一屏内完成
登录入口与登录状态账号级一个按钮 两者都下沉到角色行：状态列显示在线 / 离线，行尾是登录按钮，点哪个角色就以哪个角色进游戏 登录的对象是角色，不是账号；而且同一账号下可以有多个角色同时在线，所以在线状态也只能是角色级属性
打开角色管理— 只有点角色行或右侧齿轮「角色管理」按钮才打开弹层；卡片其他区域不响应 整卡可点会让"想看一个角色"变成"总是弹层"，误触代价高
角色管理无 右侧「角色管理」按钮 → 底部弹层列出该账号全部角色（启用与未启用都在）并逐条开关；未启用角色一键加入工作区并启用，账号卡角色区实时同步 "工作区"这个概念必须有一个能被点到的落点，否则用户只能靠猜。按钮名称按你确认的口径：角色管理（此前误写为"价格"）
视图切换无 全局只有两种形式：卡片 = 3 列游戏图标墙，列表 = 详细卡；首页与账号页共用同一状态，切一次两页同步（首页默认卡片、账号页默认列表） 45 个号：卡片适合"认号"，列表适合"看信息"。之前多做的"紧凑行""双列小卡"两套形式已删掉——同一份数据不该有四种长相
号库矩阵首页主视图 暂时从首页移除，规格与样式保留，可作为第三视图随时加回 首页回归原设计后不再有它的位置，但它在 45 号场景下确实有用
账号页悬浮按钮右下角悬浮「＋」 改为顶栏「＋」图标 悬浮按钮会压住卡片右侧的「登录」按钮，列表页不适合放 FAB

设计上下文 Context

设计不从"好看"开始，从"谁在什么情况下用它"开始。以下三条来自功能文档与真机使用记录，是本方案的唯一依据。

用户

一人多号 · 45 个账号

手上 45 个账号、20 个互异号库，多数是接码平台的一次性号，token 失效就只能丢弃。 一个号的价值在于"还在里面"，所以看错一个状态、误删一个号，代价极高。

使用情境

单手 · 竖屏 · 碎片时间

早 8 点、晚 11 点各跑一次日常；跑的时候手机可能放着不动，人去做别的事。 回来只看一件事：哪个号没成功。白天偶尔进来领一个限时活动奖励。

品牌气质

冷静 · 可靠 · 有一点寒意

游戏是冰原生存题材，产品是"后台账房"。基调取极地工程的冷静感： 冰蓝主色、克制的霜面质感、等宽数字对齐。不做炫光、不做玻璃拟态泛滥——那是"AI 味"最重的一类。

一条必须尊重的事实：旧版卡片上写着「单击启动 · 长按管理」，用户已经形成肌肉记忆。 新方案保留单击卡片主区 = 直接启动游戏，把"管理"挪到卡片右侧明确的「⋯」按钮上——习惯不动，只是不再需要长按。

五条设计原则 Principles

这五条会出现在后面每个决策里。两个方案冲突时，按序号从前往后让路。

P1

一眼知状态（Glanceable）

首屏 3 秒内回答三个问题：今天跑了没？成了几个？哪个出事了？——用环形进度 + 号库矩阵 + 异常聚合，而不是一句"就绪"。

P2

常用一步到（One-tap）

最高频动作「跑全部工作区」永远是页面里最大、最亮、离拇指最近的那个按钮，不需要滚动、不需要进二级页。

P3

渐进式披露（Progressive Disclosure）

50 项功能全部可见，但配置收进折叠区。默认只看到「名字 + 状态 + 开关」，想调策略才展开——这是把 1500 行的滚动列表压回可读长度的关键。

P4

危险可回退（Reversible）

删除账号、清除容器数据：二次确认 + 撤销窗口。这个号库里任何一个号被误删都不可恢复，值得多花一次点击。

P5

去卡片化（De-carding）

旧版每个功能都是一张白卡片，视觉上"平权"，于是层次消失、滚动变长。新方案：细分割线 + 分组标题承担大部分分组， 卡片只留给真正需要被"拎出来"的对象——账号、主行动区、运行中的任务。首页的账号卡墙是刻意保留的：账号本身就是这个产品最核心的对象，值得用卡片承载。

信息架构 Information architecture

底部四个 Tab，按"使用频率"而非"功能分类"划分——这是与旧版最大的结构差异。50 项功能全部收进「任务」页，不再占用首屏。

Tab 1 · 首页

认号与启动的地方

保留原卡片设计的账号墙（3 列游戏图标卡），顶栏放「跑全部」与视图切换。回答"今天跑哪几个"。

Tab 2 · 账号

挑号 · 管角色的地方

搜索、筛选、详细账号卡（备注 / 登录方式 / 已启用角色）、角色管理弹层、导入导出 token。回答"我要动哪一个号、它下面哪些角色在跑"。

Tab 3 · 任务

调策略的地方

7 大类 50 项功能的开关与策略配置，外加「进阶工具」入口。回答"它到底帮我做什么"。

Tab 4 · 我的

管设置的地方

授权状态、运行日志、通知与保活、备份与基线、初始化向导。回答"它还正常吗"。

为什么是这四个，而不是按 7 个功能分类做 Tab

  • 频率优先：用户每天 95% 的点击落在"跑一遍 → 看结果 → 补领"，而"奖励/城镇/活动/野外/联盟/商店/其他"是游戏内的分类，不是操作的分类。用游戏分类做导航，用户每次都要先想"联盟捐献算联盟还是奖励"。
  • 分类降级为筛选器：7 类仍是任务页的分段控件，一次滑动就能切，信息不丢，只是不再占领导航。
  • 账号必须独立成 Tab：45 个号的挑选、批量、导入导出本身就是一条完整任务线，塞进任何一页都会撑爆。
  • 14 个独立工具（排行榜 / 攻击 / 迁城 / 三消 / 练号 / 侦查 / 移民…）不新开 Tab：访问频率远低于日常，统一收进「任务 → 进阶工具」，未实现的显式标注「规划中」，不用灰按钮污染主流程。

色彩系统 Color tokens

主色沿用品牌蓝（原 #2962FF），只做微调使其在白底上达到 5.1:1 对比度。冰青作为辅助色，只服务于"进行中"这一种状态，保证它一出现就被识别。

为什么背景不用纯白：纯白 #FFFFFF 会让白色卡片"消失"、必须靠阴影浮起来，而低端机上大面积阴影滚动很贵。 把画布压到 #F2F5FA，卡片用 1px 描边就能分层，去掉阴影后滚动更省电。暗色同理，用 #080C17 而非 #000。
品牌色必须拆成两个 token，不能只有一支。这是本方案在暗色模式下修掉的一个真实缺陷： 品牌色同时承担两种角色——① 当底色（蓝底 + 白字，如主按钮、悬浮按钮、头像）；② 当文字色（页面底上的蓝字，如链接、选中项）。 如果只有一支色值，切到暗色时它必然变浅：变浅后"蓝字"在白/暗底上都够亮，但"蓝底"承白字时对比度就掉到 2.8:1，白色文字直接糊掉。
所以拆成三支：--brand-fill #2E5BFF（浅色/暗色分别 #2E5BFF / #2C55E8，白字 ≥5.1:1）、 --brand-fill-hover、--brand-text #1E43D9（暗色 #93A9FF，在页面底上 ≥8.7:1）。
同理，Hero 卡与授权卡永远用固定的亮蓝渐变（#1E43D9 → #2E5BFF），不跟随主题变色——因为它们永远承载白字。

状态语义色（底 / 字 双层）

同一种状态有两个值：solid 用于色块、矩阵格子、进度；bg + ink 用于徽章。 徽章不用 solid 当底色配白字——那样对比度只有 2.3:1，不达标。

字体层级 Type scale

不引入网络字体。三个原因：工具类 App 必须离线可用、包体已经很重（游戏 830MB + 容器）、Android 中文字体加载成本高。 所以用系统字体栈，靠字重、字距、数字对齐建立层次——尤其数值统一 tabular-nums，让倒计时和点数不跳动。

排印规则

  • 行高：正文 1.62，标题 1.3，单行控件 1.2。中文比英文需要更大行高，别照搬 1.5。
  • 数字对齐：所有数值（活跃度、倒计时、UID、队列数）使用 font-variant-numeric: tabular-nums，避免每秒刷新时整行抖动。
  • 大数字收字距：≥24sp 的数值加 letter-spacing:-.03em，否则中文字体下的数字间距会显得松散。
  • 一行一句话：任务副描述 ≤ 18 个汉字，超出省略号——宁可点进去看，也不要让卡片高度参差不齐。

间距 · 圆角 · 层级 Space · Radius · Elevation

4dp 基准栅格。屏幕左右固定 18dp（比常见的 16 略宽，因为 400dp 宽屏上 16dp 会让信息贴边）， 卡片内 14–16dp，元素之间 8–12dp，区块之间 22dp。用间距变化制造节奏，而不是靠加阴影。

组件库 Components

下面每个都是可点的真实实现，不是截图。改过的组件会标注它替换了旧版的什么。

按钮

主按钮 48dp 高（高于 Material 默认的 40dp，因为这是单手拇指操作的高频动作）；次级 40dp；行内小按钮 32dp。 全局只有一处使用主按钮——首屏的「一键跑全部」，符合"每个界面只有一个主行动"。 旧版把所有操作做成同权重按钮，是层次丢失的主因。

危险操作：删除账号（三层防护）

  • 第 1 层：滑动或点「删除」→ 二次确认弹层，文案写明「该账号为 live 状态，删除后需要重新导入 token」。

现有实现是纯 Java 程序化构建 View（无 XML 布局）+ UiStyle.java 常量化样式。新方案可在同一套技术上落地， 只需把 UiStyle 升级为真正的 token 表，并把长列表改为 RecyclerView 多 ViewType。

实现要点

  • 列表性能：账号页与任务页改用 RecyclerView + 稳定 ID，列表项不设 elevation，用 GradientDrawable 描边实现分层。45 个账号 + 50 个任务不能一次性 inflate 进 LinearLayout。
  • 多 ViewType：任务页需要 4 类 item——分类胶囊（可做成列表外的横向条）、任务折叠行、任务展开体、工具入口行。
  • 折叠动效：用 TransitionManager.beginDelayedTransition 或 MotionLayout；优先只做 opacity 变化，避免每帧测量高度。
  • 暗色模式：用 values-night/ 资源别名映射同一套 token 名，代码只引用 token，不写 if (dark) 判断。
  • 状态栏 / 手势条：WindowCompat.setDecorFitsSystemWindows(false) + insets 处理；底部导航 62dp 已含手势条留白。
  • 环形进度：用 Canvas.drawArc 自绘（比多层 drawable 省），stroke 宽 8dp，起始角 -90°。
  • 震动反馈：VibratorManager 的 EFFECT_CLICK，时长 ≤ 15ms，尊重系统"触感反馈"开关。
  • 文案约束：按钮 ≤ 6 个汉字，任务副描述 ≤ 18 个汉字，超长省略；中文字符串统一进 strings.xml。
不引入任何网络字体与第三方图标库。图标用系统 emoji 或自绘 vector（<1KB/个）即可；这一层刻意保持"轻"，避免给已经 830MB 的游戏容器再增负担。
