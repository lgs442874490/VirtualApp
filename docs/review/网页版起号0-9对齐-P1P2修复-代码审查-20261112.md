## 二、发现（按优先级）

### P1-1 R-05：单号只读请求会消费并丢弃批次依赖的资源增量

- **位置**：
  - `vault-server/src/main/java/com/carlos/vaultserver/bootstrap/BootstrapApi.java:469`（所有 single-* 先 `serviceOf`）
  - `BootstrapApi.java:516-523`（每请求 `new BootstrapService(...)` 并 `syncLoadData`）
  - `BootstrapService.java:400-430`（`syncLoadData` 第 404 行 `port.consumeResourceUpdate()`）
  - `app/src/main/java/com/carlos/vault/wjdr/WjdrEngine.java:732-746`（消费即清空）
- **问题**：`single-status` 等只读请求同样走 `serviceOf → syncLoadData`，消费引擎累积通道后随临时 service 一起丢弃；消费到的增量不会进入批次 service 的 `state`。而批次资源表依赖“登录快照 + 增量”：`BootstrapBatchRunner.java:571` 每轮只把 `notify_resource_init` 的缓存内容合成 `res`，`BootstrapBatchRunner.java:582-583` 注释明确“资源增量更新…唯一通道”。
- **影响**：批次运行中调用任意 `single-*`（尤其前端轮询 `single-status`）即可让一批增量永久丢失 → 批次资源表偏小 → 51 频发、重复购买、停滞；只读接口产生写副作用本身也不合理。
- **依据/不确定性**：`BootstrapBatchRunner.java:563-566` 注释称 `req_loaddata` 只回 `{code}`、资源全在推送里，与 `BootstrapApi.java:506-508` 注释称 loaddata 同步全量相矛盾；若真实环境 loaddata 返回最新资源快照，损失会被下一轮快照掩盖。需实测确认后再定处置（但“只读接口消费共享通道”无论快照是否新鲜都应消除）。
- **优先级：P1（高）**

### P1-2 R-07：本地会尝试购买煤/铁，却仍按“全量缺口”判不可覆盖

- **位置**：
  - `BootstrapService.java:1244-1250`（对 `COAL_PACK_ITEM_ID=100133`、`IRON_PACK_ITEM_ID=100143` 也调用 `buyForMissing`）
  - `BootstrapService.java:1255-1261`（104/105 按 `needCoal`/`needIron` 全量计入 unsupplied）
  - 网页版参考：`design/research-20261111/wjdr-tool-new/modules/bootstrap/service/BootstrapShopService.java:132-133`（只买 100113/100123）
- **问题**：需求 R-07 写明“统帅商店不卖煤/铁，故有煤/铁缺口即 coverable=false”，但统帅商店目录 `vault-server/src/main/resources/bootstrap/daily-town-shop-catalog.json` 含 `100133`（10 钻/包）、`100143`（40 钻/包），代码也对二者发起购买；同时 unsupplied 仍按全量缺口计算，购买结果不抵扣。
- **影响**：若线上 `req_shop_info` 返回这两类商品，则每个 51 冷却周期都会花钻购买，而 `coverable` 仍恒为 false——花钱不改变判定，且与网页版行为分叉；若资源包下一轮被 `useAllFixedPacks` 打开，还可能出现“判了不可覆盖却实际推进”的语义不一致。
- **不确定性**：线上统帅商店是否上架煤/铁未验证（网页版刻意不买）。
- **优先级：P1（高，需确认后修复或降级）**

### P2-1 R-07：`purchaseUnsupplied` 恒返回空，ENDED/WAITING 缺口摘要从未生效

- **位置**：`BootstrapService.java:1130-1140`；根因 `BootstrapService.java:3136-3150`（`maps(Object)` 对 Map 遍历 value）。
- **问题**：unsupplied 元素本身是 Map（`{resourceId,remain,name}`），`purchaseUnsupplied` 对每个元素调用 `maps(item)`，`maps(Map)` 会把 value（Long/String）当容器解析，`mapOf` 全部返回空 → 结果恒为空列表。
- **影响**：`unsuppliedSummary(...)` 在 ENDED 与 WAITING 文案中恒为空串，R-07“ENDED 时带 `resourceEnded=true` 与 unsupplied 摘要”未实现；现有测试只断言原始 `unsupplied` 列表，未断言文案，故缺陷逃逸。
- **依据**：`BootstrapServiceTest.java:917-938`（只校验返回列表）、`:983-1011`（只断言文案含“资源”）。
- **优先级：P2（中）**

### P2-2 R-07：purchase 缺失时 coverable 默认 true，显式 `buyShopResources=false` 时永不 ENDED

- **位置**：`BootstrapService.java:1122-1128`（purchase 缺失视为可覆盖）；`BootstrapService.java:1183-1190`（仅 `cfg.buyShopResources() && retryAllowed("buy:"+key)` 才写 `purchase`）。
- **问题**：R-12 明确尊重显式 `false`；该配置（或购买冷却命中）下 preparation 中不存在 `purchase`，煤/铁缺口无法通过 unsupplied 体现，`coverable` 默认 true。
- **影响**：熔炉 7/8 → `stall` 恒 0；熔炉 9 → attempts 不增 → 永不 ENDED，退化为 WAITING / 10 分钟停滞 FAILED（R-07 口径未达）。
- **说明**：网页版同样“purchase 缺失视为可覆盖”（`BootstrapService.java:1452-1453`），但网页版每次 51 都必算 topUp；本地新增开关使 purchase 可缺失，属本地特有缺口。
- **优先级：P2（中）**

### P2-3 R-07：≥9 分支未加购买冷却，残留基线 P1-3 的“每轮全量强制购买”

- **位置**：`BootstrapService.java:1053-1069`（直接 `waitForResources`，无 `markRetry`）vs `BootstrapService.java:1102-1105`（仅 <9 分支写动作/购买冷却）；购买为 `BootstrapService.java:1186`（`force=true` 按动作成本全量买，忽略库存）。
- **问题**：R-03 的冷却只落在 `<9` 分支；`>=9` 分支 coverable=true 时清零计数后直接 WAITING，下一轮重新规划并再次全量购买（每轮一次）；coverable=false 时也直到 attempts≥3 才停。
- **影响**：熔炉 9 时若发生建筑 51（生产主链路 target≤9 时仅手动 `single-level-building` 非熔炉建筑可达），每个轮次/冷却周期都会全量买资源，钻石消耗；基线 P1-3 同类问题在该分支残留。
- **优先级：P2（中）**

### P2-4 R-02：复合操作跨临界区，并发 single-* 会重复发 world / 重复跑 finishPass

- **位置**：
  - `BootstrapSessionState.java:58-155`（仅字段级 `synchronized`）
  - `BootstrapService.java:488-500`（world：检查 `worldKingdomInfoSent` → 网络请求 → 置位）
  - `BootstrapService.java:692-709`（finishPass：检查 `finishPassDay` → 领邮件/里程碑/开钻石 → 置位）
- **问题**：字段读写原子，但“检查-执行-置位”跨越网络 IO，未在同一临界区；同一 fpid 的并发 `single-run-next` 会重复发送 world 请求、重复执行收尾（重复领邮件/里程碑/开背包钻石）。
- **影响**：Exactly-once 语义在并发下失效；字段更新本身不丢（符合 R-02 边界文字“不丢更新”）。前端/批量脚本并发调用时风险放大。
- **依据**：`BootstrapSessionStateTest.concurrentIncrement_neverLosesUpdate` 只覆盖计数器原子性，未覆盖上述执行路径。
- **优先级：P2（中）**

### P2-5 R-06：终态未在 `levelBuilding` 拦截；ENDED 文案硬编码 9 级

- **位置**：`BootstrapService.java:752-776`（`levelBuilding` 无 `session.resourceEnded()` 守卫，直接规划并 `executeFirstAction`）；`BootstrapService.java:479-480`（ENDED 早退文案固定“大熔炉已到 9 级”）。
- **问题**：`runNext` 有终态拦截，`levelBuilding` 没有；ENDED 早退文案与 `<9` 场景（`stall>=10` 在熔炉 7/8 触发）不符。
- **影响**：ENDED 后 `single-level-building` 仍可推进动作，违背 R-06“不可再推进”；日志/前端文案在熔炉 7/8 ENDED 时误导。
- **优先级：P2（中低）**

### P2-6 R-06：ENDED 与 SUCCESS 优先级两层不一致，且批次 ENDED 用例用非生产配置

- **位置**：`BootstrapBatchRunner.java:704-722`（先 `furnace >= target → SUCCESS`，后判 ENDED）vs `BootstrapService.java:3069-3092`（`runState()` 中 ENDED 优先于 `LEVEL_COMPLETED`）；测试 `BootstrapBatchRunnerTest.java:277`（`targetFurnaceLevel=10`）。
- **问题**：同一状态 status 显示 ENDED、批次记 SUCCESS；`targetFurnaceLevel` 经 API 校验/`fromMap` 限定 1–9（`BootstrapConfig.MAX_TARGET_FURNACE_LEVEL=9`），但 record 构造器不夹取，测试用 10 覆盖的 ≥9 分支生产批次入口不可达。
- **影响**：展示/统计不一致；真正可生产的 `<9` ENDED（熔炉 7/8 + `stall>=10`）没有批次级用例保护。
- **优先级：P2（中低，含测试缺口）**

### P2-7 R-02：`clearScope` 未覆盖“起号重跑（单号）/账号删除”，holders 无淘汰

- **位置**：`BootstrapSessionState.java:39-41`；生产调用仅 `BootstrapBatchRunner.java:335`（取消）与 `:407`（批次开始）。
- **问题**：R-02 要求“起号重跑、账号删除、批次取消时清理”；单号重跑入口与账号删除未接 `clearScope`，ENDED 状态在单号路径只能靠批次重跑或重启进程清除；holders 随 fpid 单调增长。
- **影响**：单号 ENDED 后无法手动重置（与 R-06“不可自动重试”不冲突，但缺少人工重跑路径）；每号 holder 体积小，长期内存风险低。
- **优先级：P2（低）**

## 四、放行结论

**不通过（阻断）**。无 P0；存在 2 项 P1 未闭环，测试缺口未补。

- 阻断项 1：**P1-1**（R-05 跨实例消费丢增量）——修复（消费权归属长期实例；或 `BootstrapState` 资源表按 fpid 持久化；至少 `single-status` 不消费通道）或用户明确接受延期并写入交接文档。
- 阻断项 2：**P1-2**（煤/铁购买与 R-07 口径矛盾）——先确认线上 `req_shop_info` 是否返回 100133/100143：返回则删除这两次购买调用（对齐 `BootstrapShopService:132-133`）；不返回则删除死调用并加注释，避免后续误判。
- P2 可按“先修 P2-1/P2-3，其余排期”收敛；放行前建议补“R-07 <9 ENDED 批次用例”“R-05 双实例用例”，并跑 `BootstrapSessionStateTest`、`BootstrapServiceTest`、`BootstrapApiTest`、`BootstrapBatchRunnerTest`、`BootstrapStateTest`、`WjdrEngineTest` 六个定向类。

## 五、修复建议（单独标注，不改变上述问题描述）

1. **P1-1**：禁止 `serviceOf` 逐请求消费共享通道；把资源表（或整个 `BootstrapState`）与 session 同寿命持久化，或引入“唯一消费方”（批次 service）并在单号路径复用其 state。
2. **P1-2**：`buyMissingResources` 只买 100113/100123（对齐网页版）；若确需买煤/铁，则 unsupplied 改为“购买后剩余缺口”，并同步调整 coverable 与文案。
3. **P2-1**：`purchaseUnsupplied` 改为 `out.add(mapOf(item))`（直接走 List 分支），并补“ENDED 文案包含缺口名称/数量”的断言。
4. **P2-2**：purchase 缺失时不要默认 coverable=true；按 `missingOf`/`costAmount` 计算缺口并把煤/铁计入 unsupplied。
5. **P2-3**：≥9 分支在返回 WAITING 前同样 `markRetry(holdKey)` + `markRetry("buy:"+holdKey)`；或统一在 `upgradeRejected51Building` 出口写冷却。
6. **P2-4**：Holder 增加 in-flight 标志（如 `claimWorldStep()`/`claimFinishPass()` 返回 boolean）或按 fpid 串行化整段流程，避免并发重复执行。
7. **P2-5/P2-6**：`levelBuilding` 首行加 `resourceEnded` 守卫；统一 ENDED/SUCCESS 优先级（建议两层都以 ENDED 优先；若目标已达成需判 SUCCESS，则写入设计说明并同步 status 的 `completed`）；ENDED 早退文案改为通用“资源耗尽，起号结束”。
8. **P2-7**：在单号重跑入口与账号删除入口调用 `clearScope`；批次终态后清理该批 entries 的 holder。
