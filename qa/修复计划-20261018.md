## 1. 修复原则与发布门禁

1. **任何发布包必须满足**：
   - APK 内 `lib/arm64-v8a/libvbox.so` sha256 前缀 = `0dd16cb7`；
   - 签名证书 SHA-256 = `5022610a…de1e`（`CN=scorpion`）；
   - `versionCode/versionName` 与 `VAConfig.gradle` 一致；
   - `:app:testDebugUnitTest` 全绿；
   - `GameKeepAliveService` 无 `android:process=":p0"`；
   - 包含 `POST_NOTIFICATIONS` 权限声明。
2. **不直接改仓库 `app/sdk/lib-release.aar` 的提交态**：构建时临时换入 patched AAR，构建后 `git checkout --` 还原；或把 patched AAR 放到独立可追踪路径（见 P0-1）。
3. **不删除客户共享外部资源层**（`Android_va/0/Android/data/com.gof.china/`）；任何清理必须先备份并确认没有账号在用。
4. **资源状态同步只写白名单键**，绝不复制 `com.cg.sdk.xml`、`lastUserId`、账号/区服等凭据。
5. 每项改动单独分支，合并前人工审核；实验性开关默认关闭，可一键回滚。

- `tools/release.sh:72` 直接 `assembleRelease`，无 AAR 替换、无哈希校验、无测试门禁。

**改动**
1. `tools/release.sh`：

4. `app/sdk/lib-release.aar` 保持仓库原版，避免影响引擎升级目录。

**验收**

**风险/回滚**

### P0-2 修游戏存活判断与 kill/wait

**现状证据**
- `VaultEngine.java:204` `isContainerGameAlive()` 用 `processName.startsWith("com.gof.china")`；
- ANR 原文 `Process: com.carlos.multiapp:p0`、`Cmd line: com.gof.china`；
- `VaultEngine.java:865` `isContainerGameRunning()` 用 `/proc/<pid>/cmdline`，口径正确；
- `killGameAndWait`/`SessionSaver`/`captureEntrySnapshot`/`extractCurrentSession` 依赖前者。

**改动**
1. `isContainerGameAlive()` 改为委托 `isContainerGameRunning()`；或两者合并为一个方法。
2. `killGame()` 后把 `procScanAt=0`，让 wait 循环立即重新扫描。
3. `killGameAndWait()` 超时返回 false；`launchEntry()` 收到 false 时中止，提示“游戏未退出，请从任务栏划掉后重试”，不继续 wipe/注入。
4. `SessionSaver.java:167` 改用正确口径；写快照前再次确认进程不存在。
5. 增加结构化日志：`killGameAndWait` 的耗时、旧 PID、`/proc` 命中、返回结果。
6. 可选：抽一个纯函数 `isGameProcess(processName, cmdline)`，加 JVM 单测覆盖 `com.carlos.multiapp:p0` / `com.gof.china` 两种输入。

**验收**
- 启动游戏后 `killGameAndWait` 必须等旧 `:p0` 真正消失才返回；
- 连续切号 20 次，旧 PID 都在 wipe 前消失；
- 快照保存时游戏进程必须已死；
- 断网/卡死场景 10 秒超时后明确失败，不继续注入。

**风险/回滚**
- `/proc` 扫描在极端权限下可能读不到：保留 `ActivityManager` 作为辅助，二者任一命中即视为存活（宁可多等，不可误判已死）；
- 超时失败会让用户看到“启动失败”，但比数据损坏安全；UI 文案要清楚。

### P0-3 启动/切号串行化

**改动**
1. `VaultEngine` 增加 per-account（或全局）`ReentrantLock`；`launchEntry()` `tryLock(timeout)`，拿不到直接返回“正在切换，请稍候”。
2. `AccountVaultActivity.doSwitch` / `EntryDetailActivity.doLaunch` / `HomeActivity` 启动入口统一走同一锁；启动中禁用按钮/进度框不可取消。
3. 双开实例之间用文件锁（`FileChannel.tryLock`，锁文件放宿主 files）协调，避免两个容器实例同时 kill/wipe。
4. `launchEntry` 的顺序固定为：拿锁 → kill 并确认死亡 → 结算/存档 → wipe/restore/inject → 启动 → 释放锁。
5. 锁只在后台线程持有，不在 UI 线程阻塞。

**验收**
- 快速连点 10 次只启动一次；
- 双开同时点启动，只有一个实例进入 wipe/注入，另一个提示占用；
- 无 ANR/无数据串号；
- 启动失败后锁能正确释放（finally）。

## 4. P1 修复

### P1-1 `runSingle()` 按 fpid 串行

**现状**
- `DailyRunner.java:946`：有 live 会话则复用；否则 `closeAccountSessions(fpid)` + fresh 登录；
- 通知线程、手动执行、定时 worker 可并发；
- 现场 `notify_events.txt` 出现 `target gather ... IllegalStateException: 协议调用失败: req_players_base_info`。

**改动**
1. 增加 `ConcurrentHashMap<String, ReentrantLock>`（key=fpid）；`runSingle` 先 `tryLock`，拿不到排队/返回“该账号正在执行”。
2. 有 live 会话时优先复用；只有在确实没有会话且没有其他 run 持锁时才关闭会话。
3. `closeAccountSessions` 后 fresh 登录失败时，确保 `syncOnline()` 在 finally 执行。
4. 记录失败时的会话状态（ONLINE/RECOVERING/TAKEOVER/NEED_TOKEN），写入 `notify_events.txt`。
5. 同一 fpid 的多个通知合并为一次执行（可选：100-300ms 去抖）。

**验收**
- 同时触发 MARCH_RETURN + HEAL_DONE + 手动执行，同一账号只跑一次；
- 不再出现 `req_players_base_info` 并发失败；
- 常驻会话不被无关任务踢掉。

### P1-2 调度器单飞与闹钟唯一化

**现状**
- `DailySchedulerService.onStartCommand` 每次 `tick()`；
- `ensureStarted` 被每条游戏通知调用；真机 `lastStartId=5`；
- `scheduleAlarmAt` 用 `1002 + hashCode%900`，仍有碰撞可能。

**改动**
1. `AtomicBoolean tickScheduled`：只有第一次启动/`onCreate` 启动 tick 链；`onStartCommand` 只做一次性 `sweepDueAccounts`（用 single-flight 标志），不再新增 10 分钟链。
2. `sweepDueAccounts` 用 `AtomicBoolean sweeping` 防并发。
3. 闹钟 requestCode：
   - 用持久化的 per-fpid 唯一索引（0-899）分配，或
   - `Intent.setData(Uri.parse("vault://alarm/" + fpid + "/" + type))` 让 PendingIntent 唯一。
4. 加日志：当前 tick 链数量、sweep 开始/结束、闹钟 requestCode↔fpid 映射。

**验收**
- 启动 + 10 条通知后只有 1 条 tick 链；
- 每个自动账号在 `dumpsys alarm` 中都有独立闹钟；
- 无重复整轮执行。

### P1-4 资源状态同步（专项）

**已取证事实**
- UI 资源本体在共享外部层：`files/data` 6819 个 / 1.9GB；原生 9756 / 2.2GB；
- `patch_1.16.11_146_12` 37 项全部存在；11→12 只改 `luapatch_32/64`；
- `split_1.16.11_146_12` 51 个 data 项中只缺 1 个 55KB 登录特效 prefab；
- 每账号内部：`htpUpdate.config` 32B；PlayerPrefs 有 `__KEY_MD5_PATCH__`、`__KEY_MD5_SPLIT__`、`__KEY_RES_VERSION_*`、`login_step_first_CheckHotFix/DownloadHotFixVersion/DownloadSplitAsset/CheckAssets`；
- 内部 `files` 仅 4.3MB、`cache` 6.6MB，没有大 UI payload。

**目标**
- 不复制 1.9GB；只同步“每账号更新状态”，让其他账号跳过重复 hotfix/split 校验。

**设计**
1. `files/resource_state.json`（宿主 files，**不进账号快照**）：
   ```json
   {
     "gameVersion": "1.16.11_146",
     "patchManifest": "patch_1.16.11_146_12",
     "splitManifest": "split_1.16.11_146_12",
     "md5Patch": "e95142f4…",
     "md5Split": "c2453d82…",
     "resVersions": {"1784206943": 28, "1788966990": 12},
     "htpUpdate": "{\"a\":\"5.5.9\",\"l\":0,\"s\":0,\"u\":\"\"}",
     "updatedAt": 0,
     "sourceAccount": ""
   }
   ```
2. 更新成功后采集：
   - 读该账号的 `htpUpdate.config`；
   - 读 `com.gof.china.v2.playerprefs.xml` 的白名单键；
   - 校验共享层存在 `patch/split` 清单中所有文件（按清单 code/size 对账；缺一个就不写 canonical）。
3. 启动前应用：
   - 在 `launchEntry` 完成快照还原/注入后、`launchGame()` 前；
   - 读 canonical；若当前账号的 `md5Patch/md5Split/resVersions` 落后，先备份该账号 prefs + htpUpdate.config；
   - 只覆盖白名单键；原子写；失败回滚；
   - 记录 before/after；若游戏仍触发下载，打标记并停止对该账号同步。
4. 开关：`resource_state_sync_enabled` 默认关；先在测试账号开启，验证后再灰度。
5. 缺失的 55KB 登录 prefab：
   - 先让一个账号在稳定网络下完成登录，确认 `files/data/art_effect_ui_prefab_login_depend_265dacda…unity3d` 出现；
   - 若一直不出现，检查下载失败原因（`ENOSPC` vs `EINVAL`）；不要直接从原生目录盲拷（code/版本可能不同）。
6. 存储空间：
   - 先区分 `ENOSPC` 与 `EINVAL`；
   - 修 P0-1 引擎补丁；
   - 共享层只保留一份；旧 content-addressed 文件是否可清理需先确认没有账号引用，默认不动；
   - 客户机至少留 5–8GB 空闲再首启。

**验收**
- A 账号更新后，B 账号启动不再触发 `DownloadHotFixVersion/DownloadSplitAsset/CheckAssets`（或日志中下载量为 0）；
- B 的账号数据/token 不被改写；
- 共享层 patch/split 文件哈希与清单一致；
- 关闭开关后行为完全回到现状；
- 客户机不再出现“存储空间已满”（若是 `EINVAL`，以 P0-1 修复为准）。

**风险/回滚**
- 游戏可能校验 MD5 与真实文件：只在该账号对应文件确实存在时同步；
- 键可能含账号/区服差异：先只同步 `MD5/版本`，不动 `login_step_first_*`；验证后再逐步加入；
- 快照回滚会把状态带回旧值：同步必须在快照还原之后执行；
- 默认关闭 + 备份 + 失败回滚。
