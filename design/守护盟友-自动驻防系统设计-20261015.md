## 1. 需求、目标与非目标

### 1.0 决策公理序（v1.5，用户裁决，全设计最高约束）

```
优先级 1（不可妥协）：驻防盟友成功——防御先于敌方攻击生效，任何机制不得以任何
                    理由（含经济理由）让位于此
优先级 2（次约束）  ：加速道具/钻石消耗最小化——在所有能保证优先级 1 的可选方案中，
                    选消耗最小者（例：能等就不花、单队加速优于迁城优于多队加速、
                    迁城优于钻石；见释队阶梯 §6.10.4 与仲裁 §6.10.5 的排序依据）
优先级 3（权重为零）：队列经济帐——采集停摆、行军中断损失、队列机会成本等一律
                    不进入决策函数；仅作为状态行展示信息（可见性，非决策量）
```

推论：
- 战争态/预警态的进入与维持**不再有经济顾虑**（侦查骚扰导致的采集停摆不构成设计负担）；
- hold-fire、保留池、迁城等机制的存在理由全部重述为**保护防御能力（队列可用性）**，
  与省钱无关；
- 唯一仍被计算的"消耗"是加速道具/钻石存量（优先级 2 的预算管理）。

### 1.1 功能需求（对应立项四条）

| # | 需求 | 设计落点 |
|---|---|---|
| R1 | 可配置触发条件（敌军兵力阈值 + 目标须为盟友城池） | §4 规则模型 `GuardRule` |
| R2 | 精准拦截：实时监测敌方进攻行军与 ETA，我方驻防**先于敌军约 1 秒**落地 | §3 流程 + §6 时间模型 |
| **R2a（v1.1 新增）** | **极限压缩场景**：敌方全程加速，3 分钟行军可在数秒内压缩至约 5 秒剩余；须高频监测识别压缩突变，剩余骤降时**立即秒进驻防**，保证先于敌军落地 | §6.7 突变检测 + §6.8 秒进执行 + §6.9 时效保证 |
| R3 | 动态同步：敌加速（25%/50%）→ 我同步加速；末段加速防御；敌召回 → 我立即召回 | §6.6 加速博弈（巡航省道具路径）+ §6.8 秒进（保底路径） |

### 1.2 非目标（本期不做）

- 不做进攻性拦截（半路截击/主动开团），只做**使馆驻防**（embassy help march）。
- 不做跨角色联合调度（每个角色独立 Guardian 实例；多角色协同留 v2）。
- 不做阵型/兵种自动优化（用户在功能页固定指定驻防编队；自动选兵留 v2）。
- 不代理他人账号的驻防决策（只对我方角色发令）。

### 1.3 验收指标（量化）

| 指标 | 目标值 |
|---|---|
| 卡秒精度 | 我方驻防落地时刻早于敌军到达 **≥0.5s 且 ≤5s**（服务器 endtime 域） |
| 敌加速反应延迟 | 收到 speedup 推送到发出我方 speedup req **≤800ms**（p95） |
| 敌召回反应延迟 | 收到 march_del 到发出 recall req **≤500ms**（p95） |
| **极限压缩检测延迟（v1.1）** | 敌方 endtime 突变到"我方必须行动"的判定，**≤600ms**（p95，推送+300ms 轮询双通道） |
| **秒进执行链（v1.1）** | 触发到我方最终落地 ≤ **r_e − 1s**（r_e=触发时敌剩余；5s 窗内 ≤4s 落地，含全部请求耗时） |
| **极限压缩拦截率（v1.1）** | 敌 3min→5s 压缩场景，道具预算充足时拦截成功率 **≥95%** |
| **佯攻队列不变量（v1.2）** | 任意"敌方已过介入点的真实进攻"到达时，我方可用队列 ≥1（保留池保证）；佯攻（未过介入点即召回）占用我方队列次数 = **0**（hold-fire 保证） |
| **队列释放延迟（v1.2）** | 威胁蒸发（敌召回）到我方队列重新可用 ≤ **2s**（p95，回程瞬进） |
| 时钟精度 | serverClock 偏差上界 ≤±150ms（校准间隔 ≤60s 时） |
| 误触发率 | 非"盟友城池被进攻"场景触发 = 0 |

## 3. 总体架构与端到端流程

### 3.1 组件图

```
LiveSession(每角色)
 └─ GuardianEngine（单线程执行器 + 单调钟定时轮）
     ├─ ThreatDetector      检测器：推送→Threat；二级信号(WAR通知)+兜底轮询
     ├─ RuleEngine          规则评估：GuardRule → QUALIFIED/REJECTED
     ├─ DefensePlanner      决策：可行性(时间/道具/驻防位/兵力)→ Mission 计划
     ├─ QueueManager        队列账本(v1.2)：全类型我方行军队列占用/回程/驻扎实时账
     │    ├─ AttackerProfile 可信度模型：佯攻/真攻历史 per-attacker
     │    ├─ SlotPools       普通池/保留池（reserve 硬保留）
     │    └─ Arbitrator      队列仲裁：抢占/回程瞬进/钻石释队
     ├─ LaunchScheduler     发射控制：waitUntil(T_fire)→发驻防 req→校验 endtime
     ├─ CruiseMonitor       巡航监视：敌我 endtime 重估、加速博弈、召回同步
     ├─ EndgameGuard        末段防御：SAFE-LOCK 判定与道具预算执行
     ├─ SnapExecutor        秒进执行(v1.1)：发射链+道具链 blind-burst
     │    └─ ReturnSnap      回程瞬进(v1.2)：召回后对回程行军执行同款压缩链
     └─ SlotLedger          驻防位账本：每目标容量/占用/我方存量
 GameServerClock（共享，M0）  MarchCoordinator（资源锁）
```

设计原则：
1. **单线程**：GuardianEngine 内部一个执行器，所有状态变更串行（无锁状态机）；网络请求走引擎 requestLock。
2. **单调钟**：内部一切定时用 `SystemClock.elapsedRealtime()`；与服务器时间换算只经 GameServerClock。
3. **防御式解析**：所有推送字段按 proto_log 实证形状 + 候选名深找（项目惯例），缺字段降级不崩溃。

### 3.2 端到端主流程（v1.1：提前戒备 + 突变检测 + 秒进执行）

**设计原则变更（相对 v1.0）**：敌方 ETA 不再被视为可排程的稳定量——它可在数秒内塌缩。
因此我方**永不把发射安排在"敌 ETA − 我方时长"的远期时刻**，而是：尽早让驻防行军进入
在途状态（戒备），把"先于敌军落地"的达成手段从*发射时机*转移到*我方加速链*（秒进）。
卡秒（落地早于敌 0.5~5s）由秒进链的终止条件保证，而非由发射排程保证。

```
[1] 检测     notify_player_march_add 到达
             → 解析 endpoint/owner/type/soldier/endtime
             → endpoint 命中盟友坐标表(§4.3) 且 type=进攻【A-1】
             → 生成 Threat(DETECTED)，进入规则评估
[2] 评估     RuleEngine：敌兵力≥阈值? 盟友目标? 编队空闲? 驻防位余量?
             → REJECTED(留痕) / DEFERED / QUALIFIED
[3] 戒备     (原"计划排程"改为"提前戒备"; v1.2 再改为"按可信度分级戒备")
             ① 可信度评估(§6.10.2)：AttackerProfile → HIGH / MEDIUM(未知) / LOW(佯攻者)
             ② 发射时机按档：
                HIGH(EXTREME锁存/集结/无召回史/大军)：
                  r_e ≤ prelaunch_horizon 立即发射（v1.1 原路径，可占保留池）
                MEDIUM(首见)：r_e ≤ commit_point+2s 才发射+秒进（普通池）
                LOW(佯攻者)：**hold-fire**——r_e ≤ commit_point(默认8s) 才发射+秒进
                  （佯攻通常在更早时刻召回 → 我方从未发射 → 队列零占用, §6.10.3）
             ③ 队列准入(§6.10.1)：发射前过 SlotPools——普通池满则普通档威胁降级等待
               或放弃；保留池(2)仅"已过介入点的 HIGH/紧急威胁"可占
             ④ 道具链可达性预计算(§6.8.5)
             敌若不加速：我方按名义落点提前落地驻防（PRE_LANDED，绝对安全态）
             敌若压缩：进入 [4]
[4] 突变检测 CompressionDetector(§6.7)：
             双通道采样 = march_update 推送(事件驱动) + 自适应轮询
             (STABLE 5s / WATCH 1s / CRITICAL 300ms 三档，见 §6.7)
             判定：单次 endtime 前移 > 40%×r_e，或 3s 窗口累计前移 > 50%
                   → Threat 置 EXTREME 锁存（该 owner 后续行军默认按极端对手处理）
[5] 秒进执行 SnapExecutor(§6.8)，触发条件（满足其一）：
               a. r_e ≤ snap_trigger（默认 5s）
               b. EXTRENE 模式下压缩率超阈
               c. (兜底) 推送+轮询双静默 >2s 且 r_e < 15s → 按最坏假设行动
             执行（若我方未在途：先发射再执行链；在途：直接执行链）：
               while (我方到达 > 敌当前到达 − δ) and 道具有余 and 上个道具仍有效:
                   选档/连发 speedup（CRITICAL 用 blind-burst 流水线，§6.8.3）
                   读新 endtime（响应或即时轮询）
               达成 → 落地即胜（驻防先于敌生效）；未达成 → [6]
[6] 不可救   道具耗尽或道具进入无效区（endtime 不再变化=触底，§6.8.4）：
             r_me > 5s → 立即召回止损；≤5s → 放行落地（无害驻防）
[7] 落地后   驻防生效 → 敌到达进入战斗 → 结算 → SlotLedger 更新
             多击连防/补驻（§7.8）；敌召回 → 我召回+**回程瞬进**（§6.10.4，队列≤2s释放）
             结算后无同目标待办 → 自动 repatriation（队列健康, §6.10.1）
[8] 收尾     撤离策略 / repatriation；释放锁；Mission CLOSED；全链路时间戳
             写 ProtoLogger（验收数据源：检测/判定/发射/每个道具/落地/释队各环节耗时）
```

## 4. 触发规则配置模型（R1）

### 4.1 规则结构 `GuardRule`（FnParams `p:guard.rules`，JSON 数组，顺序=优先级）

```json
[{
  "id": "default",
  "enabled": true,
  "min_enemy_troops": 50000,      // 敌军进攻兵力下限(士兵总数；squad_list.soldier 求和)
  "min_enemy_power": 0,           // 可选：战力下限(有则优先于兵力)
  "target": "ally_castle",        // ally_castle=盟友主城(本期唯一); 预留 ally_object
  "target_uid_whitelist": [],     // 空=全部盟友; 非空=仅这些盟友 uid
  "target_uid_blacklist": [],
  "max_threat_eta_s": 1800,       // ETA 超过此值不驻(太远必然来得及, 挂起转巡航再决策)
  "formation_id": 0,              // 0=功能页选定的默认驻防编队
  "speedup_budget": {"t25": 4, "t50": 2},   // 每任务可用加速道具预算
  "busy_policy": "preempt",       // preempt=抢占日常出征 / yield=让位
  "priority": 100
}]
```

### 4.2 评估伪代码

```
evaluate(threat, rule):
  troops = Σ soldier.count           // 全兵种含伤兵
  if troops < rule.min_enemy_troops: REJECT("兵力不足阈值")
  if threat.targetKind != rule.target: REJECT("目标类型不符")
  if threat.targetUid in blacklist: REJECT("黑名单")
  if whitelist非空 and targetUid not in whitelist: REJECT("不在白名单")
  if threat.etaS > rule.max_threat_eta_s: DEFER("挂起巡航")   // 不拒绝, ETA 进入窗口后再评估
  if !SlotLedger.hasSlot(threat.targetUid): REJECT_RULE("驻防位满")   // 处置见 §7.6
  if !formationReady(rule.formation_id, busy_policy): REJECT("无可用编队") // §7.9
  QUALIFY(rule)
```

多条规则命中取 `priority` 最高者；全部 REJECT 时 Threat 仍保留 TRACKING（可被后续事件重新评估，如敌二次增兵）。

### 4.3 盟友城池坐标表

- 来源：联盟成员列表协议（`notify_alliance_members_*`【假设：确切推送名，proto_log 立项清单 3】）→ `Map<uid, {x,y,castelLevel}>`。
- 刷新：登录快照全量 + 成员变更推送增量；坐标变更（盟友迁城）以推送为准。
- 匹配：Threat.endpoint 与坐标表做**精确等值匹配**（x,y 均为整数格）；不命中即非盟友目标。

## 5. 状态机定义

### 5.1 威胁对象 Threat（敌方行军）

```
DETECTED ──评估──┬─ REJECTED（终态：留痕, 可被增兵事件唤醒回 DETECTED）
                 ├─ DEFERRED ──(ETA 入窗/规则变化)──→ QUALIFIED
                 └─ QUALIFIED ──戒备可行──→ INTERCEPTABLE
                                └戒备不可行(时长/道具双缺)──→ UNINTERCEPTABLE（终态）
INTERCEPTABLE ──敌加速/压缩突变──→ RETIMED（重估; EXTREME 锁存, §6.7）
INTERCEPTABLE/RETIMED ──敌召回(march_del+state 判定)──→ RECALLED（终态）
INTERCEPTABLE/RETIMED ──敌到达──→ LANDED（进入战斗, 等结算）
任意活跃态 ──超时看门狗(超过 endtime+60s 无后续)──→ EXPIRED（终态）

EXTREME 锁存（v1.1）：owner 级属性而非 Threat 级——某 owner 一旦触发压缩突变判定，
其后续所有行军按极端对手处理（prelaunch_horizon 提前、轮询默认 WATCH 起步、
秒进预案道具按上限预留）。锁存 24h 滑动过期。
```

### 5.2 驻防任务 Mission（我方行军）

```
CREATED
  → ARMING            // 锁资源(MARCH+SOLDIERS)、编队 RESERVED、SlotLedger 占位
      └失败(锁超时/编队无效/驻防位满)→ ABORTED(code 对应 §9.4)
  → WAIT_PRELAUNCH    // 等敌剩余 ≤ prelaunch_horizon（默认路径很快通过；期间持续重估）
      └敌召回/威胁失效 → ABORTED(GD_ENEMY_RECALLED)   // 未发射, 零成本
  → ARMED_HOLD        // 已发射在途(v1.1 默认状态)：名义落点=E−hold_margin
      │                // 不再等到 T_fire——发射本身提前, 见 §3.2[3]
      ├敌无动作 → 我方提前落地 → PRE_LANDED（绝对安全态, 胜出）
      ├敌渐进加速(非突变) → 镜像博弈省道具(§6.6), 保持先至
      ├压缩突变/r_e≤snap_trigger → SNAP_EXEC
      └敌召回 & 我剩余>阈值 → RECALLING (§7.3)
  → SNAP_EXEC         // 秒进链执行中(blind-burst 或逐发, §6.8)
      ├链达成(到达≤敌−δ) → SNAP_CONFIRMED → 落地 → LANDED_GARRISON
      ├道具耗尽/触底仍落后 → IRRECOVERABLE → (r_me>5s)RECALLING / (≤5s)放行落地
      └每发响应校验 endtime; 连续 2 发无效 → 触底判定, 提前止损
  → LANDED_GARRISON   // 落地驻防生效(含 PRE_LANDED 提前落地)
  → SETTLED           // 战斗结算完成
      └撤离策略(驻留到期/威胁清零/保留池任务结算即撤)→ REPATRIATING → CLOSED
  → RECALLING         // 发出召回（v1.2：召回≠释队，回程仍占队列）
      └回程期间有新待办 → 可对回程行军再加速（RETURN_SNAP, §6.10.4）复用出击
      → RECALLED（到家, 队列 FREE）→ CLOSED
  → RETURN_SNAP       // 回程瞬进态：对 RETURNING 行军跑 L1/L2 释队链
      └释队达成 → RECALLED / 链失败 → 自然回程
  任意活跃态 ──会话断线不可恢复/看门狗──→ ABORTED(GD_SESSION_LOST)（在途行军走 §7.11 重建）
```

不变量：Mission 与 Threat 一对一（多威胁同目标见 §7.7 的 TargetPlan 聚合）；
状态迁移只允许 GuardianEngine 单线程执行；每次迁移写 ProtoLogger 留痕。

## 6. 毫秒级时间计算模型（核心）

### 6.0 前提认知（重要）

【实证】march 推送 `starttime/endtime` 为**秒级** unix 时间戳。因此：
- "卡秒"的落点分辨率由服务器秒域决定：目标是我方 endtime 落在敌 endtime 前一秒窗口；
- **毫秒能力的真正用途**是三处：① 反应链延迟最小化（推送→决策→发令）；
  ② 发射时刻选择（让服务端接收时刻落在正确的秒窗）；③ 末段博弈先手（§6.5）；
- 秒窗口内的毫秒差由服务器内部处理，端侧不可见也不可控——验收以 endtime 差 ≥1s 为准，
  落地生效是否存在亚秒延迟【假设 A-4，实测两条人工行军对拍】。

### 6.1 时钟体系（M0：GameServerClock 落地，本功能为其首个强依赖方）

```
offset := E[server_ts − mono_ts]                     // 校准样本期望
校准源(优先级)：登录响应 server_time → notify_game_init → 每 20 次心跳
样本权：RTT 越小越可信；取近 5 分钟内 RTT 最小样本的 offset，其余弃置
offsetErrBound := max(|sample_offset − chosen_offset|) + 8μs/s × 距上次校准秒数
nowServerMs() := SystemClock.elapsedRealtime() + offset
waitUntil(serverMs)：对齐等待 —— 差值>100ms 用 sleep，≤100ms parkNanos 自旋收敛
```

规则：所有绝对时刻（E_enemy、T_land、T_fire）存服务器毫秒域；
所有相对等待用单调钟；两域换算只经 offset。**禁止 System.currentTimeMillis()**。

### 6.2 我方行军时长 D 的标定

- **标定表**：`Map<formationKey, Map<distanceBand, D_seconds>>`，formationKey=编队 id+兵种构成哈希。
- 首跑标定：功能开启后的第一次真实驻防（或 dry_run 探测行军【假设 A-5：是否存在不落地的侦察行军】）
  记录 发令接收时刻(估) 与响应/回推 endtime → D = endtime − launchServerTs。
- 兜底公式（未标定时）：`D = k × dist(start, end) / formationSpeed`，
  k 与 formationSpeed 由首批标定回归；**未标定且无公式参数时禁止 WAIT_LAUNCH 排程**，
  只允许"立即发射+巡航修正"模式（发射后按真实 endtime 校正）。
- 距离：欧氏格距；地形修正系数【假设 A-6：是否存在地形减速，实测回归】。

### 6.3 安全提前量 Δ

```
Δ = Δ_land + Δ_clock + Δ_exec + Δ_guard_margin

Δ_land       = 1000ms    // 目标：早敌 1 秒落地（需求 R2 字面）
Δ_clock      = 2 × offsetErrBound      // 双向时钟误差上界
Δ_exec       = 500ms    // 驻防"落地→可参战"生效延迟上界【假设 A-4 实测修正】
Δ_guard_margin = 自适应 0~1500ms：
   基础 500ms；每发生一次"我方 endtime 修正超容错窗"(§6.4) +250ms；
   每次成功拦截(验收 endtime 差≥1s 且防御生效) −125ms；夹在 [0,1500]
```

Δ 每次 Mission 创建时快照，任务内不变（避免中途漂移引入不可比）。

### 6.4 发射时刻求解与容错窗

```
T_land*  = E_enemy − Δ                        // 期望落地(服务器域)
T_fire   = T_land* − D_me                     // 期望服务端接收时刻
T_send   = T_fire − net_p95                   // 本端发出时刻; net_p95=近 20 次 req RTT p95

可行性：T_send > now + 100ms                    // 正常排程
        T_send ≤ now 且 加速后可行              // 透支场景：先算需几次加速(§6.6)
        无解                                    // UNINTERCEPTABLE

发射后校验：真实 endtime_me(响应/回推) 与 T_land* 偏差 ≤ W_tol=1.5s → 接受进入巡航
        偏差 > W_tol → 若 endtime_me 晚于 E_enemy−Δ_min(=Δ−1500ms)：立即加速修正
                    否则(仍先于敌)→ 接受但计入 Δ_guard_margin 自适应
```

### 6.5 末段防御 EndgameGuard（R3 重点；v1.1 起为次级路径）

> v1.1 地位变更：**PRE_LANDED（我方已提前落地驻防）是绝对安全态**，优先于一切在途博弈；
> 本节 SAFE-LOCK 只对"仍在途的我方行军"有意义，且仅覆盖渐进加速——**突变压缩由 §6.8
> 秒进链接管**。SAFE-LOCK 保留用于巡航期的道具经济决策（能否停止响应敌加速）。

**Worst-Case 模型**：敌军在任意 t 的最优可达到达时刻
```
E_wc(t) = t + r_e(t) / (1 + β_max)         // r_e=敌剩余时长; β_max=0.5(已知最高档)
```
（敌道具存量未知 → 保守按无限；若战报/情报可观测敌加速使用记录【假设 A-7】则收紧。）

**SAFE-LOCK（安全锁定）判定**——本设计的核心不变量：
```
LOCKED ⇔ A_me(t) ≤ E_wc(t) − Δ_min
```
即：**即使敌方此刻立即用最高档加速，也追不上我方**。一旦 LOCKED：
- 停止响应敌方后续加速（其到达只可能更早于原 E 但仍晚于我方——数学上不可能反超）；
- 停止消耗道具；Mission 进入终局等待落地。

**锁定策略（两档，配置项 `guard.endgame_mode`）**：
1. `reactive`（默认，省道具）：按原计划飞行；敌加速才镜像回应（§6.6）。风险：末段突发。
2. `proactive`（抢锁）：在 `t_lock_feasible`（用一档加速即可达成 LOCKED 的最早时刻）到达时
   主动加速抢锁。代价：道具；收益：免疫一切末段突袭。计算：
   ```
   t_lock_feasible = min{ t : t + r_me(t)/b ≤ E_wc(t) − Δ_min, b ∈ {1, 1.25, 1.5} }
   ```
   每次巡航重估；道具预算内取最小 b。

**不可救窗（Irrecoverable Window）**——诚实失败：
```
敌在 t 用 β 档加速后，若 ∀ 我方可行动作 a: A_me(t,a) > E_enemy'(t) − Δ_min
（E_enemy' = 敌加速后到达）→ 判 IRRECOVERABLE
处置：若我方剩余 r_me > 5s 立即召回止损；≤5s 放行落地（驻防无害，只是没拦到这一击）
```

### 6.6 加速博弈（镜像策略）

事件：敌 march_update 携带新 endtime / 或专用加速推送【假设 A-8：加速如何体现在推送，
候选 = march_update.change.endtime 变更；实证方法见 §13】。

```
onEnemySpeedup(t, E_enemy'):
  1. 重估所有同目标 Threat/Mission
  2. 对每个未 LOCKED 的我方 Mission：
     need = A_me − (E_enemy' − Δ)                     // 需要压缩的毫秒数
     若 need ≤ 0：继续巡航
     否则选档：最小档 b 使  r_me/(b) ≤ r_me − need    // b ∈ {1.25, 1.5}，逐次可叠加
     受限：预算(SlotLedger 记账道具消耗)、冷却【假设 A-9：加速是否有 CD】
     发 req_arsenal_league_march_speedup → 用响应/回推的新 endtime 覆盖 A_me → 复评 SAFE-LOCK
  3. 道具不足：能追到 E_enemy'−Δ_min(放松 Δ) 就放参数追；仍不行 → IRRECOVERABLE 流程(§6.5)
```

道具账本：`SpeedupBudget{t25, t50}` 每 Mission 独立 + 角色级库存同步
（道具数量来源：背包协议 notify_item_*【假设 A-10】；未同步前用配置预算近似并告警）。

### 6.7 压缩突变检测（CompressionDetector，v1.1 核心）

**为什么推送不够**：march_update 推送依赖服务器分发与网络，极限压缩发生时恰是全联盟
推送洪峰（集结/战场事件并发），推送延迟可达数秒——对 5 秒窗不可接受。故检测必须是
**推送（事件驱动，快但不可靠）+ 轮询（主动，慢但确定）双通道**。

#### 6.7.1 自适应轮询节律（对敌 march 的 owner+kid 定向查询）

| 档位 | 进入条件 | 轮询间隔 | 查询 |
|---|---|---|---|
| STABLE | r_e > 60s 且 owner 无 EXTREME 锁存 | 5000ms | req_world_march_detail_4_player_situation |
| WATCH | r_e ≤ 60s，或 owner 曾有一次压缩事件 | 1000ms | 同上 |
| CRITICAL | r_e ≤ 15s，或 EXTREME 锁存者的活跃行军，或已检出突变未收尾 | **300ms** | 同上 |
| STOP | 我方 PRE_LANDED / 敌消失 | — | — |

节律只升不降（任务内滞回），避免临界值附近抖动；CRITICAL 期间轮询请求走引擎
**优先车道**（插队于日常任务请求之前，§9.2）。300ms 上限依据：服务器 tick 秒级，
亚 300ms 轮询不产生信息增量，只增加风控暴露。

#### 6.7.2 突变判定（对每个敌 march 维护样本序列 {(t_i, E_i)}）

```
压缩事件   : E_i < E_{i-1} − 50ms                       // endtime 前移即加速
单步突变   : E_{i-1} − E_i > 0.40 × r_e(t_i)            // 一步吃掉 40% 剩余
窗口突变   : 3s 滑窗内 Σ(E 前移) > 0.50 × r_e(3s 前)     // 连环小额道具同效
EXTREME 锁存: 单步或窗口突变命中 → owner 级锁存(§5.1)
秒进触发   : r_e ≤ snap_trigger_s(默认 5s)
              或 突变后重估 "我方名义到达 > 新 E − δ"
              或 (兜底) 双通道静默 >2s 且 r_e < 15s     // 宁可误秒进, 不可漏
```

样本不分来源（推送/轮询）统一入序列；乱序（推送晚于轮询到达）按时间戳丢弃过期样本。

#### 6.7.3 检测延迟构成（p95 预算）

```
突变发生 → 我方判定 = min(推送路径, 轮询路径)
  推送路径: 服务器分发 ~50-200ms + 网络 ~100-300ms + 解析<5ms  → p95 ≈ 500ms
  轮询路径: 间隔 300ms + RTT ~150-300ms + 解析<5ms           → p95 ≈ 600ms
双通道并行 → 检测延迟 p95 ≤ 600ms（指标 §1.3）
```

### 6.8 秒进驻防执行（SnapExecutor，v1.1 核心）

#### 6.8.0 道具力学模型【A-3/A-12/A-16 实证前的工作模型】

按"剩余时间乘法压缩"建模（与"3min 数秒压至 ~5s"的现象自洽）：第 i 次使用后
`r ← (r − λ) × f`，f ∈ {0.75, 0.5}，λ = 该次请求 RTT。**算法不依赖该模型成立**：
每发请求后以响应/回推的**真实 endtime** 为准重估（经验回环），模型仅用于预先选档。

#### 6.8.1 触发（满足其一，见 §6.7.2）

#### 6.8.2 执行链（含未在途的先发射）

```
snapExecute(mission):
  t0 = nowServer
  if 我方未在途:
      发射驻防 req(优先车道) → 读 endtime → r_me
  target(t) = E_enemy(t) − δ        // δ = 0.5~1s, 卡秒终止条件
  while (A_me = now + r_me) > target(now):
      if 无道具 or 上一发无效果: break                // 触底/耗尽 → 6.8.4
      tier = 最小档使 (r_me − λ̂) × f ≤ r_me − need    // need = A_me − target
             need 大或 CRITICAL → 直接 50% 档（宁过勿缺）
      发 speedup → r_me ← 响应新 endtime − now（经验回环）
  if A_me ≤ target: SNAP_CONFIRMED（等待落地, 状态回 ARMED_HOLD 终局/直接落地）
  else: IRRECOVERABLE → §6.8.4
```

#### 6.8.3 blind-burst 流水线（CRITICAL 窗的时间保险）

逐发-等待-重估的延迟 = k×RTT（k 个道具 × 200-300ms）；5 秒窗内 k≤3 勉强够，k≥4 不可接受。
**CRITICAL 档启用 blind-burst**：按 6.8.0 模型**一次性预计算整条链**（k 个 50% 档），
将 k 个 speedup 请求**背靠背流水线发出**（不等待响应），发完后单次查询 march detail
读取最终 endtime 校验。延迟从 k×RTT 压到 ≈ RTT + (k−1)×服务器处理间隔（~80-150ms/发）。
代价：可能过头（提前数秒落地）——**防御场景下提前落地无害**，多耗 0~1 个道具可接受。
【A-17：服务器是否允许未依次确认的连发加速——若拒绝串行化，退回逐发并把 snap_trigger
上调到 7s 换预算】。

#### 6.8.4 触底（floor）与耗尽的诚实失败

- 触底判定：连续 2 发 speedup 响应 endtime 无变化（<50ms 前移）→ 道具对该行军已无效
  （服务器存在最短剩余下限【A-16】或道具无效区）→ 停止发送（防风控）。
- 若我方触底时刻仍晚于敌：判 IRRECOVERABLE。r_me > 5s → 立即 recall 止损；
  r_me ≤ 5s → 放行落地（驻防无害，只是没拦到这一击，转 §7.8 备下一击）。
- 敌方触底同样可观测（样本序列 E 不再前移）→ 其到达时刻进入可精确预测区，
  我方 target 随之钉死，链终止条件稳定。

#### 6.8.5 数值演算（以用户场景标定）

敌 3min 行军被压缩至 r_e=5s 触发；我方驻防编队同距 D_me≈14s（proto_log 实证样例同量级），
RTT λ̂=250ms，δ=0.5s，全部 50% 档：
```
发射后 r_me=14.0s, target = 5.0−0.5 = 4.5s, need = (0.25+14.0)−4.5 ≈ 9.75s
第1发: (14.0−0.25)×0.5 = 6.88s   A≈0.5+6.88 = 7.38s  > 4.5 继续
第2发: (6.88−0.25)×0.5 = 3.31s   A≈0.75+3.31 = 4.06s ≤ 4.5 ✓
→ 2 个 50% 道具、~750ms 内落地，敌 5s 到达 → 先至约 1s。
blind-burst: 2 发连发 ≈ RTT+1×处理 ≈ 400ms → 更快。
若 D_me=60s(远盟友): 60→29.9→14.8→7.3→3.5 = 4 发逐发 ≈ 1.75s；blind-burst ≈ 0.8s ✓
→ 结论：5s 触发窗内可拦的前提 = 道具存量 ≥ ⌈log₂((D_me)/4.5s)⌉ 个 50%（或等效 25% 组合），
  该下限在戒备期(§3.2[3])预计算并作为"预案可达性"输出，不足即提前告警+降级 PRE_LANDED 策略。
```

#### 6.8.6 道具预算与 PRE_LANDED 降级

- 戒备期预算检查：`必耗 = ⌈log(D_me/(snap_trigger−δ))/log(2)⌉` 个 50% 等效 + 1 富余。
  库存 ≥ 必耗 → 正常戒备（等突变再秒进，省道具）；
  库存 < 必耗 → **降级为 PRE_LANDED 策略**：敌剩余一到 prelaunch_horizon 立即发射并
  把我方自身秒进到底（尽早落地驻防）——道具换确定性，不再等触发窗。
- EXTREME 锁存者：默认直接 PRE_LANDED 策略（已被证明会极限压缩的对手，等待无意义）。

### 6.9 极限压缩场景的时效保证（v1.1，对应用户质询）

**保证命题**：敌行军从任意剩余时间被压缩至 5s 触发窗时，在"道具存量满足 6.8.5 下限 +
双通道检测可用"的前提下，我方驻防先于敌落地 ≥δ（0.5~1s），端到端延迟预算如下：

| 环节 | 预算(p95) | 保证手段 |
|---|---|---|
| T0 敌突变发生 → 检测判定 | ≤600ms | 推送+300ms 轮询双通道并行（§6.7.3），取先到者 |
| 判定 → 首个请求发出 | ≤50ms | 单线程内存状态机，预案已预计算（§6.8.5 戒备期算好链） |
| 发射（如未在途）| ≤RTT(300ms) | 戒备期已发射（§3.2[3]）则此项为 0——**正常路径无发射延迟** |
| 秒进链 k 发道具 | ≤RTT+(k−1)×150ms | blind-burst 流水线（§6.8.3）；k≤4 → ≤750ms |
| 链尾校验 | ≤300ms | 单次 march detail 查询 |
| 合计（k=2, 已在途） | **≤1.7s** | 对 5s 窗裕量 3.3s（吸收时钟误差 ±150ms、网络抖动、服务器排队） |
| 合计（k=4, 未在途） | ≤2.6s | 裕量 2.4s |

**保证的成立条件与失效声明**（诚实边界）：
1. 道具存量不满足 6.8.5 下限 → 无法保证，戒备期即降级 PRE_LANDED（提前落地，等效保证）；
2. blind-burst 被服务器拒绝（A-17 不成立）→ 逐发模式预算 ×k，snap_trigger 上调 7s 补偿；
3. 双通道同时静默（服务器故障级延迟）→ 保证失效，此时按 §6.7.2 兜底条款已提前行动；
4. 我方与敌同时触底且我 floor > 敌 floor（A-16 实测两者不同）→ 失效，只能 PRE_LANDED 预防。
   —— 以上 4 条全部由"戒备期降级 PRE_LANDED"兜底：**宁可提前落地暴露驻防情报，
   不可晚于敌到达**（v1.1 的优先级裁决，与 v1.0 卡秒隐身优先相反）。

### 6.10 QueueGuard：出征队列资源管理与反佯攻（v1.2 核心）

**问题本质**：我方共 6 个出征队列。驻防任务的队列占用 = 发射→落地→驻扎→召回→**回程**
（回程行军仍占队），单次佯攻可钉住一个队列数分钟。敌方反复佯攻 → 6 队全出 → 趁我召回
间隙真攻 → 我无队可防。**道具可再买，队列不可再生**——本节把队列作为一等受保护资源。
（成本立场：用户已确认 1/2 阶加速与钻石损耗可接受；本节全部机制以此为前提。）

#### 6.10.1 队列账本与双池（QueueManager / SlotPools）

```
QueueLedger（实时账本, 数据源=我方 uid 的 march_add/update/del 全量推送+兜底轮询）:
  slots[6] = { state: FREE | OUT(去程) | GARRISONED(驻扎) | RETURNING(回程),
               marchId, kind: GUARD | GATHER | HUNT | ..., etaHome, valueRank }

双池准入：
  普通池 = 6 − reserve（默认 reserve=2，guard.queue_reserve）
    → HIGH/MEDIUM 威胁的驻防、以及全部日常任务行军
  保留池 = reserve
    → 仅两种准入：① HIGH 可信度且已过介入点；② 普通池全忙且出现"已过介入点"威胁
    → 保留池的驻防任务结算后立即 repatriation（不留驻扎, §6.10.4 释队）
队列健康不变量：任意时刻 保留池全忙 ⟹ 忙者全为"过介入点"的防御且均已落地或即将落地
```

#### 6.10.2 可信度模型（AttackerProfile）

```
每个攻击方 owner 维护：
  feintCount   : 佯攻数（进攻在 r_e > commit_point + 5s 时被召回）
  realCount    : 真攻数（坚持到 r_e ≤ 2s 或落地）
  recallPoints[]: 每次召回时的 r_e（识别其习惯召回点, P50/P90）
  extLock      : EXTREME 锁存（§6.7.2, 压缩突变者）
评分：
  P(feint) = feintCount / (feintCount + realCount + 1)   (+近期样本加权)
  HIGH   : extLock 或 mass/rally 编队 或 P(feint) < 0.2
  MEDIUM : 首见（无样本）
  LOW    : P(feint) ≥ 0.5
证据即时性：任何一次"坚持到 ≤2s/落地"立即把该 owner 提为 HIGH 并 24h 滑动保持
（佯攻者真攻一次就是最强信号——狼来了的最后一次是真的）。
```

#### 6.10.3 最晚介入点（commit_point）与 hold-fire

秒进链（§6.8.5）证明：从**家里直接发射**+道具链可在 ~1s 内把到达压到 4s 内——
即**我方根本不需要为"来得及"而提前占队**。因此：

```
commit_point = snap_chain_time(D_me) + 检测预算 + 安全垫 ≈ 6~10s 敌剩余（默认 8s）

LOW 可信度 → hold-fire：敌剩余 > commit_point 期间一个队列都不给
  （佯攻的召回点若早于 commit_point → 我方零队列成本白吃一次情报）
MEDIUM → commit_point + 2s 缓冲介入（防首见对手直接极限压缩）
HIGH  → prelaunch_horizon 提前戒备（v1.1 原路径, 对手已证明会玩阴的）
```

hold-fire 的残余风险：佯攻者把佯攻坚持到 commit_point 之后才召回（付出接近真攻的时间
成本）诱我发射。按 §1.0 公理序核算：我方损失 = 1 次秒进链 + 回程瞬进的**道具消耗**
（优先级 2 范畴，真实但可承受）；队列占用 ~10s 后即释放（§6.10.4），**不构成防御能力
损失**。hold-fire 的存在理由只有一个——防止佯攻钉住队列（保护优先级 1），与省钱无关；
道具消耗的把关由优先级 2 的预算管理（§6.8.6）负责。

#### 6.10.4 回程瞬进（ReturnSnap）与释队

威胁蒸发（敌召回）时，召回不是终点——**队列要尽快回家**。
（v1.2.1 更新：玩家实证确认回程可加速、且**高级迁城=全队一键释放**，释队层级重排如下，
经济学对比见 `design/行军队列战术手册-20261015.md` §5.2。）

```
释队四级（对 RETURNING/GARRISONED 队列按成本从零到高）：
  L0 自然回程     : etaHome ≤ r_need（新威胁所需释队时限）→ 等，不花资源
  L1 单队列回程加速: 对该回程行军跑秒进链（25/50 道具）——玩家实证可行【A-21 ✅】
                    只困住 1~2 个队列时最省
  L2 高级迁城释队 : 原地附近迁城 → 全 6 队瞬间回城【玩家实证 ✅, 协议/CD 待 A-23】
                    ★多队列困境（≥3 队被困/全返程/无危险驻扎满员）时经济最优：
                    1 个迁城道具 vs Σ 各队单独释放所需道具
  L3 钻石直加     : 无道具时对单行军钻石加速【玩家实证 ✅】；日预算帽
释队触发时机：
  - 敌召回确认（§7.2 区分规则）且同目标无其他待办 → 立即召回+释队
  - 战斗结算完成且无待办 → repatriation + 释队（驻扎占队为玩家实证，纪律=打完即撤）
  - 队列仲裁需要（6.10.5）→ 强制释队
```

#### 6.10.5 队列仲裁（Arbitrator）——全忙时的强制腾挪

尽管保留池+hold-fire 在设计上使"真攻时无队可用"不可达，防御性兜底仍需仲裁
（配置漂移/多目标高压/日常任务占队）：

```
当"已过介入点"威胁需要发射而队列全忙：
  P1 找 etaHome ≤ r_need 的 RETURNING 队列 → 等它（零成本）
  P2 困住队列 ≤2 个 → 召回 valueRank 最低的 OUT 队列（日常 GATHER/HUNT 优先,
     召回免费, MarchCoordinator preempt 已有让位语义）→ 其回程若 etaHome > r_need
     再对该回程跑 L1 加速链 → 释队
  P3 困住队列 ≥3 个（全返程/无危险驻扎满员/混合态 etaHome 都远）→ L2 高级迁城一键全释
      （原地附近迁，迁前自检无我方在途去程驻防会被中断；迁后立即按优先级重分配，
        队列优先给本威胁，不顺手派日常）
  P4 迁城不可用（CD/无货）→ L3 钻石逐队列直加（日预算帽内）
  P5 全部失败（理论上不可达）→ 按 GuardRule priority 放弃 valueRank 最低目标，
     状态行红色告警 + 通知用户（人工介入通道）
valueRank：保留池任务 > 普通池驻防 > HUNT > GATHER；同级比 etaHome 近者优先释放
（v1.5 注：排序量纲 = 对防御能力的贡献，非经济价值——GATHER/HUNT 对防御零贡献故最先
释放；道具消耗取舍由阶梯顺序 P1→P4 保证：能免费（召回/等待）不用道具，能少用不多用）
```

#### 6.10.6 反佯攻不变量（对用户场景的正式回答）

**命题**：敌方无法通过"反复佯攻→耗尽 6 队→趁召回间隙真攻"使我方对真攻无队可用。

论证（三条机制各自独立成立，任一失效仍有下一条）：
1. **hold-fire**：佯攻在 commit_point(8s) 前召回 → 我方从未发射 → 队列占用 0。
   敌要骗出一个队列，必须把佯攻坚持到最后 8 秒（时间成本≈真攻）。
2. **保留池**：即使佯攻全部坚持到介入点骗出普通池 4 个队列，保留池 2 个
   只对"过介入点"威胁开放——佯攻蒸发后普通池队列经回程瞬进 ≤2s 释放；
   敌方"召回→重新发射→压缩到 5s 落地"的最短周期 > 5s（含其发射 RTT 与 floor）
   > 我方释队周期 2s。**真攻到达介入点时，保留池必有余**。
3. **仲裁**：极端配置漂移下全忙，P1-P4 用道具/钻石强制释队（成本已获用户授权），
   P5 才放弃最低价值目标并人工告警。

敌方视角的博弈均衡：佯攻对我方的边际成本递减（可信度模型越打越准，hold-fire 越狠），
对敌方的成本递增（每轮佯攻 3 分钟行军+可能的加速道具）；持续佯攻的唯一"收益"是
喂坏自己的 P(feint) 评分。设计上我方不存在"6 队全出且无法释队"的稳定态。

### 6.11 WarState：战争状态判定与队列管制（v1.3 核心）

**定位**：WarState 是叠加在 QueueGuard 之上的**系统级模式开关**——它不替代 §6.10 的
单威胁决策，而是改变队列准入的总政策：平时"日常与防御共存（保留 2 队）"，
战时"6 队全部为驻防/支援预留，一切非战斗行为暂停"。

#### 6.11.1 战争信号与评分（联盟域事件，按角色实例独立计分、按信号 id 去重）

```
HARD 硬触发（任一命中 → 立即 WARTIME，不等评分）：
  H0 **任意敌方玩家的侦查行军指向盟友**【v1.4 用户裁决：召回必须先于开战——开战后
     召回须耗加速道具，道具成本 >> 提前中断日常采集的少量资源损失；A-24 升级为
     M1 阻塞项：侦查行军识别是 H0 的唯一依赖】
  H1 盟友城池战斗结算确认（敌攻落地，战报/战斗推送【A-25】）
  H2 ≥2 条 QUALIFIED 进攻行军同时指向盟友（多路并发）
  H3 EXTREME 锁存者的行军指向盟友（全程加速/数秒级攻击进行中, §6.7.2）
  H4 系统性牵制：同源 30min 内 ≥5 次佯攻（反复试探的火力侦察形态）

SOFT 软信号（积分制，指数衰减 τ=10min：score = score×e^(−Δt/τ) + w；
仅用于 ALERT 预警级与 H 系之外的情势感知，不再决定战争态进出——v1.4 简化）：
  +40 战斗结算（同 H1 重复计入时取一次）
  +30 新增 QUALIFIED 进攻行军（指向盟友）
  +10 佯攻召回
  +15 联盟 WAR/RECON 原生通知（GameNotifyListenerService 既有事件源）

阈值：ALERT_TH=25（预警级：停 P4 可选出征、采集限近郊）
战争态进出完全由 HARD 触发与 §6.11.2 退出规则决定（v1.4）。
```

#### 6.11.2 状态机（v1.4：进入看 H 系硬触发，退出看全敌静默/开盾）

```
NORMAL  ──软分≥ALERT_TH──▶ ALERT（预警级：停 P4 可选出征、采集限近郊）
ALERT  ──软分衰减至 <10 且静默 10min──▶ NORMAL
NORMAL/ALERT ──任一 HARD（H0-H4）──▶ WARTIME   ← H0 侦查即入，召回先于开战
WARTIME ──【退出二选一，见 §6.11.5】──▶ NORMAL
          ① 全敌静默：敌情板上所有敌方威胁源 lastSignalAt 距今 ≥ QUIET_EXIT(30min)
             ——多敌不满足例外：任一敌人的任一侦查/进攻/佯攻信号都重置其 lastSignalAt，
               只要还有一个敌人"未静默"，30min 计时不成立（§6.11.8）
          ② 全敌开盾：敌情板上全部敌方威胁源 shielded=true（开盾=解除攻击能力【A-26】）
WARTIME/ALERT ──任意新信号──▶ 保持/回到 WARTIME（重入即时，无冷却期）
任意态 ──人工强制──▶ WARTIME 锁定 / 解锁回 NORMAL（优先级最高）
```

v1.4 变更说明：删除 v1.3 的 COOLDOWN 中间态与"软分 EXIT_TH"条件——退出判据收敛为
**全敌静默 30min 或全敌开盾**（用户裁决），滞回由"进入即时（H 系）vs 退出须 30min 全静默"
的自然不对称保证；被暂停的日常由补跑机制在退出后自动恢复（兼容性不变，§6.11.5）。

#### 6.11.3 进入 WARTIME 的动作清单（原子化执行；H0 使其在开战前完成）

```
E1 日常发射闸关闭：DailyRunner/DailySchedulerService 在任务发射前检查
   WarState——非 war.allowlist 内任务一律 SKIP("战时暂停")，当日轮次不烧
   （复用 45min 补跑机制：退出战争态后当日任务自动补齐）
E2 在途非战斗行军全部召回（召回免费）——H0 语义下这一步发生在战斗打响之前，
   正是"提前召回省道具"的落点：gather/hunt/adventure_sweep 等 OUT 队列
   → RETURNING，QueueLedger 如实记账 etaHome；不打断战斗类驻防在途
E3 队列池改组：reserve = 6（保留池=全部），日常准入 = 0
   —— §6.10.1 双池在战时退化为"单池全保留"
E4 MEDIUM 可信度的发射档提前：由 commit_point+2s 提前到 prelaunch_horizon
   （队列富余换更早就绪；LOW 佯攻者仍 hold-fire——战时佯攻更常见，纪律不松）
E5 状态行/通知：进入原因（触发信号明细：哪个敌人/哪类信号/哪个盟友目标）
   + 持续影响提示（采集停摆计时）+ 敌情板摘要（当前威胁源清单）
E6 ProtoLogger 全量留痕（信号 id、敌情板快照、进入时刻）
```

#### 6.11.4 战时队列调度优先级（全 6 队均为战争资源）

| 序 | 用途 | 准入 |
|---|---|---|
| 1 | 已确认真攻的驻防（P0） | 任何队列；卡秒/秒进规则照 §6.8 |
| 2 | 高可信威胁的戒备驻防 | 任何队列 |
| 3 | 被攻目标的增援补驻（多击连防 §7.8） | 任何队列 |
| 4 | 其他盟友的预防性驻防（战时策略可选，默认关） | 配置 war.preguard |
| — | **采集/狩猎/游历/探险/宴会/运宝等一切非战斗** | **禁止（E1/E3 双闸：任务发射闸+队列准入闸）** |
| — | 战斗支援类（battle_shield 反应式开盾、medic 伤兵治疗——不占行军队列） | war.allowlist 允许（默认含此二项） |

战时全忙仲裁：§6.10.5 阶梯照用，但 P2"召回日常 OUT 队列"在战时通常无对象
（E2 已召空）→ 实际主路径 = P1 等待最近回程 → P3 迁城（权重上升：战时多队
回程态更常见）→ P4 钻石。

#### 6.11.5 退出与恢复（v1.4：全敌静默 30min 或全敌开盾）

退出判据（二选一，作用于敌情板全部威胁源）：

```
① 全敌静默 ≥ QUIET_EXIT(30min)
   ThreatBoard.allQuiet(now) = ∀ e ∈ 活跃威胁源: now − e.lastSignalAt ≥ 30min
   —— e.lastSignalAt 被该敌人的**任何**信号刷新：侦查行军、进攻行军（含加减速/召回）、
     佯攻、以及"开盾后撤盾"（撤盾=恢复攻击能力，视为新信号【A-26】）
   —— 多敌语义：10 个敌人里 9 个静默 2 小时、1 个 5 分钟前还在侦查 → allQuiet=false，不退
② 全敌开盾
   ThreatBoard.allShielded() = ∀ e: e.shielded == true（且无在途进攻行军——
   已发出的进攻不受开盾保护语义影响时以在途清零为准）
```

退出动作清单：
```
X1 状态行/通知：退出原因（静默计时明细或开盾名单）+ 本次战争态持续时长与采集停摆损耗
X2 日常恢复：任务闸重开，当日被暂停任务由补跑机制（DailySchedulerService 45min 轮）补齐
X3 队列池还原：reserve 回 guard.queue_reserve(2)；在途 RETURNING 队列自然回位不强制加速
X4 敌情板归档：本次战争的信号时间线入 ProtoLogger（复盘与 A-24/A-26 命中率统计）
X5 若为人工强制退出，记录操作者与原因（不自动重入——直至出现新 H 系信号）
```

- 人工通道：功能页"强制战争态/解除"（优先级最高），误判止损。
- 误判成本不对称（v1.4 重申）：侦查即入的战争态最坏成本 = 停采集至静默 30min；
  漏入的最坏成本 = 盟友裸攻 + 战后召回烧道具——**宁可错入**（用户经济裁决）。

#### 6.11.6 经济性与残余风险（v1.5：经济帐权重归零，按 §1.0 公理序重述）

- **设计公理（用户裁决 2026-10-15，v1.5 收敛）**：①驻防成功不可妥协；②道具/钻石消耗
  最小化；③**队列经济帐（采集停摆等）不进入决策函数**。
- ~~侦查骚扰经济战~~：v1.4 曾以"敌方侦查骚扰可致采集长期停摆"为残余风险——按 v1.5
  公理序该顾虑**权重为零**，战争态判定只看军事信号（H 系与全敌静默/开盾），不为采集
  收入做任何让步。原防护件降级为纯可见性工具：持续时长提醒（war.war_duration_alert_min，
  提醒而非劝退）、敌情板指认骚扰者（可拉黑，属于情报价值不属于经济止损）。
  `war.scout_hard` 旋钮保留，但仅在"H0 识别质量差（误报多）"时使用，不再承担经济防护。
- 佯攻经济：佯攻仍是信号（重置静默计时）；道具消耗把关全部交给优先级 2 的预算管理。
- 误判成本重述：误入战争态的代价只剩**道具机会性消耗 + 指挥注意力**（优先级 2 范畴）；
  漏入的代价是优先级 1 直接失守（盟友裸攻）——不对称裁决不变：**宁可错入**。

#### 6.11.8 敌情板 ThreatBoard（v1.4 新增：多敌跟踪，退出判据的数据底座）

```java
/** 战争态期间的全部敌方威胁源（多敌场景：不假设只有一人）。 */
class ThreatBoard {
    static class Enemy {
        long ownerUid;
        long lastSignalAt;          // 该敌人的最近信号（侦查/进攻/加减速/召回/佯攻/撤盾）
        boolean shielded;           // 当前是否开盾【A-26 观测】
        long shieldSeenAt;
        int  signalCount;           // 本次战争态期间该敌人的信号总数（骚扰度展示）
        MarchKind lastKind;         // 最近信号类型（SCOUT/ATTACK/FEINT/…）
    }
    Map<Long, Enemy> enemies();     // 本次战争态累计出现过的全部威胁源
    void onSignal(long ownerUid, MarchKind kind, long at);   // 刷新 lastSignalAt/shielded
    void onShield(long ownerUid, boolean on, long at);       // 开盾=true 静默；撤盾=新信号
    boolean allQuiet(long now, long quietMs);                // ∀e: now−e.lastSignalAt ≥ quietMs
    boolean allShielded();                                   // ∀e: e.shielded 且无在途进攻
    String summary();             // 状态行/通知摘要：威胁源×N、最活跃者、静默进度条
}
```

设计要点：
- **威胁源只增不减**（本次战争态内）：第 29 分钟出现的第二个敌人，其 30 分钟静默
  从零起算——"先后侦查"的多敌场景天然满足"任一未静默则不退"（用户规则 3）。
- 敌人身份来源：侦查/进攻/佯攻行军的 owner uid；同联盟多敌人各自独立成条目。
- 战争态退出时 ThreatBoard 归档（X4）；重入战争态时重建为空板。
- 与 AttackerProfile（§6.10.2）分工：Profile 是**长期**可信度画像（跨战争态），
  ThreatBoard 是**本次战争态**的局势快照（退出即归档）。

#### 6.11.7 与既有状态的关系

- Guardian §5.3 的 READY/ACTIVE/DEGRADED 描述"单威胁执行能力"，WarState 描述
  "联盟局势模式"——两者正交：DEGRADED（时钟失锁）在战时同样禁止发射。
- AttackerProfile（§6.10.2）与 EXTREME 锁存（§6.7.2）是 WarState 的信号上游。
- vault-server 服务器模式（RoundScheduler）共享同一 WarState 语义（服务器侧
  对等移植，M4c 同批）。

## 8. 核心数据结构

```java
/** 威胁：一条敌方进攻行军。全部时刻为服务器毫秒域。 */
class Threat {
    long id;                 // march id
    long ownerUid;           // 攻击方
    long targetUid;          // 被攻盟友（由 endpoint 匹配坐标表得出）
    int  targetType;         // 城堡/建筑
    long troopsTotal;        // squad_list 兵力合计
    long startTs, endTs;     // 原始 starttime/endtime(秒) → 毫秒域换算
    long endTsCurrent;       // 当前生效到达时刻（含加速重估）
    int  boostEvents;        // 敌方加速事件计数（反博弈条款）
    ThreatState state;       // §5.1
    GuardRule matchedRule;
}

/** 驻防任务：我方一次驻防行军生命周期。 */
class Mission {
    String mid;              // uuid
    long threatId;           // 绑定 Threat（TargetPlan 下可换绑下一击）
    long targetUid;
    long formationId;
    long launchSendTs, launchAckTs;     // 发令本端时刻 / 服务端确认时刻
    long arriveTsPlanned;    // T_land* 快照
    long arriveTsCurrent;    // 响应/回推真实 endtime（巡航基准）
    DeltaSnapshot delta;     // Δ 及其成分快照（验收与复盘）
    SpeedupBudget used;      // 已耗 {t25, t50}
    MissionState state;      // §5.2
    String lastErrorCode;    // GD_*
}

/** 安全提前量快照（复盘可解释性）。 */
class DeltaSnapshot { long land, clock, exec, margin; long offsetErrBoundAtPlan; }

/** 加速道具账本。 */
class SpeedupBudget { int t25, t50; }

/** 每目标账本：驻防位与存量。 */
class SlotLedger {
    // targetUid → {capacity, mine, others, myMarchIds, garrisonTroops}
    int capacity();          // embassy simple_info【A-13：容量字段】
    boolean tryReserve(long targetUid, long troops);
    void onSettle(long targetUid, long troopsAfter);
}

/** 盟友坐标表。 */
class AllyMap { // uid → {x, y, castleLevel, name}
    Long matchOwner(long x, long y);          // 命中盟友 uid 或 null
}

/** 行军时长标定表。 */
class MarchCalib { // formationKey → List<{distBand, dSec, sampleAt}>
    long estimate(long formationKey, double dist);      // 无样本 → -1（禁止排程）
    void record(long formationKey, double dist, long dSecMs);
}

/** 出征队列账本（v1.2）：我方 6 队实时状态。 */
class QueueLedger {
    enum SlotState { FREE, OUT, GARRISONED, RETURNING }
    enum Kind { GUARD, GATHER, HUNT, OTHER }
```
