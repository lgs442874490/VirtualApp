## 二、逐项整改明细

### R1 导入后 App 崩溃/向导覆盖弹窗（最重要）

**现象与误判修正**：原报告将"导入结果弹窗看不到、被向导顶掉"定性为 UX 问题。整改复现时抓到崩溃堆栈：

```
java.lang.NullPointerException: TileAdapter.notifyDataSetChanged() on a null object reference
    at AccountVaultActivity.refresh(AccountVaultActivity.java:625)
    at AccountVaultActivity$10.onPostExecute(AccountVaultActivity.java:986)   ← runImport 完成回调
```

并回查 crash 缓冲区确认**首轮测试当日（16:48）同一崩溃已发生**——即该缺陷是 v3.8.0 原版既有缺陷，首轮"向导顶掉弹窗"的实际链条是：导入落库 → 完成回调 `refresh()` NPE → **App 崩溃重启** → 重新 onCreate → 无基线 → 弹向导。用户视角即"导入后弹窗闪没、跳出一个向导"。

**根本原因**（`AccountVaultActivity.java`）：
1. 新版四 Tab `HomeActivity` 继承 `AccountVaultActivity` 但走 `buildHomeUi()` 分支，**从不构建经典九宫格**（`adapter`/`status` 恒为 null）；
2. 引典路径各有"意外守卫"掩盖了问题：`onResume()` 里 `if (status == null) return;` 早退；引擎就绪回调在 HomeActivity 分支调 `onEngineReady()`；
3. 但 **`runImport` 的 onPostExecute 与 `doSwitch`（启动分身）的 onPostExecute 无条件调用 `refresh()`** → HomeActivity 下必崩。`doSwitch` 是高频路径（点账号卡进游戏），意味着**启动分身成功瞬间 App 即崩溃**——比导入问题严重得多，同一根因。

**修改点**：

| 文件 | 修改 |
|---|---|
| `app/src/main/java/com/carlos/vault/AccountVaultActivity.java` | ① `refresh()` 开头加守卫：`adapter == null` 时转调 `((HomeActivity) this).onAccountsChanged()` 并 return——一次性兜住全部 9 个调用点（含未来的）；② 引擎就绪后的向导自动弹出改为 `autoWizardIfIdle()`：以 `hasWindowFocus()` 为"用户空闲"信号（对话框/输入法各自成窗会夺焦点），忙则 1.5s 顺延重试（上限 60 次≈1.5 分钟，超限放弃仍可从 ☰ 进入），每次触发前复核向导是否仍必要（用户可能已手动完成初始化） |
| `app/src/main/java/com/carlos/vault/HomeActivity.java` | 新增包级钩子 `onAccountsChanged()` → `refreshAccounts()`（账号页后台安全刷新），承接父类 `refresh()` 的守卫分支 |

**不破坏性论证**：经典视图（AccountVaultActivity 直接实例）路径 `adapter != null`，行为与原先完全一致；HomeActivity 原先这两条路径必然崩溃（无既有行为可破坏），修复后获得"账号页刷新"的预期行为；`autoWizardIfIdle` 仅改变"弹窗正显示时"的时序（顺延），最终仍会弹出。

**回归验证方式**：
1. 模拟器复现原场景：HomeActivity 下批量导入 → **不崩（crash 缓冲区 0 新增）+「导入结果 成功 2 · 失败 0 · 跳过 0」弹窗完整可见**（本次已执行 ✓）；
2. HomeActivity 下点账号卡「启动分身」→ 游戏启动 + App 不崩、toast「已启动»…»」（**建议真机再验一次**，本环境无游戏 APK 未跑该路径）；
3. 经典视图（账号页 ⇅ 进入）九宫格刷新/分组/拖拽如常；
4. 无基线设备首启：向导仍自动弹出（空闲时），用户操作中不打扰。

**修改点**：全部统一为 FnRegistry 名（用户可见的唯一事实源）。均为纯展示字符串，`fn id`/执行器绑定/协议不变。

### R3 社交礼物数量档位校验

**根本原因**：`socialgifts.json` 中基础礼物（1xxx）有固定 5 档 `amountOptions=[1,10,20,50,100]`、高级礼物（2xxx/3xxx）为空数组；执行器 `ShopTasks.socialGift` 只读 params 的 `count`（任意值）直接发协议，与原版 Web 版「按目录校验」的取向不符，错误数量只能靠服务端拒绝、报错不友好。

**修改点**（`daily/ShopTasks.java` `socialGift()`）：参数读取后、发送循环前，若所选礼物目录档位非空且 `count` 不在档位内 → 直接 SKIPPED「数量 N 不在可选档位 [..]（礼物名）」，不发协议。空档位（高级礼物）维持原行为交服务端判定。

**回归验证**：JVM 数据测试已断言目录形状（前 4 礼物 5 档、其余 0 档）；建议真机执行一次 social_gift（选基础礼物+错误数量 → 应见「不在可选档位」跳过文案）。

## 七、追加整改 M1：角色切换后配置残留/状态未刷新（真机反馈）

**用户报告**：真机从 K888 切换到 K913（铁柱）后，三个兵营训练等级仍保留 K888 的 t3、只有一个兵营在训练、存在其它类似问题，功能实际不可用。

**根因**：「当前角色」存在**双事实源分裂**——`setCurrentRole()` 只写 `home:current_role` 不写 `RoleStore.activeRole`，而日常页功能开关读写（fnOn/setFnOn 经 activeSid）、功能详情页 sid 兜底、**常驻在线会话选角（syncOnline）** 均消费 activeRole → 切换后配置读写与会话仍停留在旧角色 K888（K888 的兵营 t3 数据被展示/使用；K913 的执行实际发生在 K888 会话上）。代码中 `runSingleCurrent()` 已有一处执行前手动对齐的补丁，佐证分裂早已存在但未全面修复。

**修改点**（`HomeActivity.java`）：
| # | 位置 | 修改 |
|---|---|---|
| F1 | `setCurrentRole()` | 同步 `RoleStore.setActiveRole(fpid, sid)`——统一事实源，开关/详情页/常驻会话/调度兜底全部跟随 |
| F2 | `fnOn()/setFnOn()` | `activeSid(taskAccount)` → `currentRoleSid()`（同页面口径一致，双保险） |
| F3 | `buildHomeUi()` 新增 `alignActiveRoleWithCurrent()` | 启动时以 currentRoleKey 为准对齐 activeRole（存量设备自愈） |

**验证**（详见《qa/角色切换专项测试与修复验证-v3.8.0.md》，RS-01~RS-12 全过）：模拟器用开发账号真实三角色（K888/K913/K902）实测——切换后双源同步（RS-01）、开关写入正确角色键且双向隔离无串写（RS-02/03）、详情页角色行跟随（RS-04）、常驻会话换角（状态行「913区·在线」，RS-05）、存量分裂数据冷启动自愈（RS-06）；修复后 JVM 103/103、既有功能无回归。**兵营执行环节（三营齐训）需真机按 RS-10 复核**（本环境无游戏 APK）。
