# 多角色并行在线验证与"账号单会话"终判（v3.9.0 → v3.9.1）

> 日期：2026-10-07/08 · 环境：模拟器 diudiu2（API34，root）+ 开发账号 80971192（三角色：
> 领主1182430719·K888 / 铁柱、·K913 / 领主1041164144·K902 未入区）+ 本地 license-server 签发测试码激活。
> 背景：v3.9.0 曾按"web 原版可双角色同时在线"的判断拆除了同账号单会话约束（每角色独立设备指纹 +
> syncOnline 全角色保活）。本文档记录模拟器实测对该判断的**证伪**与 v3.9.1 的回正。

## 一、实验记录（logcat SessionKeeper，时间线摘录）

### 实验 A：异指纹双角色（v3.9.0 设计形态，888/913 各自独立 device_id）

```
23:53:54.579  888→logging → (web 抢回打断) → 913→logging
23:53:57.505  913→online
23:54:06.121  888→logging（重试）        ← 同账号另一角色开始登录
23:54:06.341  913→takeover · 账号在其他设备上线   ← 220ms 后 913 被踢（code=5）
23:54:07.654  888→online
```

```
00:06:08.330  902→online（web 安静窗口，已稳定 9 秒）
00:06:16.984  888→logging（重试）
00:06:17.177  902→takeover · 账号在其他设备上线   ← 193ms 后被踢
00:06:18.382  888→online
```

**同账号新登录开始后 193/216/241ms，既有会话必被 code=5 踢掉（三次独立复现，间隔高度一致）。**

### 实验 B：同指纹双角色（复刻 web 形态，全部角色共用账号级 device_id/distinct_id）

```
00:09:30.661  888→online
00:09:30.678  902→logging
00:09:30.887  888→recovering · 同设备连接冲突(code=46)   ← 209ms 后被踢（code=46！）
00:09:33.372  902→online
00:09:33.717  902→recovering · 同设备连接冲突(code=46)
```

**同指纹同样互踢，仅错误码从 code=5（异设备顶号）变为 code=46（同设备冲突）。**

### 结论（终判）

1. **游戏服务器按账号（fpid）维度唯一会话**：同账号新 loginauth 到达后 ~200ms 内踢掉该账号全部
   既有会话，与设备指纹无关。code=5/46 只是被踢方看到的"来者与本设备关系"标签。
2. **设备指纹不能实现同账号多角色并行在线**。v3.9.0 的拆除约束 = 自家角色互踢循环
   （实验 A/B 均复现：轮到谁登录谁在线，另一方进退避）。
3. **web 版"双角色同时在线"是呈现层效果**：实验全程测得第三方（web）对本账号的抢回节拍
   ~200-250ms 高度规律——与其"两角色互相瞬时抢回"的亚秒级轮换一致；协议层 web 同一时刻
   也只有一条会话，但 UI/游戏内呈现为两个角色都"在线"。10-06 的"服务器按 fpid 唯一会话"
   结论（号库端侧形态补充文档 §二）**正确**。
4. 顺带验证：v3.9.x 新增的 code=46 处理（60s 冷却 + 指数退避）工作正常，不再出现快踢死循环。

## 二、v3.9.1 回正内容（保留与回滚）

| 项 | 处置 | 理由 |
|---|---|---|
| syncOnline 全角色保活 / ensureOnline 不关同账号会话 | **回滚**至 v3.8.1 行为（activeRole 优先选一个角色；建新会话前关同账号旧会话 = 切换角色） | 账号单会话是服务器硬约束，多角色保活=自家互踢 |
| runSingle fresh 登录只关本角色会话 | **回滚**为关全账号会话（closeAccountSessions） | 不关也会被服务端踢（46/5），先关更干净 |
| 角色级设备指纹（AccountStore.role_settings:<fpid>:<sid>，主角色沿用账号级旧指纹迁移） | **保留** | 身份稳定性/风控分散；语义：每角色固定一台"设备" |
| WjdrEngine code=46 显式处理（60s 被踢冷却） | **保留** | 实验 B 直接验证；防互踢抖动环 |
| UI 在线口径（● 日常在线=协议会话 / ● 游戏在线=容器挂机 / △ 被顶号暂停；账号页角色行+弹层+hero 卡+头行徽标接入 RoleSessionKeeper） | **保留** | v3.9.1 实测正确（见截图） |
| FunctionActivity.buildUi NPE（roleConfig 返回 null 未判空） | **顺手修复** | 实验中发现：全新配置状态下打开功能详情页必崩 |

## 五、遗留与建议

1. **"web 双在线"若要复刻**：唯一途径是 web 式亚秒级轮换抢回（takeover_policy=grab_back 类策略
   的双角色版），本质是高频互踢，对服务器不友好且会持续顶掉人玩，不建议在端侧实现。
2. 角色级指纹保留后，切换角色时服务端看到的是"另一台设备登入"（code=5 语义）而非同设备切换
   （code=46），对风控侧的呈现更接近多设备真实用户；如不希望此语义，可回退共用账号级指纹，
   行为无实质差异。
3. daily_config 全新状态下 FunctionActivity 的 NPE 已修，建议后续在真机回归一遍功能详情页。

## 六、追加：竞速登录验证（v3.9.2，2026-10-08 凌晨）

用户提供关键领域知识：游戏可"卡多角色在线"——**在第一个角色"登录中未完成"的瞬间登录第二个角色**，两条会话可长期共存（不掉线不互踢）。据此实现 v3.9.2 竞速登录并实测：

### 机制修正

- 踢人检查发生在 **loginauth 完成时**，清除同账号"已过 loginauth"的会话；服务器对同账号登录
  做串行化（两次实测：跟进者 loginauth 响应恰在先行者完全登记后 **3ms** 释放并将其踢掉）。
- 因此纯同时起跑无效（输家被黑洞在 req_loaddata）；有效窗口 = 先行者
  "loginauth 已完成、loaddata 未完成"之间（约 0.6~1s，随网络抖动）。
- **错峰 600~1200ms 带抖动 + 失败重赛循环**可命中窗口：实测两次「竞速成功：2 角色同时在线」
  （02:01:19 / 02:08:21），第二次稳定共存 **30 秒**，UI 账号页两行同时显示「● 日常在线」
  （截图 v392-双在线-账号页.png）。两次成功对最终均被 **web 端反抢**打散
  （"账号在其他设备上线"），非自身互踢。

### v3.9.2 行为设计

- 多角色账号：各角色线程错峰竞速登录（主角色先起跑）；任一会话掉线 → **整号关旧重赛**
  （绝不单独重连，单独重连必踢兄弟）；竞速前人玩避让（容器挂本账号游戏时 60s 后再看）；
  连续 5 次未全员在线 → **降级单会话**（在线者优先选角，停止重赛；重开常驻开关可再试）。
- 日常整轮 / 单功能 fresh 登录收尾后 poke syncOnline，立即整号重赛建回多角色会话。

### 使用前提（重要）

**同账号在 web 端的常驻会话必须停掉**——App 与 web 抢同一账号会互相顶号，竞速对永远
稳不住（今晚全部"不稳定"均来自 web 反抢）。web 停掉后，竞速成功即长期共存，掉线才重赛。

### 七、追加：web 停用后的复测（v3.9.2 终版，2026-10-08 02:13~02:53）

web 端停用后干净环境下复测约 20 轮竞速（错峰 300~1000ms 全区间采样）：

- **未再命中窗口**（0/20）。失败模式一致：跟进角色的 loginauth 完成时必清除先行角色
  （无论其已登记还是登录中）；先行者若先完全登记，被踢时刻精确滞后 1~4ms——服务器对
  同账号登录存在近似串行化的处理。
- **热补模式证伪**：保留在线会话、只补缺角色的"热补"同样会踢掉在线兄弟（02:30:22 复现）。
- **兜底实测通过**：连续 8 次未全员在线 → 自动降级单会话（pick=K888）→ 1 秒内恢复在线、
  稳定运行；并修复了两个配套 bug——结算改为结算时刻实际会话态（+800ms 宽限，防"登录后
  4ms 被踢"虚报成功）、ensureAccountOnline 增加降级标记守卫（防 UI 触发的 syncOnline
  绕过降级再起竞速）。
- 结论：竞速机制成立（02:01/02:08/02:10 三次真实双在线，UI 截图在案）但**模拟器命中率低**；
  窗口宽度与网络时序强相关。真机（真实网络 RTT/抖动不同）命中率待验证；兜底保证不中时
  自动退回单会话，安全可 shipped。若真机也难命中，下一步方向：抓真机游戏客户端做
  "卡多角色"操作的协议包（tcpdump/Charles），比对第二条会话的真实建立路径（可能不走
  独立 loginauth）。
