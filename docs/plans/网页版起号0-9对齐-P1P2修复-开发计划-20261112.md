### 阶段 1：C1 — 三项 P1

**R-01 资源合并顺序（先改 `BootstrapState` + `BootstrapService`）**

1. `BootstrapState`：把 `applyResourceUpdate` 提升为包内可见（`void applyResourceUpdate(Object raw)`），或在 `fromLoadData` 增加重载 `fromLoadData(content, previous)`；推荐前者更小。
2. `BootstrapService.syncLoadData` 改为：
   ```
   Object delta = port.consumeResourceUpdate();      // R-05 后生效；先留回退
   if (delta == null) delta = content.get("res_update");
   BootstrapState next = BootstrapState.fromLoadData(contentWithoutResUpdate);
   next.mergeLegacyFrom(previous);
   next.applyResourceUpdate(delta);
   this.state = next;
   ```
   `fromLoadData` 内部对 `res_update` 的调用移除（或保留但 content 已移除该键）。
3. 移除 `lastResUpdateSignature` 字段及其去重分支（由 R-05 的消费语义替代）；若 R-05 尚未落地，C1 先保留该字段但注释标注「R-05 后删除」。

**R-02 会话状态持久化**

1. `BootstrapService` 的 8 个字段改为 `session().xxx` 读写：
   - 位置清单（现状行号，改后以搜索为准）：`334-341`（定义）、`453-455`、`578-614`、`620-646`、`387-397`、`798`、`1289-1310`、`878-907`。
2. 构造：5 参构造新增 `BootstrapSessionState` 参数（与 `BootstrapHoldStore` 同形），2 参/4 参构造使用 `new BootstrapSessionState()`（测试隔离）。
3. `BootstrapApi.serviceOf`、`BootstrapBatchRunner` 的 `new BootstrapService(...)` 传 `BootstrapSessionState.shared()`。
4. 新增清理点：`BootstrapApi` 批次取消/重跑入口、`BootstrapBatchRunner` 开始处理某 fpid 前调用 `clearScope(fpid)`（避免上一轮残留）。

**R-03 建筑 51 退避与购买冷却**

1. `upgradeRejected` 的 51/建筑/熔炉≥5 分支：钻石失败后 `markRetry(holdKey(action), ACTION_RETRY_MILLIS)`，返回 WAITING 前写 `markRetry("buy:" + holdKey(action), ACTION_RETRY_MILLIS)`。
2. `topUpResources` 内 `buyMissingResources(costs, true)` 前判 `retryAllowed("buy:" + holdKey(action))`。
3. 保持家具分支与熔炉<5 分支现有行为不变。

**测试（先红后绿）**

- `BootstrapStateTest`：无 `res` 快照 + `res_update` → 旧值+增量。
- `BootstrapApiTest`：熔炉 7 + 情报推送 + 两次 `single-run-next`。
- `BootstrapServiceTest`：51 建筑钻石失败后 30s 内不重复购买（用可控时钟 hold store）。

### 阶段 2：C2 — 数据源与终态

**R-05 累积缓冲**

1. `WjdrEngine`：新增 `pendingResUpdate`（`ConcurrentHashMap<Long, Long>`）；入站监听里对 `notify_resource_update` 解析 `data` 列表累加；新增 `consumeResourceUpdate()` 原子取走并清空；起号结束/重登时清理。
2. `BootstrapService.ProtocolPort`：`default Map<String,Object> consumeResourceUpdate() { return null; }`；`EnginePort` 转发。
3. `BootstrapBatchRunner` 合成推送处（575-577）移除 `putIfPresent(merged, "res_update", ...)`，改为 `syncLoadData` 内部消费。
4. `BootstrapService.syncLoadData` 加入消费与回退（与 R-01 合流）。

**R-06 ENDED 接线**

1. `AccountState` 加 `ENDED`；`isTerminal` 加 `"ENDED"`。
2. `runLeveling`：`started == 0` 分支之前先判 `stateView.status`/`resourceEnded` → ENDED 直接收尾。
3. `BootstrapService.runState()`/`runMessage()`：`resourceEnded` → `"ENDED"` + 「大熔炉资源耗尽，起号结束」。
4. `BootstrapApi.batchStatus` 无需改（透传）；App `BootstrapForms` 4 处映射加 `ENDED`。

**R-07 耗尽语义**

1. `buyMissingResources` 返回值增加 `unsupplied`（`[{itemId, resourceId, remain, name}]`）与 `coverable = unsupplied.isEmpty()`；只买 102/103，104/105 计入 unsupplied。
2. `upgradeRejected` 51 分支按需求 R-07 的 4 条重写：`>=9` 与 `<9` 两段；`<9` 时第一次钻石不要求 `>=5`。
3. `resourceExhaustedAttempts` 仅钻石成功清零；普通动作成功（`798`）不再清零。
4. 状态存 `BootstrapSessionState`（R-02）。

**测试**

- `WjdrEngine` 单测：两次相同增量 → 消费得 1800；消费后清空。
- `BootstrapServiceTest`：`buyMissingResources(force=true)` 的 coverable/unsupplied；`<5` 也试钻石；coverable=false 累计 3 次 ENDED。
- `BootstrapBatchRunnerTest`：ENDED 立即结束、计入终态。
